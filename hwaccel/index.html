🍳 硬件加速：不是更快的 CPU，而是更专的工位

软件编码像一位全能厨师：切菜、炒菜、摆盘全包，什么都能做，但一次只能做一份。硬件编码像把“切配”交给一台专用切片机：它只会切片，但一秒能切几百份，而且几乎不占厨师的手。视频解码/编码正是这种“重复、规则、量大”的活，天生适合固定功能电路。

但专用工位也有代价：它能做的菜式有限。硬件编码器的参考帧结构、B 帧、码控模式、psychovisual 优化都比 x264/x265 少；同一码率下，硬件编码的画质不一定更好，甚至可能更差。它真正省下的是 CPU 占用、功耗和整机成本，让你能把一台机器从“2 路 1080p”做到“16 路 1080p”。

先找瓶颈，再上硬件

用 top 看 CPU：如果 ffmpeg 单核跑满、sy 很高，可能在拷贝；如果 GPU 利用率低但帧率上不去，可能是解码/上传/下载在等。盲目换编码器，常常只是把瓶颈从 CPU 挪到 PCIe。

硬件编码的画质前提

同码率下，硬件编码通常不如 x264 slow/x265 medium；但在高码率、低延迟、多路场景，它的性价比极高。直播/监控优先吞吐，归档优先画质，这是两条不同的路线。

“支持硬件”不等于“已启用”

驱动、权限（render 组）、FFmpeg 编译选项、容器内设备映射、像素格式协商，任何一环缺失都会静默回退到软件。必须用日志和 ffmpeg -hwaccels 验证。

⚠️先纠正一个常见误解：“用了 NVENC，画质就会更好”是错的。硬件编码器的目标是在给定功耗与吞吐下足够好，不是“最强压缩”。要极致画质，仍然要用软件编码的慢速 preset；要极致路数与低功耗，才轮到硬件。

🔗 解码与编码链路：每一段都可能偷偷拷贝

一条典型的转码链路是：demux → parse → decode → scale/convert → encode → mux。硬件加速的本质，是让 decode 与 encode 的输出/输入都是“设备表面（surface）”，中间不经过 AVFrame 的系统内存拷贝。只要中间插入一个只认 CPU 内存的滤镜（比如 drawtext、subtitles、overlay），整条链路就会被迫 hwdownload，零拷贝立刻破功。

像素格式是第一道门槛

硬件编码器几乎都吃 NV12（8-bit 4:2:0，Y 平面 + 交织的 UV）或 P010（10-bit）。解码器输出的可能是 AV_PIX_FMT_CUDA、VAAPI、QSV、VIDEOTOOLBOX、D3D11 这类“设备像素格式”，它们不是内存里的 YUV 数组，而是显存表面的句柄。FFmpeg 用 AVHWFramesContext（hw_frames_ctx）描述这组表面的格式、尺寸与池化策略，编码器必须接受同一个 context，才能做到零拷贝。

硬件编码器对 B 帧的支持因格式与代际而异：有的只支持 P 帧，有的支持 B 帧但会牺牲低延迟。上表可以帮你直观看到 GOP 与 B 帧如何影响“首帧等待”和“编码延迟”——GOP 越长，随机访问越慢；B 帧越多，编码器需要缓存更多未来帧。

🔍零拷贝的判定标准：看 FFmpeg 日志里有没有 auto_scale_0 / hwdownload，看滤镜图里是否出现 format 转 yuv420p，看编码器输入 pix_fmt 是否仍为设备格式。只要出现一次下载，PCIe 带宽就会成为新的天花板。

🗺️ 七大后端全景：先认平台，再认名字

硬件加速不是一套 API，而是每个厂商各自的一套：Intel/AMD 在 Linux 上共同支持 VAAPI，NVIDIA 有自己的 NVENC/NVDEC，Intel 还有 QSV，苹果是 VideoToolbox，Windows 有 D3D11VA 与 Media Foundation，AMD 在 Windows 上还有 AMF，瑞芯微则有 MPP。名字记不住没关系，先记住它们在哪个平台、负责解码还是编码。

“解码器”和“编码器”是两套硬件

NVDEC 与 NVENC 是独立单元，可以同时工作；Intel 的媒体引擎也分解码与编码。GPU 利用率高不代表编码单元忙，反过来也一样——监控时要看专门的 enc/dec 计数器。

API 之上还有一层

FFmpeg 的 h264_vaapi、GStreamer 的 vah264enc、Intel 的 oneVPL 都是“封装层”。同一个硬件可能有多条调用路径，性能与可用参数并不完全等价。

容器里最容易漏设备

Docker 需要 --device /dev/dri（VAAPI/QSV）或 NVIDIA Container Toolkit（NVENC）。设备没映射时，FFmpeg 可能不报错，直接回退软件，让你误以为“硬件不过如此”。

🔌 VAAPI：Linux 上的“公共插座”

VAAPI（Video Acceleration API）像墙上的公共插座：Intel 和 AMD 的显卡都把自己的媒体引擎接到这个标准上，应用只要插同一种插头（libva），就不用为每家写一套代码。它不规定硬件怎么做，只规定“怎么申请表面、怎么提交解码/编码任务、怎么同步”。

Linux 上先确认设备和驱动：Intel 常见 iHD 驱动（较新核显）或 i965（老平台）；AMD 走 Mesa 的 radeonsi。设备节点通常是 /dev/dri/renderD128，用户需要在 render 组里，否则会报权限错误。

# 查看驱动、版本与支持的 profile/entrypoint
vainfo --display drm --device /dev/dri/renderD128

# 解码 → 缩放 → 编码，全程留在 VAAPI 表面
ffmpeg -hwaccel vaapi -hwaccel_device /dev/dri/renderD128 \
  -hwaccel_output_format vaapi -i in.mp4 \
  -vf 'scale_vaapi=format=nv12' \
  -c:v h264_vaapi -rc_mode CQP -global_quality 23 out.mp4

# 输入是软件帧时，需要显式上传到 VAAPI 表面
ffmpeg -vaapi_device /dev/dri/renderD128 -i in.mp4 \
  -vf 'format=nv12,hwupload' \
  -c:v h264_vaapi -global_quality 23 out.mp4
写法发生了什么代价 / 适用
-hwaccel_output_format vaapi解码输出直接是 VAAPI 表面，不下载零拷贝的前提；后续滤镜必须是 VAAPI 版本
scale_vaapi=format=nv12在 GPU 上缩放并转成编码器要的 NV12正确做法；10-bit 则用 p010
format=nv12,hwupload先在 CPU 内存转格式，再上传到显存软件输入时才用；每帧一次上传
hwdownload,format=nv12把表面搬回系统内存需要 CPU 滤镜/算法时被迫使用，PCIe 开销明显
-global_qualityVAAPI 的质量旋钮（配合 -rc_mode）不同驱动的支持模式不同；先查 ffmpeg -h encoder=h264_vaapi
⚠️最常见的 VAAPI 报错：“Impossible to convert between the formats”。八成是滤镜图里既写了设备输出、又写了普通 format=nv12，FFmpeg 只好尝试下载再转换。把 format 改成 scale_vaapi=format=nv12，或明确加 hwdownload，不要让它猜。

🎛️ NVENC / NVDEC：显卡上的独立车间

NVIDIA 把解码和编码做成了两个独立车间：NVDEC 负责拆包还原画面，NVENC 负责压回码流，它们和 CUDA 计算单元是分开的。这就是为什么一张卡可以一边跑推理、一边压十几路视频——只要显存和 session 限制撑得住。

FFmpeg 里，-hwaccel cuda -hwaccel_output_format cuda 让解码结果留在显存；scale_cuda 在显存里缩放；h264_nvenc/hevc_nvenc/av1_nvenc 直接吃这些表面。注意 AV1 编码只在较新代际的 GPU 上提供，具体支持矩阵以 NVIDIA 官方文档为准。

# 查看本机支持的硬件加速与编码器参数
ffmpeg -hwaccels
ffmpeg -h encoder=h264_nvenc

# 解码 + 缩放 + 编码，帧留在显存
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -vf 'scale_cuda=format=yuv420p' \
  -c:v h264_nvenc -preset p5 -tune hq -rc vbr -cq 23 -b:v 0 \
  -spatial_aq 1 -temporal_aq 1 -bf 3 -g 50 out.mp4

NVENC 的 preset 现在常用 p1–p7：p1 最快、p7 最慢但画质最好；旧的 fast/medium/slow 仍可能被接受，但映射关系由版本决定。-tune hq 偏画质，-tune ll/ull 偏低延迟（会牺牲压缩效率）。-rc vbr 配 -cq 才是“按质量”而不是“按码率”。

并发 session 限制

消费级 GeForce 历史上对同时编码路数有限制，专业卡/数据中心卡通常不限制。NVIDIA 在部分驱动版本放宽过限制，但具体数字随驱动与产品线变化，以官方文档和实测为准。部署前先跑满目标路数压测，别等上线才发现第 9 路起不来。

显存怎么算

每一路都要解码表面、参考帧、编码输入表面与队列。1080p 单路占用不大，4K 会成倍增长；多路并发时先看 nvidia-smi 的显存，再谈路数。显存不足时会出现“编码器初始化失败”而不是优雅降级。

🔍低延迟场景：-tune ll 或 -tune ull 会减少前瞻与 B 帧，让编码更“来一帧出一帧”。代价是同码率画质下降、码率波动更大。直播连麦优先低延迟，归档转码优先画质，别用同一套参数打天下。

⚡ QSV：核显里的快速通道

QSV（Intel Quick Sync Video）是 Intel 核显的媒体引擎，像办公楼里的专用货梯：不参与通用计算，只负责把货快速上下楼。它功耗低、发热小，特别适合 NUC、笔记本、边缘盒子做多路轻量转码。现代接入层通常通过 oneVPL 统一调度，底层可以是 VAAPI，也可以是 Windows 的 D3D11。

# 解码 → 缩放 → 编码，全部在 QSV 表面
ffmpeg -hwaccel qsv -hwaccel_output_format qsv -i in.mp4 \
  -vf 'scale_qsv=format=nv12' \
  -c:v h264_qsv -preset veryfast -global_quality 23 \
  -look_ahead 1 -async_depth 4 out.mp4

# 查看 QSV 编码器可用选项
ffmpeg -h encoder=h264_qsv
参数作用注意
-hwaccel qsv用 QSV 解码需要驱动与 oneVPL 运行时；容器内要映射 /dev/dri
-hwaccel_output_format qsv解码结果留在 QSV 表面后续滤镜必须用 *_qsv 版本
scale_qsv / vpp_qsv缩放、去隔行、色彩转换不同平台支持的处理项不同，先查文档
-global_quality质量优先的码控旋钮与 -b:v 的优先级随模式变化，别同时乱写
-look_ahead前瞻，提升码率分配low_power 模式下可能不可用
-async_depth并行深度，提高吞吐越大越吃显存/内存，低延迟场景要收敛
⚠️low_power 模式的取舍：它省电、启动快，但可能不支持前瞻、B 帧或部分码控模式。需要画质时关掉它；需要低功耗边缘部署时再打开。具体能力以 Intel 的 oneVPL/Media SDK 文档与实测为准。

🍎 VideoToolbox：苹果的统一内存优势

在 Apple Silicon 上，CPU 与 GPU 共享同一块统一内存，VideoToolbox 的输出是 CVPixelBuffer（底层是 IOSurface），编码器可以直接消费，不需要像独显那样跨 PCIe 搬一次。这就是 Mac 上“剪 4K 很顺”的底层原因之一。

# 硬件解码 + HEVC 硬件编码
ffmpeg -hwaccel videotoolbox -i in.mp4 \
  -c:v hevc_videotoolbox -b:v 4M -g 50 -realtime 1 out.mp4

# 确认编码器是否真的走了硬件
ffmpeg -h encoder=hevc_videotoolbox

VideoToolbox 的码控选项相对少，很多场景以目标码率为主；-allow_sw 1 允许在硬件不支持时回退软件，调试性能时可以先关掉它，避免“看起来成功、其实全在 CPU”。-realtime 1 适合直播/录屏，会减少前瞻换取更低延迟。

优势

统一内存让“解码→处理→编码”的拷贝成本很低；功耗极佳，笔记本续航友好；HEVC 硬件编码在 Apple Silicon 上成熟。配合 IOSurface，自家应用可以做到真正的零拷贝。

限制

参数空间小，想做精细的 psychovisual 调优不如 x265；部分旧机型只支持 H.264；跨平台部署时，VideoToolbox 只覆盖苹果生态，服务端仍要准备别的后端。

🪟 D3D11VA / Media Foundation / AMF：Windows 的三条路

Windows 上的硬件视频有三套常见入口：D3D11VA 负责解码，把画面放进 D3D11 纹理数组；Media Foundation 用 MFT（Media Foundation Transform）封装解码与编码，具体走硬件还是软件由系统选择；AMF 是 AMD 自己的编码框架，主要在 Windows 上使用。

# D3D11VA 硬解（输出留在 D3D11 纹理中）
ffmpeg -hwaccel d3d11va -hwaccel_output_format d3d11 -i in.mp4 \
  -c:v h264_mf -b:v 4M out.mp4

# Media Foundation 编码（是否硬件由系统 MFT 决定）
ffmpeg -i in.mp4 -c:v h264_mf -b:v 4M out.mp4

# AMD AMF 编码
ffmpeg -i in.mp4 -c:v h264_amf -quality quality -rc cbr -b:v 4M \
  -usage transcoding out.mp4
组件职责零拷贝条件常见坑
D3D11VADXVA2 的现代替代，硬解 H.264/HEVC/AV1（视硬件）输出 AV_PIX_FMT_D3D11，后续用 D3D11 滤镜纹理数组的切片索引、hwdownload 的格式转换
Media Foundation系统媒体管线，MFT 可硬可软MFT 接受 DXGI 表面时可零拷贝“成功”可能是软件 MFT；参数随厂商实现变化
AMFAMD 编码（H.264/HEVC/AV1，视代际）D3D11 互操作Linux 上通常不用 AMF，改走 VAAPI；quality 预设映射因版本而异

Windows 的硬件路径碎片化最严重：同一份命令在不同显卡、不同驱动、不同 FFmpeg 构建上可能落到不同 MFT。排查时先看 ffmpeg -v verbose 里实际选择的 decoder/encoder，再用任务管理器的 GPU 引擎（Video Decode / Video Encode）确认硬件真的在动。

🔍Media Foundation 的“坑王”属性：它可能悄悄选择软件 MFT，也可能因为分辨率/格式不支持而回退。不要用“命令没报错”当作“硬件已启用”，一定要看日志与 GPU 计数器。

🧩 Rockchip MPP：嵌入式板的 VPU 工具箱

瑞芯微的 RK3588、RK3568 这类 SoC 把视频编解码放进 VPU，通过 MPP（Media Process Platform）暴露给应用。它像一块“板载的专业转码卡”：功耗几瓦，能同时处理多路 1080p，非常适合摄像头、边缘盒子、车载与国产化设备。代价是工具链不如 x86 成熟，很多细节要看 Rockchip SDK 文档。

MPP 的典型特征是大量使用 DMABuf 与 DMA heap：采集（V4L2）、解码、缩放、编码之间传递的是文件描述符，而不是内存指针。这样 CPU 完全不碰像素，VPU 与 ISP/GPU 之间直接交接。要零拷贝，就必须让整条 GStreamer/FFmpeg 链路都协商到 memory:DMABuf。

# GStreamer：采集 → 硬件编码 → RTP 发送（元素名以 gst-rockchip 为准）
gst-launch-1.0 v4l2src device=/dev/video0 io-mode=dmabuf ! \
  video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1 ! \
  mpph264enc ! h264parse ! rtph264pay config-interval=1 ! \
  udpsink host=192.168.1.10 port=5004

# FFmpeg 的 rkmpp 支持通常来自 Rockchip 维护的分支/补丁
ffmpeg -c:v h264_rkmpp -i in.mp4 -c:v h264_rkmpp -b:v 4M out.mp4

常见约束

NV12 的宽高常有对齐要求（例如 16 像素），分辨率不对齐会报 “invalid frame size”；DMABuf 需要正确的 plane 布局与 stride；容器/权限要能访问 /dev/mpp_service 与 /dev/dma_heap。具体对齐规则以 SoC 与 MPP 版本文档为准。

怎么验证

用 MPP 自带的 mpi_dec_test/mpi_enc_test 先跑通硬件，再接入 GStreamer 或 FFmpeg；用 gst-inspect-1.0 mpph264enc 看元素是否存在；用 GST_DEBUG=3 看协商失败在哪一步。

⚠️不要把 x86 的参数直接搬过来：Rockchip 的编码器对 GOP、码控、B 帧的支持与 NVENC/QSV 不同；有些 preset 根本不存在。先在板子上用最小流水线跑通，再逐步加缩放、叠加、多路，别一上来就套用“通用优化参数”。

🚚 零拷贝：别让货离开传送带

传统链路像这样：解码器把画面写进显存 → 为了做缩放/加字幕，搬回系统内存 → CPU 处理 → 再搬回显存给编码器。货每上下一次传送带，就要过一次 PCIe。零拷贝的思路是：让货一直留在传送带上，解码、缩放、编码都在显存里完成，CPU 只传“货架号”（表面句柄），不搬货。

memory:DMABuf 是什么

DMABuf 是 Linux 内核里的“缓冲区共享机制”：驱动 A 分配一块内存，把文件描述符（fd）交给驱动 B，B 直接映射使用，不需要复制。GStreamer 用 caps video/x-raw(memory:DMABuf) 表达“这帧是 DMABuf”；V4L2 用 io-mode=dmabuf 让摄像头直接把帧写进共享缓冲；MPP/VAAPI 再把同一个 fd 交给编码器。整个过程中，CPU 只参与协商，不参与搬运。

操作实际发生了什么代价怎么避免
hwdownload把设备表面拷贝到系统内存（通常一次 PCIe DMA 或映射）1080p 单帧约 3 MB，30 fps 就是 ~90 MB/s；4K 翻四倍不要在中途插入只认 CPU 内存的滤镜
hwupload把系统内存里的帧上传成设备表面与下载对称，且可能多一次格式转换让解码输出直接是设备格式，或全程用设备滤镜
format=nv12若上游是硬件表面，FFmpeg 往往先下载再转格式隐式下载，日志里才看得见改用 scale_cuda=format=nv12 / scale_vaapi
drawtext / subtitlesCPU 滤镜，必须拿到可读像素强制下载 + 上传，链路断裂用 GPU 叠加，或把字幕烧录放到编码前单独处理
多路缩放每路都要表面与队列显存上涨，可能触发同步等待限制并发、复用表面池、降低队列深度

“零拷贝”不等于“零开销”

即使不拷贝，仍有格式协商、表面分配、fence 同步、队列调度。多路 4K 时，显存带宽与编码单元数量才是瓶颈。零拷贝解决的是“无谓的来回搬”，不是“所有成本归零”。

什么时候必须下载

做人脸识别、OpenCV 处理、CPU 字幕、复杂叠加，或编码器不支持当前设备格式时，下载无法避免。此时要接受一次拷贝，并尽量把它放在链路末端，避免“下载→处理→上传→再下载”。

💡算一笔账：1080p YUV420 单帧约 3.1 MB。30 fps 下，一次下载加一次上传就是约 186 MB/s 的额外内存/PCIe 流量；4K 30 fps 则约 746 MB/s。多路并发时，这就是为什么“明明 GPU 利用率不高，却只能跑几路”的真正原因。

🛠️ FFmpeg 硬件命令：先选设备，再选编码器

FFmpeg 的硬件用法有一条固定套路：用 -hwaccel 指定解码后端，用 -hwaccel_output_format 决定帧留在哪里，用 -vf 里的设备滤镜做缩放，最后用对应的硬件编码器。任何一步不匹配，FFmpeg 就会自动插入下载/上传，性能瞬间回到解放前。

先跑单路，再压多路

⚠️性能验证的黄金标准：同一条命令、同一份输入，对比“硬件全链路”与“软件全链路”的 CPU 占用、GPU 利用率、单路延迟、可并发路数。只看“命令跑通了”远远不够——很多所谓硬件加速，实际是硬件解码 + 软件编码。

📊 显存、并发与画质：没有全能的硬件

下表是经验性对比，不是跑分承诺。同一后端在不同代际、不同驱动、不同码控参数下差异很大；上线前必须用自己的素材、自己的码率、自己的并发数实测。

后端显存 / 内存占用并发路数画质与码控适合
NVENC独显显存：表面 + 参考帧 + 队列，4K 明显高于 1080p受编码单元、显存与 session 限制；专业卡通常更宽Turing 之后画质明显提升；低码率仍可能不如 x264 slow；p1–p7 可调多路转码、直播、GPU 服务器
NVDEC只占解码表面；并发看显存与解码单元解码路数通常高于编码不涉及画质，只负责还原硬解、解码后交给其他单元
QSV核显共享系统内存（部分平台有专用显存）受媒体引擎与内存带宽限制，适合中低路数日常画质够用；极低码率弱于软件慢速 preset；low_power 功能受限边缘盒子、NUC、低功耗多路
VAAPI取决于 Intel/AMD 设备，共享或独立显存受 GPU 媒体引擎与驱动影响驱动差异大；Intel 与 AMD 的画质/码控不完全相同Linux 通用部署、国产化平台
VideoToolboxApple Silicon 统一内存，拷贝成本低受媒体引擎数量限制；桌面机型更强HEVC 画质好，但可调参数少；以码率控制为主macOS/iOS 客户端、剪辑、录屏
D3D11VA / MFWindows 显存；MFT 可能额外缓冲受 GPU 与 MFT 实现影响取决于实际选中的 MFT；可能是硬件也可能是软件Windows 服务、桌面应用
AMFAMD 显存；互操作可能多一次转换受编码单元与驱动限制代际差异明显；quality/usage 预设影响大Windows + AMD 显卡
Rockchip MPP共享 DDR；DMABuf 省内存，但表面池要规划嵌入式 VPU 路数有限，4K 更紧工具链与参数空间较小；高码率下够用摄像头、边缘盒子、车载

还有一个常被忽略的维度：解码能力不等于编码能力。一张卡可能能解 8K AV1，却只能编 4K H.264；也可能解码路数很多，但编码 session 被驱动限制。做容量规划时，解码、缩放、编码要分别算。

上面这个量化演示能帮你建立“QP 与画质/码率”的直觉。硬件编码器同样有这个旋钮，只是名字不同：NVENC 是 -cq，VAAPI/QSV 常见 -global_quality，AMF 是 -qp_i/-qp_p 或质量预设。名字不同，本质都是“让编码器在码率与失真之间选一个点”。

🔍画质对比的正确做法：固定码率、固定 GOP、固定分辨率，用同一段含运动/暗场/细节的素材，比较 VMAF/SSIM 与主观观感。只对比“文件大小”或“看起来还行”，很容易被码控模式误导。

🕳️ 常见参数陷阱：硬件加速的“静默失败”

硬件加速最浪费时间的，不是报错，而是不报错：它悄悄回退软件、悄悄下载再上传、悄悄忽略了你的质量参数。下面这些坑，几乎每个部署都会踩一遍。

NVENC：preset 与码控

-preset p1 最快、p7 最慢最好；旧名字可能被接受但映射不一定符合预期。-cq 只有配合 -rc vbr（并通常配 -b:v 0）才是恒定质量；只写 -cq 很可能被忽略。-tune ll 降延迟但降画质。

VAAPI：格式协商

解码输出已是 VAAPI 表面时，再写 format=nv12 会强制下载；应写 scale_vaapi=format=nv12。10-bit 要 p010。软件输入才用 format=nv12,hwupload，并且要先 -vaapi_device。

QSV：low_power 的隐形限制

-low_power 1 省电，但可能关闭 lookahead、B 帧或部分码控；需要画质时不要开。`-async_depth` 增大吞吐也增大延迟与内存，低延迟场景要调小。

VideoToolbox：别被 allow_sw 骗了

-allow_sw 1 允许硬件不支持时回退软件，表面上永远成功。做性能验证时先设为 0，确认硬件路径；正式部署再按需打开容错。

通用：B 帧与延迟

不是所有硬件/格式都支持 B 帧；支持也不代表适合低延迟。B 帧需要缓存未来帧，直播连麦常直接 -bf 0。GOP 过长会让首帧等待变长，切片/秒开场景要把 -g 调到与关键帧间隔一致。

通用：隐式下载

只要滤镜图里出现 hwdownload、format 转普通 yuv420p，或编码器输入不是设备格式，零拷贝就断了。用 -v verbose 看自动插入的 scale/format 滤镜，别假设“没写就没有”。

症状根因验证 / 修复
CPU 仍然很高，GPU 几乎不动硬件未启用或静默回退软件看 ffmpeg -v verbose 的 encoder 初始化；确认设备权限与驱动
GPU 解码忙、编码不忙只硬解，编码仍是 x264/x265检查输出编码器名；看 CPU 是否有单核跑满
4K 多路时帧率骤降PCIe/内存带宽、显存或表面池不足减少 hwdownload；限制并发；看显存与 DMA 带宽
编码器初始化失败分辨率/格式/10-bit 不支持，或 session 达上限查厂商支持矩阵；降到 8-bit/NV12；减少并发
画面偏色/发绿色彩范围（limited/full）或格式转换错误检查 color_range、colorspace；避免多余的 RGB 往返

Profile 与 Level：同一个编码器也有“档位”

就像同一辆车有经济模式、运动模式，编码器也用 profile 决定“允许用哪些工具”，用 level 决定“允许多大的画面与码率”。硬件支持某个 codec，不等于支持所有 profile；很多“编码失败”其实是 profile 或 level 选错了。

解码强 ≠ 编码强

一张卡能解 8K AV1，不代表能编 AV1；能解 4:2:2，不代表能编 4:2:2。矩阵里“解”和“编”必须分列看，做转码容量规划时也要分别算。

8K 解码 ≠ 8K 编码

解码只还原画面，编码还要做运动搜索、码控、熵编码，显存与时间预算高得多。很多型号“8K 解码”只是播放能力，“8K 编码”要降帧率或根本不存在。

同一 API ≠ 同一能力

VAAPI 在 Intel 与 AMD 上是两套实现；QSV 在旧核显与新 Arc 上也不是一个能力表。别拿“VAAPI 支持”当跨平台保证，要按具体设备查。

💡采购三问：① 我要的是解码、编码，还是两者都要？② 我的分辨率、帧率、位深、色度分别是什么？③ 我要几路并发，瓶颈会落在媒体引擎、显存还是总线？三问答完，再看“支持列表”，就不会被一行“支持 8K”带偏。

🧵 零拷贝逐跳拆解：帧在哪一步被搬下传送带

把转码链路想成快递中转：每换一种交通工具，就要卸货、扫码、再装车。所谓零拷贝，就是让同一个包裹始终待在同一个托盘上，中转站只换司机、不换托盘。下面把“解码器 → 滤镜 → 编码器”拆成逐跳，指出哪些动作会偷偷把帧搬回系统内存。

第一跳：解复用只送“压缩包”，不送像素

解复用像把整箱快递拆成一个个小包裹：包裹里仍是压缩码流，体积只有 KB 级。这一步本来就在 CPU 上完成，硬件帮不上忙，也不该帮——真正开始搬像素，是解码器把码流还原成帧的那一刻。

因此“零拷贝”讨论的从来不是码流，而是像素帧。1080p 一帧 NV12 约 3.1 MB，码流一帧可能只有几十 KB；两者的搬运成本差了两个数量级。

第二跳：解码输出留在哪，决定后面全部

解码器像把压缩包拆成实物，然后决定把实物放在哪个货架。货架有两种：GPU 的设备表面（显存）和 CPU 的系统内存。只要它把帧放到系统内存，后面再编码就必须重新上传——这是最隐蔽、也最常见的一次额外搬运。

关键开关是 -hwaccel_output_format。只写 -hwaccel cuda 而不写输出格式时，FFmpeg 可能把解码结果下载成软件帧，后面所有滤镜都回到 CPU；日志里编码器名字仍然是 h264_nvenc，所以很容易误判。

# 反例：只开了硬解，没有把帧留在显存；scale 在 CPU 上做
ffmpeg -hwaccel cuda -i in.mp4 -vf "scale=1280:720" \
  -c:v h264_nvenc -preset p5 out.mp4

# 正例：解码输出 CUDA 表面，缩放也在显存里完成
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -vf "scale_cuda=w=1280:h=720:format=yuv420p" \
  -c:v h264_nvenc -preset p5 out.mp4

# VAAPI：设备表面 + 设备滤镜
ffmpeg -hwaccel vaapi -hwaccel_device /dev/dri/renderD128 \
  -hwaccel_output_format vaapi -i in.mp4 \
  -vf "scale_vaapi=w=1280:h=720:format=nv12" \
  -c:v h264_vaapi -rc_mode CQP -global_quality 22 out.mp4

# QSV：注意 low_power 模式可能少了 lookahead / B 帧
ffmpeg -hwaccel qsv -hwaccel_output_format qsv -i in.mp4 \
  -vf "scale_qsv=w=1280:h=720:format=nv12" \
  -c:v h264_qsv -global_quality 23 -look_ahead 1 out.mp4

第三跳：滤镜是零拷贝的分界线

滤镜像中转站里的安检机：如果安检机只认“拆开的散货”，托盘就必须先卸下来。FFmpeg 的多数传统滤镜（drawtext、subtitles、overlay、fps）只认系统内存里的帧；硬件帧进来时，框架会插入 hwdownload，处理完再 hwupload。

尤其要注意 overlay：它内部用 framesync 对齐两路时间戳，默认按 CPU 帧处理。即使主画面是硬件帧，只要叠加层来自 CPU，整条链路就会被拉回内存。画中画、水印、字幕滚动都是这个套路。

四种常见的“断点触发器”：

普通 format

-vf "format=nv12" 看起来只是转格式，但对设备表面来说，它意味着“给我 CPU 可读的 NV12”。应改成 scale_cuda=format=yuv420p 或 scale_vaapi=format=nv12。

CPU 滤镜与 framesync

drawtext、subtitles、overlay、部分 fps/setpts 组合会要求软件帧；能换 overlay_cuda/overlay_vaapi 就换，不能换就把它们挪到链路末端。

位深 / 色度不匹配

软解常见输出 yuv420p10le，硬件编码器要 p010le；RGB、4:2:2 输入也可能触发隐式转换。不是报错，而是静默插入 scale/format。

跨后端映射

D3D11 解码后交给 NVENC、VAAPI 解码后交给 QSV，都需要显式映射或下载再上传。别假设“都是硬件”就能直接握手，先看 hwmap 是否支持该派生方向。

第四跳：编码器只认少数几种“托盘”

编码器像只有固定卡槽的装车机：NVENC 主要吃 NV12/P010 的 CUDA 表面，VAAPI 吃 VA surface，QSV 吃 QSV surface。卡槽不一致时，FFmpeg 不会拒绝工作，而是自动插一段转换——这段转换往往就是下载、软件转换、再上传。

所以验证时不要只看“有没有报错”，要看编码器初始化时声明的输入 pix_fmt，以及滤镜图里是否出现自动插入的 auto_scale。一个简单判断：日志里的 pixfmt 从 cuda/vaapi/qsv 变成 yuv420p，链路就已经断了。

单步走到第 5–7 步，就能看到“看起来开了硬件、实际每帧上下传送带”的完整路径。红色不是故障，而是参数协商的结果；修复方式不是换卡，而是把 CPU 滤镜换成 GPU 版本，或明确接受一次下载。

第五跳：从 V4L2 / D3D11 进来，第一跳就可能要上传

摄像头采集像直接从传送带旁边进货：V4L2 把帧写进系统内存（或 DMABuf），它本身不是 GPU 表面。要送进编码器，第一步就得 hwupload；能走 DMABuf 的平台（如 Rockchip）则可以免掉这次上传。

Windows 的 D3D11VA 解码输出是 D3D11 纹理数组，若编码器是 NVENC，还需要一次跨 API 映射或下载。两者都是“硬件”，但不是同一个货架，别默认能直接对接。

# V4L2 摄像头 → CUDA 上传 → NVENC（先初始化设备，再指定滤镜设备）
ffmpeg -init_hw_device cuda=cu:0 -filter_hw_device cu \
  -f v4l2 -video_size 1920x1080 -framerate 30 -i /dev/video0 \
  -vf "hwupload_cuda,scale_cuda=format=yuv420p" \
  -c:v h264_nvenc -preset p5 out.mp4

# D3D11 解码 → 下载成 NV12 → 上传 CUDA → NVENC（跨后端最稳的保守写法）
ffmpeg -init_hw_device cuda=cu:0 -filter_hw_device cu \
  -hwaccel d3d11va -hwaccel_output_format d3d11 -i in.mp4 \
  -vf "hwdownload,format=nv12,hwupload_cuda" \
  -c:v h264_nvenc -preset p5 out.mp4

# 能映射时优先映射，避免像素落地；是否支持 derive_device=cuda 以本机构建为准
ffmpeg -hwaccel d3d11va -hwaccel_output_format d3d11 -i in.mp4 \
  -vf "hwmap=derive_device=cuda,scale_cuda=format=yuv420p" \
  -c:v h264_nvenc out.mp4

V4L2 还有一种“零拷贝”路线：使用 SoC 的 V4L2 M2M 设备（如 h264_v4l2m2m）或 Rockchip 的 MPP，让采集缓冲直接交给硬件编码器。它依赖平台与内核驱动，通用 x86 桌面不一定有。

怎么用日志证明链路断了

日志像快递的扫码记录：不用猜，扫一次就知道包裹在哪个站被卸下来了。把 FFmpeg 开到 verbose，只筛关键行，重点看 pixfmt 的变化和自动插入的滤镜。

# 只看关键行：设备、解码器、像素格式、自动缩放、下载/上传
ffmpeg -v verbose -i in.mp4 -c:v h264_nvenc out.mp4 2>&1 | \
  grep -E "Using device|Using hardware|pixfmt|auto_scale|hwdownload|hwupload"

# 典型输出（地址与路径会变，格式可能随版本略有差异）
[AVHWDeviceContext @ 0x...] Using device 0: NVIDIA GeForce ...
[h264 @ 0x...] Using hardware decoding (cuda).
[graph 0 input from stream 0:0 @ 0x...] w:1920 h:1080 pixfmt:cuda tb:1/30 fr:30/1 sar:1/1
[auto_scale_0 @ 0x...] w:1920 h:1080 fmt:cuda -> w:1920 h:1080 fmt:yuv420p
💡十秒判读法：① 搜 Using hardware decoding 确认硬解；② 搜 pixfmt，看是否从设备格式变成 yuv420p；③ 搜 auto_scale/hwdownload，有就是断点；④ 看编码器初始化是否接受同一个 hw_frames_ctx。四步都过，才叫全链路零拷贝。
⚠️“零拷贝”不是“零延迟”：设备表面池、fence 同步、编码器队列都会引入等待。1080p 单路时，一次下载可能只花几毫秒；多路 4K 时才会变成 PCIe 与内存带宽灾难。要不要死守零拷贝，取决于分辨率、路数与延迟目标，而不是口号。

🎚️ 参数对照：把 x264 的手感翻译成硬件旋钮

同一台相机，光圈、快门、ISO 在另一台机身上位置不同，但原理相同。硬件编码器的参数名和 x264 不一样，旋钮位置也不同；理解“每个旋钮在调什么”，比背一串命令更可靠。这一节做三件事：把目标翻译成硬件参数、拆开 NVENC 的 preset/码控、对比 HEVC 与 QSV 的差异。

把 preset 想成餐厅出菜速度：p1 是快餐窗口，p7 是慢火细炖。它们调的是编码器愿意开多少工具、做多少搜索，而不是简单地把码率调高。p7 也不会变成 x264 veryslow，只是“在硬件允许的范围内更认真”。

码控三兄弟：CQ、CBR、constqp

码控像开车时的三种目标：CQ 是“保持舒适度，油费随路况变”；CBR 是“每小时只能烧这么多油”；constqp 是“固定油门”。选错目标，参数再漂亮也没用。

模式你固定了什么什么会波动适合必配参数
-rc vbr + -cq质量目标码率随画面复杂度波动点播、归档、画质优先-b:v 0，否则仍可能被目标码率牵制
-rc cbr码率画质随内容波动直播、固定带宽传输-b:v，必要时配 -bufsize
-rc constqp量化步长码率波动最大实验、固定质量对比、特殊素材-qp；不适合带宽受限场景

-cq 与 x264 的 -crf 都常被翻译成“恒定质量”，但它们不是同一个算法：-cq 更接近“目标量化级别”，-crf 带有人眼感知与自适应量化的取舍。数值相近不代表观感相同，拿 VMAF 或主观对比说话。

hevc_nvenc 与 h264_nvenc：不只是换个编码器名字

H.264 像家用小货车，兼容性最好；HEVC 像厢式货车，同货量更省空间，但装卸要求更高。硬件上它们共享 NVENC 单元，参数却有关键差异，尤其是 10-bit 与 B 帧参考。

同码率兼容优先，效率较低通常更省码率但解码成本与专利/兼容性要一起考虑
4:2:2 / 4:4:4编码普遍不支持专业档位视型号广播流程要单独查支持矩阵，不要默认
 
# 画质优先：CQ + 自适应量化 + B 帧参考（注意 -b:v 0）
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -vf "scale_cuda=format=yuv420p" \
  -c:v h264_nvenc -preset p7 -tune hq -rc vbr -cq 20 -b:v 0 \
  -spatial_aq 1 -temporal_aq 1 -aq-strength 8 \
  -bf 3 -b_ref_mode middle -g 60 out.mp4

# 固定带宽直播：CBR + 低延迟，关闭 B 帧
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -c:v h264_nvenc -preset p3 -tune ull -rc cbr -b:v 6M -bufsize 12M \
  -bf 0 -g 30 out.mp4

# 10-bit HEVC：Main10 + P010，MP4 里加 hvc1 标签
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mkv \
  -vf "scale_cuda=format=p010le" \
  -c:v hevc_nvenc -profile:v main10 -pix_fmt p010le \
  -rc vbr -cq 22 -b:v 0 -tag:v hvc1 out.mp4

QSV：-global_quality 与 -look_ahead 怎么用

QSV 像核显里的省电模式：它不追求极限压缩，但能在很低的功耗下把活干完。它的质量旋钮常写作 -global_quality，前瞻写作 -look_ahead；两者都受 low_power 模式影响。

参数调的是什么代价注意
-preset veryfast … veryslow速度 / 工具使用量越慢越吃时间，画质略好映射到目标使用率，不等同 x264 档位
-global_quality N质量目标（ICQ 类行为）码率随内容波动与 -b:v 同时乱写会让意图变模糊
-look_ahead 1前瞻，改善码率分配增加延迟与缓冲low_power 下可能不可用；部分构建还有 -look_ahead_depth
-async_depth N并行深度 / 吞吐增加内存与延迟低延迟场景调小，离线转码可调大
-low_power 1省电模式可能关闭前瞻/B 帧/部分码控要画质时关掉；边缘低功耗再打开
 
# QSV：质量优先 + 前瞻；若 low_power 开启，look_ahead 可能被忽略
ffmpeg -hwaccel qsv -hwaccel_output_format qsv -i in.mp4 \
  -vf "scale_qsv=format=nv12" \
  -c:v h264_qsv -preset medium -global_quality 23 -look_ahead 1 \
  -async_depth 4 out.mp4

VAAPI / AMF / VideoToolbox 的旋钮地图

三个后端的参数哲学不同：VAAPI 像 Linux 的通用遥控器，功能有但命名抽象；AMF 像 AMD 自带遥控器，预设直观；VideoToolbox 像苹果的极简遥控器，按钮少但够用。先查本机 ffmpeg -h encoder=…，再写参数。

VAAPI-rc_mode CQP/CBR/VBR + -global_quality（部分构建用 -qp）编码器与驱动决定，参数空间中等受驱动与硬件影响把 format=nv12 写成普通滤镜，触发下载
AMF-rc cbr/vbr，-qp_i/-qp_p-quality speed/balanced/quality，-usage transcoding/ultralowlatency/lowlatency/webcam-usage ultralowlatency质量预设与代际强相关；Linux 通常不用 AMF
VideoToolbox以 -b:v 目标码率为主，质量旋钮少系统决定，参数少-realtime 1-allow_sw 1 会掩盖“其实跑在 CPU”
 
# VAAPI：CQP 质量模式
ffmpeg -hwaccel vaapi -hwaccel_output_format vaapi -i in.mp4 \
  -vf "scale_vaapi=format=nv12" \
  -c:v h264_vaapi -rc_mode CQP -global_quality 23 out.mp4

# AMF：质量优先 + 转码场景
ffmpeg -i in.mp4 -c:v h264_amf -quality quality -rc cbr -b:v 4M \
  -usage transcoding -qp_i 22 -qp_p 24 out.mp4

# VideoToolbox：关闭软回退，先确认真的走了硬件
ffmpeg -hwaccel videotoolbox -i in.mp4 -c:v hevc_videotoolbox \
  -b:v 4M -g 50 -realtime 1 -allow_sw 0 out.mp4
⚠️同名参数不同义：NVENC 的 -preset p5 不是 x264 的 medium；-cq 不是 -crf；VAAPI 与 QSV 的 -global_quality 也不是同一套实现。跨后端复制命令时，先删掉“看起来眼熟”的参数，再按本机 ffmpeg -h encoder=… 重新填。
💡参数排查顺序：① 先确认参数真的出现在 ffmpeg -h encoder=… 输出里；② 用 -v verbose 看编码器初始化；③ 看实际输出码率是否随 -cq/-b:v 变化；④ 最后才比较画质。参数没生效时，调数值只会浪费时间。

📦 单机密度：先找最短板，再谈能跑几路

一条生产线能产多少，不取决于最快的那台机器，而取决于最慢的工位。转码密度也一样：解码、缩放、编码、显存、PCIe、网络，任何一项先到顶，整机就卡在那里。下面用一张“木桶图”和一个估算公式，把“能跑几路”拆成可验证的问题。

实际路数 ≈ min（解码产能, 缩放产能, 编码产能, 显存容量, PCIe 带宽, 内存带宽, 网络带宽）/ 单路需求

先算像素流量：拷贝为什么这么贵

像素搬运像给每一帧称重再装车：单帧不重，但每秒 30 次、每路都来一遍，很快就压垮传送带。先算清“一帧多重、一秒多少趟”，就知道瓶颈会在哪。

1080p NV12

1920 × 1080 × 1.5 ≈ 3.1 MB / 帧；30 fps 约 93 MB/s。一次下载 + 一次上传约 186 MB/s。

4K NV12

3840 × 2160 × 1.5 ≈ 12.4 MB / 帧；30 fps 约 373 MB/s。来回一趟约 746 MB/s。

10 路 4K 来回

理论下限约 7.5 GB/s 的像素流量，还没算 stride、对齐与队列开销。PCIe 与内存带宽会先于编码器喊停。

以上是理论量级，不是实测承诺；实际帧率、stride、色彩格式、是否 10-bit 都会改变数字。10-bit P010 每像素 3 字节，流量约为 8-bit 的两倍。

再算显存：表面池比你想的能吃

显存像后厨的案板：每路都要有解码表面、参考帧、滤镜中间帧、编码输入表面和队列。单块案板不大，但十路同时开火，很快就没地方放盘子。

粗略估算：1080p 单路若保留 10–20 个表面，约 30–60 MB；4K 单路约 120–250 MB。10 路 4K 就可能吃掉 1.2–2.5 GB，再叠加模型、纹理、桌面占用，消费卡的显存很快见底。

表面数量由解码器参考帧、-extra_hw_frames、滤镜队列、编码器 async_depth 共同决定；数字随实现变化，必须用 nvidia-smi 或 intel_gpu_top 实测。

密度估算表：只给量级，不给假精确值

下表像餐厅的“预估接待能力”：能坐多少人，要看客人吃多久、后厨几口灶、门口多宽。任何精确到个位的承诺，离开素材与参数都不成立。

平台 / 型号量级1080p30 H.264 编码主要瓶颈备注
消费级 GeForce（RTX 30/40 量级）个位数到十几路session 限制、显存、编码单元驱动版本会影响上限；先压测再承诺

为什么瓶颈常常不在编码器

编码器像收银台：它可能确实在忙，但队伍不动的原因，往往是前面的安检（解码/滤镜）或中间的搬运（PCIe）堵住了。判断瓶颈要看“谁先到 100%”，而不是看谁听起来最重要。

解码器先满

现象：nvidia-smi dmon 的 dec 列接近高位，enc 还有余量。对策：降低输入分辨率/码率，换解码单元更多的型号，或把部分流交给 CPU 软解。

PCIe / 拷贝先满

现象：CPU sy 高、Windows 任务管理器 Copy 引擎高、hwdownload 频繁。对策：去掉 CPU 滤镜、改用设备滤镜、检查是否漏写 -hwaccel_output_format。

显存先满

现象：编码器初始化失败、帧率骤降、驱动日志报内存不足。对策：降低 -extra_hw_frames 与队列深度、减少分辨率/路数，或换更大显存。

🚫不要把“消费卡 session 限制”当唯一瓶颈：很多部署在 session 还没到顶时，就已经被解码、显存或 PCIe 卡死。先采集四项指标（CPU、enc、dec、Copy/显存），再决定是加卡、换型号，还是改链路。
💡压测方法：固定输入与参数，逐路增加；每加一路记录帧率、CPU、GPU enc/dec、显存、Copy/PCIe、网络。找到“第 N 路开始掉帧”的拐点，比看一个平均值有用得多。用 -stream_loop -1 模拟长时间负载，别用 10 秒短片下结论。

🎨 色彩、位深与 HDR：硬件链路最容易“看起来对”的地方

同一罐可乐，标签写“零度”还是“经典”，喝起来是两回事；同一帧画面，色彩标签写错，看起来就会偏黄、发灰或死黑。硬件加速把像素搬得很快，但格式、位深、色彩矩阵、范围任何一项没对齐，快到飞起也救不回观感。这一节从 NV12/P010 的内存布局讲到 HDR 元数据透传。

NV12 与 P010：同一块“半平面”，不同的字长

NV12 像把亮度装一箱、色度装一箱，色度箱里 U 和 V 交替摆放；P010 是同一套装箱法，只是每个样本换成 16-bit 的“加厚箱”，里面实际只装 10-bit 的值。理解这个布局，才能看懂 stride、对齐和“为什么多了一次转换”。

P010 的“左对齐”是理解字节的关键：看到 80 c4 不要按 0xC480 直接当亮度值，要右移 6 位才是 0x312。不同厂商的 stride/对齐可能不同，但“高位有效、低位补零”的常见规则可以帮助你判断转换是否出错。

⚠️10-bit 最常见的“假成功”：输入是 yuv420p10le，编码器是 h264_nvenc，FFmpeg 会自动转成 8-bit yuv420p 并继续跑，不报错。想要 10-bit，必须用 hevc_nvenc -profile:v main10 -pix_fmt p010le（或 AV1 对应配置），并检查输出 ffprobe 的 pix_fmt。

BT.601 / BT.709 / BT.2020：颜色也要“对暗号”

色彩矩阵像两国插头标准：电压都对，但插头形状不对就插不上。BT.601 是标清时代的老标准，BT.709 是高清 SDR 的通用标准，BT.2020 是 HDR/广色域的基础；写错矩阵，红绿会偏，肤色最先“露馅”。

ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,pix_fmt,color_space,color_transfer,color_primaries,color_range,chroma_location \
  -of default=nw=1 in.mp4

# 转成 BT.709 SDR 输出，并显式写清标签
ffmpeg -i in.mp4 -c:v libx264 -crf 20 -pix_fmt yuv420p \
  -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv out.mp4

# 只在必须转范围时做，避免多余往返
ffmpeg -i in.mp4 -vf "scale=in_range=tv:out_range=pc" -pix_fmt yuv420p out.mp4
🔍色彩标签是“三件套 + 范围”：primaries 决定红绿蓝的坐标，transfer 决定亮度曲线，colorspace（matrix）决定 YUV 怎么变成 RGB，range 决定 16–235 还是 0–255。四个都要对；只改其中一个，画面仍然会偏。

HDR 元数据：转码不是“把 10-bit 搬过去”就完事

HDR 像一封带附件的邮件：画面是正文，元数据是附件。只搬正文、丢了附件，播放器就不知道该按多亮、多广的色域显示。HDR10 的静态元数据（Mastering Display、MaxCLL/MaxFALL）通常放在 SEI；HDR10+ 是动态元数据；Dolby Vision 还有 RPU。

普通 FFmpeg 转码不一定保留所有 HDR 元数据，尤其是 HDR10+ 与 Dolby Vision。要做 HDR 转 HDR，至少显式写对颜色标签；要做 HDR 转 SDR，则需要 tone mapping，通常在 CPU 上用 zscale + tonemap 完成，硬件全链路会被打断。

# HDR10 转 HDR10：10-bit HEVC，显式保留颜色标签
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mkv \
  -vf "scale_cuda=format=p010le" \
  -c:v hevc_nvenc -profile:v main10 -pix_fmt p010le \
  -color_primaries bt2020 -color_trc smpte2084 -colorspace bt2020nc -color_range tv \
  -rc vbr -cq 22 -b:v 0 out.mkv

# HDR → SDR 的常见 tone mapping 链（CPU，硬件滤镜一般不替代）
ffmpeg -i in.mkv -vf "zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p" \
  -c:v libx264 -crf 20 out.mp4

HDR10+ 的动态元数据、Dolby Vision 的 RPU 需要专门的工具链（如 HDR10+ 元数据工具、dovi_tool 量级），不能指望一条 FFmpeg 命令自动处理。转码后用 MediaInfo / ffprobe 核对 Mastering Display、MaxCLL 等字段是否还在。

scale_cuda 与 scale_npp：两把不同的剪刀

两者都像“在显存里剪裁画面”，但一把是 FFmpeg 自带的通用剪刀，另一把是 NVIDIA NPP 库的专业剪刀。日常缩放用前者更省事；需要 NPP 的算法或历史工作流才用后者，而且要先确认本机构建是否启用。

# 确认本机是否有 scale_npp，以及它支持哪些选项
ffmpeg -hide_banner -h filter=scale_npp

ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -vf "scale_npp=w=1280:h=720:format=yuv420p" \
  -c:v h264_nvenc -preset p5 out.mp4
🚫偏色排查先停“RGB 往返”：每做一次 YUV→RGB→YUV，就可能丢色彩矩阵与范围信息。硬件链路里尽量保持 NV12/P010；确实需要 RGB 处理时，把范围与矩阵显式写死，并在输出前核对 ffprobe 的 color_range、color_space。

🐳 容器、WSL2 与虚拟机：硬件在宿主机，不在镜像里

设备像宿舍的门禁卡：容器只是租客，房东没把卡给你，你就进不去。镜像里写满 ffmpeg 命令也没用——设备节点、驱动库、权限必须从宿主机透传进来。这一节按 Docker、Kubernetes、WSL2、虚拟化的顺序排一遍最常见的“设备不见了”。

Docker：Intel / AMD 用 /dev/dri，NVIDIA 用 Toolkit

Docker 容器像合租房：房东（宿主机）有全套设备，但不会自动把每个房间的门卡给你。VAAPI/QSV 需要把 /dev/dri 整目录映射进去，并让容器用户有 render 组权限；NVIDIA 则通过 Container Toolkit 注入设备节点与驱动库。

# Intel / AMD：映射整个 /dev/dri，补上渲染组 GID
docker run --rm -it \
  --device /dev/dri:/dev/dri \
  --group-add "$(stat -c '%g' /dev/dri/renderD128)" \
  -v "$PWD:/work" my-ffmpeg \
  vainfo --display drm --device /dev/dri/renderD128

# 进容器后先看设备在不在
ls -l /dev/dri
ffmpeg -hwaccels
ffmpeg -h encoder=h264_vaapi

--device /dev/dri 会把 card0、renderD128 等节点一起带进去；只映射单个 renderD128 也能工作，但某些库会尝试打开 card0。非 root 用户还需要容器内存在对应 GID 的组，否则会报权限错误。

# NVIDIA：先确认宿主机驱动与 nvidia-smi
nvidia-smi

# 容器里验证驱动可达（视频能力需要 video capability）
docker run --rm --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,video,utility \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 你自己的 ffmpeg 镜像里再验证编码器
docker run --rm --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,video,utility \
  my-ffmpeg ffmpeg -hwaccels

注意：nvidia/cuda 基础镜像只用来验证驱动透传，不一定自带 FFmpeg。真正的转码镜像要把 FFmpeg 装进去，并确认它编译了 nvenc。默认 capability 往往不含 video；漏了它，nvidia-smi 正常但编码器会加载失败。

Docker Compose 与 Kubernetes：把设备写成资源

Compose 像点菜时把“忌口”写进订单：设备不是运行时临时加，而是声明在服务配置里。Kubernetes 则把 GPU 变成调度资源，Pod 申请到卡后，视频能力仍要靠环境变量与设备插件配合。

# docker-compose.yml（NVIDIA）
services:
  ffmpeg:
    image: my-ffmpeg
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu, video]

# Kubernetes：NVIDIA device plugin 暴露 nvidia.com/gpu
resources:
  limits:
    nvidia.com/gpu: 1

Kubernetes 里还要设置 NVIDIA_DRIVER_CAPABILITIES（或通过 RuntimeClass 配置）才能启用 video；Intel 核显通常用 Intel device plugin 或 hostPath 映射 /dev/dri。不同集群的插件实现不同，别假设“Pod 里有 GPU 就一定有编码器”。

WSL2：有 CUDA，不等于有 /dev/dri

WSL2 像“合租房的独立隔间”：它共享 Windows 内核的一部分能力，但不是完整 Linux。NVIDIA 通过 GPU-PV 提供 CUDA 与部分编解码能力，设备节点是 /dev/dxg；Intel/AMD 的 Linux 原生 VAAPI 路径通常没有 /dev/dri。

# WSL2 内先看有什么
ls -l /dev/dri /dev/dxg
nvidia-smi
ffmpeg -hwaccels

# 不要假设 VAAPI/QSV 的 /dev/dri 路径存在
vainfo --display drm --device /dev/dri/renderD128

WSL2 里 NVENC/NVDEC 能否工作，取决于 Windows 驱动、WSL 内核与 FFmpeg 构建；即使能跑，零拷贝与性能也可能与裸机不同。VAAPI/QSV 的 Linux 原生路径在 WSL2 里基本不可用；需要 Intel 核显加速时，优先考虑原生 Linux、Windows 的 D3D11/MF，或虚拟机直通。

虚拟机与 vGPU：直通最稳，虚拟化最复杂

PCIe 直通像把整间厨房租给你，设备几乎和裸机一样；vGPU/SR-IOV 像共享厨房，按时间片分配，方便但媒体引擎可能被限制。云上 GPU 还可能是 MIG 或 vGPU 切片，“有卡”不等于“有编码器”。

方式设备可见性媒体引擎典型限制建议
PCIe 直通（VFIO）整卡进入虚拟机接近裸机需要 IOMMU、设备绑定、驱动隔离对性能/零拷贝要求高时首选
NVIDIA vGPU按 profile 切分取决于 profile 与许可编码 session、显存、许可都可能受限先查该 profile 的媒体能力矩阵
AMD MxGPU / SR-IOV按分区共享视代际与驱动Linux/Windows 支持不一致以厂商文档与实测为准
Intel SR-IOV按 VF 切分视平台消费级平台支持有限边缘/服务器平台单独确认

虚拟化层可能把一次 DMA 变成两次拷贝，也可能屏蔽某些 ioctl。先用 vainfo、nvidia-smi、ffmpeg -hwaccels 在虚拟机内验证，再跑端到端压测；不要拿裸机数据直接承诺虚拟机容量。

💡容器排错顺序：宿主机 nvidia-smi/vainfo → 设备节点是否存在 → 容器是否映射 → 容器内权限/组 → FFmpeg 是否编译了该编码器 → 参数是否真的走硬件。任何一步跳过，都可能得到“命令成功、CPU 满载”的假象。

📈 验证与观测：把“感觉快”变成几行数字

开车不能只凭发动机声音判断车速，要看仪表盘。转码也一样：“看起来在跑”不等于“硬件在干活”，更不等于“链路是零拷贝”。这一节把 NVIDIA、Intel、FFmpeg 日志、Windows 任务管理器四个仪表盘对齐，告诉你每个数字到底在说什么。

NVIDIA：先分清 sm、enc、dec、mem

四个指标像汽车上的四个表：sm 是发动机转速（3D/计算），enc 是编码器工时，dec 是解码器工时，mem 是油管流量（显存带宽），不是油箱剩余量。把它们混在一起看，就会得出“GPU 100% 所以编码器满了”的错误结论。

# 每秒采样：利用率 + 显存带宽 + 编解码器 + 频率
nvidia-smi dmon -s um -d 1

# 需要 CSV 喂监控时，直接用 query（字段随驱动版本可能略有差异）
nvidia-smi --query-gpu=timestamp,utilization.gpu,utilization.encoder,utilization.decoder,memory.used,memory.total,pcie.link.gen.current,pcie.link.width.current \
  --format=csv,noheader -l 1

# 按进程看谁在占用 GPU
nvidia-smi pmon -d 1
字段 / 指标它到底表示什么正常时异常信号与下一步
sm3D / 计算单元利用率转码时通常不高很高但 enc 很低：可能是滤镜/CUDA 核在忙，或别的任务占卡
enc硬件编码器利用率随路数上升接近高位且开始掉帧：编码产能到顶；若很低却慢，查链路是否断
dec硬件解码器利用率转码时先于 enc 上升先满：解码是瓶颈，降低输入规格或换解码单元更多的卡
mem显存控制器带宽利用率随分辨率/拷贝上升很高但 enc 不高：可能在缩放/下载/上传，或显存带宽被别的任务占用
mclk / pclk显存频率 / 核心频率负载时升频被限频/过热降频时，性能会突然塌陷
memory.used显存占用容量随路数缓慢上升接近上限：表面池/队列太多，减少路数或换大显存

dmon 的 mem 列是带宽利用率，不是已用显存；要看容量用 nvidia-smi --query-gpu=memory.used,memory.total 或 nvidia-smi 顶部表格。部分 GPU/驱动对 enc/dec 的利用率上报不完整，显示 N/A 时以帧率与日志为准。

Intel / AMD：媒体引擎藏在哪一栏

intel_gpu_top 像核显的分时电表，把 Render、Blitter、Video、VideoEnhance 各引擎分开计费。转码主要看 Video 与 VideoEnhance；如果 Render 很高而 Video 很低，多半是滤镜或色彩转换在跑，不是编码器。

# Intel：需要 perf 权限，通常用 sudo
sudo intel_gpu_top

# AMD：两个常用工具，选一个即可
radeontop
amdgpu_top

Intel 的 Video 引擎负责编解码，VideoEnhance 负责缩放/去噪等 VPP；两者合起来才是完整媒体管线。AMD 的 VCN 利用率在不同工具里命名不同，关注 “VCN / Video” 一栏，而不是 3D 占用。

FFmpeg 日志：三行就能判断链路

日志像快递的扫码记录：Using hardware decoding 只证明“解码上了硬件”，pixfmt 才证明“帧还在显存”，auto_scale 则暴露“链路已经被拉回 CPU”。开 verbose 或 debug，再用 grep 缩小范围。

# 关键行过滤
ffmpeg -v verbose -i in.mp4 -c:v h264_nvenc out.mp4 2>&1 | \
  grep -E "Using hardware|pixfmt|auto_scale|hwdownload|hwupload|Incompatible"

# 需要完整滤镜图时用 debug；日志会明显变长
ffmpeg -v debug -i in.mp4 -c:v h264_nvenc out.mp4 2>&1 | head -n 200

# 让 FFmpeg 自动落盘日志，方便事后对比
ffmpeg -report -i in.mp4 -c:v h264_nvenc out.mp4

# 端到端耗时与各阶段基准
ffmpeg -benchmark -i in.mp4 -c:v h264_nvenc out.mp4
日志片段含义下一步
Using hardware decoding (cuda)解码走 NVDEC只说明硬解，不代表全链路零拷贝
pixfmt:cuda帧是 CUDA 设备表面继续看后续滤镜是否保持该格式
auto_scale_0 … fmt:cuda -> fmt:yuv420p自动插入了软件缩放/格式转换改用 scale_cuda，删掉普通 format
hwdownload / hwupload像素在显存与内存之间搬运定位是哪个滤镜/格式协商造成的
Incompatible pixel format编码器不接受当前像素格式检查 8/10-bit、4:2:0/4:2:2、pix_fmt 名称
Cannot load libnvidia-encode.so.1运行时找不到编码库查驱动 capability、容器映射、FFmpeg 构建

Windows 任务管理器：Copy 引擎是零拷贝的照妖镜

任务管理器的 GPU 页像机场的行李分拣屏：Video Decode、Video Encode、3D、Copy 各走各的传送带。Copy 引擎升高，通常意味着有 DMA 在搬像素；如果你的链路号称零拷贝，它却很忙，就要查 hwdownload/hwupload。

引擎 / 指标含义转码时的读法
Video Decode硬件解码引擎应随输入路数上升；先满说明解码瓶颈
Video Encode硬件编码引擎应随输出路数上升；接近高位且掉帧说明编码到顶
3D渲染/计算引擎滤镜、色彩转换、部分 CUDA 核会占用；高但 enc 低要查滤镜
CopyDMA 拷贝引擎零拷贝链路应基本安静；持续升高 = 有显存↔内存搬运
Dedicated GPU memory独显显存占用持续接近上限：表面池/队列/分辨率过大
Shared GPU memory共享系统内存大量使用说明显存不够或走了软件路径

Windows 性能监视器里可看 GPU Engine(*)\Utilization Percentage 与 GPU Adapter Memory(*)\Dedicated Usage；不同驱动/系统的计数器命名略有差异。任务管理器适合快速判断“哪条引擎在忙”，精确压测仍要回到日志与帧率。

端到端：别只看 GPU

仪表盘不只看发动机，还要看油耗、胎压和车速。转码的 SLO 通常是“不丢帧、延迟可控、码率稳定”，这些指标在 GPU 之外：网络、磁盘、复用器、CPU 中断都可能先出问题。

指标怎么看正常异常时先查
输出帧率 / speedffmpeg 统计行里的 fps=、speed=speed > 1 才比实时快滤镜、解码、编码、磁盘
丢帧 / 重复帧输入与输出帧数对比、framecrc 校验帧数与时间戳连续时间基、fps 滤镜、可变帧率
CPUtop/htop，关注 sy 与单核占用低且平稳CPU 滤镜、拷贝、mux、加密
网络iftop/nload/ss码率稳定、无重传带宽、TCP 窗口、推流协议
磁盘 / 容器 IOiostat/df写盘不阻塞日志、临时文件、网络存储
温度 / 功耗nvidia-smi、sensors不降频、不撞功耗墙散热、机箱风道、电源
💡先定 SLO，再看仪表：“单机 20 路 1080p30、延迟小于 2 秒、连续 24 小时不丢帧”比“GPU 利用率 80%”更像验收标准。没有 SLO，任何数字都可以被解释成“正常”。

🧯 常见坑 FAQ：八个踩坑现场

下面八条像急诊室的分诊牌：先看症状，再按顺序排查，别一上来就换卡。每条都给出可执行的验证命令；涉及绕过厂商限制的内容只说明风险，不提供操作步骤。

▶高频 驱动和 FFmpeg 都说支持，为什么 CPU 还是满的？

最常见的原因不是“没装驱动”，而是链路中途被拉回 CPU：漏写 -hwaccel_output_format、用了 CPU 滤镜、像素格式不匹配，或者参数被自动忽略。先证明编码器真的在跑，再证明帧真的没落地。

ffmpeg -hwaccels
ffmpeg -h encoder=h264_nvenc
ffmpeg -v verbose -i in.mp4 -c:v h264_nvenc out.mp4 2>&1 | \
  grep -E "Using hardware|pixfmt|auto_scale|hwdownload|hwupload"

如果日志里 pixfmt 从 cuda 变成 yuv420p，或者出现 auto_scale，说明链路已断；先改滤镜与输出格式，再谈性能。

▶高频 前几路都正常，第 N 路突然失败，是卡坏了吗？

更可能是 session 上限、显存耗尽或表面池不够。消费级 GeForce 历史上受驱动 session 限制；专业/数据中心卡的额度更高。先看失败时的显存与编码器日志，再判断是“产品限制”还是“资源不够”。

nvidia-smi
nvidia-smi --query-gpu=memory.used,memory.total,utilization.encoder,utilization.decoder \
  --format=csv,noheader -l 1
nvidia-smi pmon -d 1

若是 OpenEncodeSessionEx failed 一类错误，且显存充足，通常是 session 额度；若是显存接近上限，先减队列/分辨率/路数，或调低 -extra_hw_frames。

▶风险 消费卡并发限制能“解锁”吗？

修改驱动或打补丁绕过 session 限制，通常违反厂商许可与保修条款，也可能带来稳定性与合规风险；生产环境不建议这么做。需要高并发时，优先选专业/数据中心型号，或增加机器、改用多卡与分布式转码。这里不提供绕过步骤。

▶ 显存爆了：-extra_hw_frames 是越大越好吗？

不是。它像给传送带多放几个托盘：太少会卡住（解码器没有可用表面），太多会占满仓库（显存）。它解决的是“表面池不够”，不是“编码器产能不够”。

# 适度增加解码表面，观察显存与是否还报错
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
  -extra_hw_frames 8 -i in.mp4 -c:v h264_nvenc out.mp4

同时检查 -async_depth、滤镜队列、并发路数与 4K/10-bit 输入。显存是总账，单看一个参数容易误判。

▶ 加了一行 drawtext，画质没变，CPU 却翻倍？

drawtext 只认 CPU 帧：硬件帧进来会先被 hwdownload，画完再 hwupload。每帧上下传送带两次，CPU 与 PCIe 都被拖下水。能换 GPU 叠加就换，不能换就把文字烧录放到离线环节。

# overlay_cuda 需要两路 CUDA 输入；叠加层也要先上传到设备表面
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 -i overlay.mp4 \
  -filter_complex "[0:v]scale_cuda=format=yuv420p[base];[1:v]scale_cuda=format=yuv420p[ov];[base][ov]overlay_cuda=x=20:y=20" \
  -c:v h264_nvenc out.mp4

用 PNG 水印时，把图片循环成视频流并 hwupload_cuda 后再叠加；具体写法以本机 ffmpeg -h filter=overlay_cuda 为准。如果必须用 CPU 字幕，至少把它放在编码前一次完成，别在多路并发里反复下载/上传。

▶高频 10-bit 输入，输出却变成 8-bit / 出现断层？

先看编码器是否支持 10-bit：h264_nvenc 一般只做 8-bit；hevc_nvenc 需要 Main10 与 p010le。FFmpeg 可能静默转换而不报错，所以必须检查输出的 pix_fmt。

ffprobe -v error -select_streams v:0 -show_entries stream=pix_fmt,profile \
  -of default=nw=1 out.mp4

ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mkv \
  -vf "scale_cuda=format=p010le" \
  -c:v hevc_nvenc -profile:v main10 -pix_fmt p010le out.mp4

还要确认输入不是 8-bit 上采样成 10-bit；真正的 10-bit 源才有额外色阶。P010 与 yuv420p10le 的转换也可能是一次隐藏成本。

▶ 全链路零拷贝了，为什么反而更慢？

零拷贝省的是带宽，不是延迟。设备表面池、fence 同步、编码器队列、GPU 滤镜的调度都可能增加等待；低分辨率时，一次下载可能比同步开销还便宜。零拷贝不是无条件更优。

对比方法：固定输入与输出参数，分别跑“全硬件”和“下载到 CPU 再编码”，记录 speed=、端到端延迟、CPU、显存与 Copy 引擎。用数据决定，而不是口号。

▶ 容器里 nvidia-smi 正常，FFmpeg 却报找不到 libnvidia-encode.so.1？

这像“门禁卡能刷开大门，却刷不开机房”：驱动容器能力不等于视频编码能力。常见原因是 NVIDIA_DRIVER_CAPABILITIES 没包含 video，或 FFmpeg 构建没启用 nvenc，或驱动版本与容器库不匹配。

docker run --rm --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,video,utility \
  my-ffmpeg sh -c "ldconfig -p | grep nvidia-encode; ffmpeg -h encoder=h264_nvenc"

先在宿主机确认 nvidia-smi 与编码器可用，再进容器复测；仍然失败就查镜像里的 FFmpeg 构建与驱动库路径。
