CPU 是全能厨师，什么都能做；GPU 里的解码器、编码器、缩放器则是后厨专岗——只做一件事，但快得多、省电得多。硬件加速不是“画质变好”，而是把重复劳动从通用核搬到固定电路。真正难的不是打开开关，而是让帧一直留在显存里，别在 CPU 和 GPU 之间来回搬。

🍳 硬件加速：不是更快的 CPU，而是更专的工位

软件编码像一位全能厨师：切菜、炒菜、摆盘全包，什么都能做，但一次只能做一份。硬件编码像把“切配”交给一台专用切片机：它只会切片，但一秒能切几百份，而且几乎不占厨师的手。视频解码/编码正是这种“重复、规则、量大”的活，天生适合固定功能电路。

但专用工位也有代价：它能做的菜式有限。硬件编码器的参考帧结构、B 帧、码控模式、psychovisual 优化都比 x264/x265 少；同一码率下，硬件编码的画质不一定更好，甚至可能更差。它真正省下的是 CPU 占用、功耗和整机成本，让你能把一台机器从“2 路 1080p”做到“16 路 1080p”。

先找瓶颈，再上硬件

用 top 看 CPU：如果 ffmpeg 单核跑满、sy 很高，可能在拷贝；如果 GPU 利用率低但帧率上不去，可能是解码/上传/下载在等。盲目换编码器，常常只是把瓶颈从 CPU 挪到 PCIe。

硬件编码的画质前提

同码率下，硬件编码通常不如 x264 slow/x265 medium；但在高码率、低延迟、多路场景，它的性价比极高。直播/监控优先吞吐，归档优先画质，这是两条不同的路线。

“支持硬件”不等于“已启用”

驱动、权限（render 组）、FFmpeg 编译选项、容器内设备映射、像素格式协商，任何一环缺失都会静默回退到软件。必须用日志和 ffmpeg -hwaccels 验证。

⚠️先纠正一个常见误解：“用了 NVENC，画质就会更好”是错的。硬件编码器的目标是在给定功耗与吞吐下足够好，不是“最强压缩”。要极致画质，仍然要用软件编码的慢速 preset；要极致路数与低功耗，才轮到硬件。

🔗 解码与编码链路：每一段都可能偷偷拷贝

一条典型的转码链路是：demux → parse → decode → scale/convert → encode → mux。硬件加速的本质，是让 decode 与 encode 的输出/输入都是“设备表面（surface）”，中间不经过 AVFrame 的系统内存拷贝。只要中间插入一个只认 CPU 内存的滤镜（比如 drawtext、subtitles、overlay），整条链路就会被迫 hwdownload，零拷贝立刻破功。

阶段软件路径硬件路径典型症状
解复用libavformat 读 MP4/TS同样在 CPU；硬件不参与磁盘/网络 IO 慢，GPU 一直闲着
解码libavcodec（H.264/HEVC）NVDEC / VAAPI / QSV / VT / D3D11VA解码帧格式是 AV_PIX_FMT_CUDA 等，不是 yuv420p
缩放/转格式swscale（CPU，吃内存带宽）scale_cuda、scale_vaapi、scale_qsv、vpp_qsv写了 format=nv12 却忘了设备限定，触发下载
编码x264 / x265 / libsvtav1h264_nvenc、h264_vaapi、h264_qsv、hevc_videotoolbox…编码器期望 NV12/P010，输入却是 RGB 或 10-bit 不匹配
复用/分发mp4/ts/flv muxerCPU；只处理码流，不碰像素mux 不是瓶颈，别在这里找性能

像素格式是第一道门槛

硬件编码器几乎都吃 NV12（8-bit 4:2:0，Y 平面 + 交织的 UV）或 P010（10-bit）。解码器输出的可能是 AV_PIX_FMT_CUDA、VAAPI、QSV、VIDEOTOOLBOX、D3D11 这类“设备像素格式”，它们不是内存里的 YUV 数组，而是显存表面的句柄。FFmpeg 用 AVHWFramesContext（hw_frames_ctx）描述这组表面的格式、尺寸与池化策略，编码器必须接受同一个 context，才能做到零拷贝。

硬件编码器对 B 帧的支持因格式与代际而异：有的只支持 P 帧，有的支持 B 帧但会牺牲低延迟。上表可以帮你直观看到 GOP 与 B 帧如何影响“首帧等待”和“编码延迟”——GOP 越长，随机访问越慢；B 帧越多，编码器需要缓存更多未来帧。

🔍零拷贝的判定标准：看 FFmpeg 日志里有没有 auto_scale_0 / hwdownload，看滤镜图里是否出现 format 转 yuv420p，看编码器输入 pix_fmt 是否仍为设备格式。只要出现一次下载，PCIe 带宽就会成为新的天花板。

🗺️ 七大后端全景：先认平台，再认名字

硬件加速不是一套 API，而是每个厂商各自的一套：Intel/AMD 在 Linux 上共同支持 VAAPI，NVIDIA 有自己的 NVENC/NVDEC，Intel 还有 QSV，苹果是 VideoToolbox，Windows 有 D3D11VA 与 Media Foundation，AMD 在 Windows 上还有 AMF，瑞芯微则有 MPP。名字记不住没关系，先记住它们在哪个平台、负责解码还是编码。

“解码器”和“编码器”是两套硬件

NVDEC 与 NVENC 是独立单元，可以同时工作；Intel 的媒体引擎也分解码与编码。GPU 利用率高不代表编码单元忙，反过来也一样——监控时要看专门的 enc/dec 计数器。

API 之上还有一层

FFmpeg 的 h264_vaapi、GStreamer 的 vah264enc、Intel 的 oneVPL 都是“封装层”。同一个硬件可能有多条调用路径，性能与可用参数并不完全等价。

容器里最容易漏设备

Docker 需要 --device /dev/dri（VAAPI/QSV）或 NVIDIA Container Toolkit（NVENC）。设备没映射时，FFmpeg 可能不报错，直接回退软件，让你误以为“硬件不过如此”。

🔌 VAAPI：Linux 上的“公共插座”

VAAPI（Video Acceleration API）像墙上的公共插座：Intel 和 AMD 的显卡都把自己的媒体引擎接到这个标准上，应用只要插同一种插头（libva），就不用为每家写一套代码。它不规定硬件怎么做，只规定“怎么申请表面、怎么提交解码/编码任务、怎么同步”。

Linux 上先确认设备和驱动：Intel 常见 iHD 驱动（较新核显）或 i965（老平台）；AMD 走 Mesa 的 radeonsi。设备节点通常是 /dev/dri/renderD128，用户需要在 render 组里，否则会报权限错误。

# 查看驱动、版本与支持的 profile/entrypoint
vainfo --display drm --device /dev/dri/renderD128

# 解码 → 缩放 → 编码，全程留在 VAAPI 表面
ffmpeg -hwaccel vaapi -hwaccel_device /dev/dri/renderD128 \
  -hwaccel_output_format vaapi -i in.mp4 \
  -vf 'scale_vaapi=format=nv12' \
  -c:v h264_vaapi -rc_mode CQP -global_quality 23 out.mp4

# 输入是软件帧时，需要显式上传到 VAAPI 表面
ffmpeg -vaapi_device /dev/dri/renderD128 -i in.mp4 \
  -vf 'format=nv12,hwupload' \
  -c:v h264_vaapi -global_quality 23 out.mp4
写法发生了什么代价 / 适用
-hwaccel_output_format vaapi解码输出直接是 VAAPI 表面，不下载零拷贝的前提；后续滤镜必须是 VAAPI 版本
scale_vaapi=format=nv12在 GPU 上缩放并转成编码器要的 NV12正确做法；10-bit 则用 p010
format=nv12,hwupload先在 CPU 内存转格式，再上传到显存软件输入时才用；每帧一次上传
hwdownload,format=nv12把表面搬回系统内存需要 CPU 滤镜/算法时被迫使用，PCIe 开销明显
-global_qualityVAAPI 的质量旋钮（配合 -rc_mode）不同驱动的支持模式不同；先查 ffmpeg -h encoder=h264_vaapi
⚠️最常见的 VAAPI 报错：“Impossible to convert between the formats”。八成是滤镜图里既写了设备输出、又写了普通 format=nv12，FFmpeg 只好尝试下载再转换。把 format 改成 scale_vaapi=format=nv12，或明确加 hwdownload，不要让它猜。

🎛️ NVENC / NVDEC：显卡上的独立车间

NVIDIA 把解码和编码做成了两个独立车间：NVDEC 负责拆包还原画面，NVENC 负责压回码流，它们和 CUDA 计算单元是分开的。这就是为什么一张卡可以一边跑推理、一边压十几路视频——只要显存和 session 限制撑得住。

FFmpeg 里，-hwaccel cuda -hwaccel_output_format cuda 让解码结果留在显存；scale_cuda 在显存里缩放；h264_nvenc/hevc_nvenc/av1_nvenc 直接吃这些表面。注意 AV1 编码只在较新代际的 GPU 上提供，具体支持矩阵以 NVIDIA 官方文档为准。

# 查看本机支持的硬件加速与编码器参数
ffmpeg -hwaccels
ffmpeg -h encoder=h264_nvenc

# 解码 + 缩放 + 编码，帧留在显存
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -vf 'scale_cuda=format=yuv420p' \
  -c:v h264_nvenc -preset p5 -tune hq -rc vbr -cq 23 -b:v 0 \
  -spatial_aq 1 -temporal_aq 1 -bf 3 -g 50 out.mp4

NVENC 的 preset 现在常用 p1–p7：p1 最快、p7 最慢但画质最好；旧的 fast/medium/slow 仍可能被接受，但映射关系由版本决定。-tune hq 偏画质，-tune ll/ull 偏低延迟（会牺牲压缩效率）。-rc vbr 配 -cq 才是“按质量”而不是“按码率”。

并发 session 限制

消费级 GeForce 历史上对同时编码路数有限制，专业卡/数据中心卡通常不限制。NVIDIA 在部分驱动版本放宽过限制，但具体数字随驱动与产品线变化，以官方文档和实测为准。部署前先跑满目标路数压测，别等上线才发现第 9 路起不来。

显存怎么算

每一路都要解码表面、参考帧、编码输入表面与队列。1080p 单路占用不大，4K 会成倍增长；多路并发时先看 nvidia-smi 的显存，再谈路数。显存不足时会出现“编码器初始化失败”而不是优雅降级。

🔍低延迟场景：-tune ll 或 -tune ull 会减少前瞻与 B 帧，让编码更“来一帧出一帧”。代价是同码率画质下降、码率波动更大。直播连麦优先低延迟，归档转码优先画质，别用同一套参数打天下。

⚡ QSV：核显里的快速通道

QSV（Intel Quick Sync Video）是 Intel 核显的媒体引擎，像办公楼里的专用货梯：不参与通用计算，只负责把货快速上下楼。它功耗低、发热小，特别适合 NUC、笔记本、边缘盒子做多路轻量转码。现代接入层通常通过 oneVPL 统一调度，底层可以是 VAAPI，也可以是 Windows 的 D3D11。

# 解码 → 缩放 → 编码，全部在 QSV 表面
ffmpeg -hwaccel qsv -hwaccel_output_format qsv -i in.mp4 \
  -vf 'scale_qsv=format=nv12' \
  -c:v h264_qsv -preset veryfast -global_quality 23 \
  -look_ahead 1 -async_depth 4 out.mp4

# 查看 QSV 编码器可用选项
ffmpeg -h encoder=h264_qsv
参数作用注意
-hwaccel qsv用 QSV 解码需要驱动与 oneVPL 运行时；容器内要映射 /dev/dri
-hwaccel_output_format qsv解码结果留在 QSV 表面后续滤镜必须用 *_qsv 版本
scale_qsv / vpp_qsv缩放、去隔行、色彩转换不同平台支持的处理项不同，先查文档
-global_quality质量优先的码控旋钮与 -b:v 的优先级随模式变化，别同时乱写
-look_ahead前瞻，提升码率分配low_power 模式下可能不可用
-async_depth并行深度，提高吞吐越大越吃显存/内存，低延迟场景要收敛
⚠️low_power 模式的取舍：它省电、启动快，但可能不支持前瞻、B 帧或部分码控模式。需要画质时关掉它；需要低功耗边缘部署时再打开。具体能力以 Intel 的 oneVPL/Media SDK 文档与实测为准。

🍎 VideoToolbox：苹果的统一内存优势

在 Apple Silicon 上，CPU 与 GPU 共享同一块统一内存，VideoToolbox 的输出是 CVPixelBuffer（底层是 IOSurface），编码器可以直接消费，不需要像独显那样跨 PCIe 搬一次。这就是 Mac 上“剪 4K 很顺”的底层原因之一。

# 硬件解码 + HEVC 硬件编码
ffmpeg -hwaccel videotoolbox -i in.mp4 \
  -c:v hevc_videotoolbox -b:v 4M -g 50 -realtime 1 out.mp4

# 确认编码器是否真的走了硬件
ffmpeg -h encoder=hevc_videotoolbox

VideoToolbox 的码控选项相对少，很多场景以目标码率为主；-allow_sw 1 允许在硬件不支持时回退软件，调试性能时可以先关掉它，避免“看起来成功、其实全在 CPU”。-realtime 1 适合直播/录屏，会减少前瞻换取更低延迟。

优势

统一内存让“解码→处理→编码”的拷贝成本很低；功耗极佳，笔记本续航友好；HEVC 硬件编码在 Apple Silicon 上成熟。配合 IOSurface，自家应用可以做到真正的零拷贝。

限制

参数空间小，想做精细的 psychovisual 调优不如 x265；部分旧机型只支持 H.264；跨平台部署时，VideoToolbox 只覆盖苹果生态，服务端仍要准备别的后端。

🪟 D3D11VA / Media Foundation / AMF：Windows 的三条路

Windows 上的硬件视频有三套常见入口：D3D11VA 负责解码，把画面放进 D3D11 纹理数组；Media Foundation 用 MFT（Media Foundation Transform）封装解码与编码，具体走硬件还是软件由系统选择；AMF 是 AMD 自己的编码框架，主要在 Windows 上使用。

# D3D11VA 硬解（输出留在 D3D11 纹理中）
ffmpeg -hwaccel d3d11va -hwaccel_output_format d3d11 -i in.mp4 \
  -c:v h264_mf -b:v 4M out.mp4

# Media Foundation 编码（是否硬件由系统 MFT 决定）
ffmpeg -i in.mp4 -c:v h264_mf -b:v 4M out.mp4

# AMD AMF 编码
ffmpeg -i in.mp4 -c:v h264_amf -quality quality -rc cbr -b:v 4M \
  -usage transcoding out.mp4
组件职责零拷贝条件常见坑
D3D11VADXVA2 的现代替代，硬解 H.264/HEVC/AV1（视硬件）输出 AV_PIX_FMT_D3D11，后续用 D3D11 滤镜纹理数组的切片索引、hwdownload 的格式转换
Media Foundation系统媒体管线，MFT 可硬可软MFT 接受 DXGI 表面时可零拷贝“成功”可能是软件 MFT；参数随厂商实现变化
AMFAMD 编码（H.264/HEVC/AV1，视代际）D3D11 互操作Linux 上通常不用 AMF，改走 VAAPI；quality 预设映射因版本而异

Windows 的硬件路径碎片化最严重：同一份命令在不同显卡、不同驱动、不同 FFmpeg 构建上可能落到不同 MFT。排查时先看 ffmpeg -v verbose 里实际选择的 decoder/encoder，再用任务管理器的 GPU 引擎（Video Decode / Video Encode）确认硬件真的在动。

🔍Media Foundation 的“坑王”属性：它可能悄悄选择软件 MFT，也可能因为分辨率/格式不支持而回退。不要用“命令没报错”当作“硬件已启用”，一定要看日志与 GPU 计数器。

🧩 Rockchip MPP：嵌入式板的 VPU 工具箱

瑞芯微的 RK3588、RK3568 这类 SoC 把视频编解码放进 VPU，通过 MPP（Media Process Platform）暴露给应用。它像一块“板载的专业转码卡”：功耗几瓦，能同时处理多路 1080p，非常适合摄像头、边缘盒子、车载与国产化设备。代价是工具链不如 x86 成熟，很多细节要看 Rockchip SDK 文档。

MPP 的典型特征是大量使用 DMABuf 与 DMA heap：采集（V4L2）、解码、缩放、编码之间传递的是文件描述符，而不是内存指针。这样 CPU 完全不碰像素，VPU 与 ISP/GPU 之间直接交接。要零拷贝，就必须让整条 GStreamer/FFmpeg 链路都协商到 memory:DMABuf。

# GStreamer：采集 → 硬件编码 → RTP 发送（元素名以 gst-rockchip 为准）
gst-launch-1.0 v4l2src device=/dev/video0 io-mode=dmabuf ! \
  video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1 ! \
  mpph264enc ! h264parse ! rtph264pay config-interval=1 ! \
  udpsink host=192.168.1.10 port=5004

# FFmpeg 的 rkmpp 支持通常来自 Rockchip 维护的分支/补丁
ffmpeg -c:v h264_rkmpp -i in.mp4 -c:v h264_rkmpp -b:v 4M out.mp4

常见约束

NV12 的宽高常有对齐要求（例如 16 像素），分辨率不对齐会报 “invalid frame size”；DMABuf 需要正确的 plane 布局与 stride；容器/权限要能访问 /dev/mpp_service 与 /dev/dma_heap。具体对齐规则以 SoC 与 MPP 版本文档为准。

怎么验证

用 MPP 自带的 mpi_dec_test/mpi_enc_test 先跑通硬件，再接入 GStreamer 或 FFmpeg；用 gst-inspect-1.0 mpph264enc 看元素是否存在；用 GST_DEBUG=3 看协商失败在哪一步。

⚠️不要把 x86 的参数直接搬过来：Rockchip 的编码器对 GOP、码控、B 帧的支持与 NVENC/QSV 不同；有些 preset 根本不存在。先在板子上用最小流水线跑通，再逐步加缩放、叠加、多路，别一上来就套用“通用优化参数”。

🚚 零拷贝：别让货离开传送带

传统链路像这样：解码器把画面写进显存 → 为了做缩放/加字幕，搬回系统内存 → CPU 处理 → 再搬回显存给编码器。货每上下一次传送带，就要过一次 PCIe。零拷贝的思路是：让货一直留在传送带上，解码、缩放、编码都在显存里完成，CPU 只传“货架号”（表面句柄），不搬货。

memory:DMABuf 是什么

DMABuf 是 Linux 内核里的“缓冲区共享机制”：驱动 A 分配一块内存，把文件描述符（fd）交给驱动 B，B 直接映射使用，不需要复制。GStreamer 用 caps video/x-raw(memory:DMABuf) 表达“这帧是 DMABuf”；V4L2 用 io-mode=dmabuf 让摄像头直接把帧写进共享缓冲；MPP/VAAPI 再把同一个 fd 交给编码器。整个过程中，CPU 只参与协商，不参与搬运。

操作实际发生了什么代价怎么避免
hwdownload把设备表面拷贝到系统内存（通常一次 PCIe DMA 或映射）1080p 单帧约 3 MB，30 fps 就是 ~90 MB/s；4K 翻四倍不要在中途插入只认 CPU 内存的滤镜
hwupload把系统内存里的帧上传成设备表面与下载对称，且可能多一次格式转换让解码输出直接是设备格式，或全程用设备滤镜
format=nv12若上游是硬件表面，FFmpeg 往往先下载再转格式隐式下载，日志里才看得见改用 scale_cuda=format=nv12 / scale_vaapi
drawtext / subtitlesCPU 滤镜，必须拿到可读像素强制下载 + 上传，链路断裂用 GPU 叠加，或把字幕烧录放到编码前单独处理
多路缩放每路都要表面与队列显存上涨，可能触发同步等待限制并发、复用表面池、降低队列深度

“零拷贝”不等于“零开销”

即使不拷贝，仍有格式协商、表面分配、fence 同步、队列调度。多路 4K 时，显存带宽与编码单元数量才是瓶颈。零拷贝解决的是“无谓的来回搬”，不是“所有成本归零”。

什么时候必须下载

做人脸识别、OpenCV 处理、CPU 字幕、复杂叠加，或编码器不支持当前设备格式时，下载无法避免。此时要接受一次拷贝，并尽量把它放在链路末端，避免“下载→处理→上传→再下载”。

💡算一笔账：1080p YUV420 单帧约 3.1 MB。30 fps 下，一次下载加一次上传就是约 186 MB/s 的额外内存/PCIe 流量；4K 30 fps 则约 746 MB/s。多路并发时，这就是为什么“明明 GPU 利用率不高，却只能跑几路”的真正原因。

🛠️ FFmpeg 硬件命令：先选设备，再选编码器

FFmpeg 的硬件用法有一条固定套路：用 -hwaccel 指定解码后端，用 -hwaccel_output_format 决定帧留在哪里，用 -vf 里的设备滤镜做缩放，最后用对应的硬件编码器。任何一步不匹配，FFmpeg 就会自动插入下载/上传，性能瞬间回到解放前。

ffmpeg -hwaccels
ffmpeg -h encoder=h264_nvenc

# 指定设备（多卡时尤其重要）
ffmpeg -init_hw_device vaapi=va:/dev/dri/renderD128 \
  -filter_hw_device va -i in.mp4 -vf 'scale_vaapi=format=nv12' \
  -c:v h264_vaapi out.mp4

# 解码器需要更多参考帧时，显式给表面池加余量
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
  -extra_hw_frames 8 -i in.mp4 -c:v h264_nvenc out.mp4

别用 -c:v copy 来验证硬件

-c copy 只搬码流，根本不经过解码器与编码器，自然看不到硬件。验证硬件必须真的解码再编码，并看日志里的 Using hardware accelerator 与编码器初始化信息。

先跑单路，再压多路

单路成功不代表多路能行：session 限制、显存、表面池、队列深度、PCIe 带宽都可能在第二路暴露。用 -stream_loop -1 或真实并发压测，逐路加，记录 CPU/GPU/显存/帧率。

⚠️性能验证的黄金标准：同一条命令、同一份输入，对比“硬件全链路”与“软件全链路”的 CPU 占用、GPU 利用率、单路延迟、可并发路数。只看“命令跑通了”远远不够——很多所谓硬件加速，实际是硬件解码 + 软件编码。

🎛️ GStreamer 硬件命令：用 caps 谈好“帧住哪儿”

GStreamer 的硬件链路靠 caps 协商：上游说“我能给 video/x-raw(memory:DMABuf),format=NV12”，下游说“我只要这个”，双方握手成功才零拷贝；只要有一方要普通 video/x-raw，GStreamer 就会插入下载/转换元素。因此排错时先看协商，不要先怀疑驱动。

📊 显存、并发与画质：没有全能的硬件

下表是经验性对比，不是跑分承诺。同一后端在不同代际、不同驱动、不同码控参数下差异很大；上线前必须用自己的素材、自己的码率、自己的并发数实测。

后端显存 / 内存占用并发路数画质与码控适合
NVENC独显显存：表面 + 参考帧 + 队列，4K 明显高于 1080p受编码单元、显存与 session 限制；专业卡通常更宽Turing 之后画质明显提升；低码率仍可能不如 x264 slow；p1–p7 可调多路转码、直播、GPU 服务器
NVDEC只占解码表面；并发看显存与解码单元解码路数通常高于编码不涉及画质，只负责还原硬解、解码后交给其他单元
QSV核显共享系统内存（部分平台有专用显存）受媒体引擎与内存带宽限制，适合中低路数日常画质够用；极低码率弱于软件慢速 preset；low_power 功能受限边缘盒子、NUC、低功耗多路
VAAPI取决于 Intel/AMD 设备，共享或独立显存受 GPU 媒体引擎与驱动影响驱动差异大；Intel 与 AMD 的画质/码控不完全相同Linux 通用部署、国产化平台
VideoToolboxApple Silicon 统一内存，拷贝成本低受媒体引擎数量限制；桌面机型更强HEVC 画质好，但可调参数少；以码率控制为主macOS/iOS 客户端、剪辑、录屏
D3D11VA / MFWindows 显存；MFT 可能额外缓冲受 GPU 与 MFT 实现影响取决于实际选中的 MFT；可能是硬件也可能是软件Windows 服务、桌面应用
AMFAMD 显存；互操作可能多一次转换受编码单元与驱动限制代际差异明显；quality/usage 预设影响大Windows + AMD 显卡
Rockchip MPP共享 DDR；DMABuf 省内存，但表面池要规划嵌入式 VPU 路数有限，4K 更紧工具链与参数空间较小；高码率下够用摄像头、边缘盒子、车载

还有一个常被忽略的维度：解码能力不等于编码能力。一张卡可能能解 8K AV1，却只能编 4K H.264；也可能解码路数很多，但编码 session 被驱动限制。做容量规划时，解码、缩放、编码要分别算。

上面这个量化演示能帮你建立“QP 与画质/码率”的直觉。硬件编码器同样有这个旋钮，只是名字不同：NVENC 是 -cq，VAAPI/QSV 常见 -global_quality，AMF 是 -qp_i/-qp_p 或质量预设。名字不同，本质都是“让编码器在码率与失真之间选一个点”。

🔍画质对比的正确做法：固定码率、固定 GOP、固定分辨率，用同一段含运动/暗场/细节的素材，比较 VMAF/SSIM 与主观观感。只对比“文件大小”或“看起来还行”，很容易被码控模式误导。

🕳️ 常见参数陷阱：硬件加速的“静默失败”

硬件加速最浪费时间的，不是报错，而是不报错：它悄悄回退软件、悄悄下载再上传、悄悄忽略了你的质量参数。下面这些坑，几乎每个部署都会踩一遍。

NVENC：preset 与码控

-preset p1 最快、p7 最慢最好；旧名字可能被接受但映射不一定符合预期。-cq 只有配合 -rc vbr（并通常配 -b:v 0）才是恒定质量；只写 -cq 很可能被忽略。-tune ll 降延迟但降画质。

VAAPI：格式协商

解码输出已是 VAAPI 表面时，再写 format=nv12 会强制下载；应写 scale_vaapi=format=nv12。10-bit 要 p010。软件输入才用 format=nv12,hwupload，并且要先 -vaapi_device。

QSV：low_power 的隐形限制

-low_power 1 省电，但可能关闭 lookahead、B 帧或部分码控；需要画质时不要开。`-async_depth` 增大吞吐也增大延迟与内存，低延迟场景要调小。

VideoToolbox：别被 allow_sw 骗了

-allow_sw 1 允许硬件不支持时回退软件，表面上永远成功。做性能验证时先设为 0，确认硬件路径；正式部署再按需打开容错。

通用：B 帧与延迟

不是所有硬件/格式都支持 B 帧；支持也不代表适合低延迟。B 帧需要缓存未来帧，直播连麦常直接 -bf 0。GOP 过长会让首帧等待变长，切片/秒开场景要把 -g 调到与关键帧间隔一致。

通用：隐式下载

只要滤镜图里出现 hwdownload、format 转普通 yuv420p，或编码器输入不是设备格式，零拷贝就断了。用 -v verbose 看自动插入的 scale/format 滤镜，别假设“没写就没有”。

症状根因验证 / 修复
CPU 仍然很高，GPU 几乎不动硬件未启用或静默回退软件看 ffmpeg -v verbose 的 encoder 初始化；确认设备权限与驱动
GPU 解码忙、编码不忙只硬解，编码仍是 x264/x265检查输出编码器名；看 CPU 是否有单核跑满
4K 多路时帧率骤降PCIe/内存带宽、显存或表面池不足减少 hwdownload；限制并发；看显存与 DMA 带宽
编码器初始化失败分辨率/格式/10-bit 不支持，或 session 达上限查厂商支持矩阵；降到 8-bit/NV12；减少并发
画面偏色/发绿色彩范围（limited/full）或格式转换错误检查 color_range、colorspace；避免多余的 RGB 往返
码率怎么调都不变码控模式没生效（如 CQ 未配 VBR）用 ffmpeg -h encoder=... 确认参数；看实际输出码率
⚠️部署前的三问：① 我的帧到底在哪儿（系统内存还是设备表面）？② 编码器真正吃的是什么格式？③ 这条命令在目标机器上是硬件还是软件？三问答不出来，就先别谈“优化”。

指标正常表现异常含义
CPU 占用硬件全链路时明显低于软件编码仍很高：可能在软件编码，或在做下载/上传/色彩转换
GPU enc/dec 引擎随路数与帧率上升解码动、编码不动：编码仍是软件；两者都不动：根本没启用
显存随分辨率、路数、队列增长接近上限会导致初始化失败或帧率骤降
单路延迟与 GOP、B 帧、队列深度相关异常升高：队列堆积、下载/上传、TCP 重传
输出码率接近目标码率，随内容波动远高于目标：码控未生效；远低于：质量参数过于激进
💡压测方法：固定输入、逐路增加，记录“第 N 路开始掉帧/报错”的拐点，并同时采集 CPU、GPU enc/dec、显存、PCIe 与网络。拐点通常比平均值更能说明瓶颈在哪里。
