🏭 先建立直觉：一条会自己协商的工厂流水线

想象一家工厂：原料从这头进，成品从那头出，中间是一排工位。每个工位只做一件事——切割、打磨、喷漆、包装。工位之间有传送带，传送带上跑着零件。工厂还有一个总节拍器，保证所有工位按同一个节奏工作；以及一个意见箱，任何工位出问题都会往里投纸条，厂长（你的程序）负责处理。

GStreamer 就是这个工厂的运行系统。它不生产具体的“切割机”或“喷漆机”，而是规定：工位怎么插传送带、传送带上的零件规格如何约定、节拍如何统一、出错如何上报。具体的编解码能力由插件提供——x264、libav、VA-API、NVIDIA 的编码器都是可插拔的工位模块。

source原料 / 摄像头
→
filter转换 / 缩放
→
encoder压缩
→
mux / pay封装 / 打包
→
sink显示 / 落盘 / 发送

它是运行时，不是编解码库

GStreamer 核心只负责元件生命周期、调度、时钟、事件和总线。H.264 解码靠 avdec_h264，编码靠 x264enc / vah264enc，协议靠 rtspsrc / webrtcbin。装了什么插件，就有什么能力。

它擅长“变”

运行时增删元件、动态 pad 出现、分辨率/码率切换、热插拔摄像头、seek、变速——这些在 FFmpeg 里要写不少代码，在 GStreamer 里是框架自带的能力。

它天生关心“时间”

每个 buffer 带 PTS/DTS；pipeline 有统一时钟；live source 有延迟补偿；sink 按节拍渲染。做低延迟直播、会议、监控时，这些机制决定了唇音同步与卡顿。

💬一句话记住：FFmpeg 像一台功能齐全的“瑞士军刀”，你调用它完成一次任务；GStreamer 像一套“乐高 + 流水线控制系统”，你搭出结构，它在运行时自己协商、调度、同步。两者不是替代关系，很多项目里它们同时存在。

🧩 七件套：把工厂的比喻落到 API 上

GStreamer 的概念不多，但每个都很“硬”。先记住下面的对照表，再看后面的细节，会轻松很多。

工厂里的东西GStreamer 概念它到底是什么你会在哪里遇到
整条生产线Pipeline / Bin装载元件的容器。Pipeline 是最外层 Bin，额外提供时钟与总线。gst_pipeline_new()、gst_parse_launch()
一个工位Element最小功能单元：源、转换、编码、封装、接收。插件注册后才有具体实现。videotestsrc、x264enc、filesink
工位的进出接口Pad数据出入口，有方向（src/sink）和存在方式（always/sometimes/request）。gst_element_get_static_pad()、pad-added 信号
接口规格书Caps用 MIME + 字段描述数据格式，如 video/x-raw,format=I420,width=1280。capsfilter、协商失败时的 not-negotiated
传送带上的零件Buffer / Sample一段数据 + 时间戳 + 内存。Sample 再包一层 caps 与 segment。GstBuffer、GstSample、appsink
工单 / 广播Event / Query控制面消息：CAPS、SEGMENT、EOS、SEEK、QOS；查询：位置、时长、延迟、可分配内存。gst_event_new_eos()、gst_element_query_duration()
节拍器 + 意见箱Clock / BusClock 统一时间；Bus 把元件产生的消息送给应用主循环。gst_pipeline_get_clock()、gst_bus_timed_pop_filtered()

数据面 vs 控制面

数据面：Buffer 一路向下游流，承载像素、采样、码流。它追求吞吐，通常零拷贝、批量、在多个线程间传递。

控制面：Event/Query 描述“这批数据是什么格式、从哪段时间开始、何时结束”。它追求正确性，必须与数据严格配对。很多播放问题不是数据坏了，而是控制面错了（例如 segment 没更新、caps 没送达）。

Element 的三种角色

Source：只有 src pad，例如 videotestsrc、v4l2src、rtspsrc、filesrc。

Filter：有 sink 也有 src，例如 videoconvert、h264parse、x264enc。它可能 1 进 1 出，也可能 1 进多出（tee）或多进 1 出（videomixer）。

Sink：只有 sink pad，例如 autovideosink、filesink、rtspclientsink、appsink。数据在这里被消费。

Pad 的三种“存在方式”

Always pad

元件创建时就存在，数量固定。例如 videoconvert 的 sink/src、filesink 的 sink。链接最简单。

Sometimes pad

运行时才出现，数量不固定。例如 rtspsrc（几路音视频）、qtdemux（几条轨道）、decodebin（解出什么码流）。写代码必须监听 pad-added，不能假设它一开始就在。

Request pad

由你主动申请。例如 tee 的分支、videomixer 的输入、webrtcbin 的 sink_%u。用完要 gst_element_release_request_pad()。

🔌Ghost pad 是什么？Bin（容器）可以把内部某个元件的 pad 暴露到外面，像“延长线”一样。这样外面看到的还是一个普通元件。例如 playbin 内部很复杂，但对外只暴露 audio/video sink pad，靠的就是 ghost pad。

🚦 状态机：为什么“设成播放”不是立刻播放

GStreamer 的元件有四个状态，顺序固定：NULL → READY → PAUSED → PLAYING。这不是形式主义，每个状态都解决一个具体问题。

NULL未初始化：没有分配任何资源
↓
READY设备已打开、内存已分配，但还没处理数据；可以探测能力
↓
PAUSED预滚（preroll）：协商 caps、填好第一帧、准备好时钟，但不推进时间
↓
PLAYING时钟开始走，sink 按时间戳消费数据

PAUSED 是最容易被忽视、却最有用的一档。它让整条链“预热”：解码器解出第一帧，sink 拿到这帧但不显示；此时你可以截图、查询时长、做 seek，也可以确认协商是否成功。很多“点了播放却黑屏”的问题，其实卡在 PAUSED 的 preroll 没完成。

异步状态切换

gst_element_set_state() 的返回值可能是 GST_STATE_CHANGE_ASYNC：元件表示“我在切，但还没切完”。正确做法是继续等：

// 设置状态后，等待它真正完成（或超时）
GstStateChangeReturn ret =
    gst_element_set_state(pipeline, GST_STATE_PLAYING);
if (ret == GST_STATE_CHANGE_ASYNC) {
  ret = gst_element_get_state(pipeline, NULL, NULL, 10 * GST_SECOND);
}
if (ret == GST_STATE_CHANGE_FAILURE) {
  // 去 bus 上取错误详情，不要只看返回值
}
⚠️常见坑：set_state(PLAYING) 返回 ASYNC 就以为已经在播，于是立刻去取帧/截图，结果拿到空数据。等 STATE_CHANGED 消息，或用 get_state 阻塞等待，才是可靠的做法。

状态切换时，元件内部发生了什么

切换典型动作目的
NULL → READY打开设备/文件，分配缓冲池，重置内部状态把“资源”准备好，但还不碰数据
READY → PAUSED协商 caps、激活 pad、预滚第一帧、配置时钟让数据链路真正通起来，但时间停住
PAUSED → PLAYING设置 base_time，时钟开始走，sink 开始按点渲染从“准备好”进入“按节拍运行”
PLAYING → PAUSED停时钟、保留最后一帧、保留状态暂停/seek/切轨，不销毁资源
任意 → NULL释放设备、内存、线程，断开 pad彻底清理，可重新配置

🔧 搭一条流水线 可点击 · 可切换硬件后端

下面把常见场景做成了可交互模型。点击任意元件查看它“在工厂里干什么”；点“走一遍数据”观察 buffer 的流动；切换编码后端，同一条链会从 CPU 编码变成 GPU 编码。命令可以直接复制到终端。

🧭读链的顺序：从左到右是数据方向；每个元件的 sink pad 在左、src pad 在右。方框下方的青色文字是“这个环节之后，数据大致长什么样”——它是协商结果，不是命令里必须写死的值。

⌨️ gst-launch-1.0：一条命令就是一张图

gst-launch-1.0 是 GStreamer 的“命令行编译器”：你用 ! 把元件串起来，它解析成 pipeline 并运行。语法看着古怪，其实规则很少：

写法含义例子
!把左边元件的 src pad 接到右边元件的 sink padvideotestsrc ! videoconvert ! autovideosink
key=value设置元件属性；值里有空格时用引号filesink location=out.mp4
caps直接写 MIME 串，等价于插入一个 capsfilter，强制格式... ! video/x-raw,format=I420 ! ...
name=x给元件命名，便于后面引用或代码里查找videotestsrc name=src
tee name=t t.t. 表示“给我一个新的输出 pad”，用于一分多路tee name=t t. ! queue ! sink1 t. ! queue ! sink2
-v / -e-v 打印 caps 与状态；-e 退出时发 EOS，保证文件索引写完gst-launch-1.0 -e ...

四个最常用的配方

# 1. 最小可用：彩条 → 窗口（先验证安装与显示后端）
gst-launch-1.0 videotestsrc ! videoconvert ! autovideosink

# 2. 播放本地文件：playbin 会自动解封装、解码、选 sink
gst-launch-1.0 playbin uri=file:///path/to/movie.mp4

# 3. Linux 摄像头实时预览
gst-launch-1.0 v4l2src device=/dev/video0 ! videoconvert ! autovideosink

# 4. 播放 RTSP（延迟 200 ms；越小越实时，也越怕抖动）
gst-launch-1.0 rtspsrc location=rtsp://192.168.1.64/Streaming/Channels/101 latency=200 \
  ! rtph264depay ! h264parse ! avdec_h264 ! videoconvert ! autovideosink

playbin 是一个“全家桶”元件：内部自动完成解封装、解码、同步和 sink 选择。学习单条链路时别用它，排障时也别用它——它藏了太多细节。

# 5. 只换封装，不重编码（最快，CPU 几乎不干活）
gst-launch-1.0 -e filesrc location=in.mp4 ! qtdemux ! h264parse \
  ! mp4mux ! filesink location=out.mp4

# 6. 重编码并切片 HLS（需要 gst-plugins-rs 的 hlssink3）
gst-launch-1.0 -e filesrc location=in.mp4 ! qtdemux ! h264parse \
  ! avdec_h264 ! videoconvert ! x264enc speed-preset=veryfast bitrate=3000 key-int-max=48 \
  ! h264parse ! hlssink3 location=seg%05d.ts playlist-location=index.m3u8 target-duration=4

# 7. 抽音频成 AAC（ADTS）
gst-launch-1.0 -e filesrc location=in.mp4 ! qtdemux ! aacparse \
  ! avmux_adts ! filesink location=audio.aac

能不解码就不解码：“换封装”只需要 demux + parse + mux；一旦加上 avdec_h264 ! x264enc，就从“搬运工”变成“重新生产”，CPU 与画质都会付出代价。

# 8. 推 RTSP 到 MediaMTX（需要 gst-rtsp-server 的 rtspclientsink）
gst-launch-1.0 v4l2src device=/dev/video0 ! videoconvert \
  ! x264enc speed-preset=ultrafast tune=zerolatency bitrate=2500 key-int-max=30 \
  ! h264parse config-interval=-1 \
  ! rtspclientsink location=rtsp://127.0.0.1:8554/cam

# 9. 推 RTP/UDP（自己管接收端；适合局域网实验）
gst-launch-1.0 videotestsrc is-live=true ! videoconvert ! x264enc tune=zerolatency \
  ! rtph264pay config-interval=1 pt=96 ! udpsink host=127.0.0.1 port=5000

# 10. 收 RTP 并显示
gst-launch-1.0 udpsrc port=5000 caps="application/x-rtp,media=video,encoding-name=H264,payload=96" \
  ! rtph264depay ! h264parse ! avdec_h264 ! videoconvert ! autovideosink

推流方向与播放方向是镜像的：pay ↔ depay，src ↔ sink。把这两条命令对照着看，比背文档有效。

# 看装了什么、某元件支持什么属性
gst-inspect-1.0 | head -n 30
gst-inspect-1.0 x264enc
gst-inspect-1.0 vah264enc

# 看一个文件/URL 的真实流信息（类似 ffprobe）
gst-discoverer-1.0 -v input.mp4

# 打开 3 级日志（error/warning/fixme），输出到文件
GST_DEBUG=3 gst-launch-1.0 videotestsrc ! autovideosink 2>gst.log

# 把 pipeline 图导出为 dot，再用 Graphviz 转图片
GST_DEBUG_DUMP_DOT_DIR=/tmp/gst gst-launch-1.0 videotestsrc ! autovideosink
dot -Tsvg /tmp/gst/*.dot > pipeline.svg

排错时优先用“最小链 + fakesink”确认数据能流，再逐段加回真实元件。一次只改一个变量，才能定位到具体环节。

queue、tee 与线程：为什么“加个 queue 就好了”

GStreamer 默认让相邻元件在同一个线程里“推”数据。上游推得快、下游吃得慢，整条链就会被拖住。更糟的是：一个分支卡住，tee 的另一路也拿不到数据。

# 一路采集，同时预览 + 编码落盘：每个分支都要有 queue
gst-launch-1.0 v4l2src ! tee name=t \
  t. ! queue ! videoconvert ! autovideosink \
  t. ! queue ! videoconvert ! x264enc ! h264parse ! mp4mux ! filesink location=cam.mp4

queue 的本质是“线程边界 + 缓冲”。它让上下游解耦：上游按自己的节奏生产，下游按自己的节奏消费。代价是内存与延迟；max-size-buffers、max-size-bytes、max-size-time 决定缓冲上限，leaky 决定满了是丢旧数据还是阻塞。

⚠️直播场景慎用大 queue：缓冲越深，延迟越大，而且丢帧时更容易“追不上”。实时链路通常用小 queue + leaky=downstream（丢旧帧保新帧），并用 sync=false 的 fakesink 做吞吐测试。

🔌 Caps 协商：GStreamer 里最容易“卡住”的一步

把 caps 想成插头和插座的规格：电压、孔距、针脚数必须匹配。上游说“我给 RGB 1920×1080 30fps”，下游说“我只吃 I420 1280×720”，中间又没有转换器，链接就会失败。GStreamer 不会魔法般帮你转——它只会报 not-negotiated。

一条 caps 长什么样

# 原始视频（未压缩）：格式、宽高、帧率、像素宽高比
video/x-raw, format=I420, width=1920, height=1080, framerate=30/1, pixel-aspect-ratio=1/1

# 压缩码流：编码类型 + 档次 + 码流组织方式
video/x-h264, profile=high, stream-format=avc, alignment=au

# RTP 包：媒体类型 + 编码名 + 负载类型
application/x-rtp, media=video, encoding-name=H264, payload=96, clock-rate=90000

# 带内存特性：告诉下游“这帧在 DMABuf 里，不在普通系统内存”
video/x-raw(memory:DMABuf), format=NV12, width=1920, height=1080

MIME 后面的字段不是随便写的：format 决定像素排列，width/height 决定图像尺寸，framerate 是分数（避免 29.97 被浮点数吃掉精度），stream-format 决定 H.264 是 AVCC 还是 Annex B。字段写错，后面整条链都会跟着错。

协商的四步

① 问：上游通过 query 问下游“你能接受哪些 caps”（gst_pad_peer_query_caps）。

② 交：把双方的能力求交集。交集为空，链接就失败。

③ 定：从交集里 fixate 出一个具体值（比如在 30/1 与 25/1 里选一个）。

④ 通知：发 CAPS 事件，下游据此配置解码器/缓冲池，然后才开始收数据。

为什么它总在“运行时”发生

因为 GStreamer 允许动态结构：rtspsrc 收到 DESCRIBE 后才知道是 H.264 还是 H.265；qtdemux 读到 moov 后才知道有几条轨道。caps 不是启动时一次性算完的，而是每次数据格式变化都重新协商。

这也是它比“写死格式”的 API 灵活的地方，但代价是：你必须理解协商，否则错误会以各种奇怪的面貌出现。

capsfilter：把“建议”变成“强制”

# 强制输出 1280×720、30fps 的 I420；不满足就协商失败
gst-launch-1.0 videotestsrc ! videoconvert \
  ! video/x-raw,format=I420,width=1280,height=720,framerate=30/1 \
  ! x264enc ! h264parse ! mp4mux ! filesink location=out.mp4

# 只约束格式，宽高交给协商（更灵活）
... ! video/x-raw,format=I420 ! ...

capsfilter 是一个“只做过滤、不改数据”的元件。它把上游的 caps 与给定约束求交，逼下游接受。常见用途：统一像素格式、限制分辨率、给编码器固定输入、给硬件链路声明 DMABuf。

🧯not-negotiated 的排查顺序：① 看日志里最后一条 CAPS 事件是什么；② 把可疑段换成 fakesink，确认上游能出数据；③ 在中间插入 videoconvert / videoscale / audioconvert / audioresample；④ 用 capsfilter 明确格式；⑤ 检查 stream-format（AVCC vs Annex B）与 memory:DMABuf 特性是否被下游支持。

常见 caps 速查

caps含义常见下游踩坑点

📦 Buffer 与 Event：数据面和控制面

Buffer 是“零件”，Event 是“工单”。零件决定画面内容，工单决定这段内容属于哪段时间、什么格式、何时结束。只盯着像素会漏掉一半问题。

GstBuffer 里到底有什么

PTS（显示时间戳）与 DTS（解码时间戳）：64 位纳秒，类型 GstClockTime。B 帧会让 DTS 早于 PTS。

duration：这一帧/这段音频持续多久；音频通常按采样数换算。

offset / offset_end：在流里的序号范围，便于 seek 与丢帧统计。

flags：DELTA_UNIT（非关键帧）、HEADER、DISCONT、GAP 等，告诉下游“这帧能不能独立解码”“时间是否跳变”。

memory：一个或多个 GstMemory 块，可能是系统内存、DMABuf、GL 纹理；meta 附加信息（裁剪、旋转、HDR、音频通道）。

GstSample = Buffer + Caps + Segment

appsink 交给你的是 GstSample，不是裸 Buffer。因为它必须同时告诉你：这帧的格式（caps）、它属于哪个时间段（segment）、以及数据本身（buffer）。

很多初学者只取 buffer 就丢掉 sample，结果不知道时间基与格式，后面同步/换算全错。正确姿势：gst_sample_get_buffer()、gst_sample_get_caps()、gst_sample_get_segment() 一起用。

控制面的两大家族

类型典型成员方向作用
EventSTREAM_START、CAPS、SEGMENT、TAG、EOS主要向下游宣告流开始、格式、时间范围、元数据、结束
EventSEEK、QOS、RECONFIGURE向上游请求跳转、反馈质量、要求重新协商

📌Sticky event（黏性事件）：STREAM_START、CAPS、SEGMENT、TAG、EOS 会“粘”在 pad 上。新加入的元件或新请求的 pad 会自动收到最近一次，不必从头播放。这是动态 pad 能工作的关键机制之一。

时间基与 segment：为什么 seek 后时间会“跳”

GStreamer 用 GstSegment 描述“当前这段数据对应媒体时间的哪一段”。它包含 start、stop、time、base、rate。播放位置不是简单地把 PTS 除以 1 秒，而是要经过 segment 换算。

running_time ≈ (PTS − segment.start) / rate + segment.base

对普通 1 倍速播放，rate=1、base=0，所以 running_time ≈ PTS − start。发生 seek 后，新的 segment 会把起点重置；变速播放则改变 rate。如果自定义元件无视 segment、直接拿 PTS 当“已经播放了多久”，seek 或变速后一定错乱。

⏱️ 时钟与延迟：谁决定“这一帧什么时候出现”

编码器只管把帧压小，不管它该在第几毫秒出现。真正决定“什么时候显示、什么时候发声”的，是 pipeline 的时钟。GStreamer 把这件事做成了一套明确的数学：每个 buffer 有 PTS，每个 pipeline 有一个 clock，sink 拿着两者算出“还要等多久”。

三个时间概念

概念含义谁负责典型用途
PTS / DTS媒体时间轴上的显示/解码时刻解封装器、解码器、parser音画同步、字幕对齐、seek
running_time从“这段流开始播放”算起的相对时间由 segment 换算sink 判断距离渲染还有多久
base_timerunning_time = 0 对应的系统时钟时刻Pipeline 在进入 PLAYING 时设置把媒体时间映射到真实世界时间
render_time = base_time + running_time   |   sink 等待 clock 到达 render_time

换成大白话：base_time 是“开机时刻”，running_time 是“这段视频播放了多少秒”，两者相加就是“这帧应该在墙上的哪个时刻出现”。sink 看到当前时钟还没到，就睡一会儿；到了就渲染。

Pipeline 怎么选时钟

默认用 GstSystemClock（单调时钟）。音频 sink 往往能提供更稳定的时钟（基于声卡采样计数），Pipeline 会在多个 clock provider 中选一个。你也可以强制指定：gst_pipeline_use_clock()。

为什么音频常当主时钟：声卡按固定采样率消费数据，抖动小；视频晚一点可以丢帧/重复帧，音频断流却会被听出来。

Live source 的特殊性

摄像头、麦克风、RTSP 是“实时源”：它们不受你控制地产生数据。Pipeline 会给它们加上最小延迟，保证不会“等一帧却等不到”。is-live=true 就是告诉框架“按实时处理”。

非实时源（文件）可以跑得比现实快；如果你希望它按实时速度播放，需要 sink 的 sync=true 或加 queue/identity sync=true。

Latency：框架预留的“安全垫”

Pipeline 启动时会发 LATENCY query，逐级向上游问“你需要多少延迟”。各环节把答案累加，sink 据此决定预滚多深。这个值不是“编码延迟”，而是为保证同步而预留的缓冲。

来源典型量级怎么调代价
rtspsrc 抖动缓冲100–1000 mslatency=200调小更实时，但丢包/抖动时容易卡
解码器内部帧1–4 帧选低延迟解码器/关闭多帧缓冲太低可能无法处理 B 帧重排
queue 缓冲0–数秒max-size-time、leaky越大越抗抖动，延迟越高
sink 显示/音频缓冲1–3 帧 / 10–100 mssync、ts-offset太小会撕裂/爆音
编码器 lookahead / B 帧0–数百 mstune=zerolatency、bframes=0压缩率下降
🧮算一笔端到端延迟：摄像头曝光 33 ms + 编码 30 ms + 网络 20 ms + rtspsrc 缓冲 200 ms + 解码 30 ms + 显示 33 ms ≈ 346 ms。这还没算 Glass-to-Glass 的采集与显示链路。想进 200 ms，必须同时压 rtspsrc 缓冲、编码 lookahead 和显示缓冲，而不是只改一个参数。

音画不同步：先分清是“偏移”还是“漂移”

固定偏移（从头到尾都差同样的时间）：通常是采集端时间戳错了，或某个环节擅自改了 PTS。用 identity 打印 PTS，逐段对比。

逐渐漂移（越播差得越多）：多半是两端用了不同时钟（比如视频按系统时钟、音频按声卡时钟），或某个 sink 设了 sync=false。让 Pipeline 统一时钟、让音频当主时钟，通常能解决。

💻 C API：从“能跑”到“能控”

命令行适合验证，产品里总要写代码。GStreamer 的 C API 不难，难在错误处理与生命周期：消息要取、sample 要解引用、pad 要释放、状态要等。下面三段代码覆盖 90% 的日常场景。

① 最小播放器：解析命令 + 等消息

#include <gst/gst.h>

int main(int argc, char *argv[]) {
  gst_init(&argc, &argv);

  GstElement *pipeline = gst_parse_launch(
      "videotestsrc ! videoconvert ! autovideosink", NULL);
  if (!pipeline) return 1;

  GstBus *bus = gst_element_get_bus(pipeline);
  gst_element_set_state(pipeline, GST_STATE_PLAYING);

  // 阻塞等 ERROR 或 EOS；真实程序通常用 GMainLoop + bus watch
  GstMessage *msg = gst_bus_timed_pop_filtered(bus, GST_CLOCK_TIME_NONE,
      GST_MESSAGE_ERROR | GST_MESSAGE_EOS);

  if (msg) {
    if (GST_MESSAGE_TYPE(msg) == GST_MESSAGE_ERROR) {
      GError *err = NULL; gchar *dbg = NULL;
      gst_message_parse_error(msg, &err, &dbg);
      g_printerr("ERROR: %s\nDEBUG: %s\n", err->message, dbg ? dbg : "");
      g_clear_error(&err); g_free(dbg);
    }
    gst_message_unref(msg);
  }

  gst_element_set_state(pipeline, GST_STATE_NULL);
  gst_object_unref(bus);
  gst_object_unref(pipeline);
  return 0;
}

编译：gcc demo.c -o demo $(pkg-config --cflags --libs gstreamer-1.0)。注意：gst_parse_launch 适合原型；生产代码里手动 gst_element_factory_make + gst_bin_add_many + gst_element_link 更可控，也能拿到每个元件的指针。

② appsink 抓帧：把流水线接进你的算法

#include <gst/gst.h>
#include <gst/app/gstappsink.h>

static GstFlowReturn on_sample(GstAppSink *sink, gpointer user_data) {
  GstSample *sample = gst_app_sink_pull_sample(sink);   // 取最新一帧
  if (!sample) return GST_FLOW_ERROR;

  GstBuffer *buf = gst_sample_get_buffer(sample);
  GstCaps   *caps = gst_sample_get_caps(sample);        // 格式
  GstSegment *seg = gst_sample_get_segment(sample);     // 时间段

  GstMapInfo map;
  if (gst_buffer_map(buf, &map, GST_MAP_READ)) {
    // map.data / map.size：例如 NV12 或 RGB 像素
    // GST_BUFFER_PTS(buf) 是纳秒；GST_BUFFER_DURATION(buf) 是持续时长
    gst_buffer_unmap(buf, &map);
  }

  gst_caps_unref(caps);       // get_* 返回的是引用，必须释放
  gst_segment_unref(seg);
  gst_sample_unref(sample);
  return GST_FLOW_OK;
}

// 建链时给 appsink 命名，并打开信号
GstElement *pipeline = gst_parse_launch(
    "videotestsrc ! videoconvert ! video/x-raw,format=RGB ! "
    "appsink name=sink emit-signals=true max-buffers=2 drop=true sync=false", NULL);
GstElement *sink = gst_bin_get_by_name(GST_BIN(pipeline), "sink");
g_signal_connect(sink, "new-sample", G_CALLBACK(on_sample), NULL);

编译时加 gstreamer-app-1.0。几个容易踩的细节：drop=true 防止算法慢时内存堆积；sync=false 让 appsink 不等时钟（适合“要最新帧”的分析）；max-buffers=2 限制队列深度。做 AI 推理时，这三项几乎必设。

③ 动态 pad：rtspsrc / decodebin 的正确接法

static void on_pad_added(GstElement *src, GstPad *pad, gpointer data) {
  GstElement *sink = GST_ELEMENT(data);
  GstCaps *caps = gst_pad_get_current_caps(pad);
  if (!caps) caps = gst_pad_query_caps(pad, NULL);

  const GstStructure *s = gst_caps_get_structure(caps, 0);
  const gchar *name = gst_structure_get_name(s);

  if (g_str_has_prefix(name, "video")) {          // 只接视频，忽略音频
    GstPad *sinkpad = gst_element_get_static_pad(sink, "sink");
    if (!gst_pad_is_linked(sinkpad)) {
      GstPadLinkReturn ret = gst_pad_link(pad, sinkpad);
      if (ret != GST_PAD_LINK_OK)
        g_printerr("link failed: %d\n", ret);
    }
    gst_object_unref(sinkpad);
  }
  gst_caps_unref(caps);
}

// rtspsrc 的 src pad 会在 DESCRIBE 之后才出现
GstElement *src = gst_element_factory_make("rtspsrc", NULL);
g_object_set(src, "location",
    "rtsp://192.168.1.64/Streaming/Channels/101", "latency", 200, NULL);
g_signal_connect(src, "pad-added", G_CALLBACK(on_pad_added), videoconvert);

关键点：pad-added 回调里拿到的 pad 可能还没有 current caps，所以用 query_caps 兜底；同一个元件可能多次触发，必须用 gst_pad_is_linked 防重复；pad-added 的 src 参数是“哪个元件产生了 pad”，不要拿它当目标。

🧠引用计数是 C API 的第一道坎：gst_bin_get_by_name、gst_element_get_static_pad、gst_sample_get_caps 都返回新引用，必须 gst_object_unref / gst_caps_unref / gst_sample_unref。漏掉不会立刻崩，但会慢慢泄漏，最终在长时间运行的监控/直播程序里爆掉。

⚡ 硬件与零拷贝：让帧别来回搬家

软件编码像“用 CPU 一针一线缝”，硬件编码像“用专用模具压”。但硬件不只快在算力，更快在数据不用来回搬：摄像头写进显存，编码器直接从显存读，显示也直接从显存取。任何一次“下载到 CPU”都会把优势吐回去。

零拷贝的三层含义

① 采集不拷

v4l2src io-mode=dmabuf 让驱动把帧写进 DMABuf，而不是先拷到普通内存。caps 会带 memory:DMABuf。

② 编解码不拷

硬件编码器直接消费 DMABuf；解码器直接输出 DMABuf。中间若插 videoconvert，就会隐式 map 到 CPU，零拷贝断掉。

③ 显示不拷

waylandsink / kmssink / glimagesink 能直接导入 DMABuf/EGLImage；若 sink 只吃系统内存，就会再下载一次。

三条真实链路

# A. 摄像头 → VAAPI 编码 → 落盘（尽量不碰 CPU）
gst-launch-1.0 -e v4l2src device=/dev/video0 io-mode=dmabuf \
  ! vah264enc bitrate=4000 key-int-max=30 \
  ! h264parse ! mp4mux ! filesink location=cam.mp4

# B. RTSP 硬解 → GL 显示（解码后留在显存）
gst-launch-1.0 rtspsrc location=rtsp://192.168.1.64/Streaming/Channels/101 latency=200 \
  ! rtph264depay ! h264parse ! vah264dec \
  ! glupload ! glcolorconvert ! glimagesink

# C. NVIDIA 硬编 + 推流
gst-launch-1.0 v4l2src ! videoconvert ! nvh264enc bitrate=4000 gop-size=30 \
  ! h264parse config-interval=-1 ! rtspclientsink location=rtsp://127.0.0.1:8554/cam
⚠️“硬件编码”不等于“零拷贝”：如果链里出现 videoconvert、videoscale、appsink（默认系统内存），帧就会被拉回 CPU。判断方法：看日志里的 caps 是否带 memory:DMABuf / memory:GLMemory，以及有没有 gst_video_frame_map 之类的下载动作。

软件 x264 的 speed-preset、tune=zerolatency 在硬件元件上通常不存在。硬件后端各有自己的“延迟/质量”旋钮：

🧯 调试与排错：从“黑屏”到“第 137 行日志”

GStreamer 的错误信息往往很抽象：not-negotiated、Internal data stream error、streaming stopped。它们不是“结论”，而是“线索的起点”。掌握三样工具，定位速度会快一个数量级：日志、dot 图、最小链。

① GST_DEBUG：按类别打开日志

# 0=无 1=ERROR 2=WARNING 3=FIXME 4=INFO 5=DEBUG 6=LOG 7=TRACE（数字越大越啰嗦）
GST_DEBUG=3 gst-launch-1.0 ... 2>gst.log

# 只看特定类别，避免日志淹没
GST_DEBUG=GST_STATES:6,GST_ELEMENT_PADS:6 gst-launch-1.0 ...

# 所有类别开到 INFO（信息量很大，先重定向到文件）
GST_DEBUG=*:4 gst-launch-1.0 ... 2>gst.log

# 日志写文件、去掉颜色，方便 grep
GST_DEBUG=4 GST_DEBUG_FILE=/tmp/gst.log GST_DEBUG_NO_COLOR=1 gst-launch-1.0 ...

一条日志通常长这样：0:00:02.123456789 1234 0x55d0 INFO GST_ELEMENT_PADS gstpad.c:1234:gst_pad_link: linking...。依次是：运行时间、进程号、线程/对象地址、级别、类别、源文件:行号:函数、消息。排错时优先按类别过滤，而不是从第一行读到最后一行。

② dot 图：看清“到底连成了什么”

# 设置目录后，状态变化会自动 dump .dot 文件（每个状态一份）
GST_DEBUG_DUMP_DOT_DIR=/tmp/gst gst-launch-1.0 rtspsrc location=... ! ... ! autovideosink

# 转成 SVG/PNG，直接看元件、pad、caps、链接
dot -Tsvg /tmp/gst/0.00.00.123456-gst-launch.PLAYING.dot > pipeline.svg

动态 pad 的场景尤其需要 dot：你以为 rtspsrc 只连了视频，图上却可能多出一条未连接的音频 pad；你以为 tee 两路都接了，图上可能有一路悬空。

③ 最小链与二分法

不要一上来就调整条 20 个元件的链。先跑 videotestsrc ! fakesink 确认框架正常；再换成真实源 + fakesink，确认能出数据；再加 parser/decoder，确认 caps 协商；最后加 sink。每次只改一个变量——这和调试任何系统都一样。

⚖️ GStreamer 与 FFmpeg：不是谁强，而是谁合适

两者都能解封装、解码、转码、推流，但设计哲学完全不同。用错工具，不是“性能差一点”，而是代码结构会越来越别扭。

什么时候优先选 GStreamer

需要长时间运行、动态接入多路源、要精确控制延迟与同步、要接硬件编解码并保持零拷贝、要做“采集 + 预览 + 编码 + 推流”多分支、要嵌入到设备里。

什么时候优先选 FFmpeg

一次性文件转码、批量抽帧/抽音轨、快速验证、生成 HLS/DASH、做 WebAssembly 端实验、只需要“输入 → 输出”而不需要运行时改结构。

🤝它们经常一起用：GStreamer 的 avdec_h264、avenc_h264、avmux_* 插件内部就是 libav；很多服务器（MediaMTX、SRS、ZLMediaKit）既能收 GStreamer 推的流，也能收 FFmpeg 推的流。选型看“边界”：谁负责采集/调度，谁负责一次转码。

🌍 生态与场景：GStreamer 到底被用在哪里

插件分层

base：核心元件（videoconvert、videotestsrc、playbin、appsink）。good：常用且许可宽松（rtspsrc、rtpjitterbuffer、videoparser）。bad：实验/不稳定（webrtcbin、qsv）。ugly：可能有专利/许可问题（x264）。libav：封装 FFmpeg 的编解码器。rs：Rust 重写的新插件（hlssink3、dashsink2 等）。

协议与服务器

gst-rtsp-server 提供 RTSP 服务端与 rtspclientsink；webrtcbin 做 WebRTC 端点；hlssink3/dashsink2 做分发；splitmuxsink 做录制分段。它们常与 MediaMTX/SRS 组合：GStreamer 负责采集与编码，服务器负责分发。

行业应用

NVIDIA DeepStream 以 GStreamer 为骨架做视频分析；机顶盒/电视用 playbin + 硬解；会议终端用 webrtcbin；NVR 用 rtspsrc + 多路 tee + 硬编；车载/机器人用 v4l2src + DMABuf 低延迟链路。

安装与验证（三条命令）

# Ubuntu / Debian：工具 + 常用插件（bad/ugly/libav 按需安装）
sudo apt install gstreamer1.0-tools gstreamer1.0-plugins-base \
  gstreamer1.0-plugins-good gstreamer1.0-plugins-bad \
  gstreamer1.0-plugins-ugly gstreamer1.0-libav

# macOS
brew install gstreamer

# 验证：版本 + 是否能跑最小链 + 查硬件元件
gst-launch-1.0 --version
gst-launch-1.0 videotestsrc ! videoconvert ! autovideosink
gst-inspect-1.0 | grep -E 'vah264|nvh264|qsvh264|vtenc|mpph264'

Windows 用官方 MSVC 安装包（或 Cerbero 自建）。装完后把 bin 目录加入 PATH；插件路径由 GST_PLUGIN_PATH 控制，自定义插件常踩这个坑。

🧩和本站其他页面的关系：RTSP/GB28181 的播放与推流最终会落到 rtspsrc / rtspclientsink；WebRTC 的低延迟分发会落到 webrtcbin；硬件细节与 FFmpeg 的 hwaccel 是同一批 GPU/ASIC，只是调用方式不同。把这条链和服务器选型放在一起看，才不会“只会写命令，不懂为什么”。

📖 术语表

术语通俗解释为什么重要
Pipeline整条生产线，装着所有元件提供时钟与 bus，是应用的根对象
Element一个工位，只做一件事所有能力都由插件注册成 element
Pad工位的进/出接口链接的方向与类型决定数据能否流动
Caps接口规格书（MIME + 字段）协商失败就是 not-negotiated
Buffer传送带上的零件（数据 + 时间戳）PTS/DTS 决定同步与 seek
SampleBuffer + Caps + Segment 的打包appsink 交给你的是它，不是裸 buffer
Event工单/广播：格式、时间段、结束控制面错了，数据面对了也没用
Query向上下游“问问题”时长、位置、延迟、可接受 caps 都靠它
Segment“当前这段流”的时间范围与速率seek/变速后 running_time 换算的依据
Clock / base_time总节拍器 / 开机时刻决定每一帧在真实世界的出现时刻
PrerollPAUSED 状态下先填好第一帧黑屏/首帧慢常卡在这里
Live source按现实时间产生数据的源摄像头/RTSP 必须按实时策略处理
Latency为保证同步预留的缓冲不等于编码延迟；是端到端延迟的一部分
Request pad主动申请的输出/输入口tee、mixer、webrtcbin 都靠它扩展
Ghost pad把内部 pad 暴露到容器外playbin 等复杂元件对外的统一接口
parse / demux / mux整理码流 / 拆容器 / 装容器“换封装”只走这三类，不解码
pay / depay打成 RTP 包 / 从 RTP 还原推流与播放方向的镜像
DMABuf设备间共享的内存缓冲零拷贝的物理基础
appsink / appsrc把流水线接进应用 / 把应用数据送进流水线AI 推理、自定义源、与业务代码的接口
GESGStreamer Editing Services，时间线式剪辑把“非线编”能力做成高层 API
