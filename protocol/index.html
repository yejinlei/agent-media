🚚 为什么协议不止一种：三种路况，三套规矩

把音视频传输想成寄东西：RTP 是带编号的快递面单，丢了哪一箱能立刻发现；RTSP 是你和仓库之间的点菜电话，只负责“我要哪一路、用什么包装”，不负责运货；RTMP 是把大件拆成标准托盘装车；HLS/DASH 是先把整场演出切成小段，再让观众按目录一段段取；SRT 是给快递加一个缓冲仓库，宁可晚一点也要齐；WebRTC 则是两个陌生人在没有中间商的情况下，先互相验身份、再拉一条加密专线。

它们要解决的矛盾其实只有三个：延迟、稳定、覆盖范围。局域网里可以任性，公网里必须妥协；浏览器只认 HTTP/WebRTC，摄像机只会 RTSP/GB28181；直播要扛并发，就得靠 CDN 和切片。理解了这个取舍，你看到任何新协议都不会慌。

控制面与媒体面分开

RTSP、RTMP 的命令、SIP 的 INVITE 都属于“控制面”；真正的画面走 RTP、TCP 或 HTTP。排错时先问：是命令没谈成，还是媒体没到达？这两类问题的证据完全不同。

封装不等于传输

FLV、TS、fMP4 是“箱子”，RTMP、HLS、DASH 是“运输方式”。同一个 FLV 可以走 RTMP，也可以走 HTTP-FLV；同一个 fMP4 可以进 HLS，也可以进 DASH。别把容器名当协议名。

延迟是设计出来的

HLS 的 10 秒延迟不是“技术差”，而是切片、CDN 缓存、播放器缓冲共同换来的可扩展性。WebRTC 的 1 秒延迟也不是白来的：它放弃了 CDN 友好性，要求端到端连通。

🔍一句话记住分工：RTP 负责“每一包是什么”，RTCP 负责“收得怎么样”，RTSP/RTMP 负责“开始与结束”，HLS/DASH 负责“怎么让很多人同时看”，SRT 负责“在不稳定的网络上稳住”，WebRTC 负责“在浏览器里低延迟地互通”。

看延迟先问“谁等谁”

HLS 的延迟是播放器等切片凑够；SRT 的延迟是缓冲等丢包补回；WebRTC 的延迟只等网络一圈往返。同样是 1 秒，成因完全不同，优化方向也不同。

看可靠性先问“谁来补”

TCP 由内核协议栈补，应用管不着；RTP/UDP 要靠 NACK 让发送端补；HLS 直接重新下载整段。补得越靠近应用层，策略越灵活，但实现越复杂。

看场景先问“观众是谁”

观众是浏览器：HLS/DASH/WebRTC/WHEP；观众是机房里的另一台服务器：RTSP/SRT/RIST；观众是 CDN：只能给 HTTP 切片。先把观众定下来，协议表自动缩到两三行。

📦 RTP：给每一帧发一张带编号的快递面单

RTP（Real-time Transport Protocol，RFC 3550）不保证送达，也不保证顺序——它只保证你能知道丢了什么、该怎么拼回去。就像快递面单：箱号（序号）让你发现少了一箱，寄出时间（时间戳）让收件人知道哪箱先拆，寄件人编号（SSRC）让你在一堆包裹里认出“这是我买的”。

为什么 90 kHz 而不是 90000 Hz 的“秒”

视频时间戳用 90 kHz 时钟，是因为它同时能被 24、25、30、50、60 fps 整除，帧间隔都是整数刻度：25 fps 一帧 3600 tick，30 fps 一帧 3000 tick。音频则直接用采样率（8 kHz、44.1 kHz、48 kHz），所以音视频同步不能直接比时间戳数字，必须按各自的时钟换算成秒，再用 RTCP 的 SR 做对齐。

H.264 的三种打包方式

RFC 6184 定义了单 NAL 模式、STAP-A（把多个小 NAL 聚成一包）和 FU-A（把一个大的 IDR 切片分装）。看到 FU-A 的起始包丢了，整个大帧都拼不起来——这就是“只丢一个包却花屏两秒”的原因。

抖动缓冲不是越大越好

接收端用 jitter buffer 把早到的包压住、等晚到的包。缓冲越大越抗抖动，但延迟越高。WebRTC 会动态估算；HLS 干脆不用 RTP，交给 HTTP 缓存。调优时先量网络抖动，再定缓冲，不要凭感觉加。

⚠️别把“有 RTP”当成“能出画面”：RTP 只证明包到了。还要确认 PT 与 SDP 匹配、SSRC 没被过滤、时间戳连续、并且收到了完整的关键帧。缺任何一条，播放器都可能停在黑屏。

☎️ RTCP：客服回访，不送画面只送反馈

如果 RTP 是快递，RTCP 就是客服回访电话：“这一批收到 98 箱、丢了 2 箱、第 37 箱请补发；画面已经花了，麻烦立刻重发一个关键帧；我这边带宽只剩 3 Mbps，别再往上顶了。”它不搬货，只让发送方知道收货质量，从而调整节奏、重传或降码率。

RTCP 与 RTP 通常成对出现：RTP 用偶数端口，RTCP 用相邻的奇数端口（这是 RFC 3550 的经典约定）。WebRTC 为了省端口，普遍启用 a=rtcp-mux，把两者塞进同一个五元组；此时不能再按“奇数端口”找 RTCP。RTCP 的会话带宽一般只占 5% 左右，发送间隔会自动拉长，别指望它像 RTP 一样密集。

“补包”与“补帧”的取舍

丢一两个包，NACK 重传最便宜；一个关键帧被拆成几十个包、丢了中间一片，重传成本高且延迟大，不如直接 PLI 请求新的 IDR。浏览器通常两种都会发，具体策略由接收端决定。

REMB 与 TWCC 不是一回事

REMB 是接收端直接说“我能收多少”；TWCC 是接收端把每个包的到达时间回传，让发送端自己算。前者简单，后者更准但反馈量大。工程上不要同时迷信两者，选一条主策略。

💡排错提示：“一直花屏但网络看起来不丢包”，先看有没有 PLI/FIR 发出、发送端有没有响应。只看 RTP 序号是不够的，反馈报文可能被防火墙挡在反方向——RTCP 也需要双向放行。

🧬 RTP/RTCP 深潜：扩展头、CSRC 与五种回访单

基础 RTP 头只是快递面单的正面。有些包裹还要在背面贴一张附加说明书（头扩展），或者列出中转站清单（CSRC）；而 RTCP 也不是“一种报文”，而是五种格式完全不同的回访单：汇报（SR）、收货统计（RR）、名片（SDES）、告别（BYE）、自定义便条（APP）。看懂这些字节，你才能在没有服务器日志时判断“这包是谁发的、带了什么、该不该补”。

头扩展：X=1 时，面单后面先加一段“目录”

想象寄快递时勾选了“含附件”：工作人员会先在面单背面写一行目录——“附件共 3 页、编号体系是 A”，然后才把附件钉上去。RTP 的扩展头就是这行目录：X=1 时，固定头（含 CSRC 列表）之后紧跟 4 个字节的扩展头，前 2 字节是 profile（编号体系），后 2 字节是 length（附件长度，单位是 32 位字，不是字节）。算错这个单位，载荷起点就会整体偏移，解码器只会看到一堆垃圾字节。

RTCP 五种报文：一份公共头，五种身体

所有 RTCP 报文都以同一个 32 位公共头开头。它像快递单最上面的那行“单据类型 + 后面还有几联”：版本、填充位、报告数（反馈报文里这个字段改叫 FMT）、报文类型（PT）、以及整包长度（以 32 位字计，且不包含这 4 个字节本身）。

RC（Report Count）在 SR/RR 里表示“后面有几个报告块”；在 NACK/PLI 这类反馈报文里，同一块字段改称 FMT（Feedback Message Type），用来区分同类报文的不同子类型。这就是为什么 RTCP PT=205 FMT=1 才是 Generic NACK。

① SR：发货汇报，兼带时钟对齐

SR 是发送端的“发货小结”：一共发了多少包、多少字节，以及发货那一刻的墙上时间（NTP）和对应的 RTP 时间戳。接收端拿到这一对映射，才能把音频的 48 kHz 时钟和视频的 90 kHz 时钟对齐——这就像两个乐队各自数拍子，SR 是那句“现在整点，双方都记一下”。

② RR：收货统计，指出“少了哪几箱”

RR 是接收端的“收货回执”：丢包率、累计丢包数、最高收到序号、抖动，以及“我上次收到你的 SR 是什么时候”。它像仓库回单：不但说少了 2 箱，还告诉你“我最后一次点货是在 1.5 秒前”，让发货方知道这份统计有多新。

上面 DLSR 的换算容易记混：它的单位是 1/65536 秒，所以 0x00000096 = 150 → 150 ÷ 65536 ≈ 0.00229 秒（约 2.3 毫秒）。工程上常把它与 LSR 一起用来估算 RTT：RTT ≈ 当前 NTP − LSR − DLSR。若 LSR 为 0，说明对方根本没收到过 SR，这个 RTT 估算也就无效。

③ SDES：名片，告诉对方“我叫什么”

SDES 是随包附上的名片，最重要的是 CNAME（规范名）。SSRC 是随机数，重启一次就变；CNAME 稳定，用来把同一台设备的音频流和视频流绑在一起。没有它，接收端只能靠时间戳猜“这两路是不是同一个人”。

④ BYE：挂断电话

BYE 就是“我要下线了”。它不带统计数据，只列出要结束的 SSRC；可选的 reason 字段能写一句“为什么断”。收到 BYE 后，接收端应释放抖动缓冲、清理该 SSRC 的状态，而不是继续等包。

⑤ APP：自定义便条

APP 是留给厂商的“自定义便条”：前 4 个字节写应用名（ASCII），后面随便放私有数据。规范只规定信封格式，不规定内容，所以跨厂商基本不通用。看到 APP 不要慌，先查是哪家设备、哪个版本定义的。

NTP 与 RTP 时间戳：两把尺子怎么换算

NTP 用的是“自 1900 年起算的秒”，RTP 用的是“自某个随机起点起算的 90 kHz 刻度”。这就像两个人都从不同日期开始记“第几天”：单看数字毫无意义，必须先拿到一次同时发生的双记录（SR），之后才能用一个差值互相推算。

unix_sec = NTP_sec − 2,208,988,800
秒 = NTP_sec + NTP_frac / 232 − 2,208,988,800
RTP_B = RTP_SR + (NTP_B − NTP_SR) × 90,000   (mod 232)

逐项解释：NTP_sec 是 SR 里的高 32 位（1900 起算的秒），减去 2,208,988,800 就是 Unix 秒；NTP_frac 是低 32 位，除以 232 得到秒的小数部分；RTP_SR 与 NTP_SR 是 SR 给出的一对同时记录；NTP_B 是你要换算的目标时刻。90,000 是视频时钟频率，音频要换成 48,000 或 8,000。最后取模 232，因为 RTP 时间戳是 32 位、会回绕。

算一遍：0.5 秒之后的 RTP 刻度

SR 说：NTP = 0xEE925100 00000000（2026-11-02 00:00:00 UTC），RTP = 0x00054A2C = 346,668。0.5 秒后：346,668 + 0.5 × 90,000 = 391,668 = 0x0005F9F4。反过来，看到两个 RTP 时间戳相差 45,000，就是相差 0.5 秒。

回绕周期：别用“小于”直接比较

32 位时间戳在 90 kHz 下约 13.25 小时回绕一次；48 kHz 音频约 24.85 小时；8 kHz 约 6.2 天。比较大小时要用“有符号差值”或扩展序号，直接写 if (a < b) 会在回绕点把新包当成旧包。

抖动：为什么不能只看“平均延迟”

抖动不是“延迟有多大”，而是“相邻两个包的时间间隔，和发送端原本的间隔差了多少”。像等公交：平均 10 分钟一班不代表体验好，如果一班 2 分钟、下一班 18 分钟，队伍就会积压。RFC 3550 用一阶平滑递推来估计它：

D(i−1, i) = (Ri − Ri−1) − (Si − Si−1)
J = J + ( |D(i−1, i)| − J ) / 16

R 是接收端到达时刻（换算成 RTP 时间单位），S 是包里的发送时间戳；两者相减得到“这一对包的实际间隔偏差”D；取绝对值后，用 1/16 的权重更新滑动平均 J。这就是 RR 里 interarrival jitter 字段的来源。它回答的是“抖动缓冲该开多大”，而不是“网络延迟多高”。

NACK 与 RTX：补的是包，不是帧

NACK 像收件人打电话说“第 1001 箱没到，麻烦补发”。发送端如果还留着这包的副本，就原样再发一次；如果已经清出缓存，只能等下一个关键帧。WebRTC 里的 RTX（RFC 4588）更讲究：重传包走独立的 SSRC 和独立的序号空间，载荷开头 2 字节写“原包序号（OSN）”，接收端据此把补发的包塞回原来的位置。

# SDP 里声明 NACK 与 RTX 的典型写法
a=rtpmap:96 H264/90000
a=rtcp-fb:96 nack
a=rtcp-fb:96 nack pli
a=rtpmap:97 rtx/90000
a=fmtp:97 apt=96

# 重传包的关键：RTX 自己的 seq 是新的，原序号藏在载荷头 2 字节
RTX packet: SSRC=0x0BADCAFE seq=5001 PT=97 payload=00 03 E9 ... # OSN=0x03E9=1001
⚠️别把重传当丢包：开启 RTX 后，同一路媒体会出现两个 SSRC、两套序号。只按“序号跳变”统计丢包，会把重传误判成新的丢包，丢包率越算越高。正确做法是先按 OSN 还原，再按原 SSRC 与时间戳统计。

🍽️ RTSP：先看菜单，再下单，最后上菜

RTSP（Real-Time Streaming Protocol）像在餐厅点菜：DESCRIBE 是看菜单（这路流有哪些轨道、什么编码、地址在哪），SETUP 是告诉服务员“用哪张桌子、哪个端口上菜”，PLAY 才是真正下单开做。它只负责“点菜和撤单”，菜（媒体）由 RTP 另外端上来——这就是所谓的带外控制。

UDP 还是 TCP 复用

Transport: RTP/AVP;unicast;client_port=8000-8001 是 UDP，速度快但要放行一整段 UDP 端口；RTP/AVP/TCP;interleaved=0-1 把 RTP/RTCP 塞进 RTSP 的 TCP 连接，只要 554 通就能看，代价是 TCP 重传带来的延迟抖动。

常用方法与状态码

DESCRIBE / SETUP / PLAY / PAUSE / TEARDOWN / OPTIONS / GET_PARAMETER / SET_PARAMETER。401 是鉴权失败，404 多是 URL 或 trackID 写错，454 是 Session 不存在（常因过期或服务器重启），455 是方法在当前状态不可用。

⚠️RTSP 的“延迟”经常不是协议本身：默认播放器会缓冲几秒；编码器 GOP 太长会让首帧等待更久；TCP 复用遇到丢包会阻塞整条连接。先分别验证“首帧时间、缓冲深度、丢包重传”，再决定改哪一层。

📋 RTSP 方法全集：从看菜单到撤单的每个口令

RTSP 像餐厅里的一套标准服务口令：OPTIONS 是先问“你们提供哪些服务”，DESCRIBE 是看菜单，SETUP 是订座位，PLAY 是下单，PAUSE 是“先别上”，TEARDOWN 是结账走人。推流场景则反过来：ANNOUNCE 先把菜单递过去，SETUP 订好上菜口，RECORD 才开始收货。每个方法都带 CSeq 配对，服务器按序号判断哪条回复对应哪条请求。

方法方向它在做什么关键头 / 参数典型坑
OPTIONS客户端 → 服务器查询服务器支持哪些方法与 URL 范围Public 响应头、Require200 只说明“会这个动词”，不代表这路流能播
DESCRIBE客户端 → 服务器取 SDP：有几条轨道、什么编码、control 地址Accept: application/sdpSDP 里的 a=control 可能是相对路径，拼错就 SETUP 404
ANNOUNCE客户端 → 服务器推流前把媒体描述交给服务器（相当于“我要上架这些菜”）Content-Type: application/sdp + SDP body摄像头一般不用；编码器、推流软件才用；body 长度必须与 Content-Length 一致
SETUP客户端 → 服务器为某条轨道建立传输：UDP 端口对或 TCP 交织通道Transport、可选 Sessioninterleaved 通道号必须与服务器返回一致；UDP 端口对要成对

PAUSE客户端 → 服务器暂停媒体，但保留会话与端口Session暂停不等于释放；长时间不操作仍会被 timeout 回收

TEARDOWN客户端 → 服务器结束会话，释放端口与解码资源Session不发也能靠超时回收，但会拖住服务器端口，批量场景要主动发
GET_PARAMETER双向读取参数；工程上最常被拿来当“保活心跳”Session有的设备必须带 body 才回 200，空 body 可能直接 400
SET_PARAMETER客户端 → 服务器写参数：OSD 文字、倍速、码率等Session、Content-Type参数名与取值是厂商私有约定，换品牌就不通用
REDIRECT服务器 → 客户端告诉客户端“这路流搬到另一台服务器了”Location，配合 3xx 状态码负载均衡/级联时常见；客户端不跟随就会一直连旧地址

推流方向：ANNOUNCE → SETUP → RECORD

前面 RTSP 章节讲的是“拉流”，这里把反方向的报文补齐。推流像把自家厨房搬到对方仓库：先把菜单（SDP）交过去（ANNOUNCE），再约定卸货口（SETUP 的 server_port），最后喊一声“开始卸”（RECORD）。注意 SETUP 的方向相反——这次是服务器告诉你“往我的 17000 端口发”。

RTP over TCP：用 $ 把媒体塞进同一条连接

很多企业网只放行 TCP 554，UDP 一律封。RTSP 的解决办法是“把菜和点菜单塞进同一个服务员手里”：在 RTSP 的 TCP 连接上，媒体数据用 interleaved 格式混流，每条消息前加 4 个字节——$、通道号、2 字节长度。看到 0x24 开头，就说明下面不是 RTSP 文本，而是 RTP/RTCP。

# ffmpeg 强制用 RTSP over TCP（即 interleaved）
ffplay -rtsp_transport tcp rtsp://user:pass@192.168.1.64/Streaming/Channels/101

# 让 ffmpeg 打印底层协议，确认到底走了 TCP 还是 UDP
ffprobe -v verbose -rtsp_transport tcp \
  rtsp://user:pass@192.168.1.64/Streaming/Channels/101

状态码：服务器到底在抱怨什么

状态码含义最常见的真实原因
200 OK请求成功正常；但 PLAY 200 后仍可能收不到 RTP（端口/防火墙问题）
301 / 302资源已移动服务器换地址或级联，需跟随 Location
400 Bad Request报文格式不对缺 CSeq、Content-Length 与实际 body 不符、URL 里有非法字符
401 Unauthorized需要鉴权没带 Authorization，或 Digest 的 nonce/realm/response 算错
403 Forbidden拒绝访问账号能看到菜单但没有这路流的权限；或 IP 白名单限制
404 Not FoundURL 或 track 不存在通道号写错（如 101 写成 102）、a=control 拼接错误
405 Method Not Allowed当前状态不允许该方法没 SETUP 就 PLAY，或对已 TEARDOWN 的 Session 再 PLAY
451 Parameter Not Understood参数看不懂Transport 里带了厂商不认识的选项（如自定义 mode=...）
454 Session Not Found会话不存在Session 过期、服务器重启、负载均衡把请求转到了另一台机器
455 Method Not Valid in This State状态机不匹配已在 PLAYING 又发 RECORD，或未 ANNOUNCE 直接 RECORD
457 Invalid Range时间范围无效回放请求的 npt 超出录像区间，或 Range 语法写错
500 / 501 / 503服务器内部错误 / 未实现 / 忙并发到上限、转码进程崩了、方法不支持；重试往往无效，要看服务端日志
505 RTSP Version Not Supported版本不支持请求行写成了 RTSP/2.0 之类的非实现版本
🔍鉴权别只盯着密码：Digest 的 response 是把 username、realm、nonce、uri、method 一起做哈希的结果；URI 必须与请求行里的完全一致（含 query），method 也要一致。很多“密码明明对却 401”，就是客户端把 DESCRIBE 的 URI 拿去算了 PLAY 的哈希。

🚛 RTMP：把大件拆成标准托盘再装车

RTMP（Real-Time Messaging Protocol）原本是 Flash 时代的直播协议，现在主要活在“推流”这一段。它的核心动作是分块（chunk）：一个很大的视频帧不能整块塞进网络，就切成固定大小的小块，每块带一个“这是第几号托盘、属于哪一车”的小标签。FLV 则是它最常见的“货物清单”格式。

RTMP 跑在 TCP 1935 上，先握手再谈命令：客户端发 C0/C1/C2，服务器回 S0/S1/S2，双方确认版本与随机数后才开始发消息。握手不是加密，也不是鉴权；它只建立一条“咱俩能按同一套节奏说话”的连接。

Chunk 的结构

Basic Header: 1–3 字节
  fmt (2 bit) + chunk stream id
Message Header: 11 / 7 / 3 / 0 字节
  timestamp      3 字节（0xFFFFFF 时扩展 4 字节）
  message length 3 字节
  message type   1 字节
  stream id      4 字节（小端）
Payload: 默认 128 字节一块，可协商变大

fmt 越小，复用得越多：类型 0 带完整头，类型 1 只改长度与类型，类型 3 连时间戳都沿用上一块。分块大小协商后，太小的块会让头部开销变大，太大的块又会增加单包延迟。

AMF 命令与 FLV 的关系

connect → releaseStream → FCPublish
→ createStream → publish
play → onStatus NetStream.Play.Start

FLV tag 类型：
  8  = audio
  9  = video
  18 = script（onMetaData）

FLV 是文件/流容器，RTMP 是传输协议。推流时常见组合是 -f flv rtmp://...；第一个视频 tag 通常带 AVCDecoderConfigurationRecord（SPS/PPS），播放器靠它初始化解码器。

环节真实字段 / 命令为什么重要
握手C0 版本=3；C1/S1 各 1536 字节版本不匹配或实现不完整时，服务器会直接断开
连接connect + tcUrl + appapp 写错（如 live 写成 livestream）会 404 或直接拒流

时间戳3 字节，回绕约 4.66 小时长时间推流要处理回绕，否则播放器会“时间倒流”

HTTP-FLV 是把同样的 FLV 数据挂在一个长 HTTP 响应上，浏览器用 MSE 加 flv.js 就能播。它比 HLS 延迟低，但没有原生支持，且每个客户端都占一条长连接；大并发时仍然要 CDN 或边缘节点。

🔍一句话区分：RTMP 负责“把 FLV 推上去”，HTTP-FLV 负责“把 FLV 拉下来”，HLS 负责“把同样的内容切成很多小文件让 CDN 分发”。三者经常同时存在于一个直播间，只是各服务不同观众。

🎞️ HLS：把一场直播切成很多小集

HLS（HTTP Live Streaming，RFC 8216）的思路极其朴素：既然 HTTP 服务器最便宜、CDN 最成熟，那就把直播切成一段段几秒钟的小文件，再用一个 .m3u8 清单告诉播放器“先取哪段、后取哪段”。这就像追剧：你不需要一条不断的长线，只要拿到“本集目录”，一集一集下载即可。

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:4
#EXT-X-MEDIA-SEQUENCE:120
#EXTINF:4.000,
seg120.ts
#EXTINF:4.000,
seg121.ts
#EXTINF:4.000,
seg122.ts
#EXT-X-ENDLIST
标签作用常见坑
#EXT-X-TARGETDURATION所有分片时长的上限（整数秒）实际 #EXTINF 超过它，部分播放器会拒绝播放
#EXT-X-MEDIA-SEQUENCE清单里第一个分片的序号直播滚动窗口靠它递增，播放器据此判断新旧
#EXTINF下一段的时长（可带小数）切片必须从关键帧开始，否则拼接处会花屏
#EXT-X-ENDLIST点播结束标记直播清单不要写；写了播放器会认为已完结
#EXT-X-KEYAES-128 / SAMPLE-AES 等加密信息密钥 URL 跨域、鉴权失败会导致整段黑屏
#EXT-X-MAPfMP4 的初始化分片（init.mp4）缺它就无法建立解码器；CMAF/fMP4 场景必查
#EXT-X-DISCONTINUITY时间轴或编码参数发生跳变广告插入、切码率后漏写会导致音画不同步

延迟是怎么“攒”出来的

一次典型的 HLS 延迟 = 采集与编码延迟 + 一个分片的时长 + 播放器至少缓存 2–3 个分片 + CDN 回源与网络时间。分片 6 秒、缓存 3 片，轻松就到 20 秒。想压低延迟，要么缩短分片（代价是请求数暴增），要么上 LL-HLS（低延迟 HLS）：用部分分片、阻塞式清单刷新和预加载提示，把延迟压到几秒，但它对 CDN 与播放器的支持要求更高，具体以 8216bis 草案与各厂商实现为准。

TS 还是 fMP4

TS 兼容老设备，工具链成熟；fMP4（CMAF）更省空间、启动更快，还能与 DASH 共用同一份切片。HEVC/AV1 基本都走 fMP4。

为什么切片要对齐 GOP

播放器切到新分片时必须从关键帧开始解码。若编码器 GOP 是 2 秒而切片是 4 秒，边界刚好；如果是 3 秒 GOP 配 4 秒切片，边界就会切在 P 帧上。

多码率就是多份清单

主清单（master playlist）列出 360p/720p/1080p 各自的子清单与 BANDWIDTH，播放器根据带宽切换。切片时间轴必须对齐，否则切换会卡顿。

💡工程口诀：GOP 等于切片时长、切片从 IDR 开始、清单用相对路径、所有码率共用同一时间轴。做到这四点，HLS 的“莫名卡顿”会少一大半。

🏷️ HLS 标签全集：清单是一本会自己更新的目录

m3u8 清单像一本活页目录：每一行以 #EXT 开头的都是排版规则，不带 # 的行才是真正要取的文件名。#EXTINF 是“这一集多长”，#EXT-X-KEY 是“这一集上了锁”，#EXT-X-MAP 是“先读这页说明书才能解码”。LL-HLS 则更进一步：目录还没印完，就允许你先撕下正在印的那几行——靠的是部分分片（PART）与阻塞式刷新。

LL-HLS：把 2 秒分片再切成 4 个 0.5 秒的“部分分片”

普通 HLS 要等一整段 2 秒写完才能下发，LL-HLS 则把这一段再切成 4 个 0.5 秒的 part，写完一个就能发一个。这像连载小说：不等整本印刷完，作者每写完一章就先把这一章贴出来；读者还可以提前说“下一章写到第 3 页就叫我”（阻塞刷新）。

注意 #EXTINF 后面仍会出现完整的 seg120.ts：part 是“提前可用的碎片”，完整分片写完后仍要登记，供不支持的客户端回退。也就是说，LL-HLS 清单同时服务两类播放器：支持 part 的走低延迟，不支持的退回普通 HLS，延迟变大但不会播不了。

PART-HOLD-BACK 怎么定

它表示“播放器至少要落后正在生成的 part 多久”。经验值取 3 倍 PART-TARGET 左右：0.5 秒 part 就设 1.5 秒。设太小会频繁缺 part，设太大等于把延迟又加回去。

阻塞刷新不是 HTTP 长轮询

它是在同一个 GET 上，让服务器“等到有数据再返回”。所以 CDN 边缘必须理解 _HLS_msn 参数或直接回源，否则会把请求当成普通清单缓存住，低延迟立刻失效。

PART 与 GOP 的关系

每个 part 最好从 IDR 开始，才能标 INDEPENDENT=YES；否则只能等整段结束，低延迟收益会被吃掉。切 part 的边界通常由编码器的帧边界决定，不是随便按时间切。

💡上线前先验三件事：① #EXT-X-VERSION 与使用的标签匹配；② 清单响应头 Cache-Control 是否允许短缓存（直播清单不能缓存几分钟）；③ CDN 是否透传 _HLS_msn/_HLS_part 查询参数。任何一条不满足，LL-HLS 都会“看起来支持、实际延迟十秒”。

📋 DASH：一份 MPD 清单，描述所有画质

DASH（MPEG-DASH，ISO/IEC 23009-1）和 HLS 是同一个思路的“标准化版本”：也用 HTTP 下载分片，但它用一份 XML 格式的 MPD（Media Presentation Description）描述“有哪些 Period、哪些画质、每段切片怎么命名”。HLS 的清单是逐行的文本，DASH 的清单是结构化的树。

<MPD type="dynamic" minimumUpdatePeriod="PT2S"
     availabilityStartTime="2026-11-02T00:00:00Z"
     timeShiftBufferDepth="PT30S">
  <Period id="p0" start="PT0S">
    <AdaptationSet mimeType="video/mp4" segmentAlignment="true">
      <Representation id="v720" bandwidth="2500000"
                    codecs="avc1.64001f" width="1280" height="720">
        <SegmentTemplate timescale="1000" duration="2000"
          initialization="v720/init.mp4"
          media="v720/$Number%05d$.m4s"/>
      </Representation>
    </AdaptationSet>
  </Period>
</MPD>
概念含义实战提醒
Period一段连续的时间区间，可插入广告或切换内容Period 切换点若编码参数变化，要重新初始化解码器
AdaptationSet同一类媒体的集合（视频/音频/字幕）视频与音频通常分开，播放器要自己对齐时间轴
Representation一个具体码率/分辨率的版本bandwidth 是选码率的重要依据，但实际码率会波动
SegmentTemplate用模板批量生成分片 URL$Number$、$Time$、$RepresentationID$ 写法由服务器决定
type=static/dynamic点播 / 直播直播用 dynamic，并配合 minimumUpdatePeriod 刷新清单
UTCTiming告诉播放器去哪儿对时服务器时钟漂移会导致直播“追帧”或“卡在开头”

DASH 的强项

一份清单表达多 Period、多码率、多语言、DRM（CENC）；切片可与 HLS 共用 CMAF 文件，实现“一份存储、两套清单”。大型点播平台偏爱它，因为描述能力强、扩展性好。

DASH 的弱项

XML 比 m3u8 重，客户端实现复杂度更高；浏览器原生支持远不如 HLS（Safari 尤其偏 HLS），通常要 dash.js 或 hls.js 这类 MSE 库补齐。

🌳 DASH MPD 结构：一棵树，两种寻址

MPD 像一份乐谱的总目录：MPD 是整本谱子，Period 是一个乐章，AdaptationSet 是“弦乐组/管乐组”，Representation 是组里具体的演奏者（码率版本），SegmentTemplate 则规定“第几页、第几小节去哪里取”。HLS 用逐行文本描述这些关系，DASH 用一棵 XML 树，所以它更能表达多 Period、多语言、多 DRM。

一份真实可用的 MPD：视频双码率 + 音频单码率

type=dynamic这是直播清单，不是点播播放器会按 minimumUpdatePeriod 持续刷新 MPD
availabilityStartTime第 0 个分片“变得可用”的墙上时间所有分片的时间都由它推算；写错会让直播“永远在开头”或“追不上”

两种寻址：按“第几段”还是按“第几秒”

SegmentNumber 像按“第 120 集、第 121 集”取剧；SegmentTimeline 像按“从第 120 分钟开始、演 4 分钟”取片段。前者文件名简单、清单小，但要求每段时长固定、序号连续；后者能处理变长分片、丢段、拼接，代价是清单更大。

SegmentNumber：duration + startNumber

<SegmentTemplate timescale="1000"
  duration="2000" startNumber="120"
  initialization="v720/init.mp4"
  media="v720/$Number%05d$.m4s"/>

序号本身只是文件名的一部分，媒体起点由 Period 的 start、startNumber 与固定 duration 一起推算：第 120 段相对第 119 段正好晚 2 秒。只要编码器不丢段、不改时长，这个映射就一直成立。

SegmentTimeline：显式时间线

<SegmentTemplate timescale="90000"
  media="v720/$Time$.m4s"
  initialization="v720/init.mp4">
  <SegmentTimeline>
    <S t="0" d="360000" r="2"/>
    <S t="1080000" d="360000"/>
    <S t="1440000" d="180000"/>
  </SegmentTimeline>
</SegmentTemplate>

t 是起点、d 是时长、r 是“后面再重复几次”。前三条是 0、360000、720000（r=2 表示额外重复 2 次），接着跳到 1080000，再一段 2 秒。多出来的 180000 就是一次变长分片。

🛡️ SRT：宁可晚到，也要整箱到齐

公网丢包、抖动、带宽忽高忽低，UDP 直传会花屏，TCP 又会因为重传把延迟越拖越长。SRT（Secure Reliable Transport）的做法是：在 UDP 之上加一个可调的缓冲池，用 ARQ（自动重传请求）补丢包，用 AES 加密防偷看。它不追求“最快”，而是让你用可控的延迟换稳定的画面——像给快递加一个中转仓，晚一点，但箱子不会缺。

SRT 由 Haivision 发起、SRT Alliance 维护，协议规范以公开的 Internet-Draft 与实现文档为准，不是 IETF 的正式 RFC 标准。它最常见的载体是 MPEG-TS，因此和广电、演播室、远程回传的场景特别合拍。

参数 / 模式含义怎么用
mode=caller主动去连对方（发起方）推流端常用；需要知道对方公网地址与端口
mode=listener监听等待对方来连接收端常用；防火墙只需放行一个 UDP 端口
mode=rendezvous双方同时向对方发起，适合都在 NAT 后配置更复杂，成功与否依赖 NAT 行为
latency接收缓冲目标（毫秒级）越大越抗抖动，但端到端延迟越高；常用 200–800 ms，默认值以版本为准
passphrase / pbkeylenAES 加密口令与密钥长度两端必须一致；口令错会直接连接失败
streamid业务标识，供接收端路由一个监听端口接多路流时靠它区分
maxbw带宽上限防止一条流把整条上行吃满
 
# 接收端：监听 9000，缓冲 200 ms
ffmpeg -f mpegts -i "srt://0.0.0.0:9000?mode=listener&latency=200" \
  -c copy out.ts

# 发送端：主动连接，限制带宽
ffmpeg -f mpegts -i input.ts \
  -c copy -f mpegts "srt://10.0.0.8:9000?mode=caller&latency=200&maxbw=20000000"

# 只做转发、不转码
srt-live-transmit "srt://:9000?mode=listener" "srt://10.0.0.9:9000?mode=caller"

SRT 的“延迟”是预算，不是固定值

它把一段时间内的包先收进缓冲，等齐了再交给解码器。网络抖动 100 ms、你设 200 ms，通常够用；跨洲链路抖动 400 ms，就得设更大。设太小会频繁触发重传与丢帧，设太大则观众明显感到“慢半拍”。

什么时候不该用 SRT

观众是浏览器、要过 CDN、要按需伸缩并发——这些场景 SRT 都不合适（浏览器不原生支持，CDN 也不按 SRT 分发）。它更适合“点对点回传/贡献”这一段，到了机房再转 HLS/WebRTC。

⚠️不要把 SRT 当“万能加速器”：它不能突破物理带宽，也不能修复源头编码问题。上行只有 5 Mbps，却推 8 Mbps 的 4K，SRT 只会用延迟和丢帧来“消化”这个不可能，最终画面照样烂。

🚐 SRT 与 RIST：公网回传为什么不再用 RTMP

RTMP 跑在 TCP 上，像一条单轨铁路：只要前面一节车厢卡住，后面整列车都得等——这就是队头阻塞。公网丢包 2%、RTT 200 ms 时，TCP 的自动重传会把延迟越拖越长，而 RTMP 对此无能为力。SRT 换成了“越野车队 + 中转仓”：走 UDP，丢了哪箱补哪箱，用固定延迟预算把抖动关进笼子。RIST 则是广电行业的另一支镖局，规则更贴近 RTP 生态。

维度RTMP（公网回传）SRT
传输层TCP 1935（单条字节流）UDP 单端口（消息式传输）
延迟可控性由 TCP 重传与拥塞窗口决定，应用管不了latency 是显式预算，端到端可预期
丢包恢复内核整体重传，可能队头阻塞按序号 NAK，选择性重传，不阻塞其他包

防火墙TCP 1935，企业网易放行一个 UDP 端口；但部分网络封 UDP，需要提前确认
典型角色主播推流到平台摄像机/演播室回传到机房，再转 HLS/WebRTC

RTMP 并没有“死”，它只是退回到它最擅长的位置：平台入口的推流协议。一旦链路上行是公网、丢包不可控、又要求秒级延迟，SRT 的“延迟预算 + 选择性重传”就更合适。两者经常接力出现：现场用 SRT 回传到机房，机房再转 RTMP 推给直播平台。

ARQ 与 FEC：补票还是多买一张

ARQ 像“丢件后打电话让仓库补发”：不额外占带宽，但要等一个往返；FEC 像“每寄 10 箱就多买 2 箱备份”：不等待，但无论丢不丢都要多付运费。SRT 以 ARQ 为主，RIST Main Profile 可以叠加 FEC；选择取决于你的丢包模型与延迟预算。

机制带宽开销恢复延迟适合的丢包形态典型副作用
ARQ（自动重传）接近 0，只有重传时才占至少 1 个 RTT，抖动大随机丢包、丢包率不高（< 5%）延迟预算不足时会“补不过来”，只能丢帧
FEC（前向纠错）固定 5%–20% 冗余接近 0，无需等待连续丢包、突发丢包、单向链路带宽浪费；丢包超过冗余比例时仍然恢复不了
ARQ + FEC冗余 + 偶尔重传大部分即时恢复，少量等 RTT公网长链路、卫星、跨国回传参数调优复杂，两端实现必须匹配

握手、加密与延迟缓冲：SRT 的三根支柱

SRT 建立连接像“两个仓库核对暗号”：双方先交换版本、加密能力、延迟预算与 streamid，确认后再开始收货。握手是四步（caller 发起 → listener 回应 → caller 结论 → listener 确认），任何一步参数不一致，连接都会停在“已发起但未就绪”的状态。

latency 不是“越小越牛”，而是“你愿意为抖动与重传留多少时间”。经验规则是至少 4 倍 RTT：跨洲 RTT 200 ms，就至少给 800 ms 预算；同城 10 ms，200 ms 就绰绰有余。设得太小，晚到的包会被 TSBPD 直接丢弃，画面照样花；设得太大，观众会明显感到“慢半拍”。

加密：AES-CTR，不是 TLS

passphrase 触发密钥派生，pbkeylen 可选 16 / 24 / 32 字节（AES-128/192/256）。它加密的是 SRT 载荷，不提供证书与身份体系；因此别把它当成 HTTPS 那种“可信站点验证”，密码泄露就等于钥匙泄露。

为什么时间戳只有 32 位

SRT 用 32 位微秒计数，约 71.6 分钟回绕一圈。这比 RTP 的 13 小时短得多，所以实现里到处都要处理“刚刚回绕”的判定；这也是长连接跑几天后“突然卡住”的经典诱因之一（实现 bug，而不是协议设计）。

# 发送端：caller，200 ms 延迟预算，AES-256，限制带宽
ffmpeg -f mpegts -i input.ts -c copy -f mpegts \
  "srt://10.0.0.8:9000?mode=caller&latency=200&passphrase=MySecret12&pbkeylen=32&maxbw=20000000&streamid=live/1"

# 接收端：listener，同一口令；一个端口接多路流时用 streamid 区分
ffmpeg -f mpegts -i \
  "srt://0.0.0.0:9000?mode=listener&latency=200&passphrase=MySecret12&pbkeylen=32" \
  -c copy out.ts

# 双方都在 NAT 后：rendezvous，两边同时向对方发起
srt-live-transmit "srt://1.2.3.4:9000?mode=rendezvous&latency=300" \
  "srt://5.6.7.8:9000?mode=rendezvous&latency=300"
⚠️“连上了但没画面”先查三件事：① 两端 passphrase 与 pbkeylen 是否完全一致；② 是否真的在读 srt:// 而不是把 URL 当文件名；③ latency 是否小于链路抖动，导致包被 TSBPD 丢弃。SRT 的统计里 lost、retrans、drop 是三个不同计数器，别只看其中一个。

RIST：广电版的“另一支镖局”，一句话说清

RIST（Reliable Internet Stream Transport）由 VSF（视频服务论坛）推动，目标同样是“在公网可靠传实时媒体”，但它以 RTP 为中心：媒体仍然走 RTP，可靠性与纠错作为附加能力叠上去。所以它更容易和现有广电设备、RTP 分析工具、封装格式对接。

版本 / Profile核心组合适合谁与 SRT 的差别
RIST Simple Profile（TR-06-1）RTP + UDP + ARQ，单端口或端口对轻量回传、设备互联更贴近 RTP 生态；功能集比 SRT 小
RIST Main Profile（TR-06-2）在 Simple 之上增加自适应 FEC、多流复用、可选加密广电级长链路、跨机构互联纠错能力更强，但实现与互通复杂度更高

一句话对比：SRT 是“自成体系的 UDP 传输协议”，RIST 是“给 RTP 加可靠层的规范族”。两者都强调 ARQ、都可调缓冲、都面向公网；选型往往不是技术优劣，而是你的上下游设备支持谁、运维团队熟悉谁。

🧊 WebRTC：先交换名片，再验指纹，最后拉专线

WebRTC 的目标是“浏览器之间直接、低延迟、加密地传音视频”。它把最难的三件事拆开：SDP 谈“我会什么格式”，ICE 找“我们之间哪条路能通”，DTLS-SRTP 负责“把这条路加上锁”。三者缺一不可，而且信令（怎么把 SDP 和 candidate 传给对方）反而没有统一标准。

环节关键字段 / 协议排错抓手
媒体协商SDP（RFC 8866）、offer/answer（RFC 3264）看 m= 行与 a=rtpmap；两端没有共同编码时，SDP 会协商失败
网络穿越ICE（RFC 8445）、STUN（RFC 8489）、TURN（RFC 8656）看 candidate 类型；只有 relay 说明直连失败，TURN 带宽成了瓶颈

为什么 WebRTC 的延迟能这么低

它没有 HLS 那种“切片—缓存—再取”的链路，RTP 包几乎实时进入抖动缓冲；编码器通常开启低延迟模式（不做多帧前瞻、B 帧更少）；再加上端到端反馈（TWCC/REMB）快速调码率，整体可以做到几百毫秒。代价是：它依赖双方网络可达，规模化要靠 SFU 集群，CDN 不能直接帮它分发。

host

本机网卡地址。同一局域网内最优先，速度最快，但跨 NAT 就无效。

srflx

通过 STUN 服务器看到的“公网映射地址”。能穿透部分 NAT，但不保证双向可用。

relay

TURN 中继地址。最稳但最贵：所有媒体都绕服务器走，带宽与延迟都由它承担。

⚠️“WebRTC 连不上”先分三层：① SDP 有没有共同编码；② ICE 有没有一对候选双向通过；③ DTLS 指纹与证书是否匹配。只盯着“浏览器控制台报错”通常看不出是哪一层，必须看 chrome://webrtc-internals 的候选与统计。

🏗️ WebRTC 协议栈全图：四层积木怎么搭起来

WebRTC 不是“一个协议”，而是一套四层积木：SDP 谈“我会什么”，ICE 找“哪条路能通”，DTLS 给这条路“上锁并交换钥匙”，SRTP 才真正“搬画面”。再加一条侧路 SCTP/DataChannel 搬文字与二进制。把它想成寄贵重物品：先电话确认（SDP），再找一条能走的路线（ICE），然后双方验指纹、上锁（DTLS），最后才把箱子搬上车（SRTP）。

ICE 候选收集：先找近路，再找备用路，最后才求 relay

ICE 像给两个陌生人规划见面路线：先看“同小区直接走过去”（host），再问“门卫我出门后长什么样”（STUN 反射地址 srflx），实在不行才让“快递中转站”代收（TURN relay）。每条候选都带一个优先级，客户端按优先级从高到低两两配对，做 STUN 连通性检查，先通过且双向可达的那对就被锁定。

# SDP 里的候选不是“一个 IP”，而是一整行结构化文本
candidate:842163049 1 udp 1862270975 203.0.113.5 61722 typ srflx
  raddr 192.168.1.20 rport 61722 generation 0 ufrag 8hHf network-cost 999

# 拆开看：
# foundation 842163049 | component 1(RTP) | udp | priority 1862270975
# ip 203.0.113.5 | port 61722 | typ srflx | raddr/rport 是 NAT 内侧地址
# generation 0 | ufrag 8hHf | network-cost 999（移动网络成本更高）

优先级的官方算法是 priority = (224) × typePref + (28) × localPref + (256 − componentID)。逐项解释：typePref 是“候选类型偏好”（host 126、srflx/prflx 110、relay 0），它占最高位，所以类型优先于一切；localPref 是“同一类型内，这块网卡/这条路径的相对偏好”；最后一项保证同一 IP:port 上 RTP（component 1）比 RTCP（component 2）略高。数值越大越优先，但最终仍以连通性检查结果为准。

DTLS 的角色

a=setup:actpass 表示“我两种角色都能演”；对方回 active 或 passive，避免双方都等对方发起。角色定错，握手会一直停在 ClientHello。

指纹为什么能防中间人

证书本身可以是自签的，但 a=fingerprint 的哈希写在 SDP 里，而 SDP 经过你信任的信令通道。攻击者换了证书，哈希就对不上。

DataChannel 走哪条路

它不经过 RTP，而是 SCTP over DTLS：先 DCEP 建链（协商 sid 与可靠性），再传消息。可靠有序像 TCP，不可靠无序更像 UDP。

🔍排查顺序不要颠倒：先看 SDP 有没有共同编码（谈不成），再看 selected pair 是哪一类（通不了），最后看 DTLS 指纹与 SRTP 统计（锁不上/搬不动）。在 chrome://webrtc-internals 里，这三类信息分别落在 SDP、ICE candidate pair、transport 统计三块，不要混着看。

⚡ QUIC 与 MoQ：给每条数据流发一辆独立货车

TCP 像一条把所有货物串在一起的长龙：最前面一节车厢卡住，后面全部停摆。QUIC 把一条连接拆成许多独立 stream，每个 stream 有自己的序号与重传，A 流丢包不会堵住 B 流；再叠加 TLS 1.3 与 0-RTT，连接建立也更快。MoQ（Media over QUIC）则是在这套“多车道”上，重新定义直播的发布/订阅模型。

QUIC 长包头：第一个字节就说明“这是什么包”

QUIC 的包头像快递面单上的分区格：第一位告诉你是长头还是短头，接着两位是包类型（Initial / 0-RTT / Handshake / Retry），再往后才是版本号与连接 ID。连接 ID 是关键设计——它让连接不再绑死在“源 IP + 源端口”这个四元组上，手机从 Wi‑Fi 切到 5G，IP 变了，连接仍可继续。

0-RTT 快在哪

客户端复用上一次会话的密钥材料，第一个包就能带应用数据，省掉一整个握手往返。代价是“重放风险”：攻击者可复制首个 0-RTT 请求再发一次，所以只应对幂等请求开启。

无队头阻塞的边界

它只保证“stream 之间不互相堵”。同一个 stream 内丢包，仍要等重传；所以把大文件切成多个 stream，才有收益。

怎么确认走了 HTTP/3

curl --http3-only -I https://example.com；或看响应头 alt-svc: h3=":443"。浏览器 DevTools 的 Protocol 列会显示 h3。

MoQ：把“推流”改成“订阅”

MoQ 的核心变化是：不再由播放器反复拉清单、拉分片，而是发布者把内容挂到一棵命名树上，订阅者按名字订阅，之后新对象由传输层主动送达。这像从“每天去报摊买报纸”变成“在报社登记：有新一期就送到我家”。中转节点（relay）可以缓存、转发、按订阅裁剪，既降低延迟也降低源站压力。

🇨🇳 GB28181 在这张地图上的位置

GB28181 不是又一个传输协议，而是把 SIP 信令 + SDP 协商 + PS over RTP 媒体固定成一套组合，专门解决安防设备的联网与互操作。它和本页其他协议的关系是：借用了 RTP/RTCP 的传输能力，但用自己的 SIP 流程替代 RTSP 的点播流程，用自己的 PS 封装替代 H.264 over RTP 的常规打包。

信令：SIP

REGISTER 注册、MESSAGE 心跳与 Catalog、INVITE 点播、INFO 控制。默认 5060，UDP/TCP 都可能用到。

媒体：PS over RTP

SDP 里写 a=rtpmap:96 PS/90000 与 y=SSRC；RTP 载荷是 MPEG-2 Program Stream，不是普通 H.264 打包。

落地：网关

浏览器不认 SIP 与 PS，工程上几乎总要再加一层流媒体网关，转成 WebRTC/HLS/FLV。

想深入注册鉴权、Catalog、INVITE 与 TCP 主动/被动，直接看 GB28181 专题页。本页只把它当作“协议家族中的一员”，不再重复展开。

🔍别混用名词：GB28181 里的“点播”是 SIP INVITE，不是 RTSP PLAY；它的“控制”是 SIP INFO 里的 MANSCDP XML，不是 RTSP 的 PAUSE。抓包时如果只过滤 RTSP，永远看不到国标的信令。

怎么快速判断“是不是防火墙”

在同网段用 ffplay 能播、跨网段不能播，基本就是策略问题；抓包看到 SYN 发出但没有 SYN-ACK，或 UDP 只有出没有进，也都是典型证据。先用 nc / telnet 验 TCP，再用抓包验 UDP。

💡部署顺序：先在同一网段跑通最小链路（不经过防火墙），再逐跳加防火墙与 NAT，每加一跳验证一次。这样出问题时，你永远知道是哪一跳引入的。

🎥 抓包实战：从 tcpdump 到 RTP 载荷导出

抓包像给公路装监控：先决定拍哪条路（capture filter），再决定拍多久（-c / -G 轮转），最后决定拍多清晰（-s 0 抓整包）。拍错了路段，后面分析再细也没用；拍漏了字节，载荷就拼不回来。这一节把命令、过滤器、导出链路和 Telephony 分析串成一条可执行的路。

# 1) 控制面：RTSP 的信令、SDP 都在 554 上，整包保存
sudo tcpdump -i any -nn -s 0 -w rtsp.pcap 'tcp port 554'

# 2) 媒体面：RTP 端口是协商出来的，常抓一段端口范围
sudo tcpdump -i eth0 -nn -s 0 -w media.pcap 'udp portrange 10000-20000'

# 3) 只想在终端看 RTSP 明文，不落盘（-A 按 ASCII 显示）
sudo tcpdump -i eth0 -nn -A -c 20 'tcp port 554'

# 4) 长跑场景：每 600 秒切一个文件，避免单文件过大
sudo tcpdump -i eth0 -nn -s 0 -G 600 -w 'rtp-%Y%m%d-%H%M%S.pcap' 'udp port 9000'

# 5) Windows：dumpcap 的 -f 是 capture filter，-b 控制轮转
dumpcap -D
dumpcap -i 1 -f "udp port 9000" -w srt.pcapng -b filesize:100000

-s 0 表示抓完整包（不截断）；旧版默认 96 字节，会把 RTP 载荷截掉，导出的载荷自然拼不成一帧。-G 的单位是秒，配合 -w 里的 strftime 占位符才能自动换文件；只写文件名会被反复覆盖。抓 WebRTC 时，除了 3478 的 STUN，还要覆盖高位 UDP 端口，否则只会看到候选交换，看不到媒体。

从抓包导出 RTP 载荷：三步拼回二进制

RTP 载荷不是“一个完整文件”，而是一帧被拆成很多包。导出像把一叠散页按序号排好、再去掉每页的页码栏：先用 tshark 按 SSRC 过滤，导出序号/时间戳/标记位/载荷十六进制，再拼成二进制。注意 tshark 只做拆包，不做 H.264 的 FU-A/STAP-A 重组，拼出来的 .bin 仍需按 RFC 6184 还原，或交给 ffmpeg 处理。

# 0) 先看协议分层，确认抓到的确实是 RTP 而不是“看起来像”
tshark -r media.pcap -q -z io,phs

# 1) 按 SSRC 导出关键字段（制表符分隔，方便 Excel/awk）
tshark -r media.pcap -Y "rtp && rtp.ssrc == 0x5a3c6f12" \
  -T fields -e ip.src -e udp.srcport -e rtp.seq \
  -e rtp.timestamp -e rtp.marker -e rtp.p_type -e rtp.payload > rtp.tsv

# 2) 只留载荷，去掉冒号与换行，按十六进制还原成二进制
tshark -r media.pcap -Y "rtp && rtp.ssrc == 0x5a3c6f12" \
  -T fields -e rtp.payload | tr -d ':' | tr -d '\n' | xxd -r -p > payload.bin

# 3) 更省事的路径：还原 SDP 后用 ffmpeg 解 RTP
# 在 Wireshark 里 Follow → TCP/UDP Stream，复制 SDP 存为 session.sdp
ffmpeg -f sdp -i session.sdp -c copy out.mp4

# 或者直接从 RTSP 落一份裸 H.264（跳过 RTP 重组）
ffmpeg -rtsp_transport tcp -i rtsp://user:pass@host/Streaming/Channels/101 \
  -an -c:v copy -f h264 out.h264

-T fields -e rtp.payload 输出的是冒号分隔的十六进制，例如 41:42:43；tr -d ':' 去掉冒号，xxd -r -p 再按纯十六进制还原。-Y 是显示过滤器，写法与 Wireshark 窗口里一致；-e 是字段名，写错不会报错，只会得到空列——这也是“导出的文件是 0 字节”的常见原因。

Telephony → RTP：Wireshark 里怎么看一路流的好坏

抓包只是“有录像”，Telephony 菜单才是“回放与体检”。它把同一 SSRC 的包聚成一条流，计算丢包、抖动、延迟，并把音频解码成波形。看一路流，建议按这个顺序：

① 先确认它被识别成 RTP

菜单 Telephony → RTP → Show all streams。如果列表为空，多半是动态端口没被识别：用 Decode As… 把该 UDP 端口指定为 RTP，或在 RTP 协议首选项里确认动态载荷类型映射（96 → H.264）是否与 SDP 一致。

② 再看流统计

Statistics → RTP → Stream Analysis 会列出每个 SSRC 的包数、丢失数、丢包率、抖动、最大延迟。先看 lost 与 jitter 是否随时间恶化，再看 max delay 是否出现尖峰——尖峰通常对应一次重传或路由切换。

③ 最后听/看波形

Telephony → RTP → RTP Player 可以选中一条流播放，界面上会标出丢失区间。波形断档、规律性爆音，往往比统计数字更直观；音频流还能通过 Save Payload 导出为可播放文件。

④ 加密流要先解密

SRTP 只能看到包长与节奏。Wireshark 的 Preferences → Protocols → SRTP 可填 key/salt（或使用 srtp-decrypt 工具）解密；没有密钥就只能做统计，不能听内容。别把“解不出音频”误判成编码损坏。

抓包位置能看到什么看不到什么

两端同时抓把“发送—到达”对齐，定位丢包发生在哪一跳需要时钟同步，否则时间差不可信

🩺 排障 FAQ：八个“看起来像协议坏了”的真问题

下面每一条都对应一个高频现场：现象很吓人，根因往往只在一层。先按“最小验证链”缩小范围，再用命令取一次证，别靠猜。

❓ 公司/酒店网络封了 UDP，RTSP、WebRTC、SRT 全连不上怎么办？ ▸

先确认是“UDP 被封”还是“端口没放行”：同网段用 nc -vzu 192.168.1.64 8000，或在对端抓包看有没有收到你的包。若 UDP 确实出不去，按场景降级：

# RTSP：强制媒体走 TCP interleaved（只用 554）
ffplay -rtsp_transport tcp rtsp://user:pass@host/Streaming/Channels/101

# WebRTC：把 TURN 配在 TCP/TLS 443 上（turns:443），让媒体绕道 TLS
# SRT：没有 TCP 回退，只能换端口/走专线/隧道；或改用 RTMP(S)/HLS 过渡
# HLS/DASH/HTTP-FLV：天然走 443，通常是“最后还能用”的路径

关键判断：如果 tcpdump 只看到你的出站包、看不到任何回包，问题在网络策略；如果能看到回包但应用仍失败，问题在应用层或 NAT 映射。别把“公司防火墙”和“服务器没启动”混为一谈。

❓ 有声音没画面（或反过来），但 ffprobe 显示流正常？ ▸

“流正常”只代表容器和编码参数能被解析，不代表播放器拿到了正确的 RTP 分支。按顺序查：

检查点怎么查典型结论
SDP 的 PT 映射看 a=rtpmap:96 是 H264 还是 H265；浏览器是否支持H.265 在部分浏览器里只有音频能播
SSRC / 端口rtp.ssrc 与 SETUP 返回的端口是否对得上多轨复用时选错了轨道，拿到的是音频流
首个关键帧过滤 rtp.marker == 1，再找 H.264 NAL type 5（IDR）只收到 P 帧，解码器一直等 IDR
解码错误ffmpeg -v debug 看 decode_slice_header error编码参数（profile/level）不被硬解支持

快速验证：ffmpeg -rtsp_transport tcp -i rtsp://... -map 0:v:0 -c copy -f h264 test.h264。若这个文件能播，问题在播放器/浏览器；若不能播，问题在取流或关键帧。

❓ 跑了十几个小时后突然卡顿、音画不同步，是时间戳回绕吗？ ▸

很可能。不同协议的回绕周期差别很大：RTP 序号 16 位（65535 个包就回绕）、RTP 时间戳 32 位（90 kHz 约 13.25 小时，48 kHz 约 24.85 小时）、RTMP 时间戳 3 字节毫秒（约 4.66 小时）、SRT 时间戳 32 位微秒（约 71.6 分钟）。

# 错误写法：直接比大小，回绕点会把新包当成旧包
if (seq_b < seq_a) { /* 误判为回退 */ }

# 正确写法：有符号差值，或维护扩展序号
int16_t d = (int16_t)(seq_b - seq_a);      // 跨回绕仍能得到 +1
int32_t dt = (int32_t)(ts_b - ts_a);       // 时间戳同理

# 扩展序号 = 回绕次数 * 65536 + 当前 seq；RTCP RR 的 extended highest seq 就是它

验证：看卡顿是否发生在“整点/固定周期”附近，且 rtp.seq 从 65535 跳到 0；RTMP 则看时间戳是否从 0xFFFFFF 回到 0。把“回绕”当成“重置”，就会出现持续十几小时正常、随后永久错位。

❓ tcpdump 明明抓到了包，应用还是丢包/卡顿？ ▸

抓包点在网卡，而丢包可能发生在内核 socket 缓冲区：包已经进了网卡、也进了 tcpdump，但应用来不及读，缓冲区满了就被内核丢掉。这不是网络丢包，是“接收端自己丢”。

# 看 UDP 接收缓冲错误计数（持续增长就是它）
nstat -az UdpRcvbufErrors
netstat -su | grep -i "buffer"

# 看 socket 当前排队与内存
ss -uanm | grep 9000

# 放大接收缓冲（示例 32 MB；需 root，且应用也要设置 SO_RCVBUF）
sysctl -w net.core.rmem_max=33554432
sysctl -w net.core.rmem_default=33554432

# ffmpeg 读 UDP 时同步放大 socket buffer，并允许溢出后继续
ffmpeg -i "udp://239.0.0.1:1234?buffer_size=33554432&overrun_nonfatal=1" -c copy out.ts

判断口诀：tcpdump 有包 + 应用计数丢包 + UdpRcvbufErrors 增长 = 本机来不及读；tcpdump 就没包 = 上游没送到或网络丢。前者调缓冲区/线程，后者查链路。

❓ 播放 30 秒到 2 分钟就断，重新 PLAY 又恢复？ ▸

典型 NAT/防火墙映射超时。UDP 没有连接状态，NAT 设备靠“最近有没有包”维持映射；若一段时间只有下行、没有上行，映射会被回收，后续 RTP 就进不来。很多家用 NAT 的 UDP 映射只有 30–120 秒。

解法：让客户端周期性发上行包——RTSP 用 GET_PARAMETER/OPTIONS 保活（20–30 秒一次），RTCP 保持 RR 发送，WebRTC 开 a=rtcp-mux 并保持 STUN 连通性检查，SRT 依赖 keepalive。若仍断，换 TCP 交织、TURN/TLS 443，或让两端都在同一内网。

验证：断流时抓包看是否还有上行包；对比 NAT 设备的会话表老化时间；把心跳从 60 秒改成 20 秒，若断流时间随之变化，基本可以确认。

❓ 小包正常、一大动作就花屏，是 MTU 分片吗？ ▸

很典型。IP 分片后，任意一片丢失，整个原始数据报都无法重组；关键帧/大切片往往由很多大包组成，所以“平时没事，一动就花”。链路 MTU 可能不是 1500：PPPoE 常见 1492，VXLAN 约 1450，WireGuard 约 1420。

# Linux：禁止分片，逐步试到不通为止（1472 + 28 = 1500）
ping -M do -s 1472 8.8.8.8

# Windows
ping -f -l 1472 8.8.8.8

# 编码侧把 RTP 包控小，减少分片概率（示例上限 1200 字节）
ffmpeg ... -pkt_size 1200

# Wireshark 确认是否真的分片
ip.flags.mf == 1 || ip.frag_offset > 0

注意：降低 pkt_size 会增加包头开销与包数；真正要根治，应让整条链路 MTU 一致，或在隧道入口做正确的分片/探测（PMTUD）。别只在编码器上“压小包”就以为解决了。

❓ RTCP 显示丢包率 0，画面却在花，为什么？ ▸

“0”可能只是统计没送到，不是“真的没丢”。常见原因：

原因证据处理
RTCP 反向路径被防火墙挡住抓包只看得到 RTP，没有 rtcp.pt == 201 的 RR放行反向上行；或让发送端主动发 SR 触发回执
NACK/PLI 未被实现或未开启丢包后没有 rtcp.pt == 205 / 206在 SDP 加 a=rtcp-fb，确认发送端支持重传缓存
抖动缓冲太小包到了但播放时间已过，被 TSBPD/缓冲丢弃增大 jitter buffer / latency 预算
统计口径把 RTX 当成新流两个 SSRC、两套 seq，丢包率越算越高按 OSN 还原原序号后再统计

关键：“丢包率 0”只说明接收端上报的区间内没有缺口；如果连 RR 都没收到，这个 0 毫无意义。先确认反馈链路通了，再谈丢包率。

❓ HLS 清单能打开，播放器却一直转圈/报 403？ ▸

清单是“目录”，能打开不代表“商品能取”。按这四项查：

① CORS：浏览器跨域拉 m3u8/ts 需要 Access-Control-Allow-Origin；用 curl -H "Origin: https://你的站点" -I 看响应头。② Range：用了 #EXT-X-BYTERANGE 就必须支持 Range 请求，否则分片读不出来。③ 鉴权过期：清单里的 token 有时效，CDN 缓存了旧清单会导致 403；检查 Cache-Control 与签名时间。④ 时间轴：#EXT-X-PROGRAM-DATE-TIME 与实际时钟偏差过大，部分播放器会判定“直播已结束”。

curl -I "https://example.com/live/index.m3u8"
curl -H "Origin: https://player.example.com" -I "https://example.com/live/index.m3u8"
curl -I "https://example.com/live/seg120.ts"
ffprobe -v error -show_streams "https://example.com/live/index.m3u8"

经验：Chrome 能播、Safari 不能播，优先查 CODECS 与 fMP4 的 #EXT-X-MAP；全部播放器都不能播，优先查 403/CORS/分片 404。

🏠 NAT 四种类型：哪些能互穿

NAT 像小区门卫：内网住户出门办事，门卫会帮你在大门上贴一张"出门单"（公网 IP + 端口），回来时必须凭这张单子"原号返回"才能进。四种 NAT 的区别就在于门卫认不认"谁"、认不认"从哪个门牌号来"——这直接决定了 WebRTC 能不能在两端之间打直洞。

NAT 的"洞"存的是什么 key

所有 NAT 本质上都在维护一张"洞表"：流出 → 生成一条映射；流入 → 按 key 查表，匹配就转发，不匹配就丢。四种 NAT 的差异就是 key 包含哪些字段——字段越短越"傻大胆"，越长越"警惕"。

NAT 类型流出映射的 key流入允许的条件警惕程度常见度
Full Cone（完全锥型）内网 IP:Port任何公网主机，任何端口，都能往这张映射里塞包最松少见（运营商级设备几乎不用）
Restricted Cone（IP 限制锥型）内网 IP:Port只有我发过包的公网 主机 IP 才能回来（不管对方用哪个端口）中等较少见
Port Restricted Cone（端口限制锥型）内网 IP:Port只有我发过包的那个 IP:Port 组合才能回来较严最常见（企业/家用路由默认）
Symmetric NAT（对称 NAT）内网 IP:Port + 目的 IP:Port不仅对方的 IP:Port 要匹配，我发往不同目的地时 NAT 分配的端口还会变最严运营商级 NAT（4G/5G 网络、企业 VPN）

RFC 3489 的 NAT 类型检测（三步判定）

早期 RFC 3489 用两台有不同 IP/端口的协调服务器 s1/s2，通过几次 UDP 往返就能把 NAT 类型判出来。RFC 5780 后来用"Mapping / Filtering"两个维度重新命名（End-Independent / Address-Dependent / Port-Dependent Mapping + Address-Dependent / Port-Dependent / Symmetric Filtering），但工程上还是用四种 NAT 的名字多——WebRTC 浏览器内部的候选优先级与穿透性模型，本质上还是建立在"对方是哪种 NAT"的判断之上。

# 用 pystun 检测自己所在网络的 NAT 类型
pip install pystun
pystun -H stun.l.google.com -d
# 或
pystun3 -H stun.l.google.com:19302
⚠️现实比 RFC 复杂：运营商级 NAT（CGNAT）常常是"对内表现为 Port Restricted Cone，对外表现为 Symmetric"，即对不同 STUN 服务器返回的映射地址不同——这会让 srflx 候选在 NAT 切换后立即失效。WebRTC 的 fallback 策略（直连失败 → relay）就是为这种场景准备的。

🔮 STUN：一眼看穿我长什么样

STUN（Session Traversal Utilities for NAT）像门卫用对讲机问前台"门外现在看到我是什么样子"：内网主机通过 NAT 向 STUN 服务器发一个 Binding Request，服务器回包里就带着"我从外面看你时看到的 IP:Port"（XOR-MAPPED-ADDRESS）。这就是 srflx（server reflexive）候选的来源。它不搬运媒体，只帮你"照镜子"。

STUN Binding Request/Response 报文

XOR-MAPPED-ADDRESS 的小技巧：RFC 5389 把地址做了"异或伪装"：IPv4 整个 4 字节与 Magic Cookie 异或，IPv6 与 Magic Cookie + Transaction ID 异或。原因是早期 NAT 设备会扫描 UDP payload 里的 IP 字段并改写——XOR 后 NAT 看不到明文 IP，就不会乱改。客户端再用同样的异或恢复即可。

🔁 TURN：实在不行就让服务器代转

TURN（RFC 8656）是 STUN 的"付费升级包"：当 NAT 类型是 Symmetric、两边都 Port Restricted Cone、或防火墙封了入站 UDP——STUN 给的 srflx 候选根本通不了，这时候就走 TURN：你把媒体发给 TURN 中继服务器，服务器再转交给对方。像寄快递时找不到对门地址，就交给中转站代送——肯定能到，但中转站收手续费（带宽、延迟、成本）。

TURN 核心报文：Allocate、CreatePermission、ChannelBind

Allocate

客户端告诉 TURN "帮我开一个中继端口，用于接收来自对端的媒体"。服务器分配一个 relayed transport address（公网 IP + 端口）并回给客户端——这就是 ICE 的 relay 候选来源。

CreatePermission

客户端告诉 TURN "允许从对端 A 的公网 IP:Port 进来的包使用这个中继地址"。TURN 的安全策略：只有被 CreatePermission 显式授权的对端，才能往这个中继地址写数据。

ChannelBind

为了省带宽（STUN 包带 overhead），绑定一个 2 字节 channel number。之后客户端和 TURN 之间就可以用"4 字节 channel 头 + 载荷"的精简格式。是可选的性能优化。

    { urls: 'stun:stun.l.google.com:19302' },

  ]

# 生产环境建议用短期凭证（time-limited），防止密码外泄
# coturn 的 turn-admin 或 ownTurnRest 可以在后端签发
💰TURN 的成本账：relay 模式下媒体流量100% 经过服务器，所以带宽费是主要瓶颈。一条 1Mbps 的 HD 视频，两端都走 relay 的话，服务器进出各算 1Mbps，即 2Mbps / 通话。2000 路同时通话就需要 4Gbps 总带宽——这是"为什么 WebRTC 只有 SFU + 少量 relay 点"的根本原因。

🔗 ICE 连通性检查：从候选到一条路

WebRTC 里最难的不是"找到候选"，而是"把一堆候选配对并选一条"。ICE（RFC 8445）把这件事拆成五步法：收集候选 → 形成候选对 → 按优先级排序成 check list → 逐对做 STUN 连通性检查 → 锁定第一条双向可达的 pair。每一步都涉及 NACK、定时器、fallback 策略。

Step 1：候选收集的细节

浏览器在创建 RTCPeerConnection 后，会依次做这些事：

  1. 枚举本地网卡地址：包括 IPv4/IPv6、Wi‑Fi/有线/TUN 接口、VPN 接口、Docker 虚拟网卡，统统生成 host 候选。优先级由网卡顺序决定。
  2. 向 STUN 服务器发 Binding Request（UDP 3478），收到 XOR-MAPPED-ADDRESS 后生成一个 srflx 候选。注意：如果 NAT 是 Symmetric，不同 STUN 服务器回的映射地址不同——浏览器只保留"第一次拿到的那个"，后续检测到 NAT 变化会触发 restart。
  3. 向 TURN 服务器发 Allocate 请求（UDP 3478 / TLS 5349），拿到 relayed transport address，生成 relay 候选。Relay 优先级固定最低（typePref=0），只在所有直连尝试都失败后才会被选中。
  4. 可选：mDNS 本地发现：iOS/macOS 上浏览器会用 mDNS（.local）找到同一局域网里的候选——这在同一个家庭里两个 iOS 设备视频通话时最常见，而且完全不依赖 STUN。

Step 2：候选对（Candidate Pair）是怎么配对出来的

A 端有候选 {Ah1, As1, Ar1}，B 端有候选 {Bh1, Bs1, Br1}，理论上可以两两组合成 9 对。但 ICE 会按规则过滤掉"明显没戏"的组合，再给剩下的每对算一个本地优先级。过滤规则的核心是：类型相同或降级（host 只能对 host，srflx 可以对 host/srflx，relay 只能对 relay），加上"IP 地址族一致或可降级"（IPv6 只能对 IPv6，IPv4 可以对 IPv4）。

Step 3：check list 排序（优先级公式）

优先级越高越优先检查。单端候选的优先级公式在现有章节已给出；候选对的总体优先级：

pair priority = min(priority_local, priority_remote) × 2 + (priority_local > priority_remote ? 1 : 0)。换句话说：本地优先级 × 2 减对手优先级 × 2，再加一个固定规则"谁优先级高谁当 controlling 端"。

Step 4：连通性检查与 prflx 的来历

开始逐对发 STUN Binding Request。在检查过程中，会出现一种特殊候选：prflx（peer reflexive）。它怎么来的？

举个例子：A 发了一个 STUN 检查包，源地址是 A 的 srflx 候选地址 A_srflx:36000。B 收到后，看到"从对方的 srflx 候选地址（不是 A 的 relay 候选）发来的包"，就把"我看到的 A 地址"记下来——这是一种"在检查过程中新发现的、从对方视角出发的反射候选"。prflx 的优先级是 110（和 srflx 一样），比 relay 高得多，一旦发现就会被插入 check list 的前面重新排序。这就是为什么"两边都是 Port Restricted Cone 仍有可能打穿"：双方先"敲门"各自一个包，对方 NAT 就记下了"允许来自对方 srflx 地址"的映射——这包进来了对方 NAT，就形成了双向通路。

Step 5：锁定 selected pair 与 DTLS

第一条"双向 STUN 检查都成功"的 pair 被锁定为 selected pair。浏览器会在 chrome://webrtc-internals 的 ICE candidate pair 列表里把它标成"the one"。选定后，DTLS 握手直接在这个五元组上进行；媒体流用同一个 socket（RTCP mux 后）。此时网络路径就锁定了，不会再动态换路——除非触发 ICE restart（网络接口切换、WiFi→5G、或手动调用 pc.restartIce()）。

💡ICE restart 的触发源：① 浏览器检测到本机 IP 变化（WiFi 切 5G）；② WebSocket 信令重新拉起；③ 手动调用 pc.restartIce()。触发后候选会重新收集一遍，selected pair 可能换一条——这是 WebRTC 在移动网络下保持通话的关键机制。
