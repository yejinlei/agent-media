📚 容器到底解决什么：文字与装订

把编码器输出的 H.264 NAL 或 AAC 帧想成散页的稿纸：每页写了内容，但没有页码、没有目录、没有“第几页对应第几秒”。容器做的事情，就是把这些散页装订成书：加封面（品牌与兼容性）、加目录（索引表）、加页码（时间戳），偶尔还加版权页和字幕页。

所以“封装”不等于“压缩”。把 MP4 转成 TS 时用 ffmpeg -c copy，视频码流一个字节都没变，变的只是箱子。反过来，把 .ts 改名成 .mp4 更不会改变任何字节——播放器仍然按 TS 去解析，只是你的操作系统图标变了。

容器不负责画质

容器只搬运编码后的样本（sample）。同一段 H.264，装进 MP4 与装进 TS，画质完全一样；差别在索引、开销、可寻址性与浏览器兼容性。

裸流没有时间轴

.h264（Annex B）与 .aac（ADTS）是裸流：没有轨道概念、没有每帧时长、没有随机访问索引。能顺序播，不能可靠 seek，也很难做音画同步。

扩展名不可信

判断真实容器用 ffprobe -show_format 看 format_name，例如 mov,mp4,m4a,3gp,3g2,mj2 或 mpegts。抓包与工单里因为改后缀浪费的时间非常多。

🔍一句话记法：编码是“把画面变成比特”，封装是“把比特排成可寻址的时间轴”。前者决定 4 Mbps 能不能看，后者决定第 30 秒能不能瞬间跳过去。

🧬 MP4 的 box 树：书是怎么装订的

MP4 沿用 ISO Base Media File Format（ISO/IEC 14496-12）。整个文件由一个个 box 嵌套而成，每个 box 以 4 字节大小 + 4 字节类型开头。最小的 ftyp 只有 24 字节，最大的 mdat 可能几百 MB。理解这棵树，你就知道播放器为什么“必须先把 moov 读完才能播”。

ftyp — 品牌与兼容性：isom / iso2 / avc1 / mp42 moov — 影片元数据与全部索引（没有像素） mvhd 全局时间刻度 timescale、总时长 duration trak — 一条轨道（视频或音频） tkhd 轨道 ID、宽高、旋转矩阵 mdia mdhd 该媒体自己的 timescale / duration / 语言 hdlr vide / soun / sbtl minf → stbl 样本表：真正的索引在这里 trak — 音频轨道，结构同上，stsd 里是 mp4a mdat — 媒体数据：H.264 样本、AAC 帧，按 chunk 排列

box 的三条硬规则：① 默认 32 位 size，类型紧跟其后；② 若 size == 1，后面还有 64 位 largesize（大文件常见）；③ 若 size == 0，表示这个 box 一直延伸到文件末尾（多见于 mdat）。解析器必须先读大小再决定跳过多少字节，这也是“损坏一个长度字段，后面全乱”的原因。

💡为什么很多“下载的 MP4”不能边下边播？因为编码器默认把 moov 写在文件末尾，方便边写边追加。上传网站前跑一次 faststart，是最便宜的体验优化。

🔬 真实字节：把 ftyp 与 mvhd 拆开

下面这段是 ftyp 与 moov/mvhd 开头的真实布局（62 字节，示例文件）。前 24 字节说明“这是什么品牌的 MP4、兼容哪些规范”；随后 moov 的长度是 0x154，里面第一个子 box 是 108 字节的 mvhd。

用命令验证这些数字：ffprobe -show_entries format=duration,size,bit_rate -of default=nw=1 in.mp4。如果 duration 与 mvhd.duration / timescale 对不上，优先怀疑 timescale 被写错，或 moov 里还有 elst 编辑列表改变了呈现时长。

⚠️不要把 mvhd 的 timescale 当成视频的 timescale。视频轨道的 mdhd.timescale 常见是 90000（90 kHz，和 RTP 时钟一致），音频常见 48000。两套刻度不同，换算必须经过各自的 mdhd，而不是全局的 mvhd。

🗂️ 索引与 faststart：目录里到底写了什么

真正让播放器“瞬间跳到第 30 秒”的，是 stbl（sample table）里的六张表。它们不是缓存，而是文件的“页码 + 行号 + 字数”总账：每个样本（通常就是一帧）在哪个字节、持续多久、是不是关键帧，全在这里。

表名回答什么问题关键字段工程含义
stts每个样本显示多久（解码时长）sample_count、sample_delta90 kHz 下 delta=3000 即 33.33 ms，对应 30 fps
cttsPTS 相对 DTS 偏移多少sample_offset有 B 帧才需要；version 1 才允许负偏移
stss哪些样本是关键帧同步样本序号列表缺失时播放器只能猜，拖动会花屏或黑屏
stsz每个样本多少字节sample_size 或逐样本大小变长编码必用；固定大小时只存一个值
stsc样本怎么分组到 chunkfirst_chunk、samples_per_chunk把“样本序号”映射到“第几个块”
stco / co64每个 chunk 在文件里的偏移32 位或 64 位偏移大于 4 GB 的文件必须用 co64，否则偏移溢出

seek 的真实路径：目标时间 → 用 stts 累加找到时间附近的样本 → 用 stss 回退到最近的同步样本（I 帧）→ 用 stsc 找到它属于哪个 chunk → 用 stco 得到文件偏移 → 用 stsz 算出精确字节范围。一次拖动，本质上是一次“查六张表 + 发一个 HTTP Range 请求”。

# 把 moov 移到文件开头（不重新编码）
ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4

# 看 box 顺序（Bento4 的 mp4dump）
mp4dump --verbosity 2 out.mp4 | head -40

# 看每个包的 PTS / DTS / 关键帧标记
ffprobe -select_streams v -show_packets \
  -show_entries packet=pts_time,dts_time,flags in.mp4 | head
🔍faststart 的代价：它需要在写完后把 moov 整体搬到前面，并重写所有 stco 偏移。大文件会多一次磁盘读写，但换来“秒开 + 可拖”。这是纯容器层面的操作，与画质无关。

🧩 fMP4：活页笔记本，每页自带目录

传统 MP4 是“整本书 + 一个总目录”，必须拿到 moov 才能开始。fMP4（fragmented MP4）把它改成活页笔记本：初始化段（init）只带编码参数，后面每个分片（fragment）都自带 moof 小目录和 mdat 正文。这样流式传输时，收到第一个分片就能解码，不必等完整文件。

ftyp + moov — 初始化段（init segment），只含 track 定义，不含样本 styp — 分片类型标识，CMAF 常见 msdh / msix moof mfhd fragment sequence number，分片序号 traf tfhd track_ID、默认样本标志（关键帧/非关键帧） tfdt baseMediaDecodeTime，该片第一个样本的解码时刻 trun sample_count / duration / size / composition_time_offset mdat — 本片的实际编码样本 sidx — 可选：分片级索引，告诉客户端每片多少字节、多长

数字上很好核对：25 fps、每片 2 秒 → 每片 50 个样本，tfdt 以 90 kHz 递增 180000。若片首不是关键帧，客户端在这片里永远等不到可解码起点，所以分片必须对齐 IDR。

# 生成 keyframe-aligned 的 fMP4（适合 DASH / 低延迟 HLS）
ffmpeg -i in.mp4 -c copy \
  -movflags +frag_keyframe+empty_moov+default_base_moof out_frag.mp4

# 只做一次封装转换，视频与音频码流不变
ffmpeg -i in.mp4 -c copy -f mp4 -movflags +frag_keyframe out_cmaf.mp4

为什么 CMAF 用 fMP4

CMAF 要求同一份分片能被 HLS 与 DASH 复用。fMP4 的 moof + mdat 结构允许同一分片换一条清单即可播放，减少存储与 CDN 回源两套切片。

empty_moov 是什么

+empty_moov 让初始化段里的 moov 不携带样本表，样本信息全部下放到每个 moof/trun。这是流式写文件的常用组合，也方便边生成边发送。

🚄 MPEG-TS：一列固定 188 座的车厢

TS（MPEG-2 Transport Stream，ISO/IEC 13818-1）像一列火车：每节车厢固定 188 字节，车头写着“这节属于哪条线路”（PID）。它不追求最高空间效率，而追求丢了一节还能继续开——这正是广播与不稳定网络需要的特性。代价是每 188 字节就有 4 字节车头，固定开销约 2.13%。

TS 包头 = 4 字节（32 bit）
sync 80x47
TEI1
PUSI1
pri1
PID 130x0000–0x1FFF
scr2
AFC2
CC4

PUSI=1 表示载荷里有一个新单元（PES 或 PSI 表）的起点；AFC=01 表示只有载荷、=11 表示带自适应字段；CC 是同一 PID 内的 4 位循环计数，跳号就是丢包，这是 TS 排错最直接的证据。

PAT：节目清单的第一页

TS 里所有表的入口都藏在 PID 0 的 PAT（Program Association Table）。它只做一件事：告诉我“节目号 1 的 PMT 在 PID 100（0x64）”。拿到 PMT，才知道视频流在哪个 PID、音频流在哪个 PID。

PID典型用途怎么发现
0x0000PAT固定入口，所有解析从这里开始
0x0001CAT（条件访问）加密节目才用
0x0010NIT（网络信息表）描述运营商、频点等
0x0064PMT（本例）由 PAT 的 program_map_PID 指定
0x0100视频 PES（本例）由 PMT 的 stream_type 0x1B / 0x24 指定
0x0101音频 PES（本例）stream_type 0x0F = AAC ADTS
0x1FFF空包（null）填充用，可以安全丢弃

视频/音频数据装在 PES 里，PES 起始码固定 00 00 01 E0（视频）或 00 00 01 C0（音频）。PES 头里的 PTS/DTS 是 33 位、按 90 kHz 计数：一帧在 25 fps 下间隔 3600 tick。TS 包本身只负责切分与传输，播放时刻靠 PES 时间戳。

⚠️TS 的两个经典坑：① 同一个 PID 的 CC 不连续 → 丢包，先查网络与缓冲区；② PCR 抖动过大（> 100 ms 量级）→ 解码器时钟漂移，表现为周期性卡顿。PCR 在 PCR_PID 上，通常跟视频 PID 一致。

📝 FLV：一张张便利贴，贴出时间轴

FLV 的设计目标只有一个：让 RTMP 在浏览器插件时代尽量简单地传。它没有 MP4 那样的树状索引，而是一条条 tag 顺着写。结构简单到用几十行代码就能解析，但也因此不适合本地随机访问。

FLV 文件头 13 字节（9 字节头 + 4 字节 PreviousTagSize0）

46 4C 56 01 05 00 00 00 09 00 00 00 00
│     │  │  │           │  └────────── PreviousTagSize0 = 0
│     │  │  │           └───────────── DataOffset = 9（头长度）
│     │  │  └───────────────────────── Flags：0x05 = 有音频(0x04) + 有视频(0x01)
│     │  └──────────────────────────── Version = 1
│     └─────────────────────────────── Signature = "FLV"
└───────────────────────────────────── 文件签名：0x46 0x4C 0x56 = ASCII「FLV」
字段长度说明
TagType1 B8 = 音频，9 = 视频，18 = script（onMetaData）
DataSize3 Btag 正文长度，不含 11 字节 tag 头
Timestamp3 B低 24 位，单位毫秒
TimestampExtended1 B高 8 位，合成 32 位时间戳
StreamID3 B固定为 0
PreviousTagSize4 B上一个 tag 的“11 + DataSize”，用于反向校验

视频 tag 的第一个字节高 4 位是帧类型（1 = 关键帧，2 = 普通帧），低 4 位是编码 ID（7 = AVC）。AVC 还有 AVCPacketType（0 = 序列头 SPS/PPS，1 = NALU，2 = 流结束）和 3 字节有符号 CompositionTime——它就是 MP4 里的 ctts 偏移，用毫秒表示。没有它，B 帧的显示顺序就错了。

# 把本地 MP4 推到 RTMP（FLV 是 RTMP 的默认封装）
ffmpeg -i in.mp4 -c copy -f flv rtmp://127.0.0.1:1935/live/test

# HTTP-FLV 输出（很多直播服务器支持）
ffmpeg -i in.mp4 -c copy -f flv http://127.0.0.1:8080/live/test.flv
🔍FLV 时间戳是 32 位毫秒：理论上约 49.7 天回绕（2³² ms）。长时间不重启的直播服务要处理回绕，否则会出现“时间倒流”、播放器卡死或疯狂追帧。

⚖️ 四种容器对比：各有各的“合理场景”

没有最好的容器，只有最合适的场景。选择时优先看三件事：要不要随机访问、网络稳不稳、浏览器/播放器认不认。

要“秒开 + 可拖”

点播用 MP4 + faststart；大规模点播用 fMP4 + CDN 分片。别把长 GOP 的 TS 直接丢给浏览器。

要“弱网还能看”

TS 的固定包长与 CC 让丢包检测很便宜，但真正抗丢包靠的是 FEC/重传。TS 只是让错误可被发现。

要“最低延迟直播”

RTMP/FLV 或 WebRTC。FLV 的 tag 开销随帧变大而摊薄，但 49.7 天的时间戳回绕要自己处理。

⏱️ 时间戳与音画同步：三套刻度怎么对齐

音画不同步，十有八九不是“解码器坏了”，而是时间刻度换算错了。MP4 里至少有三套刻度：mvhd.timescale（全局，常见 1000）、视频 mdhd.timescale（常见 90000）、音频 mdhd.timescale（常见 48000）。每个样本的时间都以自己轨道的刻度表示。

t（秒） = sample_time（ticks） / mdhd.timescale　　PTS = DTS + ctts.sample_offset

以 30 fps 视频为例：90 kHz 下每帧 sample_delta = 3000；第 100 帧的 DTS 是 300000 tick，也就是 3.333 秒。音频 AAC 一帧 1024 个采样，48 kHz 下每帧 1024 tick（21.33 ms）。两套刻度必须各自换算成秒，才能比较谁早谁晚。

现象时间戳层面的原因验证方法
B 帧播放顺序乱ctts 缺失或用了 version 0 存负偏移ffprobe -show_packets 看 pts_time 与 dts_time 是否成对出现
整体早/晚几百毫秒elst 编辑列表未应用，或首帧 CTS 非零对比首帧 pts_time 与容器 start_time
越播越不同步音频 timescale 写错（如把 48000 写成 44100）看 mdhd.timescale 与 ffprobe 的 time_base
拖动后不同步seek 落在非关键帧，重建参考链断裂检查 stss；确认 seek 目标前有 IDR
 
# 逐包查看 PTS / DTS（视频）
ffprobe -select_streams v -show_packets \
  -show_entries packet=pts_time,dts_time,flags,size in.mp4

# 查看轨道时间基
ffprobe -show_streams -show_entries stream=codec_type,time_base,start_time,duration
💡修复优先级：先确认“时间戳是否正确”（容器问题），再确认“解码是否按 PTS 输出”（播放器问题）。用 ffmpeg -c copy 重封装一次，如果同步恢复正常，问题就在原容器的索引/时间戳，而不是编码。

🍰 HLS / DASH：把书切成小册子

HLS 的本质是“把整本书切成几秒一册，再给一张借阅清单”。客户端先拿 m3u8，按顺序取分片；每片都能独立起播，所以能适配不同码率、能在 CDN 边缘缓存。代价是分片边界带来额外请求与延迟。

#EXTM3U
#EXT-X-VERSION:7
#EXT-X-TARGETDURATION:4
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-MAP:URI="init.mp4"          ← fMP4 必须有初始化段
#EXTINF:4.000,
seg0.m4s
#EXTINF:4.000,
seg1.m4s
#EXTINF:4.000,
seg2.m4s
#EXT-X-ENDLIST
# 生成 4 秒一片的 HLS（TS 分片）
ffmpeg -i in.mp4 -c copy -hls_time 4 -hls_playlist_type vod out.m3u8

# 生成 fMP4 分片（CMAF 风格）
ffmpeg -i in.mp4 -c copy -hls_segment_type fmp4 \
  -hls_time 4 -hls_playlist_type vod out_fmp4.m3u8

TS 分片与 fMP4 分片

TS 分片每片都自带 PAT/PMT，能独立解码，兼容性最好；fMP4 分片依赖 init 段，体积更小、便于与 DASH 复用。两者都能被 HLS 清单描述。

低延迟靠什么

LL-HLS 用 EXT-X-PART 把一片再切成 0.5–1 秒的小块，配合阻塞式请求降低等待；DASH 侧对应 chunked CMAF。代价是请求数与服务器压力上升。

注意：#EXT-X-TARGETDURATION 必须是不小于所有 #EXTINF 的整数秒。写小了，部分播放器会直接拒绝加载清单。

🧮 体积与开销：把“感觉”换成数字

估算存储与带宽只需要一个公式。真正容易出错的是单位：码率用 bit/s，文件大小用 Byte，中间差 8 倍。

16 Mbps120 MB7.2 GB57.6 GB4K 点播

封装开销有多少

TS：每个 188 字节包只有 184 字节载荷，固定开销 4/188 = 2.128%。按 30 fps、每帧 2400 字节计算，一帧要切成 14 个包（13×184=2392，剩 8 字节进第 14 个包），封装后 14×188 = 2632 字节，多出 232 字节，约 9.7%——因为最后一包没装满。FLV：每 tag 11 字节头 + 4 字节 PreviousTagSize，2400 字节的帧开销约 0.63%。MP4：stsz 每样本 4 字节、stco 每 chunk 4 字节，通常低于 0.1%。

🔍别忽略索引本身的体积：4 万帧的 30 分钟视频，仅 stsz 就要 16 万字节，加上 stco/stsc/stts 通常是几百 KB。相比之下，TS 的 2% 固定开销在 4 Mbps 下一小时约 38 MB，哪个更贵要按场景算。

🛠️ 排错清单：从症状回到箱子

⏱️ 时间刻度手工演算：把三张表算成一条时间线

时间戳不是文件里直接写好的“第几秒”，而是用刻度尺量出来的。mdhd.timescale 是这把尺子的刻度密度，stts 是每段多长，ctts 是显示顺序相对解码顺序的补偿。三者一乘一加，才得到 PTS。

公式很短，但要分清两个时钟：秒 = tick / timescale。视频轨道常用 90000，音频用采样率（48000）。mvhd 的 timescale 只用于“整部影片”的时长与 elst，不参与单帧换算——这是最常见的误用。

例：一个 30 fps 视频轨，含 2 个 B 帧

设 mdhd.timescale = 90000，stts 只有一项 (count=4, delta=3000)：每帧 3000 tick，即 3000/90000 = 33.33 ms，正好 30 fps。编码器按“解码顺序”交付样本，但人眼要按“显示顺序”看，于是 ctts 记录每个样本该往后挪多少：

样本（解码序）DTS（tick）ctts 偏移PTS = DTS + 偏移实际呈现顺序帧类型
s0000第 1 帧（0 ms）I
s13000+60009000第 4 帧（100 ms）P
s26000−30003000第 2 帧（33 ms）B
s39000−30006000第 3 帧（66 ms）B

这张表解释了三个常见现象：

  • 为什么 P 帧排在 B 帧前面交付：B 帧要靠前后两个参考帧才能解，P 帧（s1）必须先解码出来。
  • 为什么 ctts 会出现负数：s2、s3 的 PTS 比 DTS 小。ISO 14496-12 里 ctts 的 version 0 只允许非负偏移，所以这类文件必须写 version 1（有符号），否则解码器会把偏移读成天文数字。
  • 为什么 ffprobe 有时报 “non-monotonic DTS”：不是时间戳坏了，而是容器把 DTS 写成了 PTS 的值，播放器按单调递增去校验就会报警。
# 逐包对照 DTS / PTS / 是否为关键帧
ffprobe -select_streams v:0 -show_packets \
  -show_entries packet=pts_time,dts_time,flags,duration_time \
  -of csv in.mp4 | head -20

# 只看 ctts 是否存在（有 B 帧通常就有）
mp4box -diso in.mp4 | grep -i ctts

音频轨道的换算

AAC-LC 一帧固定 1024 个采样点，mdhd.timescale = 48000，于是 stts 每项 delta = 1024，一帧 1024/48000 ≈ 21.33 ms。音频通常没有 ctts（不需要重排），所以音频的 DTS 就等于 PTS——这也是“音画对齐以音频为主时钟”的物理原因之一。

⚠️elst 用的是两把尺子：segment_duration 用 mvhd 的 timescale，media_time 用 mdhd 的 timescale。混用会把“片头剪掉 2 秒”算成完全错误的位置。

🧩 MKV / WebM：另一种记账方式（EBML）

MP4 用“定长 box”，MKV 用 EBML——一种“可伸缩的标签”，像集装箱上贴的可撕标签：ID 和长度都可以只占 1 字节，也可以占 8 字节，全看内容有多大。好处是向前兼容（老播放器能跳过不认识的新元素），代价是解析器必须逐字节猜“这个标签有多长”。

长度怎么编出来

EBML 的 ID 和 Size 都用“首位标记法”：第一个字节里最高的那个 1 决定总长度。

1xxx xxxx1 字节：值 7 位，最大 127 01xx xxxx xxxx xxxx2 字节：值 14 位，最大 16383 001x xxxx …3 字节：值 21 位 0001 xxxx …4 字节：值 28 位

ID 也有同样的规则，但 ID 的“值”是连同标记位一起当标识符用的，所以 1A 45 DF A3 就是 4 字节 ID（文件头 EBML）。长度字段则只取标记位之后的值。

元素ID（hex）作用类比
EBML1A 45 DF A3文件头，声明 DocType 与版本外箱上的“这是 MKV”
DocType42 82值为 matroska 或 webm区分 MKV 与 WebM 的唯一硬标准

SeekHead11 4D 9B 74记录其他关键元素的位置箱内的目录索引

TimecodeScale 是 MKV 的“统一刻度”：默认 1000000 ns（= 1 ms）。Cluster 里的 Timecode 是毫秒数，SimpleBlock 里再带一个相对偏移（有符号 16 位）。所以 MKV 内部其实是“毫秒 + 相对 tick”，而不是 MP4 那种按轨道 timescale 计数。

WebM 就是 MKV 的子集：DocType 写成 webm，只允许 VP8 / VP9 / AV1 视频与 Vorbis / Opus 音频，且不允许章节等少数元素。浏览器看到 webm 才保证按 WebM 规范解析，看到 matroska 不一定能播。

# 看 MKV 的元素树（MKVToolNix 自带）

# MKV → MP4：视频音频原样复制，字幕转 mov_text
ffmpeg -i in.mkv -c:v copy -c:a copy -c:s mov_text -map 0 out.mp4

# 全部原样转封装（MKV 之间最安全）
ffmpeg -i in.mkv -c copy -map 0 out.mkv

# 只挑第 1 条音轨 + 第 1 条字幕，并设为默认
ffmpeg -i in.mkv -map 0:v:0 -map 0:a:0 -map 0:s:0 \
  -c copy -disposition:a:0 default out.mkv

ffmpeg -i in.mp4 -vf "subtitles=sub.srt" -c:a copy out.mp4

disposition 决定“默认打开哪个抽屉”：default 默认轨、forced 强制显示（常用于“外语对白才出字幕”）、commentary 评论音轨、hearing_impaired 听障辅助。这些只是标志位，不改变数据本身，转封装时能原样带过去。

🔍判断“字幕为什么不显示”：先 ffprobe -show_streams -select_streams s 看有没有字幕流；再看 disposition 是否为 default；最后看播放器是否支持该编码（尤其 MP4 里的 ASS 会被直接忽略）。

📡 TS 连续性计数（CC）诊断：4 个 bit 抓丢包

TS 的每个包都有 4 bit 的 continuity_counter，像传送带上的编号贴纸：同一个 PID 每来一个带数据的包就 +1，到 15 回绕到 0。丢了一个包，编号就会跳；收到重复包，编号就停。它是整条链路里最便宜、最有效的丢包探测器。

sync8 bit，固定 0x47 TEI1 bit，传输错误 PUSI1 bit，负载单元起始 priority1 bit PID13 bit，流标识 TSC2 bit，加扰控制 AF2 bit，有无适配字段 CC4 bit，0-15 循环

关键细节：只有带负载的包才让 CC 递增。纯适配字段的包（AF=10 或 11 且无 payload）CC 保持不变。所以看到“编号原地不动”不一定有问题，先确认那个包到底有没有带数据。

CC 现象可能的原因怎么确认后果
正常 +1（15→0 回绕）无异常——
跳了 2 以上中间丢包 / 网卡丢帧 / 交换机拥塞看同 PID 前后是否缺一帧 PES画面局部花屏，音频咔嗒声
与上一个包相同重复包（重传或抓包重复）对比两包的 payload 是否一致一般无害，但会让计数失真
乱序多路径、负载均衡乱序按 PID 排序后重放解码器丢弃或报错
跳号但带 discontinuity 标志码流切换、加扰变化看 adaptation_field 的 discontinuity_indicator合法，不算故障
 
# 复制解码一遍，让 ffmpeg 把异常打出来
ffmpeg -i in.ts -c copy -f null - 2>&1 | Select-String -Pattern "continuity|corrupt|discontinuity"

# Linux / macOS 等价写法
ffmpeg -i in.ts -c copy -f null - 2>&1 | grep -Ei "continuity|corrupt|discontinuity"

# 看每个 PID 的包数与时间跨度（判断哪路流在丢）
ffprobe -show_packets -show_entries packet=stream_index,pts_time -of csv in.ts | sort | uniq -c | head

工程上还有两个“配套检查”，和 CC 一起看能快速定位：

  • PCR 间隔：规范建议不超过 100 ms。PCR 缺失或间隔过大，接收端时钟会漂移，表现为音画缓慢错位。
  • PES 长度与时间戳：同一 PID 里 PTS 突然倒退，通常是上游重连或切台，不是解码器的问题。
⚠️CC 跳号不等于“一定丢包”：编码器在网络抖动时可能主动插入 discontinuity 标志后重置计数。先看标志位，再下结论；另外，用 UDP 抓包时抓包点本身也可能丢，别把“抓包机丢的”算到业务头上。
