🧠 为什么浏览器能本地解析 File API · ArrayBuffer · 零上传

把它想成一个快递分拣中心：文件是刚送到的包裹，浏览器先拿到一张“面单”（文件对象），再剪开纸箱取出里面的字节（ArrayBuffer），最后按快递单上的格式规则逐层清点。整个过程在本地完成，包裹不需要再寄回总部（服务器）。

网页里的 File 对象只是指向本地磁盘的一个句柄。用户选择或拖入文件后，JavaScript 可以调用 file.slice() 和 arrayBuffer() 读取字节；读到的是一段 Uint8Array，之后所有解析都只是按固定规则做数组下标、移位和查表。没有 fetch、没有上传接口，也就没有“把视频发到云端”这一步。

🔒隐私承诺：本页不向任何服务器发送文件内容。拖入文件、点击示例、粘贴报文都只触发本地 JavaScript。你可以打开开发者工具的 Network 面板验证：解析过程中没有新增请求。

为什么以前做不到？因为浏览器长期只能把文件整体读成字符串，且没有高效的二进制 API。如今 ArrayBuffer、TypedArray、DataView 都已是标配，几 MB 的文件在毫秒级就能扫完。真正的限制不是“能不能读”，而是“内存能放多大、格式有没有加密”。这些边界在最后一节细说。

📦 容器解析原理 先装订，再阅读

容器的任务像集装箱码头：它不生产货物，只负责把不同来源的货物（视频帧、音频帧、字幕）按时间顺序装进统一规格的箱子，并在箱门贴上清单。解析容器就是“读清单 → 找到每件货物 → 按时间轴摆好”。

MP4：一层套一层的 box

MP4（ISO BMFF）像一套乐高说明书：每个零件都写成“尺寸 + 类型 + 内容”，内容里还可以继续放零件。这个零件就叫 box（或 atom）。任何 box 的前 8 个字节永远是：

偏移长度示例字节字段含义
0400 00 00 20size整个 box 的字节数，含头部
4466 74 79 70type4 个 ASCII 字符，如 ftyp、moov、avcC
8size−869 73 6F 6D …payload具体内容；容器型 box 的 payload 又是若干子 box

一个真实 MP4 的开头通常是 ftyp，它只有 32 字节，却回答了“这是哪种 MP4、兼容哪些品牌”：

偏移字节字段值 / 解释
0–300 00 00 20size32 字节
4–766 74 79 70typeftyp
8–1169 73 6F 6Dmajor_brandisom（ISO 基础品牌）
12–1500 00 02 00minor_version0x00000200
16–3169 73 6F 6D 69 73 6F 32 61 76 63 31 6D 70 34 31compatible_brandsisom、iso2、avc1、mp41

阅读器只需要三条规则就能安全地走完整个文件：size 等于 1 时，真正的长度写在 type 后面的 8 字节 largesize；size 等于 0 时，这个 box 一直延伸到父容器的末尾；type 等于 uuid 时，type 后面还有 16 字节用户类型。任何 size 小于 8 且不为 0 的 box 都是畸形数据，必须立刻停在这一层——否则解析器会在原地打转，形成死循环。

MP4 的“目录”主要在 moov 里：mvhd 给整部片子的时间基与总时长；每个 trak 有 tkhd（轨道号、宽高，16.16 定点）、mdhd（媒体时间基）、hdlr（视频/音频），以及 stbl 里的索引：stsd 说明编码与配置（avc1 → avcC），stts 给出每个样本的时长，stsz 给出样本大小，stco/co64 给出块偏移，stss 标出关键帧。平均帧率就是 样本数 × 时间基 / 总 tick。

stts 的 sample_delta 是解码时间间隔，不是显示时间；遇到 B 帧时还要结合 ctts 才能还原 PTS。本页解析的是“容器骨架”，不做完整的 PTS/DTS 重排。

MPEG-TS：188 字节一节的列车

TS 像一列固定长度车厢：每节车厢正好 188 字节，车头一个 0x47 同步字节。无论里面装的是视频、音频、节目表还是空包，车厢尺寸不变，所以接收端丢了一节也能立刻找到下一节。

字节示例位域含义
047sync_byte (8)固定 0x47，用于对齐
140TEI(1) PUSI(1) priority(1) PID[12:8](5)0x40 表示 PUSI=1、PID 高位为 0
200PID[7:0] (8)PID=0，这是 PAT；PMT 常见 0x1000，视频 0x100，音频 0x101
330scrambling(2) adaptation(2) CC(4)0x30 = 未加扰、适配+载荷、连续计数 0
4A6adaptation_field_length本包适配字段长度；AP 里可能带 PCR、随机接入点等
5…10 00 00 …flags / PCR / 填充PCR flag 为 1 时，后 6 字节是 33 位 base + 9 位 extension

PID 0 的载荷里放 PAT（节目关联表），告诉你“1 号节目的 PMT 在 PID 0x1000”；PID 0x1000 的 PMT 再列出每个基本流的 stream_type 与 PID：0x1B 是 H.264，0x24 是 HEVC，0x0F 是 AAC，0x03/0x04 是 MPEG 音频，0x02 是 MPEG-2 视频。PAT/PMT 都是“表”，带 12 位 section_length 和 4 字节 MPEG-2 CRC32；CRC 不对，表就不能信。

PCR（节目时钟参考）是接收端的节拍器：33 位以 90 kHz 计数，外加 9 位 27 MHz 扩展。它不直接参与音画同步，但解码器用它恢复系统时钟，再把 PTS 映射到墙钟。连续计数 CC 每位加一，丢包时会出现跳变；同一 PID 的 CC 不连续，往往就是网络丢包的第一个证据。

FLV：一张张便利贴

FLV 的结构像一叠便利贴：文件头写版本与偏移，之后每张标签（tag）独立记录类型、大小、时间戳和内容，末尾再贴一张“上一张的大小”，方便倒着检查。

字段长度示例说明
Signature346 4C 56FLV
Version / Flags1 + 101 05版本 1；0x05 表示同时有音频和视频
DataOffset400 00 00 09头长度，通常 9
PreviousTagSize0400 00 00 00第一个 tag 之前的占位
TagType1128 音频 / 9 视频 / 18 script
DataSize300 00 A6tag 内容长度
Timestamp3 + 100 00 00 00低 24 位 + 高 8 位扩展，单位毫秒
StreamID300 00 00通常为 0

类型 18 的 script tag 里是 AMF0 编码的 onMetaData 对象，常见字段有 width、height、framerate、duration。类型 9 的视频 tag 若 codecId=7（AVC），第一个包通常是 AVC sequence header，后面跟完整的 avcC；类型 8 的音频 tag 若 soundFormat=10（AAC），第一个包是 AAC sequence header，后面跟 2 字节左右的 ASC。

Matroska / WebM：可扩展的树

EBML 像一棵可以随时加枝的目录树：每个元素由“ID + 长度 + 数据”组成。ID 和长度都用变长整数（vint）表示——开头连续 0 的个数决定这个整数占几字节，长度字段还要把最前面的标记位去掉。

字节含义
1A 45 DF A3EBML 头元素的 ID（4 字节）
A3长度 vint：0xA3 → 去掉最高标记位后是 0x23，即 35 字节
42 86 81 01EBMLVersion：ID 0x4286，长度 1，值 1
42 82 88 6D 61 74 72 6F 73 6B 61DocType = “matroska”（8 字节 ASCII）
18 53 80 67Segment 的 ID，下面挂 Info、Tracks、Cluster

Info 里的 TimestampScale 给出“一个 tick 多少纳秒”（常见 1,000,000，即 1 ms），Duration 是浮点 tick 数，两者相乘再除以 1e6 就是时长毫秒。轨道在 Tracks/TrackEntry 中：CodecID 是字符串（如 V_MPEG4/ISO/AVC、A_AAC），Video/PixelWidth 与 PixelHeight 给分辨率，Audio/SamplingFrequency 与 Channels 给音频参数。CodecPrivate 往往就是 avcC 或 ASC。

⚠️四种容器的共同点是“先声明长度或索引，再放数据”，差别在于索引粒度与容错方式。MP4 假设文件完整可随机访问；TS 假设随时可能丢包，所以每个包自带同步与 PID；FLV 结构最简单；MKV 最灵活，但解析器必须严格防止 vint 长度为 0 或递归过深。

🎞️ 码流解析原理 位流是一份说明书

容器告诉你“第几秒有哪一帧”，码流告诉你“这一帧怎么还原成画面”。SPS 像乐高说明书的第一页：它不拼积木，只声明“这套积木有多大、用什么颜色、最多能拼几层”。解析码流，就是把这页说明书上的缩写逐位翻译回人话。

H.264 SPS 与 Exp-Golomb

SPS 是 H.264 的序列参数集，通常藏在 NAL 单元里，NAL 头是 0x67（type 7）。SPS 的字段大多用 ue(v)（无符号指数哥伦布）编码：先数前导 0 的个数 n，再读 n 位，值等于 2ⁿ − 1 + 读到的数。所以：

码字n解码值用途示例
100sps_id = 0、crop 偏移 = 0
01011max_num_ref_frames = 1
01112pic_order_cnt_type = 2
0010023某些扩展字段

一段 1280×720、Baseline、level 3.1 的 SPS 原始字节（含 NAL 头）是：67 42 00 1F F4 02 80 2D C8。去掉 NAL 头后逐字段解码：

字段值解读
profile_idc66（0x42）Baseline Profile
constraint_set flags0没有额外的约束位
level_idc31Level 3.1，约 1280×720@30 的常见档位
seq_parameter_set_id0（ue）第 0 号参数集
log2_max_frame_num_minus40（ue）→ 4frame_num 用 4 位
pic_order_cnt_type0（ue）POC 使用 LSB 计数
log2_max_pic_order_cnt_lsb_minus40（ue）→ 4POC LSB 用 4 位
max_num_ref_frames1（ue）最多 1 个参考帧
pic_width_in_mbs_minus179（ue）→ 80 宏块80 × 16 = 1280 像素
pic_height_in_map_units_minus144（ue）→ 45 宏块45 × 16 = 720 像素

frame_cropping_flag0不做裁剪，显示宽高等于编码宽高
vui_parameters_present_flag0这段示例没有 VUI；真实文件常见 timing 信息

如果 VUI 的 timing_info_present_flag 为 1，会读到 32 位 num_units_in_tick 和 32 位 time_scale，逐行视频的帧率约为 time_scale / (2 × num_units_in_tick)。裁剪则要按色度格式换算：4:2:0 时，左/右偏移乘以 2，上/下偏移乘以 2（逐行时）。所以同一个“1920×1088 编码宏块”可能通过裁剪显示成 1920×1080。

avcC 是 MP4/FLV 里存放 SPS/PPS 的配置记录。真实 24 字节示例：01 42 00 1F FF E1 00 09 67 42 00 1F F4 02 80 2D C8 01 00 04 68 CE 3C 80。开头 01 是版本，42 00 1F 是 profile/compat/level，FF 的低 2 位表示 NALU 长度字段为 4 字节，E1 的高 3 位清零、低 5 位为 1 组 SPS，随后是 2 字节长度和 SPS；PPS 同理。

AAC AudioSpecificConfig

AAC 的 ASC 像一张快递面单：只写三件关键事——什么档次的编码器、采样率多少、几个声道。它的开头是固定的位域：5 位 audioObjectType、4 位 samplingFrequencyIndex、4 位 channelConfiguration。

字段位宽示例 0x12 0x10含义
audioObjectType500010 = 2AAC LC
samplingFrequencyIndex40100 = 4查表得 44100 Hz
channelConfiguration40010 = 2立体声（2 声道）
后续 GASpecificConfig—000…frameLengthFlag、dependsOnCoreCoder、extensionFlag

采样率索引表为 [96000, 88200, 64000, 48000, 44100, 32000, 24000, 22050, 16000, 12000, 11025, 8000, 7350]；索引 15 表示后面跟 24 位显式采样率。AOT 为 5 或 29 时表示显式 SBR / PS，需要再读扩展采样率与核心 AOT；有些文件则在 GASpecificConfig 之后用 11 位同步字 0x2B7 声明后置 SBR。页面的解析器会尽量标注这些情况。

HEVC hvcC：先读配置，再谈 SPS

HEVC 的 hvcC 与 avcC 类似，但字段更长：1 字节版本、1 字节的 profile_space/tier/profile_idc、4 字节兼容性、6 字节约束标志、1 字节 level_idc，然后是并行度、色度格式、位深、平均帧率与 NAL 数组。页面只展开这些“配置层”字段，并统计 SPS/PPS 数组数量；HEVC SPS 内部的 profile_tier_level、short_term_ref_pic_set 语法要复杂得多，属于下一步的深水区。

📡 协议解析原理 面单、回执与电报

协议解决“怎么送”。RTP 像每件货物贴的快递面单：短、固定、每包都有；RTCP 像回执与对账单；SIP/RTSP 像电报：起始行说明意图，头部列出参数，空行之后是正文（通常是 SDP 合同）。

RTP：12 字节起步的短头

字节位域示例含义
0V(2) P(1) X(1) CC(4)80版本 2、无填充、无扩展、0 个 CSRC
1M(1) PT(7)60M=0，PT=96（动态载荷类型，H.264）
2–3sequence number (16)12 34每包加一，用于检测丢包与重排
4–7timestamp (32)00 00 0F A0采样时钟计数；视频常见 90 kHz
8–11SSRC (32)11 22 33 44同步源标识，区分同一会话的不同发送者
12…CSRC list (CC×4)—混音贡献源；CC=0 时不存在

若 X=1，CSRC 之后还有 4 字节扩展头：16 位 profile 与 16 位 length（以 32 位字为单位），再跟扩展数据。载荷偏移 = 12 + CC×4 +（X ? 4 + length×4 : 0）。P=1 时末尾还有填充字节，最后一个字节给出填充长度。RTP 头不携带“这是 I 帧还是 P 帧”，那属于载荷格式（如 H.264 的 NAL 类型）或 SDP 的 fmtp 参数。

RTCP：发送者报告与接收者报告

RTCP 包也用 32 位对齐。共同头是：版本/填充/报告计数（1 字节）、PT（1 字节）、length（16 位，单位是 32 位字，值为“总字数 − 1”）、发送方 SSRC（4 字节）。PT=200 是 SR，201 是 RR，202 是 SDES，203 是 BYE，205/206 是反馈。

字段长度SR 中的含义
NTP timestamp8高 32 位是秒，低 32 位是小数秒；把 RTP 时钟对齐到墙钟
RTP timestamp4与上面 NTP 同一瞬间对应的 RTP 时间
sender's packet count4累计发送的 RTP 包数
sender's octet count4累计发送的载荷字节数
report block24 × RCSSRC、丢包率、累计丢包、最高序列号、抖动、LSR、DLSR

RR 没有发送者信息，直接从共同头进入报告块。丢包率字段是“丢失比例 × 256”，所以页面会除以 256 再转百分比；LSR/DLSR 用来计算往返时延，是排查“网络到底慢在哪”的关键。

SIP / RTSP：文本电报

两者都是“起始行 + 头部 + 空行 + body”。起始行要么是“方法 URI 版本”，要么是“版本 状态码 原因”。SIP 的方法包括 REGISTER、INVITE、MESSAGE；RTSP 的方法包括 OPTIONS、DESCRIBE、SETUP、PLAY。状态行 SIP/2.0 200 OK 与 RTSP/1.0 200 OK 一眼可分。

# RTSP PLAY 请求（节选）
PLAY rtsp://192.168.1.10:554/live/track1 RTSP/1.0
CSeq: 5
Session: 12345678
Range: npt=0.000-

# SIP INVITE 的 body 是一份 SDP 合同
v=0
o=34020000001320000001 0 0 IN IP4 192.168.1.10
s=Play
c=IN IP4 192.168.1.10
t=0 0
y=0000000001
m=video 6000 RTP/AVP 96
a=rtpmap:96 H264/90000
a=fmtp:96 packetization-mode=1; profile-level-id=42E01F

a=control:track1

SDP 按 m= 分节：每个 m= 声明媒体类型、端口、传输协议与格式列表；a=rtpmap 把载荷类型映射到编码名与时钟频率（如 96 H264/90000）；a=fmtp 给编码器参数（如 packetization-mode=1）；a=setup 说明 TCP 主动/被动；a=control 给 RTSP 的轨道 URL；y= 在 GB28181 中表示 SSRC。没有这些映射，RTP 头里的 PT=96 根本无法解释成 H.264。

🧭排障顺序建议：先看 RTP 的 seq/timestamp/SSRC 是否连续；再看 RTCP 的丢包率与抖动；最后回到 SDP，确认 PT、时钟频率、fmtp 参数是否与发送端一致。协议字段对不上，后面怎么调播放器都没用。

🚧 能力边界与隐私 知道什么做不到

一个诚实的分析器，必须同时说清“能拆什么”和“拆不动什么”。下面是当前实现的能力边界。

✅ 真正解析（读到字段级）

  • MP4/MOV：递归 box 树、ftyp、mvhd、tkhd、mdhd、hdlr、stsd、stts、stsz、stco/co64、stss，以及 avcC/hvcC/esds 线索。
  • MPEG-TS：按 188 字节对齐扫描，PAT/PMT、stream_type、PCR、各 PID 包数、CC 错误、payload 字节。
  • FLV：头、tag 列表、onMetaData（AMF0 基础类型）、AVC/AAC sequence header。
  • Matroska/WebM：EBML ID/size 的 vint、master 元素树、TimestampScale、Duration、TrackEntry、CodecID、分辨率、采样率、声道。
  • WAV：fmt 块与 data 大小、时长；AVI：格式识别与顶层 chunk。
  • H.264 SPS（Exp-Golomb 全字段、裁剪、VUI timing）、avcC、AAC ASC、HEVC hvcC。
  • RTP/RTCP 头、SR/RR 报告块；SIP/RTSP 起始行与头部；SDP 的 m=/rtpmap/fmtp/setup/y=。

🔍 只做识别（不深入）

  • AVI 的 idx1/movi 索引与帧表；只列出顶层 chunk。
  • Ogg 的完整页表与 OpusHead/Vorbis 注释；MP3 的逐帧解析与 VBR 头；只读文件头字段。
  • HEVC SPS 的内部语法（profile_tier_level、参考图像集、RPS）；只读 hvcC 配置层。
  • 分片 MP4（fMP4）：能找到 moof，但不重建完整样本索引；moov 缺失时会给出提示。
  • 加密/DRM 内容：CENC 的 sinf/tenc 可以看见，但无法解密媒体样本。
  • HLS/DASH 清单、RTMP 握手、SRT 控制包：本页不处理，它们属于传输层/清单层。

大文件与内存

浏览器标签页的可用内存不是无限的。一个 1 GB 的视频如果整体读进 Uint8Array，仅原始字节就占 1 GB，再加上解析树与字符串，很容易触发标签页崩溃。因此：超过 100 MB 的文件会提示，并且只读取前 8 MB 做预览。这个策略对 MP4 很有效，因为 ftyp 和 moov 常在文件头部；但如果文件是“moov 在尾部”的非 faststart 布局，预览里可能只有 mdat，页面会明确提示索引缺失。

为什么不是“只读需要的部分”？浏览器可以用 file.slice(start, end) 精确读取任意区间，但通用分析的难点在于：在读到父 box 之前，你不知道子 box 在哪。递归解析本质上要顺着文件走，所以先做“头部预览”是通用性与实现复杂度的折中。

CORS：为什么不能直接填一个 URL

浏览器安全模型不允许网页随意读取别的域名下的响应。即使你用 fetch('https://example.com/a.mp4')，也必须对方服务器返回 Access-Control-Allow-Origin 等 CORS 头；否则响应对 JavaScript 不可见。更现实的是，很多媒体服务器只允许 Range 请求、要求鉴权，或根本不发 CORS 头。因此本页不提供“输入 URL 直接抓取”，而是坚持“拖入本地文件 / 粘贴字节”——这也顺带保证了隐私。

如果你确实需要分析远端文件，正确路径是：在服务端用 curl/ffprobe 抓取并导出前若干字节，或让服务端开启 CORS 并暴露 Range。浏览器端的“零上传”与“任意抓 URL”在安全模型上是冲突的，必须二选一。

🔐隐私边界：本页没有后端、没有统计脚本、没有把文件名或字节写入 localStorage。拖入的文件只在当前内存中存在，刷新页面即消失。唯一的外部链接是页脚的 GitHub 仓库地址，与解析功能无关。
