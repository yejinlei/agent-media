📞 信令层选型：WebSocket / XMPP / HTTP 对比

信令层是 WebRTC 的"快递单传递方式"：Offer/Answer SDP 和 ICE 候选必须通过它让两端互相看到。WebRTC 规范不规定用什么信令协议——WebSocket、XMPP、SIP、HTTP REST、甚至 IM 消息里贴一个 Base64 都能当信令，这正是为什么"WebRTC 工程"的第一决策通常是"信令怎么搭"。

方案方向优点缺点典型实现
WebSocket (RFC 6455)双向 / 长连接浏览器原生 API、低延迟、支持二进制；HTTP/1.1 升级而来，防火墙友好需要服务器端实现信令路由；连接断开重连逻辑需自己写Node.js ws + 任意后端；Socket.IO 做自动降级
Socket.IO双向 / 自动降级WebSocket + Ajax 长轮询 + iframe stream 自动选最优；断线重连、房间/命名空间概念现成不是原生 WebSocket（有协议开销）；生产环境要注意命名空间与鉴权开源 WebRTC 教程最常见选择
SSE（Server-Sent Events）单向：服务器→浏览器浏览器 EventSource 极简、重连自动；仅需服务器 push 事件浏览器→服务器方向必须另搞（通常还得配一个 REST POST）；只能文本事件只有通知场景；不推荐做 WebRTC 信令
XHR/AJAX 长轮询双向 / 慢无需升级、任何 HTTP 服务器都支持每个请求都有开销；高频消息时服务器连接耗尽WebSocket 不可用时的兜底
Comet双向 / 混合基于 iframe 或 BOSH 的双向流式；老浏览器唯一选择iOS 低版本 Safari 不支持 iframe stream；需要特殊 Content-Type 处理BOSH (XEP-0124) 用于 XMPP over HTTP
XMPP / SIP双向 / 开放协议成熟的 Presence / PubSub / Room 能力；XMPP over WebSocket 直接在浏览器里跑引入完整 IM / SIP 栈过重；浏览器端 JS 库维护成本高Jitsi 用 XMPP (Prosody)；Openfire / Prosody 服务器
HTTP REST（POST 轮询）单向 / 拉完全靠标准 HTTP；任何 CDN/LB 都能处理；鉴权用标准 Cookie/Token必须轮询才有新消息；浏览器→服务器方向靠 POST 丢 SDPSFU 网关（Janus）HTTP REST API
HTTP2 / HTTP3双向 / 多路HTTP2 server push、多路复用；HTTP3 基于 QUIC；WebTransport 替代 WebSocket生产环境还不普遍；WebTransport API 仍在稳定中未来方向

选型建议（一句话）

多数场景 WebSocket + 自建信令服务器 够用；需要自动降级/断线重连 Socket.IO；需要完整 IM/Room 能力 XMPP over WebSocket；SSE 不推荐做信令——因为信令必须双向。

# 极简 Node.js + ws 信令服务器
const { WebSocketServer } = require('ws');
const rooms = new Map();
const wss = new WebSocketServer({ port: 8888 });
wss.on('connection', (ws) => {
  ws.on('message', raw => {
    const msg = JSON.parse(raw);
    if (msg.type === 'join') {
      if (!rooms.has(msg.room)) rooms.set(msg.room, []);
      rooms.get(msg.room).push(ws);
      ws.room = msg.room; ws.userId = msg.id;
    } else {
      rooms.get(ws.room).forEach(other => {
        if (other !== ws) other.send(raw.toString());
      });
    }
  });
});

🎯 JSEP 状态机：Offer/Answer 的六态流转

JSEP（JavaScript Session Establishment Protocol，RFC 8829）定义了 RTCPeerConnection 的状态图。核心是六个 signalingState：stable（空闲）、have-local-offer（我发出了 offer）、have-local-pranswer（收到对端 offer 我正在组装 answer 但还没发给对端——很少直接用到）、have-remote-offer（收到了对端 offer）、have-remote-pranswer（我发出了 answer 但对端还没确认）、closed（连接已关闭）。Offer 端和 Answer 端走的是两条对称路径，同时只能有一个 offer 在飞，否则会触发协商冲突需要 renegotiation。

⚠️同时发 offer 怎么办：两端在 stable 状态同时 createOffer，就会同时发出两个 offer，双方都进入 have-remote-offer 但 setLocalDescription(offer) 会被拒。Chrome 有"ICE foundation 字段较小者当 controlling 端"的仲裁规则，失败端要放弃 offer、等对方 answer 再协商。

📝 SDP 完整结构：每一行都有意义

SDP（Session Description Protocol，RFC 8866）是 WebRTC 协商的"菜单"——双方各自把自己"能提供什么"塞进一个文本块里，发给对方，对方看到相同字段就选一个。格式固定：k=v，按 会话级 → 媒体级 分两大块。

会话级字段（全局描述，1 份）

行含义WebRTC 里必看
v=0SDP 版本号（永远是 0）确认有效 SDP
o=username sessid sessversion…会话创建者 + 会话 ID（唯一）+ 版本（每次重协商 +1）sessid 识别这是哪一轮协商
a=group:BUNDLE 0 1多轨道打包——让音频/视频/数据走同一个 socket + 同一个 DTLS 会话现代 WebRTC 必看
a=msid-semantic: WMS…MediaStream ID 与媒体级行的映射Chrome 用来匹配 local Stream / 远端 Stream

媒体级字段（每种媒体一份）

行含义WebRTC 里必看
m=video 9 UDP/TLS/RTP/SAVPF 96 97媒体类型 · 端口 · 传输层 · 载荷类型端口=0 表示"我拒绝这路媒体"；载荷类型是动态号（96–127），具体编码看 a=rtpmap
a=rtpmap:96 H264/90000PT 96 对应 H.264、时钟 90kHz两端共同编码的唯一来源——offer 端列 N 种，answer 端只保留重叠的
a=fmtp:96 packetization-mode=1;profile-level-id=42E01E编码参数（H.264 profile/level/packetization-mode）Chrome 通常只收 packetization-mode=0 或 1
a=rtcp-muxRTCP 和 RTP 用同一个端口（省一个 socket）现代 WebRTC 默认有
a=fingerprint:sha-256 AA:BB:…DTLS 证书 SHA-256 指纹——两端必须一致必看——信令通道被中间人篡改就永远锁不上
a=setup:actpass/passive/activeDTLS 握手角色：offer 端写 actpass，answer 端选一个两端都是 active 会握手冲突
a=candidate:…ICE 候选（可以在 SDP 里一次性给，也可以单独 trickle 发）候选里的 typ / priority 决定穿透路径
a=ice-ufrag / ice-pwdICE 鉴权的用户名片段 + 密码两端必须用同一套

⚡ UDP 媒体机制：NACK / RTX / FEC / JitterBuffer / NetEQ

WebRTC 媒体路径首选 UDP——快、无连接、丢包不影响其他包。但 UDP 天生不可靠，WebRTC 一整套"在 UDP 上逼近 TCP 可靠性但不牺牲实时性"的工具链：

机制解决什么问题工程上的意义
NACK (RFC 4585 RTPFB)接收端报告丢了哪些 seq 号接收端每 100-200 ms 汇总一次丢包
RTX (RFC 5562)发送端给丢包换个 SSRC 重发RTX SSRC 通常是 (原始 SSRC + 1)；需要 SDP 里 a=ssrc-group:FID
FEC (ULPFEC / FlexFEC)发送端用异或/多项式附加冗余包Chrome 支持 FlexFEC 但默认关；带宽多的时候 10-20% 冗余显著降低丢包敏感度
JitterBuffer把到包按 seq 重排、缓存几百 ms 再解码视频 ~300 ms，音频 ~500 ms；缓冲太长增加延迟，太短声音花屏
NetEQ音频抖动缓冲 + 丢包隐藏NetEQ 有 PLC（Packet Loss Concealment）算法；丢包率 <5% 时听不出来
拥塞控制 (GCC / BBR / SCReAM)根据 TWCC/REMB 反馈自适应降码率GCC 是 WebRTC 首选；REMB（旧版）已被 TWCC 取代
💡关键帧请求 PLI：丢了一个 P 帧后续全部断 → 画面花屏 → 立即发 PLI 请求对端重发关键帧。这就是为什么低延迟直播 GOP 要短（1-2 秒）。

🔒 SRTP / SRTCP 加密与密钥派生

WebRTC 要求媒体加密（Chromium 里明文 RTP 默认就被拒绝）。机制：DTLS 握手结束协商出 Master Key（30 字节） + Master Salt（14 字节），双方用 HKDF 派生出 4 把会话密钥（客户端→服务器 RTP、RTCP、服务器→客户端 RTP、RTCP）。每个 RTP/RTCP 包发送前用 AES-CM 加密 payload + HMAC-SHA1 加认证标签，接收端先验 MAC、再检查序列号重放（窗口 64 KB）、最后解密。

📦 SCTP / DCEP：DataChannel 为什么不直接用 TCP

DataChannel 走 SCTP over DTLS over UDP 而不是 TCP。原因：TCP 是单车道（一条连接所有消息必须顺序到），而 DataChannel 每条子通道可以独立配置 ordered/unordered + reliable/unreliable——你可以让"游戏位置同步"走不可靠（丢几个无所谓）、让"聊天消息"走有序可靠，都在同一个 SCTP 连接上。

多流复用

SCTP 把一条连接拆成多个独立 stream，每个 stream 自己排序/丢包恢复。10 条 DataChannel 就是 10 个 stream，互不阻塞。

部分可靠性

RFC 3758 扩展：每条 stream 可以指定 maxRetransmits 或 lifetime，超过就丢——游戏同步常用 maxRetransmits: 0。

DCEP 协商

DataChannel 参数（label、ordered、maxRetransmits）通过 DCEP (RFC 8832) 交换，用 SCTP DATA BLOCK 传。

🔐 DTLS vs TLS：握手差异与为什么必须用 DTLS

TLS 给 TCP 加密，DTLS 给 UDP 加密（RFC 4347）。WebRTC 的 UDP 媒体路径走不了 TLS（TLS 依赖 TCP 的有序/重传语义），所以 DTLS 是唯一选择。协议上 DTLS ≈ TLS 1.3 的握手 + UDP 适配层（Timer 重传、Transaction ID 乱序容忍、epoch 号）。

对比TLS 1.3DTLS 1.2
底层传输TCP（可靠有序）UDP（不可靠无序）
丢包处理TCP 自动重传DTLS 自己维护 Timer + Retransmit Queue
乱序容忍TCP 保证有序DTLS 用 epoch 号 + 序列号跳过已处理旧消息
证书CA 签发（验证链）WebRTC 通常自签——指纹通过 SDP 的 a=fingerprint 协商，不走 CA 链
适用HTTPS、WebSocketWebRTC；QUIC 也用 TLS 1.3 + UDP 但是"自带传输层"
🚫DTLS 证书不能随便换：两端握手时指纹必须和 SDP 里的 a=fingerprint 匹配。如果一方重启 WebRTC（证书重新生成），对方还拿着老指纹——DTLS 握手永远过不去。要么用固定证书，要么触发 ICE restart + 重新协商 SDP。

🎭 Web API 状态机：Signaling / IceGathering / IceConnection

RTCPeerConnection 有三套独立状态机，各管各的：SignalingState 管 SDP 协商（六态流转）、IceGatheringState 管候选收集（三态）、IceConnectionState 管候选连通性（七态）。三机并行，任何一个卡住都代表问题出在对应层。

SignalingState（六态）

状态含义触发
stable协商完毕createAnswer + setLocalDescription 后
have-local-offeroffer 已发出等 answercreateOffer + setLocalDescription
have-remote-offer收到 offer 等 answersetRemoteDescription(offer)
have-local/remote-pranswer临时 answer（现代实现基本跳过）极少用到
closed已关闭close()；ICE/DTLS 致命错误

IceGatheringState（三态）

  • new：刚开始
  • gathering：正在枚举 + STUN + TURN，onicecandidate 陆续触发
  • complete：所有候选收完。Trickle ICE 通常不等 complete 就发 offer/answer。

IceConnectionState（七态，最关键）

状态含义定位
new刚建立正常
checking正在 STUN 检查候选对正常，最多等 5-10 秒
connected至少一对双向可达✓ 直连成功
completed所有对检查完，至少一对可用（含 relay）连接稳定；selected pair 是 relay 说明直连没通
failed所有对全失败（含 relay）NAT 穿透彻底失败，检查 TURN
disconnected曾经通，现在丢包高心跳超时移动网络 / NAT 切换 / TURN 异常
closedPC 已 close 或致命错误重建

🧠 底层实现：Chromium / Pion / webrtc-rs

WebRTC 规范描述"该做什么"，真正实现分布在三套主流代码里：浏览器里跑的是 Chromium（Google 主导的 C++ 开源项目）；Go / Rust 世界里 Pion 和 webrtc-rs 是最受欢迎的替代品——它们可以跑在非浏览器环境（微服务、边缘网关、IoT）。

Chromium 内部架构（简化三层）

Signaling Thread

API 入口：createOffer/setLocalDescription/on* 事件回调都在这里执行。

Network Thread

ICE/STUN/TURN/DTLS/SRTP/SCTP——真正收发包、连通性检查、加密解密。

Worker Thread

媒体处理：编码/解码、JitterBuffer、NetEQ、NACK/RTX/GCC。现代 Chromium 多 Worker 并行编码多路视频。

三条线程用 PostTask 消息队列 通信，几乎没有共享内存（除了 video/audio 共享缓冲区）——这是 Chromium 架构稳定的关键。

Pion (Go)：最受欢迎的非浏览器 WebRTC

用纯 Go 重写了传输层（ICE/STUN/TURN/DTLS/SRTP/SCTP），上层 RTCPeerConnection API 与浏览器几乎一致。适合：SFU 服务器、Go 微服务里直接收发 WebRTC、CLI 工具、IoT/WASM。

webrtc-rs (Rust)：安全第一选择

用 Rust 重写（webrtc-rs/webrtc crate），API 类似 Pion 但所有底层内存/并发/加密由 Rust 所有权保护。适合：金融/医疗/军事级视频会议、嵌入式/WASM、零 GC 暂停。

🔍为什么 Pion/webrtc-rs 只写传输层：Chromium 的 MediaStream 依赖浏览器（getUserMedia、Canvas），Pion/webrtc-rs 都跳过这层直接从"帧字节"开始。如果要从 Go/Rust 拿摄像头还要接 cgo 调用 V4L2 或 VideoToolbox。
