🧭 它到底是什么：一个“翻译 + 流水线”，不是格式转换器

把 FFmpeg 想成一家进出口公司：客户拿来一个 MKV 集装箱，里面装着 H.265 的货；公司可以只换集装箱（转封装），也可以把货拆出来、翻译成另一种语言、再按新规格装箱（转码）。真正决定成本的是你让它做了哪几步，而不是你敲了多长的命令。

它由一组 C 库和三个命令行工具组成。库可以被你的程序直接调用（VLC、OBS、Chrome 的很多能力都来自它），命令行工具只是这套库的一层“现成外壳”。所以学会命令之后，再往回看 API，你会发现参数名几乎一一对应。

ffmpeg

执行转码、转封装、滤镜、推流、切片。它是“总调度”，自己不实现具体编码，只负责把解封装、解码、滤镜、编码、封装串起来。

ffprobe

只读不写，输出容器、流、包、帧的元数据。它像体检报告：不治病，但能告诉你码流的结构、时间戳、关键帧和真实帧率。

ffplay

一个极简播放器，基于 SDL。排错时用它验证“这条流到底能不能解”，比在业务播放器里猜快得多。

🔍先看清楚你手里的版本。执行 ffmpeg -version，注意第一行的版本号，以及下方 --enable-libx264、--enable-nvenc、--enable-libx265 这类编译开关。同一个命令在不同发行版上失败，八成不是命令写错，而是这个构建根本没编进对应编码器。第三方构建的具体能力以官方文档和构建日志为准。

🏭 六个库的分工：报关、翻译、搬运、加工、换尺码、调音

FFmpeg 的“分层”不是为了好看，而是为了让你可以只更换其中一层。只想换容器，就别碰解码器；只想改分辨率，就别碰封装。每一层都有自己的核心类型和生命周期，混用这些层，是内存泄漏和花屏的常见起点。

库生活化角色职责核心类型 / 入口

用命令行时，这些层被 -c:v（编码器）、-vf（滤镜）、-f（容器/协议）分别控制。用 API 时，你必须自己把它们串起来：打开输入 → 找流 → 打开解码器 → 读包 → 解码 → 处理 → 编码 → 写包 → 收尾。少任何一步，输出就会是空文件或坏文件。

⚠️“装了 FFmpeg 就什么都能转”是误解。容器支持、编码器支持、协议支持是三张不同的表。比如容器能写 AV1，不代表你的构建里有 libaom 或 libsvtav1；能解 H.265，不代表能编 H.265。先用 ffmpeg -encoders、ffmpeg -decoders、ffmpeg -formats 确认，再写命令。

📦 数据流：从总调度单到一张“写满备注的画布”

AVFormatContext 是搬家公司的总调度单：这趟活从哪来、有几件家具、每件多重。AVStream 是每件家具的清单：它是视频还是音频、用的什么时间基。AVCodecContext 是说明书：怎么拆、怎么装。AVPacket 是还没拆的压缩包裹，AVFrame 则是拆开后铺在桌上的画布——上面不只有像素，还有格式、宽高、时间戳和一行行“备注”（linesize、色彩信息）。

对象一句话理解谁分配生命周期要点
AVFormatContext整个容器的总上下文avformat_alloc_context / avformat_open_input结束用 avformat_close_input；不要手动 free 内部 streams
AVStream容器里的一条流（视频/音频/字幕）由 libavformat 创建只借用，不拥有；流参数从 codecpar 读
AVCodecParameters流的“裸参数”：编码、宽高、extradatalibavformat 填充建解码器时用 avcodec_parameters_to_context 拷进去
AVCodecContext解码器/编码器的工作实例avcodec_alloc_context3打开后要 avcodec_free_context；flush 用 send NULL
AVPacket压缩数据包 + 时间戳av_packet_alloc每次用完 av_packet_unref，否则缓冲会越积越多
AVFrame解码后的画布/音频缓冲av_frame_alloc用 av_frame_unref 复用；跨线程要 av_frame_ref

最小解码循环（省略错误处理）

#include <libavformat/avformat.h>
#include <libavcodec/avcodec.h>

AVFormatContext *fmt = NULL;
avformat_open_input(&fmt, path, NULL, NULL);
avformat_find_stream_info(fmt, NULL);

int v = av_find_best_stream(fmt, AVMEDIA_TYPE_VIDEO, -1, -1, NULL, 0);
const AVCodec *dec = avcodec_find_decoder(fmt->streams[v]->codecpar->codec_id);
AVCodecContext *ctx = avcodec_alloc_context3(dec);
avcodec_parameters_to_context(ctx, fmt->streams[v]->codecpar);
avcodec_open2(ctx, dec, NULL);

AVPacket *pkt = av_packet_alloc();
AVFrame  *frm = av_frame_alloc();
while (av_read_frame(fmt, pkt) >= 0) {
    if (pkt->stream_index == v) {
        avcodec_send_packet(ctx, pkt);
        while (avcodec_receive_frame(ctx, frm) == 0) {
            /* 这里拿到的是未压缩帧：frm->data[] / linesize[] / pts */
            av_frame_unref(frm);
        }
    }
    av_packet_unref(pkt);
}

这段代码对应命令行里的“解封装 + 解码”。它不包含缩放、编码、封装——那些是后续几个库的事。把每一步单独跑通，比一上来写完整转码器更容易定位问题。

💡AVFrame 为什么有 data[8] 和 linesize[8]？因为 YUV 常被拆成多个平面（Y、U、V 各一块），每块的行宽可能为了对齐而大于图像宽度。linesize 不是 width。按 width 逐行拷贝，画面会斜；按 linesize 偏移才是正确姿势。音频则常见多个声道平面，平面数超过 8 时用 extended_data。

♻️ 一条帧的一生：引用计数、缓冲池与 seek 后的 flush

AVFrame 更像图书馆里一本可以多人同时借阅的画册：av_frame_ref 是在借阅卡上再加一个名字（引用计数 +1），av_frame_unref 是还书；最后一个人还书，书才真正下架释放。复制 AVFrame 通常不是复制几兆像素，而是多一张借阅卡。

AVPacket 也一样。它包着压缩码流和 PTS/DTS，内部用 AVBufferRef 管理一块带引用计数的内存；av_packet_ref 复制的是“包的结构 + 引用”，不是码流本身。这也解释了两件事：解码器可以几乎零拷贝地把包送进流水线；而滤镜在改像素前必须先确认这块内存没人共享，否则就得 av_frame_make_writable 做写时复制（copy-on-write）。

AVPacket：压缩包裹

装的是编码后的码流、PTS/DTS、stream_index 和 flags。它是“还没拆的快递”，本身可以共享；av_packet_unref 只是还引用，不是删文件。

AVFrame：未压缩画布

装的是像素或音频采样，以及 data[]、linesize[]、format、sample_rate 等“备注”。像素内存挂在 buf[] 的引用计数上，不在结构体里。

AVBufferRef：借阅卡

真正被复制的对象。引用 +1 时数据不动，引用 −1 时数据也不动；只有计数归零，底层 AVBuffer 才被释放。

引用计数 API：谁加一，谁减一

API做什么关键约束
av_frame_alloc只分配 AVFrame 结构体，像素内存还是空的结束用 av_frame_free，它会先 unref
av_frame_get_buffer按像素格式、宽高、对齐方式分配真正的一帧分配后这帧的 buffer 引用计数为 1
av_frame_ref(dst, src)让 dst 共享 src 的底层 buffer，引用 +1dst 必须已 alloc 且不持有别的数据，否则先 unref
av_frame_clone(src)alloc + ref 的合体，返回一个新结构体失败返回 NULL；用完 av_frame_free
av_frame_move_ref(dst, src)把引用整体搬家，src 被清空常用于“交棒”，少一次加一减一
av_frame_make_writable若 buffer 被别人共享，先复制一份再让你写滤镜改像素前必须调用，否则会改到别人的帧
av_frame_unref引用 −1；减到 0 才释放 buffer不释放 AVFrame 结构体本身，结构可复用
av_packet_ref / unref包的共享复制 / 归还引用跨线程投递包时优先用 av_packet_move_ref
av_buffer_pool_get从池里拿一块可复用 buffer池适合固定分辨率、高频分配的场景
 
AVFrame *dst = av_frame_alloc();
av_frame_ref(dst, src);         // 共享同一块像素，底层 refs +1
av_frame_make_writable(dst);    // 要改像素时确认独占；被共享则内部复制
...
av_frame_unref(dst);            // refs -1，不一定是 free
av_frame_free(&dst);            // 再释放结构体本身

// 更常见的“拿走一份”写法
AVFrame *copy = av_frame_clone(src);
if (!copy) { /* ENOMEM */ }

// 缓冲池：固定分辨率流水线的高频分配
AVBufferPool *pool = av_buffer_pool_init(buf_size, NULL);
AVBufferRef  *ref  = av_buffer_pool_get(pool);
...
av_buffer_unref(&ref);
av_buffer_pool_uninit(&pool);

为什么 seek 必须清空解码器，而不是只清空 packet

解码器不是无状态计算器。H.264/H.265 解码依赖参考帧队列（DPB）、运动矢量预测和环路滤波状态；它还可能有几帧延迟没吐出来。执行 av_seek_frame 只是把“读文件的指针”挪到目标关键帧，解码器内部的旧世界还在。此时直接喂新包，轻则画面花一下，重则一直用旧参考帧，输出绿块或错帧。

av_seek_frame(fmt, v_stream, target_ts, AVSEEK_FLAG_BACKWARD);
avcodec_flush_buffers(ctx);   // 清空参考帧、延迟帧与内部时间线
av_packet_unref(pkt);         // 旧包也不要留着

// 转码收尾时同样要 flush：送 NULL 让解码器把缓存的帧吐完
avcodec_send_packet(ctx, NULL);

命令行里的 ffmpeg -ss 已经替你做了这些事；写 API 时漏掉 avcodec_flush_buffers，症状通常是“seek 后第一秒花屏”“从中间开始播却出现片头画面”“时间戳突然跳回旧值”。

⚠️flush 不等于 free。avcodec_flush_buffers 清的是解码器内部状态，不释放 AVCodecContext；av_frame_unref 清的是帧的引用，不释放结构体。把这两件事混在一起，常见结果是双重释放（double free）或继续泄漏。
💡缓冲池不是“高级优化”，而是固定分辨率流水线的默认姿势。每帧都 av_frame_get_buffer 会不断向系统申请大块内存，延迟和碎片都上来了；用 AVBufferPool 让帧归还后内存回池，下一次解码直接复用。池的生命周期通常跟解码器或滤镜图走，不要跨线程随手释放。

⏱️ 时间戳：PTS 是“上映时间”，DTS 是“装车时间”

视频帧不是按拍摄顺序到达的。B 帧要参考后面的帧才能解码，所以“送到解码器的顺序”和“显示给观众的顺序”不一样。DTS（Decoding Time Stamp）是装车顺序，PTS（Presentation Time Stamp）是上映顺序。time_base 则是这把尺子的刻度：同样写 25，刻度是 1/25 秒还是 1/90000 秒，含义差 3600 倍。

t(秒) = pts × time_base.num / time_base.den　　·　　换算：av_rescale_q(pts, src_tb, dst_tb)
概念含义典型值 / 注意点
time_base时间单位的分数表示，如 1/1000 表示每个刻度 1 毫秒不同容器/流各不相同；MP4 每个 track 自声明 timescale，TS/RTP 常用 90 kHz
PTS这一帧应该被显示的时刻有 B 帧时 PTS 与 DTS 不等；没有 B 帧时通常相等
DTS这一帧应该被送进解码器的时刻必须单调不减，否则解码器/封装器会报错
AV_NOPTS_VALUE“没有时间戳”的哨兵值定义为 INT64_MIN（0x8000000000000000），不能用 0 代替
avoid_negative_ts封装时如何处理负时间戳常见取值 auto / disabled / make_non_negative / make_zero，具体以官方文档为准

最容易被忽略的是“时间基换算”。解封装拿到的是流时间基，编码器可能要求另一套，封装器又要一套。直接把 pkt->pts 原样赋给输出，短片段没事，长片段就会漂移、音画不同步，甚至出现负时间戳导致 MP4 无法写索引。

// 把输入流时间基换算成输出流时间基（写包前的标准动作）
av_packet_rescale_ts(pkt, in_stream->time_base, out_stream->time_base);

// 只做时间换算，不碰数据
int64_t us = av_rescale_q(pkt->pts, in_stream->time_base, AV_TIME_BASE_Q);

// 比较两个不同时间基的时刻
av_compare_ts(a, tb_a, b, tb_b);

# 命令行里显式处理负时间戳（示例）
ffmpeg -i in.ts -c copy -avoid_negative_ts make_zero out.mp4
⚠️负时间戳从哪来？切片、拼接、屏幕录制、以及带 B 帧的流，起点可能小于 0。MP4 的某些版本对负值不友好，于是 muxer 会把整条时间线平移。副作用是“开头几帧时间对不上”或“音画差几十毫秒”。先看 ffprobe -show_packets 的 pts_time 是否从负数开始，再决定要不要加 -avoid_negative_ts。

另外注意：新版 FFmpeg 用 -fps_mode 替代了旧的 -vsync；两者语义相近但参数值不同。写脚本时先确认版本，不要照抄五年前的博客。相关帧类型与 GOP 的细节，可以配合 编解码页 一起看。

🚢 转码与转封装：换箱子，还是拆箱重装

转封装像海关只换集装箱：货不动，只把 MKV 的箱子换成 MP4 的箱子，几分钟的视频几秒就完成，画质一字节不差。转码像海关把货拆出来、逐件检查、翻译标签、再按新规格重新装箱：耗时、耗 CPU，画质会变，但能改编码、分辨率、码率。两者最大的区别不是命令长度，而是“有没有经过解码器和编码器”。

维度转封装（-c copy）转码（重新编码）
经过的层libavformat 读出 → libavformat 写入解封装 → 解码 → 滤镜 → 编码 → 封装
CPU / 耗时很低，通常远快于实时高，取决于编码器、分辨率、preset
画质无损（码流原样搬运）有损（除非用无损编码）
能改什么容器、封装参数、部分元数据、时间戳编码格式、分辨率、帧率、码率、像素格式、音轨
常见用途MKV→MP4、TS→MP4、抽流、快速剪辑网页兼容、压缩体积、统一规格、加滤镜
 
# 只换箱子：MKV → MP4，码流原样
ffmpeg -i in.mkv -c copy out.mp4

# 视频原样，音频转 AAC（常见于网页兼容）
ffmpeg -i in.mkv -c:v copy -c:a aac -b:a 128k out.mp4

# 只保留需要的流，并加 faststart（把索引挪到文件头，边下边播）
ffmpeg -i in.mkv -map 0:v:0 -map 0:a:0 -c copy -movflags +faststart out.mp4
⚠️-c copy 不等于“万能兼容”。容器对编码有白名单：MP4 放 H.264/H.265/AV1 通常没问题，放某些老编码或非标准 tag 就可能失败；TS 对 B 帧和负时间戳更敏感；从 MKV 抽字幕到 MP4 需要额外的字幕处理。失败时先看 muxer 的报错，再决定“换容器”还是“重编码”。

🎛️ 滤镜与 filter graph：传送带上的工位

滤镜不是“加个特效”这么简单，它是一条传送带：每一帧从一端进来，经过若干工位，从另一端出去。-vf 是单进单出的简易传送带；-filter_complex 则允许你把传送带分叉、合并、甚至接上第二路输入——比如把台标叠在视频上，或者把两路音频混在一起。

写法适用特点
-vf "scale=1280:-2,fps=25"单路视频、简单串联逗号表示顺序；-2 表示按比例算高度并保证偶数
-af "aresample=48000"单路音频等价于只处理音频的 -vf
-filter_complex "[0:v][1:v]overlay=10:10[v]"多输入/多输出、分叉合并方括号是标签，必须用 -map 把结果接出去
-filter_complex "[0:v]split=2[a][b];[a]scale=1280:-2[x];[b]scale=640:-2[y]"一源多档（ABR 阶梯）split 复制帧；分号分隔滤镜链
 
# 缩放 + 固定帧率 + 锐化，给网页一个稳妥的 720p
ffmpeg -i in.mp4 -vf "scale=1280:-2,fps=25,unsharp=5:5:0.6" -c:v libx264 -crf 22 out.mp4

# 加水印：第二路是 PNG（用 -i 输入），overlay 把 logo 叠到右下角
ffmpeg -i in.mp4 -i logo.png \
  -filter_complex "[1:v]scale=120:-1[logo];[0:v][logo]overlay=W-w-20:H-h-20[v]" \
  -map "[v]" -map 0:a? -c:v libx264 -crf 22 -c:a copy out.mp4

# 两路音频混音，并统一采样率
ffmpeg -i a.mp4 -i b.m4a \
  -filter_complex "[0:a]aresample=48000[a0];[1:a]aresample=48000[a1];[a0][a1]amix=inputs=2:duration=longest[a]" \
  -map 0:v -map "[a]" -c:v copy -c:a aac out.mp4

顺序有性能含义：先 fps 降帧、再 scale 降分辨率，比反过来少处理很多帧。硬件解码得到的帧通常是 GPU 格式，直接进 scale 可能失败，需要 hwdownload,format=nv12 下载回系统内存（细节见 硬件加速页）。

🔍为什么滤镜有时比转码还慢？因为滤镜运行在未压缩帧上。1080p 一帧 YUV420 约 3 MB，25 fps 就是每秒 75 MB 的搬运量；复杂滤镜还会反复读写。能用编码器参数解决的事（码率、preset），不要用重滤镜去“补救”。

🧩 filtergraph 逐字符拆解：方括号是站名，分号是换乘线

filtergraph 像一张地铁线路图：[0:v] 是“从 0 号输入的 video 站上车”，, 是同一条线上连续经过的工位，; 是换乘到另一条线，[base] 是给这条线的终点站起个名字，后面再把它接到别的线路。看不懂符号，就会把“两个滤镜串联”写成“两个输入并联”。

先看一条完整的、带两路输入的命令。它把主视频缩放到 1280 宽、裁成 720p，再把 logo 缩到 120 宽，最后叠到右下角：

ffmpeg -i input.mp4 -i logo.png \
  -filter_complex "[0:v]scale=1280:-2,crop=1280:720:0:0[base];[1:v]scale=120:-1[logo];[base][logo]overlay=W-w-20:H-h-20[v]" \
  -map "[v]" -map 0:a? -c:v libx264 -crf 22 -c:a copy output.mp4
片段名字逐字符含义
[0:v]输入 pad 标签0 是第几个 -i 输入，v 是 video。要指定“第一条视频流”可写 [0:v:0]。
scale=1280:-2滤镜与参数scale 是滤镜名，= 后是参数；: 分隔参数。-2 表示按比例算高度，并保证是偶数。
,串联同一路数据依次经过下一个滤镜，前一个的输出直接接后一个的输入。
;并联 / 换乘结束一条滤镜链，开始另一条独立链路。链路之间不会自动连起来，必须用标签对接。
[base]输出 pad 标签给这条链的结果起名，供后面引用。标签在同一张图里只能被“生产”一次。
[base][logo]overlay多输入滤镜两个方括号依次对应 overlay 的第 0、1 个输入；overlay 把第二个画面叠到第一个上。
[v]最终输出标签图的出口。命令行必须用 -map "[v]" 把它接进输出文件。
-map 0:a?可选映射问号表示“有音频就映射，没有也不报错”；不写这段，音频会丢。
-vf简易单路语法等价于“只对主视频做一条单进单出链”，不需要写标签，也不接受多输入。
-filter_complex完整图语法多输入、多输出、分叉、合并都用它；结果的 pad 必须自己 -map。
[0:v]0 号输入的视频
→
scale=1280:-2缩放，高度自动
,
crop=1280:720:0:0按宽高与左上角裁剪
→
[base]给结果起名
;
[1:v]1 号输入的 logo
→
scale=120:-1宽度 120，高度按比例
→
[logo]第二路标签
;
[base][logo]两路同时进 overlay
→
overlay=W-w-20:H-h-20右下角留 20 px
→
[v]最终输出 pad

三条硬规则：第一，标签必须唯一，同一个名字被两个滤镜输出会直接报错；第二，所有 pad 最终都要接上，悬空的输出会让滤镜图配置失败；第三，参数里的逗号、冒号如果属于表达式，要用 \, 或引号保护，否则会被当成滤镜分隔符。比如场景检测要写 select=gt(scene\,0.3)。

经典图 1：split —— 一源多档

split 像复印机：同一帧进来，复印成多份，分别走不同的缩放工位。它不会自动帮你输出成多个文件，你仍然要用 -map 把每份接到对应输出。

ffmpeg -i input.mp4 \
  -filter_complex "[0:v]split=3[a][b][c];[a]scale=1920:-2[v0];[b]scale=1280:-2[v1];[c]scale=854:-2[v2]" \
  -map "[v0]" -c:v libx264 -crf 20 -c:a copy out_1080.mp4 \
  -map "[v1]" -c:v libx264 -crf 20 -c:a copy out_720.mp4 \
  -map "[v2]" -c:v libx264 -crf 20 -c:a copy out_480.mp4

这条命令把三路接进三个输出文件。注意每条 -map 后面的编码参数只作用于紧跟的那个输出；不要在第一个输出后面就把编码参数“用完”。

经典图 2：overlay —— 两路画面的叠放

overlay 像把一张贴纸盖在海报上：第一个输入是底板，第二个输入是贴纸；x:y 决定贴纸左上角的位置。W/H 是底板宽高，w/h 是贴纸宽高，所以 W-w-20 就是“贴到右边、留 20 像素”。

ffmpeg -i input.mp4 -i logo.png \
  -filter_complex "[1:v]scale=120:-1[logo];[0:v][logo]overlay=W-w-20:H-h-20[v]" \
  -map "[v]" -map 0:a? -c:v libx264 -crf 22 -c:a copy output.mp4

经典图 3：amix —— 多路音频合并

amix 像调音台把所有话筒推到同一个总线：每个输入先统一采样率与声道布局，再混合。duration=longest 表示“以最长的那路为准”，短的那路结束后静音补足；first 则以第一路时长为准。

ffmpeg -i input.mp4 -i music.m4a \
  -filter_complex "[0:a]aresample=48000[a0];[1:a]aresample=48000[a1];[a0][a1]amix=inputs=2:duration=longest[a]" \
  -map 0:v -map "[a]" -c:v copy -c:a aac -b:a 128k output.mp4

如果两路响度差太多，先给每一路加 volume=0.7 之类的增益再 amix；只想让一路在特定时间段出现，用 adelay 或 atrim 先裁好，别指望 amix 自己对齐时间。

💡滤镜顺序就是性能顺序。fps 降到 10 再 scale 到 360p，比先 scale 再丢帧少处理约 60% 的像素。把“变少”的工位放在“变贵”的工位前面，是滤镜图最便宜的优化。
⚠️不要靠“自动转换”兜底。滤镜对像素格式、采样率、声道布局有要求，FFmpeg 会在某些接缝处自动插入 format/aresample，但不是所有地方都兜得住。显式写 format=yuv420p、aresample=48000，比事后对着花屏猜要省时间。

🍳 常用命令配方：切片、截图、录屏、推流、拼接、抽音轨

下面这些命令不是背下来的，而是从“输入 → 处理 → 输出”推出来的。注意参数位置：写在 -i 前的是“输入选项”，写在后面的是“输出选项”。位置错了，参数就会作用到另一个文件上。

# 快速切片：-ss 在 -i 前 = 先跳到附近关键帧，可能不准，但很快
ffmpeg -ss 00:01:00 -to 00:02:00 -i in.mp4 -c copy out.mp4

# 精确切片：-ss 在 -i 后 = 解码到该时刻再切，慢，但帧准
ffmpeg -i in.mp4 -ss 00:01:00 -t 00:01:00 -c:v libx264 -crf 20 -c:a aac out.mp4

# 切成 HLS：4 秒一片，GOP 与切片对齐，避免每片都从非关键帧开始
ffmpeg -i in.mp4 -c:v libx264 -crf 20 -g 100 -keyint_min 100 -sc_threshold 0 \
  -f hls -hls_time 4 -hls_playlist_type vod \
  -hls_segment_filename "seg%03d.ts" index.m3u8

-c copy 只能切在关键帧上；要“指哪切哪”，就得重编码。-g 与 -hls_time 不匹配时，切片器会等下一个关键帧，实际时长会漂。

# 截一张图（-frames:v 1 明确只要一帧）
ffmpeg -ss 00:00:05 -i in.mp4 -frames:v 1 -q:v 2 shot.jpg

# 截第 100 帧（select 的逗号要转义）
ffmpeg -i in.mp4 -vf "select=eq(n\,100)" -fps_mode vfr shot.png

# Windows 录屏（gdigrab）
ffmpeg -f gdigrab -framerate 30 -i desktop -c:v libx264 -preset ultrafast -pix_fmt yuv420p screen.mp4

# Windows 摄像头 + 麦克风（设备名先用 -list_devices true 查）
ffmpeg -f dshow -i video="Camera" -f dshow -i audio="Microphone" \
  -c:v libx264 -preset veryfast -c:a aac cam.mp4

# Linux / macOS
ffmpeg -f x11grab -video_size 1920x1080 -framerate 30 -i :0.0 screen.mp4
ffmpeg -f avfoundation -i "1:0" -c:v libx264 -preset veryfast mac.mp4

录屏最常见的失败是“设备名不存在”和“没有权限”。先列设备，再录；不要照抄别人的 "Camera"。

# 本地文件按实时速度推到 RTMP（-re 很重要，否则会瞬间灌满缓冲区）
ffmpeg -re -i in.mp4 -c:v libx264 -preset veryfast -tune zerolatency \
  -b:v 2M -maxrate 2M -bufsize 4M -c:a aac -ar 48000 -f flv \
  rtmp://host/live/stream?key=SECRET

# 推到 SRT（streamid 的写法由服务端访问控制决定）
ffmpeg -re -i in.mp4 -c copy -f mpegts "srt://host:8890?streamid=publish:live/stream"

# 转 H.265，并加 hvc1 tag 以兼容 Apple 生态
ffmpeg -i in.mp4 -c:v libx265 -crf 28 -preset medium -tag:v hvc1 -c:a copy out.mp4

# 两遍编码：第一遍只分析，第二遍才写文件（Windows 用 NUL，Unix 用 /dev/null）
ffmpeg -i in.mp4 -c:v libx264 -b:v 2M -pass 1 -an -f mp4 NUL
ffmpeg -i in.mp4 -c:v libx264 -b:v 2M -pass 2 -c:a aac -b:a 128k out.mp4

推流卡顿先查三件事：-re 有没有加、上行带宽够不够、关键帧间隔是否过长（GOP 过长会让首屏等待变久）。

# 同规格文件拼接：用 concat demuxer，速度最快
# list.txt 里每行写：file 'part1.mp4'
ffmpeg -f concat -safe 0 -i list.txt -c copy joined.mp4

# 规格不同：用 concat 滤镜，先统一分辨率/帧率/像素格式
ffmpeg -i a.mp4 -i b.mp4 -filter_complex \
  "[0:v]scale=1280:720,fps=25,format=yuv420p[v0];[1:v]scale=1280:720,fps=25,format=yuv420p[v1];[v0][v1]concat=n=2:v=1:a=0[v]" \
  -map "[v]" -c:v libx264 -crf 22 out.mp4

# 只抽音轨，不重编码
ffmpeg -i in.mp4 -vn -c:a copy audio.m4a

# 换掉视频里的音轨
ffmpeg -i video.mp4 -i newaudio.m4a -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -shortest out.mp4

concat demuxer 要求编码参数一致（分辨率、profile、时间基）；只要有一项不同，就会出现花屏或音画错位。宁可用 concat 滤镜重编码，也不要赌。

🍱 命令菜谱 30 条：按场景点菜，不用背参数

这 30 条配方像一张按口味分组的菜单：你想“把片子变小”“每 10 秒截一张图”“把字幕烧进去”，直接点到对应分组。每条命令下面都有一句“这在干什么”，先看懂目的，再改文件名和参数，比死记 300 字符安全得多。

输入输出统一用 input.mp4、output.mp4 占位；实际使用时替换成自己的路径。所有命令都假定输入确实存在，且构建里编进了对应编码器。

# 1 网页通用：H.264 CRF 20，画质优先、码率随画面复杂度起伏
ffmpeg -i input.mp4 -c:v libx264 -preset slow -crf 20 -c:a aac -b:a 128k output.mp4

# 2 更省带宽：H.265，Apple 生态加 hvc1 tag（否则 QuickTime 可能不认）
ffmpeg -i input.mp4 -c:v libx265 -crf 28 -preset medium -tag:v hvc1 -c:a copy output.mp4

# 3 新一代 AV1：构建里要有 libsvtav1，先 ffmpeg -encoders 确认再跑
ffmpeg -i input.mp4 -c:v libsvtav1 -crf 35 -preset 6 -c:a copy output.mp4

# 4 目标文件大小：两遍编码，第一遍只统计复杂度（输出到 null，不占磁盘）
ffmpeg -i input.mp4 -c:v libx264 -b:v 2M -pass 1 -an -f null -
ffmpeg -i input.mp4 -c:v libx264 -b:v 2M -pass 2 -c:a aac -b:a 128k output.mp4

# 5 旧设备 / 小屏：720p + 25 fps，faststart 让 MP4 边下边播
ffmpeg -i input.mp4 -vf "scale=-2:720,fps=25" -c:v libx264 -crf 23 -preset veryfast -c:a copy -movflags +faststart output.mp4

# 6 只换箱子：MKV → MP4，码流原样搬运
ffmpeg -i input.mkv -c copy -movflags +faststart output.mp4

第 4 条的两遍编码适合“必须卡死文件大小”的交付；日常点播直接用 CRF，没必要为几 MB 多花一倍时间。第 6 条不经过解码器，几秒就能完成。

# 1 每 10 秒一张：fps=1/10 把时间轴当成“每 10 秒取一帧”
ffmpeg -i input.mp4 -vf "fps=1/10,scale=640:-2" -q:v 2 frame_%03d.jpg

# 2 雪碧图：20 张缩略图拼成 5×4，先抽帧再 tile，最后只输出一张
ffmpeg -i input.mp4 -vf "fps=1/10,scale=320:-2,tile=5x4" -frames:v 1 sprite.jpg

# 3 指定时刻缩略图：-ss 放在 -i 前更快，但不保证落在精确帧上
ffmpeg -ss 00:00:12 -i input.mp4 -frames:v 1 -q:v 2 thumb.jpg

# 4 场景切换帧：只保留画面变化大的帧，0.3 是阈值，越大越少
ffmpeg -i input.mp4 -vf "select=gt(scene\,0.3)" -fps_mode vfr scene_%03d.jpg

# 5 只抽音轨：-vn 去掉视频，-c:a copy 不重编码，最快也无损
ffmpeg -i input.mp4 -vn -c:a copy output.m4a

# 6 转 AAC：兼容网页与移动端，采样率统一到 48 kHz、双声道
ffmpeg -i input.mp4 -vn -c:a aac -b:a 128k -ar 48000 -ac 2 output.m4a

雪碧图的关键是 tile 前先 fps 和 scale：先降帧、再缩小，最后才拼图，否则会先处理一堆高分辨率帧。缩略图用 -q:v 2 控制 JPEG 质量，数字越小越清晰。

# 1 同规格拼接：concat demuxer 只重排包，最快；list.txt 每行写 file 'part1.mp4'
ffmpeg -f concat -safe 0 -i list.txt -c copy output.mp4

# 2 规格不同：concat 滤镜先统一分辨率/帧率/像素格式，再重编码
ffmpeg -i part1.mp4 -i part2.mp4 -filter_complex "[0:v]scale=1280:720,fps=25,format=yuv420p[v0];[1:v]scale=1280:720,fps=25,format=yuv420p[v1];[v0][v1]concat=n=2:v=1:a=0[v]" -map "[v]" -map 0:a? -c:v libx264 -crf 22 -c:a aac output.mp4

# 3 concat protocol：只适合 MPEG-TS 这类可顺序拼接的码流，简单但容错差
ffmpeg -i "concat:part1.ts|part2.ts" -c copy output.ts

# 4 软字幕：字幕单独成轨，播放器可开关；MP4 里用 mov_text
ffmpeg -i input.mp4 -i subtitles.srt -map 0:v -map 0:a -map 1:s -c:v copy -c:a copy -c:s mov_text output.mp4

# 5 硬字幕：字幕烧进像素，任何播放器都能看，但改不了
ffmpeg -i input.mp4 -vf "subtitles=subtitles.srt" -c:v libx264 -crf 20 -c:a copy output.mp4

# 6 换音轨：视频原样，只替换一条音频；-shortest 防止音频比视频长
ffmpeg -i input.mp4 -i newaudio.m4a -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -shortest output.mp4
拼接方式要不要重编码适合最大的坑
concat demuxer否（-c copy）编码参数完全一致的分片分辨率、profile、time_base 有一项不同就花屏或音画错位
concat protocol否MPEG-TS 这类本身就是连续码流的格式MP4 分片不能用；对损坏/非连续码流几乎没有容错
concat 滤镜是规格不同、需要统一画布必须显式统一 scale / fps / format，且耗 CPU
 
# 1 右下角水印：logo 先缩放，overlay 定位到右边距 20、下边距 20
ffmpeg -i input.mp4 -i logo.png -filter_complex "[1:v]scale=120:-1[logo];[0:v][logo]overlay=W-w-20:H-h-20[v]" -map "[v]" -map 0:a? -c:v libx264 -crf 22 -c:a copy output.mp4

# 2 竖屏裁剪：1920×1080 先中心裁出 608×1080，再缩放到 1080×1920
ffmpeg -i input.mp4 -vf "crop=608:1080:(iw-608)/2:0,scale=1080:1920,setsar=1" -c:v libx264 -crf 20 -c:a copy output.mp4

# 3 补边不拉伸：先等比缩到 1280 宽，再 pad 成 16:9，空的地方补黑
ffmpeg -i input.mp4 -vf "scale=1280:-2,pad=1280:720:(ow-iw)/2:(oh-ih)/2:black" -c:v libx264 -crf 20 -c:a copy output.mp4

# 4 变速 2 倍：视频 setpts 减半，音频 atempo 加倍；两者必须配套
ffmpeg -i input.mp4 -filter_complex "[0:v]setpts=0.5*PTS[v];[0:a]atempo=2.0[a]" -map "[v]" -map "[a]" -c:v libx264 -crf 20 -c:a aac output.mp4

# 5 GIF 两步法：先造专用调色板，再按调色板抖动，颜色才不会发灰
ffmpeg -i input.mp4 -vf "fps=12,scale=480:-1:flags=lanczos,palettegen" palette.png
ffmpeg -i input.mp4 -i palette.png -lavfi "fps=12,scale=480:-1:flags=lanczos[x];[x][1:v]paletteuse" output.gif

# 6 旋转画面：transpose=1 顺时针 90°，transpose=2 逆时针；手机竖拍可先关自动旋转
ffmpeg -i input.mp4 -vf "transpose=1" -c:v libx264 -crf 20 -c:a copy output.mp4

变速只改视频不改音频，会立刻音画不同步。视频用 setpts，音频用 atempo；atempo 单级的常用范围是 0.5～2.0，超出范围就串联多个 atempo。GIF 如果不走调色板，FFmpeg 会用默认 256 色硬凑，渐变和肤色最容易脏。

# 1 Windows 录屏：gdigrab 抓桌面，ultrafast 保证实时不掉帧
ffmpeg -f gdigrab -framerate 30 -i desktop -c:v libx264 -preset ultrafast -pix_fmt yuv420p screen.mp4

# 2 Linux 录屏：x11grab 指定显示器和区域，:0.0 表示第一个 X display
ffmpeg -f x11grab -video_size 1920x1080 -framerate 30 -i :0.0 screen.mp4

# 3 macOS 采集：avfoundation 的 "1:0" 是“视频设备:音频设备”索引
ffmpeg -f avfoundation -i "1:0" -c:v libx264 -preset veryfast -c:a aac mac.mp4

# 4 先列设备：Windows 摄像头 / 麦克风名字不能猜
ffmpeg -f dshow -list_devices true -i dummy

# 5 推 RTMP：-re 按实时速度读文件，-tune zerolatency 压低编码缓冲
ffmpeg -re -i input.mp4 -c:v libx264 -preset veryfast -tune zerolatency -b:v 2M -maxrate 2M -bufsize 4M -c:a aac -ar 48000 -f flv rtmp://host/live/stream

💰 码率、CRF 与质量：给编码器一个“精细度预算”

码率是“每秒愿意花多少字节”，CRF 是“告诉编码器你能接受多大失真”。固定码率像给画家规定“每小时必须用完一盒颜料”，不管画面难易；CRF 像给画家一个精细度档位，简单的画面少花颜料，复杂的画面多花一点。直播更关心“带宽可预测”，点播更关心“同体积下更好看”。

模式怎么定码率优点代价 / 适用
CBR每秒尽量恒定，靠 buffer 约束网络友好、可预测复杂画面质量下降；直播/硬件编码常用
VBR按画面复杂度波动同码率下质量更好峰值不可控；点播、离线转码
ABR给一个目标平均码率介于两者之间需要 -maxrate / -bufsize 兜底
CRF固定质量，码率随画面变化省心、质量稳定码率不可预测；点播、归档
CQP固定量化参数实现简单码率波动大；研究/特殊场景
文件大小(GB) ≈ 码率(Mbps) × 时长(s) ÷ 8 ÷ 1024
分辨率 / 帧率H.264 经验码率H.265 经验码率说明
720p / 252–4 Mbps1–2.5 Mbps网页与移动端常见起点
1080p / 254–8 Mbps2.5–5 Mbps内容复杂度影响很大
1080p / 50–606–12 Mbps4–8 Mbps运动画面、游戏直播偏高
4K / 25–3015–30 Mbps8–18 Mbps以上均为经验区间，不是标准，以实测为准
 
# 点播：质量优先，CRF 20（x264 常用 18–23，0 为无损，范围 0–51）
ffmpeg -i in.mp4 -c:v libx264 -crf 20 -preset slow -c:a aac -b:a 128k out.mp4

# 直播：给 CRF 加一个码率上限，既稳又不过度占带宽
ffmpeg -re -i in.mp4 -c:v libx264 -preset veryfast -tune zerolatency \
  -crf 22 -maxrate 2500k -bufsize 5000k -c:a aac -f flv rtmp://host/live/key

# 硬件编码常常没有 CRF，改用码率 + 质量参数（以各编码器文档为准）
ffmpeg -i in.mp4 -c:v h264_nvenc -preset p5 -tune hq -b:v 4M -maxrate 6M out.mp4
💡CRF 不是“越小越好”。x264 的 CRF 18 附近常被当作“视觉无损”的经验值，再往下文件会迅速变大；x265 的 CRF 标尺与 x264 并不等价，不能直接照搬同一个数字。直播场景里，-maxrate 和 -bufsize 缺失，会让码率尖峰撞上网络瓶颈，表现为卡顿而非画质差。

🩺 ffprobe 排错：先体检，再开药

ffprobe 不负责修复，它只负责把“这套码流到底长什么样”摊开给你看。它像体检报告：容器格式、每条流的编码、真实帧率、时间戳、关键帧位置、码率是否写在头部，全部可以打印。排错时先做体检，能避免 80% 的盲目重编码。

# 容器 + 所有流的概览（JSON 便于脚本处理）
ffprobe -v error -show_format -show_streams -of json in.mp4

# 只看视频关键字段
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,level,width,height,pix_fmt,r_frame_rate,avg_frame_rate,bit_rate \
  -of default=noprint_wrappers=1 in.mp4

# 看前 10 个包的时间戳（PTS / DTS 是否从负值开始、是否跳变）
ffprobe -v error -select_streams v:0 -show_packets \
  -show_entries packet=pts_time,dts_time,duration_time,flags \
  -read_intervals "%+#10" in.mp4

# 数帧、看帧类型与关键帧
ffprobe -v error -select_streams v:0 -count_frames \
  -show_entries stream=nb_read_frames -of default=nw=1 in.mp4
ffprobe -v error -select_streams v:0 -show_frames \
  -show_entries frame=key_frame,pict_type,pts_time -of csv in.mp4
症状ffprobe 看什么可能结论
播放花屏 / 绿屏profile、level、pix_fmt、extradata 是否存在profile 超出播放器能力；SPS/PPS 缺失或带内未重复
音画不同步pts_time / dts_time 的起始值与跳变时间基换算错；音频起始偏移；B 帧重排异常
帧率忽高忽低r_frame_rate 与 avg_frame_rate可变帧率（VFR）；录屏/摄像头常见
时长不对duration、start_time容器头未写时长；拼接后时间线未重置
码率显示为空bit_rate容器没写；用 -count_frames 或实际文件大小反推
无法 seekkey_frame 分布；MP4 是否有 moov关键帧过少；moov 在文件尾部且未 faststart

🔬 ffprobe 全家桶：容器、流、包、帧、章节全摊开

ffprobe 像体检中心：-show_format 是总检报告，-show_streams 是分科检查，-show_packets 是抽血逐项看，-show_frames 是影像逐帧看，-show_chapters 是目录页。你不需要一次全做，按症状选项目，报告才看得懂。

参数输出什么典型用途
-show_format容器级信息：format_name、duration、size、bit_rate、tags先确认它到底是什么文件，时长和总码率对不对
-show_streams每条流的编码、分辨率、帧率、采样率、profile、extradata 概览判断兼容性、是否 VFR、音频布局是否正常
-show_packets每个压缩包的 pts/dts、duration、size、flags查负时间戳、DTS 跳变、关键帧分布、峰值码率
-show_frames解码后每一帧的类型、时间戳、像素格式、运动信息数 I/P/B 帧、找关键帧、看帧级时间戳
-show_chapters章节标题与起止时间课程、播客、蓝光目录提取
-of json / csv / flat输出格式：JSON 给脚本，CSV 给表格，flat 给人读json 结构化；csv=p=0 去掉前缀便于 awk
-show_entries只挑需要的字段，输出更小stream=codec_name,width,height
-read_intervals只读指定时间段或前 N 个包%+#10 表示从开头读 10 个
-count_frames真正解一遍并数帧，比读头部准确但更慢容器没写帧数时统计实际帧数

10 条实用查询：从“这是什么”到“哪里坏了”

# 1 总览：容器 + 所有流，JSON 交给脚本处理
ffprobe -v error -show_format -show_streams -of json input.mp4

# 2 时长 / 体积 / 总码率：flat 一行一个键值，最适合人读
ffprobe -v error -show_entries format=duration,size,bit_rate -of flat input.mp4

# 3 视频参数：编码、分辨率、帧率、像素格式、profile / level
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,profile,level,width,height,pix_fmt,r_frame_rate,avg_frame_rate,bit_rate -of csv=p=0 input.mp4

# 4 音频参数：采样率、声道数、声道布局、码率
ffprobe -v error -select_streams a:0 -show_entries stream=codec_name,sample_rate,channels,channel_layout,bit_rate -of csv=p=0 input.mp4

# 5 前 10 个包：PTS / DTS / 时长 / 大小 / flags，先看是否从负数开始
ffprobe -v error -select_streams v:0 -show_packets -show_entries packet=pts_time,dts_time,duration_time,size,flags -read_intervals "%+#10" -of csv=p=0 input.mp4

# 6 关键帧位置与 GOP：相邻关键帧的 PTS 差就是这一段的 GOP 秒数
ffprobe -v error -select_streams v:0 -show_frames -show_entries frame=pts_time,key_frame,pict_type -of csv=p=0 input.mp4 | awk -F, '$2==1 {if (last!="") printf "GOP %.2fs @ %.2fs\n", $1-last, $1; last=$1}'

# 7 帧类型直方图：I/P/B 各多少帧（第三列是 pict_type）
ffprobe -v error -select_streams v:0 -show_frames -show_entries frame=pict_type -of csv=p=0 input.mp4 | awk -F, '{print $3}' | sort | uniq -c

# 8 峰值码率估算：逐包 size×8 / duration_time，取最大值（单位 bps）
ffprobe -v error -select_streams v:0 -show_packets -show_entries packet=size,duration_time -of csv=p=0 input.mp4 | awk -F, 'NF>=2 && $2!="N/A" {v=$1*8/$2; if(v>m) m=v} END {printf "peak ≈ %.2f Mbps\n", m/1000000}'

# 9 黑场 / 静音：这不是 ffprobe，而是 ffmpeg 的检测滤镜，结果打在 stderr
ffmpeg -i input.mp4 -vf "blackdetect=d=0.5:pix_th=0.10" -an -f null -
ffmpeg -i input.mp4 -af "silencedetect=noise=-30dB:d=1" -f null -

# 10 章节：播客、课程、蓝光的目录页
ffprobe -v error -show_chapters -of json input.mp4

第 6、7、8 条用了 csv=p=0：它去掉 packet,、frame, 这类前缀，让字段从第一列开始，awk 才好数。Windows 没有 awk 时，把管道后半段换成 PowerShell 的 ForEach-Object / Measure-Object 即可，字段含义不变。

看时长不对

先看 format=duration,size,bit_rate，再用 format=duration 对比 stream=duration。容器头没写时长时，ffprobe 可能显示 N/A，不代表文件坏了。

看帧率忽高忽低

r_frame_rate 是“能表示的最小公倍率”，avg_frame_rate 才是平均帧率。两个差得远，通常说明是 VFR（可变帧率），录屏和手机视频很常见。

看关键帧太少

关键帧位置决定 seek 精度与首屏速度。切片前用 -g 或 -force_key_frames 对齐，别让切片器每次都等下一个 IDR。

⚠️ffprobe 报的 codec_tag_string 不一定可信。有些封装器会写错 tag，或者同一编码用了非标准 fourcc。判断兼容性时，codec_name、profile、level 和实际解码测试（ffmpeg -i input.mp4 -f null -）要一起看，不能只信一个字符串。
🔍先读“结构”，再读“数值”。排查顺序建议：format 看容器是否完整 → streams 看编码/分辨率/采样率 → packets 看时间戳与关键帧 → frames 看真实解码结果。跳过前两步直接数帧，往往会得到一堆噪声。

🔊 响度规范：LUFS 是“整个房间的平均音量”，不是瞬间尖峰

LUFS 像把整段音频请进一个标准房间，用一台“按人耳偏好加权”的声级计测平均值：它不是某一秒的尖峰，而是整段内容的整体响度。两个文件的分贝峰值一样，听起来却可能一个震耳、一个发闷，差别就在这个平均值。

FFmpeg 的 loudnorm 实现的是 EBU R128 思路：先测量积分响度（integrated loudness）、真峰值（true peak）和响度范围（LRA），再按目标值调整。它不是简单地“把音量拉大”，所以能避免把安静的段落也一起轰起来。

术语一句话解释注意点
LUFS / LKFS带人耳加权的平均响度，数字越大越响LKFS 与 LUFS 在数值上等价，广播里常写 LKFS
LU相对上一个参考响度的“差多少”用于描述增益变化，不是绝对值
True Peak / dBTP考虑重采样后可能出现的峰值的真峰值编码成 AAC/MP3 后峰值可能变高，留 1～2 dB 余量
LRA响度范围：整段里安静与响亮差多少LRA 太大说明动态过宽，短视频平台可能压平
Integrated整段积分响度，loudnorm 的 I门限会排除长静音，不是把静音也平均进去
场景目标响度真峰值上限说明
EBU R128 广播−23 LUFS ±0.5−1 dBTP欧洲广播的基准，强调可预测
ATSC A/85 广播−24 LKFS ±2−2 dBTP北美广播常见目标，具体以播出方规范为准
YouTube / 流媒体−14 ～ −16 LUFS−1 ～ −2 dBTP平台通常会再归一化一次，交母版别顶到 0 dBFS
播客 / 口播−16 LUFS−1.5 dBTP人声为主，LRA 不宜过大
短视频 / 广告−14 ～ −16 LUFS−1 dBTP信息密度高，但仍要避免削波

两遍法：先体检，再按报告开药

第一遍只测量，不产出文件；第二遍把测量值填回 loudnorm，让整段使用同一个线性增益。这样不会出现“安静段落被单独放大、噪声也变大”的动态抽吸感。

# 第一遍：测量并把 JSON 写进 loud.json（日志也混在里面，脚本取最后一个 JSON 对象）
ffmpeg -hide_banner -i input.mp4 -vn -af "loudnorm=I=-16:TP=-1.5:LRA=11:print_format=json" -f null - 2> loud.json

# 第二遍：把 measured_I / measured_TP / measured_LRA / measured_thresh / offset 填回去
ffmpeg -i input.mp4 \
  -af "loudnorm=I=-16:TP=-1.5:LRA=11:measured_I=-18.6:measured_TP=-3.2:measured_LRA=6.5:measured_thresh=-28.4:offset=0.3:linear=true" \
  -c:v copy -c:a aac -b:a 192k output.mp4

上面第二行里的 measured_* 是占位值，必须换成第一遍 JSON 里的真实数字。只写 I=-16 不写 measured 参数，loudnorm 会走动态模式，效果是“能用”，但不是最适合交付母版的线性归一化。

单行模式与 dynaudnorm：快，但会“呼吸”

# 单遍 loudnorm：适合快速预览或直播前粗调，动态调整会轻微改变节奏感
ffmpeg -i input.mp4 -af "loudnorm=I=-16:TP=-1.5:LRA=11" -c:v copy -c:a aac -b:a 192k output.mp4

# dynaudnorm：按窗口动态拉增益，适合口播/采访这类音量忽大忽小的素材
ffmpeg -i input.mp4 -af "dynaudnorm=p=0.9:m=10" -c:v copy -c:a aac -b:a 192k output.mp4
方案怎么工作优点代价 / 适用
loudnorm 两遍先测量，再用线性增益整体平移保留动态、结果可复现、符合 R128 思路要跑两遍；交付母版首选
loudnorm 单遍边分析边动态调整一条命令搞定可能“呼吸”或改变段落强弱；预览可用
dynaudnorm按短窗口动态拉增益口播音量更均匀会抬高底噪、产生抽吸感；不适合音乐母版
volume=+6dB整段固定增益最简单、完全可预测不知道目标响度，容易削波；只能微调
⚠️响度归一化不是“把音量开到最大”。把峰值顶到 0 dBFS，再编码成 AAC，重采样后的真峰值可能超过 0 dBTP，播放器会削波。目标响度和真峰值要一起看：TP=-1.5 就是给编码和后续处理留的余量。
💡先统一采样率，再谈响度。不同采样率、声道布局的素材混在一起，loudnorm 的测量口径会变得难解释。音频链最稳的顺序是：aresample=48000 → 声道布局统一 → loudnorm → 编码。

📶 码率阶梯：同一部片，给每条网络都备一把椅子

点播的多档码率像自助餐分大小份：胃口小的拿小份，胃口大的拿大份，服务员（播放器）根据桌面空间（带宽）随时换盘。只给一个 8 Mbps 的 1080p，弱网用户就只能等；只给一个 360p，强网用户又觉得糊。

ffmpeg -i input.mp4 \
  -filter_complex "[0:v]split=3[v0][v1][v2];[v0]scale=1920:-2[v0o];[v1]scale=1280:-2[v1o];[v2]scale=854:-2[v2o]" \
  -map "[v0o]" -map 0:a:0 -map "[v1o]" -map 0:a:0 -map "[v2o]" -map 0:a:0 \
  -c:v libx264 -preset veryfast -sc_threshold 0 \
  -force_key_frames "expr:gte(t,n_forced*4)" \
  -b:v:0 5M -maxrate:v:0 5.5M -bufsize:v:0 10M \
  -b:v:1 3M -maxrate:v:1 3.3M -bufsize:v:1 6M \
  -b:v:2 1.2M -maxrate:v:2 1.3M -bufsize:v:2 2.4M \
  -c:a aac -b:a 128k -ac 2 \
  -f hls -hls_time 4 -hls_playlist_type vod \
  -hls_segment_filename "hls_%v_%03d.ts" \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0,name:1080p v:1,a:1,name:720p v:2,a:2,name:480p" \
  "hls_%v.m3u8"

这条命令在干什么：split 把一路视频复制成三路，分别缩放；三组 -map 把三路视频和三路音频按顺序接进输出流；-b:v:0/1/2 给每条输出视频流单独设码率；最后 HLS muxer 按 var_stream_map 把输出流编号映射成 1080p/720p/480p，并生成 master.m3u8。

参数 / 写法作用容易错的地方
-var_stream_map声明每条 variant 由哪些输出流组成v:0 指“第 0 条输出视频流”，不是输入流；顺序必须与 -map 一致
hls_%v_%03d.ts用 variant 编号区分分片文件不写 %v 会互相覆盖，只剩最后一档
-master_pl_name额外生成总清单只生成 variant 清单时，播放器不知道该选哪档
-force_key_frames强制每 4 秒一个关键帧帧率未知时比固定 -g 更稳，能保证切档对齐
-hls_time 4每片目标 4 秒实际边界仍会等关键帧；关键帧不齐，片长就漂
💡先验证 master，再上传 CDN。本地用 ffplay master.m3u8 或浏览器播放器跑一遍，观察切档时有没有停顿、首屏要几秒。只检查每个 variant 的 .m3u8 文件存在，不代表播放器能正确选档。
⚠️分辨率与码率不是越多档越好。档位太多会让编码时间、存储和 CDN 回源成倍增长；通常 3～5 档足够覆盖主流网络。低档位不要低于源内容真正需要的清晰度，否则播放器频繁切档，观感比一直低清更差。

⚙️ 自动化与错误处理：让脚本替你盯进度

批量转码像一条流水线：-progress 是传送带上的计数器，-stats 是车间大屏，-xerror 是“一有次品就停线”的报警器。没有这些，脚本只能等命令跑完再看文件大小，出了问题也不知道坏在第几步。

参数作用使用建议
-hide_banner隐藏版本与构建信息脚本日志更短；不会隐藏错误
-loglevel error只留错误批处理默认；排查时改成 warning 或 info
-loglevel level+info日志带级别前缀长日志里方便筛“哪条是 error”
-stats / -nostats向 stderr 打印实时进度行 / 关闭它人在终端看用 -stats；脚本解析用 -progress
-progress pipe:1把 key=value 进度写到 stdoutstdout 给进度，stderr 留给日志，互不污染
-xerror遇到 error 级日志就退出批处理要“坏一个停一个”时用；会牺牲“尽量产出”
-y / -n直接覆盖 / 绝不覆盖自动化更推荐 -n，避免误删已有成品
-nostdin关闭交互式键盘输入后台任务、循环脚本必加，防止误触暂停

-progress 的输出长什么样

frame=1234
fps=25.0
bitrate=2100.0kbits/s
total_size=104857600
out_time_us=49360000
out_time_ms=49360000
out_time=00:00:49.360000
dup_frames=0
drop_frames=0
speed=1.21x
progress=continue

这是一组不断刷新的 key=value，最后一组以 progress=end 收尾。注意有些版本里 out_time_ms 实际也是微秒，脚本优先用 out_time_us。百分比 = out_time_us / 总时长(微秒)，不要拿 frame 去猜，VFR 素材会不准。

# 只要进度不要重复的 stats 行；stdout 给进度，stderr 仍然留给错误日志
ffmpeg -hide_banner -nostdin -loglevel error -progress pipe:1 -nostats \
  -i input.mp4 -c:v libx264 -crf 22 -preset veryfast -c:a aac output.mp4

# PowerShell 里只看时间和速度
ffmpeg -hide_banner -nostdin -loglevel error -progress pipe:1 -nostats `
  -i input.mp4 -c:v libx264 -crf 22 -c:a aac output.mp4 2>$null |
  Select-String "out_time=|speed="

批量转码：PowerShell 与 bash 各一段

# PowerShell 7：逐个转，失败只警告，不中断整批
Get-ChildItem -Filter *.mkv | ForEach-Object {
  $out = "out\$($_.BaseName).mp4"
  if (Test-Path $out) { return }              # 已存在就跳过，避免 -n 把“跳过”误判成失败
  ffmpeg -hide_banner -nostdin -loglevel error -xerror `
    -i $_.FullName -c:v libx264 -crf 22 -preset veryfast `
    -c:a aac -b:a 128k -movflags +faststart $out
  if ($LASTEXITCODE -ne 0) { Write-Warning "失败：$($_.Name)" }
}

# bash：已有成品就跳过；退出码非 0 才记入 fail.log
for f in *.mkv; do
  out="out/${f%.mkv}.mp4"
  [ -e "$out" ] && continue
  ffmpeg -hide_banner -nostdin -loglevel error -xerror -i "$f" \
    -c:v libx264 -crf 22 -preset veryfast -c:a aac -b:a 128k "$out" \
    || echo "FAIL $f" >> fail.log
done
# PowerShell 7 并行：最多同时 4 个，每个只给 2 个编码线程，避免线程超卖
Get-ChildItem -Filter *.mkv | ForEach-Object -Parallel {
  ffmpeg -hide_banner -nostdin -loglevel error -xerror -n -threads 2 `
    -i $_.FullName -c:v libx264 -crf 22 -preset veryfast `
    -c:a aac ("out\" + $_.BaseName + ".mp4")
} -ThrottleLimit 4

并行不是“开得越多越快”。x264 自己会按 CPU 核数开线程，你再开 8 个任务，每个任务都在抢核，cache 抖动、内存暴涨，总吞吐反而下降。经验规则是：并行数 × 单任务线程数 ≤ 物理核心数，留 1～2 个核给 IO 和系统。

让脚本可重跑：临时文件 + 原子改名

$out = "output.mp4"
$tmp = "$out.part.mp4"
ffmpeg -hide_banner -nostdin -loglevel error -xerror -y `
  -i input.mp4 -c:v libx264 -crf 22 -c:a aac $tmp
if ($LASTEXITCODE -eq 0) {
  Move-Item -Force $tmp $out      # 成功才替换成品
} else {
  Remove-Item -Force $tmp         # 失败留下半成品，下次会误判
}

直接写最终文件名，进程被杀就会留下一个“看起来成功、其实播不了”的 MP4。先写 .part 再改名，下次脚本只要判断目标文件是否存在就能安全跳过。配合 -n，批量任务可以随时中断、随时重跑。

🚫不要用 stderr 的自然语言做流程控制。“Conversion failed!”“Invalid data found”这些文案会随版本和语言环境变化，唯一稳定的失败信号是进程退出码非 0。日志用来给人看，退出码用来给脚本判断。
🔍-xerror 不是万能开关。它让 FFmpeg 在遇到 error 级日志时立刻退出，但有些错误只被记为 warning，仍然会产出“能播但有问题”的文件。交付前仍应做一次 ffprobe 或 ffmpeg -f null - 的完整解码校验。
🧪 动手试试：交付前用 ffprobe 做完整校验

🚑 报错词典：先看第一条错误，再看最后一行

FFmpeg 的日志像急诊病历：最后一行往往是“抢救失败”（Conversion failed!），真正的原因在更上面。先分诊是“读不懂箱子”（demuxer/容器）、“搬不动货”（解码/编码）还是“装不进新箱子”（muxer/封装），再对症下药。

▸DTSNon-monotonic DTS in output stream 0:1

原因：输出时间戳倒退了。常见于 -c copy 拼接不同时间基的文件、带 B 帧的流重排、-ss 截断后直接 copy，或输入本身时间戳就乱。

修复：先尝试重排时间戳；仍不行就让编码器重新生成时间线。

# 先保留码流，只修时间戳
ffmpeg -i input.mp4 -c copy -avoid_negative_ts make_zero -fflags +genpts output.mp4

# 仍报错：重编码，强制恒定帧率
ffmpeg -i input.mp4 -fps_mode cfr -r 25 -c:v libx264 -crf 20 -c:a aac output.mp4

拼接前先统一 time_base 与帧率；不要指望 -c copy 能自动修复两段来源不同的 B 帧顺序。

▸VFRPast duration 0.999992 too large

原因：输入是 VFR（可变帧率），或时间戳与目标帧率不匹配；编码器想按恒定帧率输出，发现“上一帧持续得太久”。录屏、手机视频、部分网络流最常见。

修复：明确指定恒定帧率，让滤镜链重新采样时间轴。

ffmpeg -i input.mp4 -fps_mode cfr -r 25 -c:v libx264 -crf 20 -c:a aac output.mp4

如果只是警告、输出时长和音画同步都正常，可以不改；如果伴随丢帧或音画漂移，就必须转 CFR。

▸容器moov atom not found

原因：MP4 的索引（moov atom）没写进文件。录制时断电、进程被杀、相机写卡中断，都会留下“有数据、没目录”的半成品。

修复：这不是转码参数能解决的。先确认文件不是 0 字节；能读的先让 FFmpeg 尝试解析；缺失索引通常需要同型号正常文件做参考的修复工具（如 untrunc）。

# 只用于诊断：能读出流说明 moov 至少部分存在
ffprobe -v error -show_format -show_streams broken.mp4

# 若容器可读、只是尾部索引损坏，尝试重写一遍容器
ffmpeg -i broken.mp4 -c copy repaired.mp4

-movflags +faststart 只能在 moov 存在时把它挪到文件头，不能凭空造出缺失的索引。

▸编码器Unknown encoder 'libx264'

原因：当前构建没有编进这个编码器（常见于精简版、系统包管理器版本、部分手机/嵌入式构建）。不是命令写错。

修复：先列出可用编码器，再换一个当前构建支持的。

ffmpeg -hide_banner -encoders | Select-String "264|265|av1"

# 没有 libx264 时的兜底（兼容性尚可，效率较低）
ffmpeg -i input.mp4 -c:v mpeg4 -q:v 4 -c:a aac output.mp4

libx264/libx265 属于 GPL 组件，不同发行版和第三方构建的授权策略不同；先看 ffmpeg -buildconf，不要在生产机上临时替换系统 FFmpeg。

▸泛化Conversion failed!

原因：这是总收尾错误，不是根因。真正的错误在它上面：编码器初始化失败、滤镜配置失败、写文件失败、参数不合法都可能落到这一行。

修复：把日志级别调高，向上找第一条 error；再用短片段复现，缩小变量。

ffmpeg -hide_banner -loglevel warning -i input.mp4 -t 5 -c:v libx264 -crf 22 -c:a aac output.mp4

# 只解码、不编码，排除编码器与封装器
ffmpeg -v error -i input.mp4 -f null -

如果 -f null - 也失败，问题在解码/输入；如果它成功而完整命令失败，重点查编码参数和输出路径/权限。

▸滤镜Error reinitializing filters / Failed to configure output pad

原因：滤镜链运行到一半，输入的宽高、像素格式或帧率变了（拼接不同素材、动态分辨率流、可变像素格式），滤镜图需要重建，但下游已经按旧参数配置好。

修复：在进入滤镜链前把参数钉死，别让下游看到两种尺寸。

ffmpeg -i input.mp4 -vf "scale=1280:720,fps=25,format=yuv420p" \
  -c:v libx264 -crf 20 -c:a aac output.mp4

多输入拼接时尤其要每一路都写 scale、fps、format；只给其中一路写，另一路仍可能在运行中改变参数。

▸选项Option not found / Error parsing options

原因：参数不属于这个编码器/封装器，或者拼写错误、版本过旧。例如把 x264 的 -crf 套到 NVENC 上，NVENC 用的是 -cq；把只存在于某个 muxer 的选项写给了另一个 muxer。

修复：直接查当前构建的帮助，而不是照抄网上的命令。

ffmpeg -hide_banner -h encoder=libx264
ffmpeg -hide_banner -h encoder=h264_nvenc
ffmpeg -hide_banner -h muxer=mp4

看到 Unrecognized option 先确认选项是否属于“输出选项”；写在 -i 前后的位置也会改变它作用的组件。

▸码流Invalid NAL unit size / decode_slice_header error

原因：H.264/H.265 码流损坏，或封装器写入了错误的 extradata/SPS-PPS。下载中断、磁盘坏块、错误拼接、非标准 remux 都可能触发。

修复：优先重新获取源文件；如果只是想把可看的部分抢救出来，可以放宽错误检测，但不要把它当“修复”。

# 只用于抢救观看：容忍坏包，重新编码，尽量跳过损坏区域
ffmpeg -err_detect ignore_err -i input.mp4 -c:v libx264 -crf 18 -c:a aac salvaged.mp4

-err_detect ignore_err 会掩盖问题，产出的文件可能仍有花屏或静音段；正式交付不要用它。

▸封装Too many packets buffered for output stream

原因：封装器在等某条流追上另一条流，缓冲队列达到上限。常见于音频比视频长很多、某条流时间戳跳变、muxer 需要交错写入时。

修复：加大交错队列只能缓解；真正的修法是让两条流时长/时间线一致。

ffmpeg -i input.mp4 -c:v libx264 -crf 20 -c:a aac \
  -max_muxing_queue_size 1024 -shortest output.mp4

如果加大队列后内存暴涨，说明某条流的时间戳严重错位，继续加数字只是把问题推迟到 OOM。

▸头信息Could not write header (incorrect codec parameters?)

原因：编码器和容器不匹配，或缺了容器/编码器要求的参数。例如把 WebM 常用的 VP9/Opus 硬塞进 MP4、rawvideo 没给宽高和像素格式、编码器尚未收到必需的 extradata。

修复：换正确的容器，或补齐编码器要求的参数；先用 -h muxer=… 确认它到底接受什么。

# VP9 + Opus 用 WebM，而不是 MP4
ffmpeg -i input.mp4 -c:v libvpx-vp9 -crf 32 -b:v 0 -c:a libopus -f webm output.webm

# rawvideo 进 MP4：必须显式给分辨率、像素格式和帧率
ffmpeg -f rawvideo -pix_fmt yuv420p -s 1920x1080 -r 25 -i input.yuv \
  -c:v libx264 -crf 20 output.mp4

HEVC 进 MP4 本身是合法的；-tag:v hvc1 是给 Apple 生态的兼容性标签，不是“修复 header 错误”的万能药。真正要确认的是“这个 muxer 是否支持这个 codec 的这些参数”。

🔍排错顺序：输入 → 解码 → 滤镜 → 编码 → 封装。先用 ffmpeg -i input.mp4 -f null - 验证输入和解码；再加滤镜；再加编码；最后换封装。每加一层跑一次，错误出现的那一层就是嫌疑人。

⚡ 性能调优：先找瓶颈，再拧旋钮

转码像一条四工位流水线：解码、滤镜、编码、IO。速度慢不一定是因为“CPU 不行”，也可能是最慢的那个工位在等人。盲目把 -threads 拉满，像给所有工位同时加人，结果大家挤在门口，吞吐反而下降。

① 解码把压缩流还原成帧；软解吃 CPU，硬解吃 GPU/显存
→
② 滤镜缩放、裁切、叠加、字幕；运行在未压缩帧上
→
③ 编码整条链路最贵的一环；preset 与编码器决定速度
→
④ 封装 / IO写磁盘、写网络、写管道；慢盘和网络挂载最先卡这里
现象先量什么更可能的瓶颈先试什么
speed 长期低于 1x，CPU 100%-benchmark 的 utime / rtime软解 + 滤镜 + 软编都在抢 CPU换 preset；降滤镜分辨率；硬件加速
CPU 只有 30%，磁盘 100%任务管理器 / iostat 的写队列IO：慢盘、网络盘、日志同步换本地盘；先写管道；减少同时写盘任务

-f null - 很快，完整输出很慢对比两次的 rtime编码或封装换 preset / 编码器；检查输出盘

-benchmark：用数字代替感觉

# 完整编码到 null muxer，不写文件，测“解码 + 滤镜 + 编码”总时间
ffmpeg -benchmark -i input.mp4 -c:v libx264 -preset medium -crf 20 -c:a copy -f null -

# 只解码 + 滤镜，不编码、不封装
ffmpeg -benchmark -i input.mp4 -f null -

# 只做解封装 + 封装（copy），看 IO 与容器开销
ffmpeg -benchmark -i input.mp4 -c copy -f null -

# 单独看某个滤镜的代价：对比加与不加 scale
ffmpeg -benchmark -i input.mp4 -vf "scale=1280:-2" -f null -

-benchmark 末尾会打印：bench: utime=…s stime=…s rtime=…s。rtime 是墙钟时间，utime/stime 是用户态/内核态 CPU 时间。处理速度 ≈ 视频时长 / rtime；speed=2x 就表示 10 分钟视频约 5 分钟处理完。-benchmark_all 会给出更细的分阶段统计，但日志更长。

preset相对速度相对压缩率典型用途
ultrafast最快最低录屏、直播兜底、只求实时
veryfast很快较低批量转码、预览、日常交付
fast / medium中等中等medium 是 x264 默认的平衡点
slow / slower慢较高点播母版、预算充足的离线转码
veryslow / placebo很慢 / 极慢边际提升placebo 通常只换来极小体积收益，不推荐生产

线程与 tune：不是越多越好

# 让编码器按机器自动选线程（默认就是 0）
ffmpeg -i input.mp4 -c:v libx264 -crf 20 -threads 0 -c:a copy output.mp4

# 给视频编码单独限线程，适合与其它任务共存
ffmpeg -i input.mp4 -c:v libx264 -crf 20 -threads:v 4 -c:a copy output.mp4

# 限制滤镜线程，避免滤镜阶段把核吃满
ffmpeg -i input.mp4 -filter_threads 4 -filter_complex_threads 4 \
  -vf "scale=1280:-2" -c:v libx264 -crf 20 -c:a copy output.mp4

# 直播低延迟：减少编码缓冲，代价是同画质需要更高码率
ffmpeg -i input.mp4 -c:v libx264 -preset veryfast -tune zerolatency -b:v 2M -c:a aac -f flv rtmp://host/live/stream

-tune 是“给编码器一个偏好”：film 保留胶片颗粒，animation 适合卡通/动画，grain 保留噪点，stillimage 适合静态幻灯片，fastdecode 降低解码端负担，zerolatency 压缩编码延迟。x265 与硬件编码器的 tune 名称不完全一样，先查 -h encoder=…。

💡先做“减法”，再做“换硬件”。把 fps 从 30 降到 25、把滤镜分辨率从 4K 降到 1080p、把 preset 从 slow 换成 veryfast，往往比换一块 GPU 更快见效，而且不改变交付格式。调优前先记录一组基线数字，否则你无法判断改动到底有没有用。
⚠️基准测试要跑两次以上。第一次读文件可能命中冷缓存，第二次才是稳定值；输出到网络盘或机械盘会污染编码器的成绩。测试时固定输入、固定输出、关闭其它重任务，否则 rtime 的波动会让你误判瓶颈。
🚀硬件加速：把解码、缩放、编码搬到 GPU 能显著提速，但滤镜链和“显存 ↔ 内存”的拷贝方式决定实际收益，细节见 硬件加速专页，这里不展开。

🎯 质量度量：别用肉眼 A/B，用 VMAF/SSIM/PSNR 说话

质量评估像考试打分：PSNR 是“逐像素对答案”，错一个像素就扣分；SSIM 看“结构像不像”，更接近人眼对亮度和轮廓的敏感；VMAF 则是请一群“人眼评委”训练出来的模型打分——它最像主观观感，但也最依赖模型和素材。

三者都不是“越高越好看”的绝对真理，而是帮你把“这个码率够不够”从感觉变成可比较的数字。正确用法是：同码率比 VMAF，同 VMAF 比码率，最后再到目标设备上看一眼。

指标原理数值范围优点盲区
PSNR逐像素均方误差换算成 dB通常 30–45 dB计算快、结果稳定、容易复现不关心结构与人眼感知；轻微模糊也可能高分
SSIM比较亮度、对比度、结构相似性0–1，越接近 1 越好比 PSNR 更贴近人眼，适合看局部结构仍是局部统计，对时间抖动/运动不敏感
VMAF用主观打分数据训练的视频质量模型0–100，越高越好最接近“人觉得好不好”，适合码率阶梯决策依赖模型版本与素材；需要额外构建支持

三条命令：SSIM、PSNR、VMAF

# SSIM：第一个输入是参考，第二个是被测；结果打在日志里
ffmpeg -i input.mp4 -i output.mp4 -lavfi "[0:v][1:v]ssim" -f null -

# PSNR：同样先参考、后被测
ffmpeg -i input.mp4 -i output.mp4 -lavfi "[0:v][1:v]psnr" -f null -

# VMAF：需要构建里带 libvmaf；可同时把结果写成 JSON
ffmpeg -i input.mp4 -i output.mp4 \
  -lavfi "[0:v][1:v]libvmaf=log_fmt=json:log_path=vmaf.json" -f null -

顺序不能反：滤镜里的第一个输入是“参考答案”，第二个才是“学生答卷”。SSIM 日志里看 All 或 Y 分量；VMAF 的 JSON 里有逐帧分数与整体均值，做码率阶梯时通常看均值，也要看最低帧，避免“平均不错、运动段崩掉”。

分辨率不一致时：先对齐，再比较

VMAF/SSIM 要求两路画面尺寸一致。把 720p 输出和 1080p 原片直接比，滤镜会拒绝配置。做码率阶梯时，正确做法是“用对应分辨率的下采样参考”，而不是把低清输出硬放大到 1080p 再比——放大不会增加信息，只会把模糊算成“更接近”。

# 两路都缩到 1280×720 再比；flags=bicubic 保证缩放算法一致
ffmpeg -i input.mp4 -i output_720.mp4 \
  -lavfi "[0:v]scale=1280:720:flags=bicubic[ref];[1:v]scale=1280:720:flags=bicubic[dist];[ref][dist]libvmaf" \
  -f null -

# 时间戳起点不一致时，先各自归零，避免错帧
ffmpeg -i input.mp4 -i output.mp4 \
  -lavfi "[0:v]settb=AVTB,setpts=PTS-STARTPTS[ref];[1:v]settb=AVTB,setpts=PTS-STARTPTS[dist];[ref][dist]ssim" \
  -f null -

用 CRF 扫一遍，找“甜点”

# bash：对同一源做 4 个 CRF，分别算 VMAF，再结合文件大小选点
for crf in 18 20 23 26; do
  ffmpeg -hide_banner -loglevel error -i input.mp4 -c:v libx264 -preset medium -crf $crf "test_$crf.mp4"
  vmaf=$(ffmpeg -i input.mp4 -i "test_$crf.mp4" -lavfi "[0:v][1:v]libvmaf" -f null - 2>&1 | awk '/VMAF/ {print $NF}')
  size=$(stat -c %s "test_$crf.mp4" 2>/dev/null || stat -f %z "test_$crf.mp4")
  echo "CRF=$crf  VMAF=$vmaf  size=$size"
done

这个循环在 Linux/macOS 上可直接跑；Windows 把 stat 换成 PowerShell 的 (Get-Item).Length。更严谨的做法是固定“目标 VMAF”，比较不同编码器/分辨率下谁用的码率更低，而不是固定 CRF 比分数。

💡用 VMAF 选阶梯，用肉眼做终审。常见经验：VMAF 90 以上通常接近“透明”，80–90 多数内容可接受，70 以下容易出现可见的块效应或涂抹感；但动画、胶片颗粒、体育镜头的阈值完全不同。最终仍要在手机、电视、笔记本各看一遍。
⚠️不要拿 PSNR 做唯一 KPI。把画面整体模糊一点，PSNR 可能仍然很高，但人眼一眼就能看出“糊”。PSNR/SSIM 适合做回归测试和快速筛查，VMAF 适合做码率决策；三者都只是代理指标，不是主观质量本身。

🗂️ 源码目录导读：从哪读，先读什么

FFmpeg 源码不算“优雅教科书”，但结构很直白：一个库一个目录，入口在 fftools/。不要从 libavcodec/h264dec.c 开始啃，那里是全库最复杂的部分之一；先看 doc/examples/，把 API 的调用顺序跑通，再回头读实现。

ffmpeg/
libavformat/ 容器与协议：mov.c(MP4) matroska.c mpegts.c rtsp.c hls.c
libavcodec/ 编解码：h264*.c hevcdec.c aacenc.c libx264.c
libavfilter/ 滤镜：vf_scale.c vf_overlay.c vf_fps.c af_amix.c
libswscale/ 像素格式与缩放
libswresample/ 音频重采样
libavutil/ frame.c dict.c mem.c opt.c mathematics.c
libavdevice/ 采集设备：dshow / v4l2 / avfoundation
doc/examples/ 官方最小示例：demuxing_decoding.c / remuxing.c / muxing.c
fftools/ 命令行入口：ffmpeg.c / ffprobe.c / ffplay.c（老版本在根目录）

推荐阅读顺序：demuxing_decoding.c（怎么读包、解码）→ remuxing.c（怎么不做解码直接换容器）→ muxing.c（怎么编码并写出）→ filtering_video.c（滤镜图怎么搭）。读完这四个，再看 fftools/ffmpeg.c 的调度逻辑，就不会迷路。

⚠️API 会变，博客不会。旧的 avcodec_decode_video2 已被 send/receive 模型取代；AVCodecContext.channels 在新版本里逐步让位给 ch_layout；-vsync 也改成了 -fps_mode。照抄老代码前，先对照你本地头文件的版本与官方文档。

🌐 浏览器端 FFmpeg：把工厂搬进沙箱

ffmpeg.wasm 是把 FFmpeg 用 Emscripten 编译成 WebAssembly，让浏览器里也能做转码、截图、抽音轨。它像把整座工厂装进一个集装箱：能跑，但没有起重机（硬件加速），燃油（内存）也有限。典型情况下它跑在单线程或受限的多线程环境里，1080p 长视频会比桌面端慢很多。

维度浏览器端（ffmpeg.wasm）服务端（原生 FFmpeg）
隐私文件不出本机，适合敏感素材需要上传，考虑加密与生命周期
性能受限：无 GPU 编码、内存上限、线程支持依赖跨源隔离可用多核、SIMD、NVENC/QSV/VAAPI
体积核心 wasm 包较大，首次加载慢无前端体积负担
适用短视频裁剪、截图、格式小转换长视频、批量转码、直播

想把浏览器端跑起来，还要处理 COOP/COEP 响应头（多线程依赖 SharedArrayBuffer）、内存上限与文件系统挂载。具体 API 与包结构随版本变化，以官方文档为准。本站的 WASM 实验页 有可直接上手的演示与限制说明。

📖 术语与坑表

术语 / 参数一句话解释最容易踩的坑
demux / mux拆容器 / 装容器以为 mux 会重新编码；其实只写封装
extradata编码器需要的带外参数（如 SPS/PPS）转封装时丢了 extradata，播放器黑屏
time_base时间刻度把不同流的时间戳直接混用
GOP两个关键帧之间的距离切片/seek/首屏都受它影响
-c copy码流原样搬运容器不兼容时仍会失败，不是万能
-crf固定质量、码率浮动直播直接用 CRF，码率尖峰打爆上行
-preset编码速度/压缩率的权衡档位ultrafast 文件大；placebo 慢到不可用
-movflags +faststart把 MP4 索引挪到文件头长视频转完才加，等于重写一遍文件
-map显式选择输出哪些流不写 -map 时默认只挑“最佳”一条，音轨会丢
AV_NOPTS_VALUE无时间戳哨兵当成 0 用，导致时间线错乱

最后一句实用建议：把复杂命令拆成“能验证的小步”。先 -c copy 验证容器，再验证解码，再加滤镜，最后才上编码参数。每一步都用 ffprobe 看一眼，比对着一条 300 字符的命令猜要快得多。
