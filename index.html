🧱 四层闭环

任何音视频系统都可以拆成四层。每一层有自己的“标准语言”，层与层之间靠时间戳、像素格式、码流格式这三个契约连接。

① 采集 / 编码 压缩

镜头 → 传感器 → ISP → YUV。编码器做预测、变换、量化、熵编码，把 12 bpp 的原始像素压到 0.02–0.2 bpp。

关键词：GOP、I/P/B、CRF、profile/level、4:2:0。

② 封装 组织

把视频帧、音频帧、字幕、元数据装进有时间轴的容器；解决随机访问索引、音画同步、分片与流式传输。

关键词：MP4 box、TS PID/PCR、EBML、FLV tag。

进入容器 →

③ 传输 分发

RTMP/SRT 负责上行，HLS/DASH 负责大规模下行，WebRTC 负责超低延迟双向，RTSP/RTP 负责监控与实时流。

关键词：延迟、丢包、拥塞控制、ABR、CDN。

④ 解码 / 渲染 还原

解封装 → 解码 → 色彩转换 → 显示；音频经抖动缓冲、重采样、混音后送到声卡。硬件解码/编码把这条链搬到 GPU/ASIC。

关键词：DPB、零拷贝、HDR、A/V sync。

🔗三个契约：像素格式（如 NV12 / yuv420p / P010）连接采集与编码；码流格式（如 Annex B / AVCC / OBU）连接编码与容器；时间基（如 1/90000 / 1/1000）连接容器与传输。排障时先定位哪个契约被破坏。

延迟都花在哪里？

环节典型延迟可控手段
采集 + ISP10–40 ms相机低延迟模式、关闭后处理
编码5–60 ms低延迟 preset、关闭 B 帧/lookahead
封装 / 切片0–6000 msLL-HLS、短 segment、fMP4
网络 / CDN10–200 ms就近边缘、专线、SRT/WebRTC
播放器缓冲0.2–30 s低延迟模式、目标缓冲、追帧
解码 / 渲染5–30 ms硬解、vsync、音频时钟对齐

三种典型延迟档

超低延迟（< 1 s）：WebRTC / SRT + 低延迟编码。用于会议、连麦、远程操控、云游戏。代价是复杂度、NAT 穿透与抗丢包。

低延迟（1–5 s）：HTTP-FLV、LL-HLS、低延迟 DASH。用于电商直播、互动直播。CDN 友好，成本可控。

标准延迟（10–30 s）：HLS/DASH 常规分片。用于点播、赛事回看、大规模分发。抗抖动能力最强。

延迟不是单一数字：首帧时间、端到端延迟、卡顿率、直播延迟稳定性要分开度量。低延迟往往以卡顿率为代价。

⚠️最常见的“直播卡顿”不是网络问题，而是编码器 GOP 过长 + 播放器等待 IDR。直播场景通常把关键帧间隔设为 1–2 秒，并让切片边界对齐 IDR。

📐 码率、存储与延迟

先建立数量级直觉，再谈参数。以下公式默认 8 bit、4:2:0、无压缩。

Rraw = W × H × fps × bpp   |   bpp4:2:0 = 8 + 8/2 + 8/2 = 12 bit/pixel

1080p30 4:2:0 8bit：1920 × 1080 × 30 × 12 ≈ 746 Mbit/s ≈ 93 MB/s。这就是为什么必须压缩：H.264 用 4–8 Mbps 就能达到可接受画质，压缩比约 100–200 倍。

存储(GB/小时) = 码率(Mbps) × 3600 / 8 / 1000 = 码率 × 0.45

例：4 Mbps 直播录 1 小时 ≈ 1.8 GB；20 路 4 Mbps 录 30 天 ≈ 20 × 1.8 × 24 × 30 ≈ 25.9 TB。做容量规划时再乘 1.1–1.2 的封装与索引余量。

HLS 延迟 ≈ 3 × target duration + 播放器缓冲   |   LL-HLS ≈ 1–2 × part duration + 缓冲

6 秒分片、3 个分片窗口 → 约 18 秒 + 缓冲；改用 2 秒分片 + LL-HLS 的部分分片，可压到 2–5 秒。代价是请求数增加、CDN 命中率下降。

CBR

恒定码率，编码器用填充/码率控制维持峰值。适合带宽固定、直播。质量随内容复杂度波动。

VBR

可变码率，按复杂度分配比特。点播更高效；直播需要设置 maxrate/bufsize 防止突发。

CRF

恒定质量因子（x264/x265），码率随内容变化。点播归档首选；数值越小质量越高（18–28 常用）。

🧭 双轴阅读法

媒体轴：内容如何被表示

像素 → 预测残差 → 变换系数 → 量化 → 熵编码 → NAL/OBU → 访问单元 → 容器 sample。

适合从 编解码 进入，再读 容器。你会理解为什么 SPS/PPS 必须随码流走、为什么 B 帧需要重排、为什么 4:2:0 的宽高必须是偶数。

传输轴：内容如何被送达

码流 → 封装单元 → 协议消息 → 网络包 → 抖动缓冲 → 解码。

适合从 协议 进入，再读 服务器 与 方案。你会理解 RTMP chunk 为什么这样切、SRT 的 ARQ 如何换延迟、WebRTC 为什么必须用 SFU。

两条轴的交点是时间戳与码流格式。建议每读一个容器就问三个问题：它的时间基是什么？它如何随机访问？它如何携带编码参数？

⚡ 快速开始

用 FFmpeg 把“容器 / 编码 / 协议”这三件事串起来。先探测，再转码，再切片，最后推流。

# 1. 看清一个文件里到底有什么：流、编码、时间基、码率、关键帧
ffprobe -hide_banner -show_streams -show_format -show_packets -select_streams v:0 input.mp4

# 2. 高质量转 H.264 + AAC MP4（Web 兼容：yuv420p + faststart）
ffmpeg -i input.mov -c:v libx264 -preset medium -crf 23 \
  -profile:v high -level 4.1 -pix_fmt yuv420p \
  -c:a aac -b:a 128k -movflags +faststart output.mp4

# 3. 生成 HLS 多档（先转码，再切片；切片边界必须对齐 IDR）
ffmpeg -i input.mp4 -c:v libx264 -crf 22 -g 48 -keyint_min 48 -sc_threshold 0 \
  -c:a aac -b:a 128k -f hls -hls_time 4 -hls_playlist_type vod \
  -hls_segment_filename 'seg_%03d.ts' index.m3u8

# 4. 推 RTMP 到本地 SRS / MediaMTX（低延迟：关闭 B 帧、短 GOP）
ffmpeg -i input.mp4 -c:v libx264 -preset veryfast -tune zerolatency \
  -g 30 -bf 0 -b:v 2500k -maxrate 2500k -bufsize 5000k \
  -c:a aac -b:a 128k -f flv rtmp://127.0.0.1/live/stream

# 5. 查看硬件能力（Linux / Windows / macOS 各有不同后端）
ffmpeg -hide_banner -hwaccels
ffmpeg -hide_banner -encoders | grep -E 'nvenc|qsv|vaapi|videotoolbox|amf'
🧪把第 4 条命令里的 -tune zerolatency、-g 30、-bf 0 分别去掉再推流，用播放器观察首帧与延迟——这是理解“编码参数如何影响延迟”的最快实验。

GOPGroup of Pictures，从一个 I 帧到下一个 I 帧之间的帧序列决定随机访问粒度、直播延迟与切片边界
