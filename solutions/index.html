音视频方案：
先算约束，再选技术

方案不是“把最火的组件拼在一起”，而是从四个约束反推：延迟能忍多少、并发有多大、网络有多差、预算怎么算。同一套 WebRTC，放在会议里是正解，放在万人在线直播里可能直接压垮预算。这一页用七类真实场景，把“链路、指标、技术栈”一条条拆开。

🧭 选型方法：先写约束表，再打开技术文档

选型像装修：先量房、问清楚住几个人、预算多少，再去挑地板。直接问“用什么协议最好”，就像不问户型就买瓷砖。把下面四列填完，答案通常会自己浮出来。

约束要问的问题影响的技术决策
延迟人能忍多久？是“看”还是“操作”？HLS → FLV → WebRTC/SRT 的选择；GOP 与缓冲策略
并发峰值多少人同时看？上行/下行谁更大？源站 + 边缘/CDN；SFU 还是 MCU；单机容量与带宽
网络局域网、公网、4G/5G、卫星？丢包率多少？SRT/FEC、ABR、多链路；是否必须 TURN 中继
成本按流量还是按带宽？存储要留多久？谁来转码？码率阶梯、存储分层、GPU/CPU 转码、CDN 计费模型
🔍一个反直觉的事实：延迟每降低一档，成本往往不是线性增加。把 HLS 换成 WebRTC，可能要新增 TURN、边缘节点和更高的运维复杂度；把 1080p 降到 720p，反而可能同时降低带宽、转码和存储三项成本。先找“约束里最硬的那一条”，再为它付费。

📺 直播：一条单向传送带，延迟与成本在两头拉扯

直播像一条单向传送带：主播把货放上去，服务器分拣，观众从不同出口取货。传送带本身不加工，只负责“尽快、稳定地复制”。真正的取舍在出口：HLS 兼容性最好但慢，FLV 快一点但要 MSE，WebRTC 最快但并发贵。

采集 / 编码OBS、FFmpeg、硬件编码
→
推流RTMP / SRT / WHIP
→
源站SRS / ZLM / MediaMTX
→
分发HTTP-FLV / HLS / CDN
→
播放器MSE / hls.js / 原生

延迟

HLS 常规 6–30 s，LL-HLS 约 2–5 s；HTTP-FLV 1–3 s；WebRTC 0.3–1 s。延迟预算是“编码 + 切片 + 缓冲 + 网络”的总和，不要只盯着协议名。

并发

瓶颈通常是出口带宽与连接数，不是 CPU。源站只服务边缘，观众连边缘；单机并发要按“码率 × 人数”算，不要按“能开多少进程”算。

成本

CDN 流量是大头，转码是固定成本，存储（录制/回看）是长尾成本。降低码率、减少档位、缩短录制保留期，通常比换服务器更省钱。

推荐技术栈：OBS / FFmpegRTMP 或 SRT 推流SRS / ZLMediaKitHTTP-FLV 低延迟HLS + CDN 大规模WebRTC/WHEP 强互动

💡首屏与延迟要分开优化。缩短 GOP 能让首帧更快，但码率会上升；LL-HLS 能降延迟，但切片更碎、请求更多。先用 播放器页 的方法量出“首帧时间”和“稳定延迟”，再决定要不要为最后 2 秒多付一倍成本。

🎞️ 点播：把一次上传，变成很多种“尺码”

点播像服装店：同一件衣服要备 S/M/L 几个尺码，顾客按身材挑。视频也一样，一次上传后转成多档分辨率/码率，播放器根据带宽切换。点播不追求“实时”，追求“起播快、拖动顺、长尾便宜”。

→
对象存储原片 + 转码产物
→
转码农场H.264 / HEVC / AV1 多档
→

播放器ABR 自适应

延迟 / 起播

点播不要求低延迟，但要求起播快：moov/faststart、首片足够小、CDN 命中率高。拖动要快，靠的是关键帧间隔与索引，而不是更快的服务器。

并发

点播并发是“长尾分布”：热门内容少数几个文件承担大部分流量，冷门内容占用存储。CDN 缓存命中率决定回源压力。

成本

存储 + 转码 + CDN 三块。档位不是越多越好：多一档就多一份存储与转码，且低档位未必有人看。按实际播放分布裁剪。

推荐技术栈：对象存储 / 分片上传FFmpeg 转码农场HLS / DASH + ABRCDN + 缓存策略hls.js / dash.js / 原生

⚠️ABR 不是“档位越多越专业”。每增加一档，就要多转一次、多存一份、多维护一条播放列表；如果最低档码率仍然高于弱网可用带宽，ABR 也救不了。先按“目标设备 + 网络分布”定 3–5 档，再用播放数据调整。

🎙️ 视频会议：不是“把直播反过来”，而是多人对讲

会议像一间圆桌会议室：每个人都同时说、同时听，服务器要做的是“把每个人的声音分发给其他人”，而不是把一路流广播给所有人。这就是 SFU（选路转发）与 MCU（混流）的区别：SFU 省 CPU、保留单独音轨；MCU 省客户端带宽、但服务器要解码混流。

终端 A采集 + 编码 + 回声消除
⇄
SFUJanus / LiveKit / mediasoup
⇄
TURNNAT 穿透失败时中继
⇄
终端 B / C解码 + 混音 + 渲染
→
录制 / 转推可选

延迟

目标通常在 300 ms 以内，否则对话会“抢话”。除了网络，回声消除、抖动缓冲、编码延迟都会吃掉预算。

并发

按“房间数 × 每房间路数 × 码率”估算 SFU 出口。10 人 720p 会议，SFU 要向每人转发另外 9 路，出口压力远大于单人直播。

成本

TURN 中继流量、SFU 带宽、录制存储。企业内网可直连时成本低；公网大规模会议必须把 TURN 与边缘算进去。

推荐技术栈：WebRTC（ICE / DTLS / SRTP）Janus / LiveKit / mediasoup（以官方文档为准）coturnSFU + 服务端混流（可选）录制 / 转推

🔍会议排错优先看 ICE，而不是编码。“一方黑屏、另一方正常”多半是某条候选路径不通；“全员卡顿”才更像带宽或 SFU 过载。TURN 不是可选项——在企业防火墙下，它经常是唯一能通的路径。

📹 安防监控：先有“可靠取流”，再谈“好看”

安防像一栋楼的消防系统：平时没人注意，出事时必须能看到、能回放、能证明。技术链路通常不是从 websocket 开始，而是从 SIP 注册、目录、点播、PS over RTP 开始。浏览器只是最后一环，前面任何一环断了，画面都不会出现。

IPC / NVRGB28181 设备
→
SIP 平台wvp-GB28181-pro
→
媒体服务器ZLMediaKit 收流
→
协议转换FLV / HLS / WHEP
→
客户端Web / 电视墙 / App

延迟

实时监看通常 0.5–2 s 可接受；电视墙对延迟更敏感。回放不追求实时，但要求拖动后尽快出关键帧。

并发

摄像头数量多、观看人数少，是典型“多路小流量”。瓶颈常在收流端口段、SIP 会话数与按需拉流的调度，而不是单路带宽。

成本

7×24 存储是长尾大头；实时观看带宽是次要成本。按“路数 × 码率 × 保留天数”算存储，比按“总摄像头数”拍脑袋可靠。

推荐技术栈：GB/T 28181wvp-GB28181-pro + ZLMediaKitFLV / HLS / WHEP 出口按需拉流 + 录像回放电视墙 / 客户端

⚠️“注册成功”不等于“能看”。注册只证明设备在线，目录证明有通道，INVITE 证明点播协商成功，RTP/PS 到达且 SSRC 匹配才证明流真的来了。排错顺序与抓包方法见 GB28181 专页。

🎮 云游戏 / 远程桌面：把“显卡”搬到离用户更近的地方

云游戏像把游戏机房搬到小区门口：画面在云端渲染，编码后通过网络送到你家屏幕，你的操作再传回去。它和直播最大的不同是“双向 + 极低延迟”：超过 100 ms，玩家就能感觉到“手不跟眼”。

云端 GPU渲染 + NVENC
→
零拷贝显存直通编码器
→
边缘节点WebRTC / SRT
→
接入网5G / 宽带
→
客户端硬解 + 低延迟缓冲

延迟

目标通常是端到端 30–80 ms（网络条件好时）；编码、传输、解码、显示各占一段。超过 100 ms 后，操作类场景的体验明显下降。

并发

并发单位是“GPU 会话”而不是“观众”。一张卡能切多少路，取决于分辨率、帧率、编码器与显存；不是软件能无限扩。

成本

GPU 机时 + 边缘带宽。1080p60 的码率远高于直播，按流量计费会很贵；通常用“包月 GPU + 边缘节点”模式。

推荐技术栈：NVENC / VAAPI 硬件编码零拷贝（GPU 显存直通）WebRTC（低延迟）边缘节点 + 就近接入硬解客户端

💡云游戏不是“把视频编码参数调低”就能做。编码器本身的帧级延迟、抖动缓冲、垂直同步都会累积。硬件编码的 low-latency 模式与零拷贝链路，往往比换协议更能减少那 20 ms。具体参数以各 GPU 厂商文档为准。

📱 短视频：一次上传，长期被反复播放

短视频像便利店货架：商品不多，但每天被很多人拿起来看一眼。它不追求实时，追求“起播快、滑动不卡、单次观看成本低”。因此重点不在推流协议，而在转码档位、CDN 命中率与播放器预加载。

手机拍摄可变帧率 / HDR
→
上传分片 + 断点续传
→
转码 / 审核多档 + 封面 + 内容审核
→
CDNHLS / DASH + 预热
→
Feed 播放器预加载 + ABR

延迟 / 起播

目标通常是首帧 < 200–500 ms。靠的是短 GOP、小首片、预加载与 CDN 命中，而不是更强的服务器。

并发

DAU 很大但单次时长短，流量呈“脉冲式”。CDN 边缘缓存与热门内容预热，比源站扩容更有效。

成本

单次观看成本 = 码率 × 时长。降低 10% 码率、裁剪无人观看的档位，长期收益远大于一次性采购折扣。

推荐技术栈：分片上传FFmpeg 多档转码HLS / DASHCDN + 预热Feed 播放器预加载

🚚 车载 / 弱网：网络像一条会断的路，方案要会“绕路”

车载图传像在颠簸的公路上送快递：丢包、抖动、切换基站、隧道断线都是常态。这里最不该做的是“假设网络稳定”。SRT 的 ARQ、FEC、可配置延迟，加上多卡聚合与本地缓存，才是主线。

车载摄像头H.265 / 多路
→
编码 / 封装低码率 + 短 GOP
→
SRT / WebRTCARQ + FEC
→
多链路4G/5G 双卡聚合
→
边缘接入MediaMTX / ZLM

延迟

可接受范围通常比会议宽：200 ms–2 s 都可能；SRT 的延迟缓冲是可配置的，用延迟换稳定是常见选择。

并发

瓶颈在上行：一辆车能推几路，取决于基站上行与套餐。多路场景优先降分辨率/帧率，而不是加天线。

成本

蜂窝流量是主要成本。H.265、按需上传（事件触发）、本地缓存回传，通常比全程高清上传更划算。

推荐技术栈：H.265 / AV1（视设备支持）SRT（ARQ + FEC）多链路聚合边缘接入（MediaMTX / ZLM）本地缓存 / 断点续传

⚠️别在弱网里追求“零延迟”。网络已经丢包时，越小的缓冲越容易花屏/卡死。SRT 的延迟参数、FEC 开销、码率自适应要一起调；只改其中一个，通常只是把“卡顿”换成“糊”。

🌳 决策树：从需求反推方案

把前面的约束压缩成几个“是/否”，从根往下走，叶子就是起点方案。它不是标准答案，而是帮你排除明显不合适的技术，避免一上来就陷入“哪个服务器最好”的争论。

读法：从顶部往下。以“安防监控”为例——不是双向互动 → 需要长期保存 → 不是用户上传短视频 → 源是摄像头且需 7×24 监看 → 落到“GB28181 + ZLM + 网关”。如果其中任一条答案不同，就应该换叶子，而不是硬套。

💰 成本估算：先把“带宽 × 码率”算清楚

音视频的成本像水费：单价不高，但一直流。最容易算错的是单位——Mbps 是“每秒多少兆比特”，GB 是“字节”，中间差一个 8，还有 1024。先把公式写对，再谈采购折扣。

峰值带宽(Mbps) = 单路码率(Mbps) × 并发路数 × (1 + 冗余比例)
流量(GB) = 码率(Mbps) × 时长(s) ÷ 8 ÷ 1024

另外两笔容易被忽略的账

存储：按“路数 × 码率 × 保留天数”

4 Mbps 连续录制：每小时约 1.76 GB，每天约 42.2 GB，每月约 1.24 TB/路。100 路、保留 30 天约 124 TB。若示例单价 ¥0.15/GB/月，仅存储就约 ¥19,000/月——通常比实时观看更贵。

固定带宽：按“并发 × 码率 × 冗余”

4 Mbps × 1000 并发 × 1.2 ≈ 4.8 Gbps。若示例单价 ¥15/Mbps/月，约 ¥72,000/月。自建机房时，这笔钱替代了 CDN 流量费，不是额外叠加。

💡降本优先级通常是：先砍没人看的档位与超长保留期 → 再优化码率/编码器 → 最后才换更便宜的带宽。转码占的是机时，带宽占的是持续现金流；先动后者，账面上更快见效。

✅ 落地检查清单：上线前先过这五关

方案写得再漂亮，落地时也会被端口、证书、鉴权和时间戳打回原形。下面这份清单按“先能通、再能看、最后能运营”的顺序排列，适合在项目评审时逐条打勾。

关卡要确认的事验收方式
① 约束延迟目标、峰值并发、网络类型、预算上限是否写成数字把“尽量低延迟”换成“P95 < 800 ms”这样的句子
② 协议最后一公里给浏览器什么协议；是否需要转码；是否需要 TURN用最小 demo 验证，不靠 PPT
③ 容量峰值带宽、存储月增、转码机时是否算过用本页公式代入真实码率与并发
④ 部署SIP/RTSP/RTMP/SRT/ICE 所需端口是否整段放行；证书与域名是否就绪从外网真实拨测，不只看内网
⑤ 可观测首帧时间、卡顿率、断流率、回源率、鉴权失败率是否有指标每一路流都能回答“卡在哪一层”
⚠️三个常见反模式：① 用 WebRTC 承载万人大直播，TURN 账单先爆；② 所有内容只留一个 1080p 档，弱网用户体验和带宽成本同时失控；③ 把“服务器能启动”当成“方案能上线”，跳过了端口、跨域、ICE 与鉴权验证。方案页的价值不在于列组件，而在于提前把这些坑写进验收表。
