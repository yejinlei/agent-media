浏览器内直播实验台：
把一个标签页变成媒体服务器

不需要安装任何东西。开三个标签页，分别扮演推流端、服务器、观众端，跑通一条完整的直播链路：WebRTC 真推流（WHIP 式信令）→ 服务器转发分发 → WebRTC 低延迟拉流（WHEP 式）+ Service Worker 当 HLS 与 DASH 双真源站（hls.js / Shaka 走真实 HTTP 拉流）。这就是媒体服务器的全部核心职责——只是把 TCP/UDP 换成了浏览器允许的三件武器。

🧱 协议边界：哪些真实、哪些模拟、哪些物理不可能

浏览器禁止网页监听任何 TCP/UDP 端口，也没有 raw socket——这对 SRS / ZLMediaKit / MediaMTX / nginx-rtmp 一视同仁，编译成 wasm 也开不了端口。但浏览器自己给了三件"服务器武器"，本实验台把它们用到极限：

方向协议本实验台说明
推流（接入）WebRTC（WHIP 式 HTTP 信令）真实浏览器唯一能"真推流"的协议；信令走 BroadcastChannel（同一台浏览器内），媒体走 RTCPeerConnection
拉流（分发）WebRTC（WHEP 式）真实服务器标签页把收到的 track 转发给 N 个观众——一个微型 SFU
拉流（分发）HLS真实MediaRecorder 产出 fMP4 分段 → Service Worker 拦截同源 fetch 当 HTTP 源站 → hls.js 真实拉流播放
拉流（分发）DASH（MPEG-DASH）真实与 HLS 共用同一批 fMP4 分段，只多推一份 live.mpd（SegmentTemplate 展开 $Number$）→ Shaka Player 真实拉流播放
推 / 拉RTMP · RTSP · SRT · GB28181物理不可能需要监听端口，浏览器沙箱禁止；wasm 无 socket。→ 用下面的真服务器联调卡对接
拉流（分发）HTTP-FLV预留Service Worker 同样能响应（sw 源站架构已就位），后续版本加入
🧩为什么标签页能当"服务器"？三件武器：① WebRTC——页面可以主动与另一个页面建立点对点连接，收到的 track 可以再 addTrack 转发给别人（转发 = SFU 的本质）；② Service Worker——能拦截并响应同源 fetch，等于一个网页内 HTTP 服务器；③ BroadcastChannel——同源多标签页零部署消息总线，充当信令通道。

🧪 实验：三步跑通直播全链路

把本页开 2–3 个标签页（同一浏览器、同一网站即可）。每个标签页在下面选一个角色：📡 推流端往服务器推流，🖥️ 服务器负责接入、转发、HLS 分发和观众管理，👀 观众端选一种协议拉流观看。也可以单标签页自测：服务器角色开启"本地测试源自播"，直接在页内看 HLS 效果。

HLS 地址：lab-hls/live.m3u8

转发原理：收到推流端的 ontrack 后保存 MediaStream；每个观众连接时 addTrack 同一批 track——这就是 SFU 转发的最小实现，不转码、只路由。

HLS / DASH 源站原理：MediaRecorder 以 2s 时间片录制 fMP4，页面拆出 init 段与媒体段（init.mp4 + seg-N.m4s）推给 Service Worker；任何标签页/播放器请求 lab-hls/live.m3u8 或 lab-hls/live.mpd 都被 SW 用内存中的清单与分段响应。两种格式共用同一批分段，只是清单语法不同——HLS 用 #EXT-X-MAP，DASH 用 SegmentTemplate。

🐳 真服务器联调卡：MediaMTX / ZLMediaKit / SRS

要推 RTMP / RTSP / SRT、要跨设备观看、要 GB28181——就需要真的媒体服务器（监听端口这件事浏览器做不了，wasm 也不行）。下面三个都是"解压即用"级别的小型稳定服务器；起一个之后，把它的播放地址粘进下面的播放器直接验证。

MediaMTX（最轻，单二进制）

docker run --rm -it \
  -p 8189:8189/udp -p 1935:1935 \
  -p 8888:8888 -p 8889:8889 \
  bluenviron/mediamtx

推：ffmpeg -re -f lavfi -i testsrc -c:v libx264 -f flv rtmp://127.0.0.1/live/test
看（WHEP）：http://127.0.0.1:8889/test/whep
看（HLS）：http://127.0.0.1:8888/test/index.m3u8

ZLMediaKit（国产 · GB28181 友好）

docker run --rm -it \
  -p 554:554 -p 1935:1935 -p 8080:8080 \
  -p 10000:10000 -p 10000:10000/udp \
  zlmediakit/zlmediakit:master

推：ffmpeg ... -f flv rtmp://127.0.0.1/live/test
看（HLS）：http://127.0.0.1:8080/live/test/hls.m3u8
（Windows 也可直接下载 release 单文件运行）

SRS（老牌直播源站）

docker run --rm -it \
  -p 1935:1935 -p 8080:8080 \
  -p 1985:1985 -p 8000:8000/udp \
  ossrs/srs:5

推：ffmpeg ... -f flv rtmp://127.0.0.1/live/livestream
看（WHEP）：http://127.0.0.1:1985/rtc/v1/whep/?app=live&stream=livestream
看（HLS）：http://127.0.0.1:8080/live/livestream.m3u8
注：SRS 5 已无内置 RTSP 服务端（主打 RTMP/SRT/HLS/FLV/WebRTC）。

xiu（纯 Rust · 极轻，边缘设备友好）

cargo install xiu

看（FLV）：http://127.0.0.1:8081/live/test.flv
看（HLS）：http://127.0.0.1:8080/live/test.m3u8
端口以自带 config.toml 为准。

lal（Go · 原生 GB28181，安防场景）

选型一句话

MediaMTX：全协议收发、配置最少，浏览器联调首选；ZLMediaKit：国标+全协议、Windows 单文件；SRS：RTMP 直播集群成熟；xiu：资源占用极低的轻量节点；lal：要 GB28181 又想避开 ZLM 重度配置时选它。共同点：都需要真端口，所以浏览器/wasm 替代不了它们——浏览器内实验台教的是原理，这五家才是生产答案。

🗺️ 与全站的关系

这里的"服务器"演示的是转发与分发职责。协议字节本身（RTMP chunk、RTSP 时序、HLS 清单结构）在协议页逐条拆解；浏览器侧播放技术（WHEP/hls.js/mpegts.js）在播放器页；wasm 就地解析（ffprobe）在WASM 页。四页合起来，就是"从摄像头到观众"的完整本体论。
