多媒体服务器：
不是加工厂，是转运中心

很多人把“流媒体服务器”想象成一台不停转码的机器。它更像快递转运中心：把一种运输方式送来的包裹收下，拆掉外箱、重新贴单，再用另一种方式送出去。延迟、并发和成本，取决于你让它“拆到哪一层”，而不是 CPU 有多强。

🚉 服务器到底在做什么：收、拆、贴、发

媒体服务器最常见的四种动作：接收（ingest，摄像头或主播推流进来）、转封装（remux，把 RTSP 的 RTP 包换成 FLV/HLS/WebRTC 需要的形式）、分发（把同一路流发给很多播放器）、按需拉流（有人看才去拉上游，没人看就断开）。它通常不转码——转码是另一台“加工厂”的活。

把这个边界认清，选型会简单很多：如果只是“RTSP 摄像头给浏览器看”，需要的是转封装 + WebRTC 网关；如果需要“把 4K 源压成 720p 再分发”，那就要在链路里加转码节点（FFmpeg、GPU 转码或服务器内置的转码能力），而不是指望一台轻量转发服务器帮你省带宽。

接入层（Ingest）

接收 RTSP/RTMP/SRT/WebRTC 推流，维持会话、鉴权、断线重连。并发压力主要在这里和网络带宽上。

源站（Origin）

保存并转发同一路流，生成 HLS/DASH 切片，提供 FLV/WebRTC 出口。通常是单点或小集群。

边缘（Edge）

从源站回源，承担大量观众。回源协议常见 RTMP/SRT，边缘只做转发，不再向上游重复拉流。

🔍先问一句：这路流需要“被处理”吗？只换协议，选轻量转发（MediaMTX）；要国标接入与多协议出口，选 ZLMediaKit；要做直播源站与集群，选 SRS；只做 WebRTC 会议网关，选 Janus；只是维护老系统，才考虑 nginx-rtmp。把“转发”和“转码”混为一谈，是最常见的选型错误。

🛣️ 协议与延迟地图：卡车、专线、对讲机、连载小说

RTMP 像专线卡车：稳定、生态成熟，但需要 Flash 时代留下的通道；RTSP 像遥控器：适合和摄像头一对一对话；SRT 像带纠错单号的快递：能在公网丢包环境下把货补齐；WebRTC 像双向对讲机：延迟最低，但要处理 ICE、DTLS、SRTP；HLS 像“切片连载小说”：兼容性最好，代价是切片与缓冲带来的延迟。

协议传输典型延迟浏览器原生支持典型用途
RTSPTCP / UDP（RTP）0.2–1 s（局域网）否摄像头、NVR、局域网监看
RTMPTCP 19351–3 s否（需 FLV.js）直播推流、源站回源
HTTP-FLVHTTP（长连接）1–3 s否（需 MSE）低延迟网页直播
HLSHTTP（切片）6–30 s；LL-HLS 约 2–5 s是点播、大规模直播、移动端
SRTUDP0.3–2 s（可配）否弱网推流、跨公网回源
WebRTCUDP（SRTP）+ ICE0.2–1 s是会议、云游戏、低延迟监看

延迟是“端到端典型值”，会随 GOP、缓冲策略、网络与播放器实现变化，不是协议标准的一部分。HLS 的延迟主要来自切片时长与播放器起播缓冲，而不是编码本身。

⚠️浏览器不是万能播放器。Chrome 不认 RTSP，不认裸 RTMP；能直接播的是 HLS（Safari 原生、Chrome 需 MSE 或 hls.js）和 WebRTC。所谓“网页看 RTSP”，中间一定有一台服务器帮你转成 HLS/FLV/WHEP。选型时先确定“最后一公里”给浏览器什么协议。

🧩 MediaMTX：一个二进制，把四种协议接在一起

MediaMTX（前身 rtsp-simple-server）像一座小型转运站：Go 写的单二进制，默认就开 RTSP、RTMP、HLS、WebRTC、SRT，配置文件按“路径（path）”组织。一条路径既可以是被推流的目标，也可以是按需从上游拉来的源。它不做国标 SIP，也不做复杂转码，定位就是“轻量、好部署、协议转换”。

# mediamtx.yml（节选；键名与默认值以官方文档为准）
rtspAddress: :8554
rtmpAddress: :1935
hlsAddress: :8888
webrtcAddress: :8889
srtAddress: :8890
apiAddress: :9997
hlsAllowOrigin: '*'

paths:
  cam1:
    # 有人观看时才去拉上游，最后一个人离开 10 秒后断开
    source: rtsp://user:pass@192.168.1.64:554/Streaming/Channels/101
    sourceOnDemand: yes
    sourceOnDemandCloseAfter: 10s

  live:
    # 没有 source：等待外部推流进来
    record: no
# 推到 live 路径
ffmpeg -re -i in.mp4 -c:v libx264 -preset veryfast -tune zerolatency \
  -f flv rtmp://server:1935/live

# 从 cam1 拉 RTSP（也可以让服务器按需回源）
ffplay -rtsp_transport tcp rtsp://server:8554/cam1

# 浏览器播放：HLS / WebRTC(WHEP)
# http://server:8888/cam1/index.m3u8
# http://server:8889/cam1/whep

MediaMTX 的默认端口是 8554（RTSP）、1935（RTMP）、8888（HLS）、8889（WebRTC HTTP）、8890（SRT）、9997（API）。部署在 NAT/云主机后，WebRTC 还需要把公网地址告诉 ICE（例如 webrtcAdditionalHosts），否则浏览器只能拿到内网候选地址。

🧰 ZLMediaKit：多协议 + 国标接入的“国产瑞士军刀”

ZLMediaKit 更像一座带报关窗口的转运中心：除了 RTSP/RTMP/HLS/HTTP-FLV/WebRTC/SRT，它原生支持 GB28181 的 RTP/PS 收流，还能通过 HTTP API 与 hook 被业务系统编排。国内常见的组合是“wvp-GB28181-pro 管 SIP 信令与业务，ZLM 管媒体收流与转协议”。

# config.ini（节选，键名与默认端口以官方文档为准）
[protocol]
enable_rtsp=1
enable_rtmp=1
enable_hls=1
enable_fmp4=1
enable_mp4=0
enable_rtc=1

[rtp_proxy]
# GB28181 收流端口段；示例值，必须与防火墙/端口映射一致
port_range=30000-30500

[http]
port=80

按需拉流在 ZLM 里通常由两件事配合完成：hook（例如“无人观看”时通知业务层）与 HTTP API（例如按需打开/关闭 RTP 收流端口）。国标点播时，wvp 先通过 SIP 让设备推流，再调用 ZLM 的 openRtpServer 分配收流端口；没人看时关闭端口并让设备停止推流，避免 7×24 空转。

# 最小启动（端口段需与 config.ini 和防火墙一致）
docker run -d --name zlm \
  -p 1935:1935 -p 8080:80 -p 554:554 \
  -p 10000:10000/udp \
  -p 30000-30500:30000-30500/udp \
  -p 5060:5060/udp -p 5060:5060/tcp \
  -v $PWD/zlm/config.ini:/opt/media/conf/config.ini \
  zlmediakit/zlmediakit:master

# HTTP API 示例（实际参数与返回结构见官方 API 文档）
# /index/api/openRtpServer?port=30000&tcp_mode=1&stream_id=test
# /index/api/closeRtpServer?stream_id=test
💡国标链路的关键不是 ZLM，而是“端口账”。SIP 5060（UDP/TCP）要通、RTP 收流端口段要整段放行、设备侧要能访问到平台的收流地址。三者缺一，表现就是“注册成功、点播 200 OK、但画面不来”。国标细节见 GB28181 专页。

📡 SRS：直播源站与边缘集群的老牌选手

SRS 像一家成熟的快递网络：RTMP 是它的主干线路，HLS/HTTP-FLV/WebRTC/SRT 是不同出口。它擅长“源站 + 边缘”的层级分发：边缘节点从源站回源，观众只连边缘，源站不会被每个观众直接压垮。

# srs.conf（节选；不同大版本的指令有差异，以官方文档为准）
listen              1935;
max_connections     1000;
http_server {
    enabled         on;
    listen          8080;
    dir             ./objs/nginx/html;
}
vhost __defaultVhost__ {
    hls {
        enabled     on;
    }
    http_remux {
        enabled     on;
        mount       [vhost]/[app]/[stream].flv;
    }
    rtc {
        enabled     on;
        rtmp_to_rtc on;
        rtc_to_rtmp on;
    }
}

集群的典型做法：源站开启 forward 把流推到边缘，边缘不再回源给观众；或者让边缘按需回源。配置项名称、WebRTC 端口与证书要求随版本变化，落地前先对照官方文档与示例配置。

源站（Origin）

接收主播推流，负责切片与回源服务。通常只部署少量实例，关注上行带宽与磁盘（HLS 切片）。

边缘（Edge）

从源站拉流并服务观众。可水平扩展，关注出口带宽与并发连接数；回源链路要稳定，否则边缘会放大故障。

🎛️ Janus：只做 WebRTC 的“会议室网关”

Janus 不是通用媒体服务器，而是一座 WebRTC 网关：它把浏览器的 PeerConnection 接到服务端，再通过“插件”决定这间屋子是会议室、直播分发、SIP 网关还是录制器。它像一栋写字楼：楼里有很多会议室（插件），但楼本身不生产内容。

插件（示例）用途典型场景
janus.plugin.videoroom多人音视频房间（SFU）视频会议、在线课堂
janus.plugin.streaming把 RTSP/RTMP 等流分发给多个 WebRTC 观众低延迟监看、直播
janus.plugin.sipWebRTC 与 SIP 互通呼叫中心、传统电话网
janus.plugin.echotest回声测试连通性排查、媒体质量验证

Janus 的部署难点不在“装起来”，而在 NAT 与 ICE：它必须让浏览器拿到可达的候选地址，必要时配合 STUN/TURN；信令层通常是你自己的业务服务器通过 REST/WebSocket 调 Janus，而不是让浏览器直连。媒体端口段、证书、鉴权 token 都要在配置里明确声明。

⚠️Janus 不做 HLS，也不做 RTMP 接入。如果业务同时需要“会议 + 大规模 HLS 回看”，通常要组合部署（Janus 负责实时房间，SRS/ZLM 负责直播与录制），而不是硬让一个组件干所有事。

🧱 nginx-rtmp：能用，但别拿它开新局

nginx-rtmp-module 像一辆还能启动的老卡车：RTMP 推拉、HLS 切片、简单的 stat 页面都有，部署也不复杂。但它长期缺少活跃维护，不支持 WebRTC/SRT，复杂的按需拉流与集群能力也有限。维护遗留系统可以继续用，新项目更适合 SRS/ZLM/MediaMTX。

# nginx.conf（节选）
rtmp {
    server {
        listen 1935;
        application live {
            live on;
            record off;
            hls on;
            hls_path /tmp/hls;
            hls_fragment 4s;
        }
    }
}
http {
    server {
        listen 8080;
        location /hls {
            types {
                application/vnd.apple.mpegurl m3u8;
                video/mp2t ts;
            }
            root /tmp;
            add_header Cache-Control no-cache;
        }
    }
}

注意：HLS 切片目录要由 HTTP 服务暴露，且 Cache-Control 不能缓存 m3u8；RTMP 本身不携带鉴权，推流密钥通常靠 URL 参数 + 业务校验。上述指令在不同分支/模块版本中可能略有差异，以所使用模块的文档为准。

🐳 最小 Docker：三条命令先跑起来

先用最小配置验证“推得进、拉得出”，再谈集群与鉴权。下面的端口映射是示例，实际要与配置文件、防火墙和安全组保持一致。

# MediaMTX：RTSP 8554 / RTMP 1935 / HLS 8888 / WebRTC 8889 / API 9997
docker run -d --name mediamtx \
  -p 8554:8554 -p 1935:1935 -p 8888:8888 -p 8889:8889 \
  -p 8890:8890/udp -p 9997:9997 \
  bluenviron/mediamtx:latest

# ZLMediaKit：注意 RTP 端口段要与容器内 config.ini 一致
docker run -d --name zlm \
  -p 1935:1935 -p 8080:80 -p 554:554 \
  -p 30000-30500:30000-30500/udp \
  -v $PWD/zlm/config.ini:/opt/media/conf/config.ini \
  zlmediakit/zlmediakit:master

# SRS：RTMP 1935 / API 1985 / HTTP 8080 / WebRTC 8000(UDP，示例)
docker run -d --name srs \
  -p 1935:1935 -p 1985:1985 -p 8080:8080 -p 8000:8000/udp \
  ossrs/srs:latest

Janus 通常需要从源码或社区镜像构建，且必须配置 NAT/ICE 与媒体端口段；镜像 tag 与配置项以官方文档/镜像页为准。容器化后最容易忘的是“UDP 端口段”——只映射 TCP 端口，WebRTC/SRT 一定失败。

💡验证顺序：① docker logs 看监听是否成功；② 用 FFmpeg 推一路测试流；③ 用 ffplay 拉 RTSP/FLV；④ 浏览器打开 HLS/WHEP；⑤ 最后才接业务鉴权。把变量分开，比一上来就调业务代码快。

🔀 推拉流路径图：一条流经过谁，在哪里变形

直播链路像一条传送带：采集端把流“推”进接入层，服务器在内部把一种包装换成另一种包装，分发层再把同一份内容复制给很多观众。观众“拉”的时候，拿到的往往不是原始码流，而是服务器转封装后的版本。

🧯 排错：端口、CORS、ICE、鉴权，四道门

媒体服务器“跑起来了”不等于“能看了”。下面四道门，任何一道没过，表现都可能是黑屏或一直转圈。按顺序验证，比在日志里翻找更快。

协议 / 组件示例端口传输常见坑
RTSP554 / 8554TCP（RTP 可 UDP）只开 TCP 没开 UDP；摄像头 URL 通道号写错
RTMP1935TCP推流 key 写错；防火墙只放行 80/443
SRT8890（示例）UDP只映射 TCP；streamid 与访问控制不匹配
WebRTC8889（HTTP）+ 动态 UDPTCP + UDPICE 只拿到内网地址；UDP 被禁；没配 TURN
HLS / HTTP-FLV8888 / 8080TCP跨域头缺失；m3u8 被缓存；切片目录未暴露
GB28181 SIP / RTP5060 / 30000–30500（示例）UDP/TCPRTP 端口段未整段放行；收流地址设备不可达

HLS、HTTP-FLV、WHEP 都是浏览器发起的 HTTP 请求，页面与流不在同一个源时，必须有正确的 Access-Control-Allow-Origin。常见配置入口：MediaMTX 的 hlsAllowOrigin，ZLM/SRS 的 HTTP 跨域开关（键名以各自文档为准）。不要用 * 搭配凭证请求，也不要把 CORS 当成鉴权。

WebRTC 失败先看候选地址：host 是内网、srflx 是 STUN 反射、relay 是 TURN 中继。云主机/容器部署要显式告诉服务器“我的公网地址是什么”，否则浏览器拿到 172.x/10.x 的候选，ICE 永远连不通。企业网禁 UDP 时，只能走 TURN/TCP 或换 HLS/FLV。

至少区分“推流鉴权”和“播放鉴权”：推流 key 泄露会导致别人冒名开播；播放 token 泄露会导致盗链。常见做法是业务服务器签发短时 token，媒体服务器通过 HTTP hook 或内置鉴权校验。不要在公开页面里硬编码长期密钥，也不要把 key 只放在 URL 里当唯一防线。

症状优先排查快速验证
推流成功，页面黑屏拉流协议是否被浏览器支持；CORS用 ffplay / VLC 拉同一路径；浏览器控制台看请求
HLS 一直转圈m3u8 是否可访问；切片是否生成；缓存头直接打开 m3u8 与首个 ts；看服务器日志
WebRTC 连不上ICE 候选、UDP、TURN、证书看 offer/answer 的候选类型；用 Trickle ICE 测试页
首个画面很慢GOP 过长；服务器等关键帧缩短 GOP；观察首个 IDR 到达时间
播放几分钟后卡死鉴权过期；按需拉流被断开；带宽不足对照 token 有效期与 sourceOnDemand 超时
⚠️四道门按顺序过：端口通 → 协议能握手 → 浏览器跨域允许 → 鉴权通过。任何一步跳过去，都会把问题带到下一层，最后变成“看起来像编码问题”的玄学。实在定位不了，就在服务器侧抓包，看请求有没有到、回包是什么。

🔗 与国标、播放器衔接：服务器只是中间那一跳

安防场景里，服务器前面是 SIP/PS 的国标世界，后面是 HTTP/WebRTC 的浏览器世界；直播场景里，服务器前面是推流端，后面是播放器与 CDN。把它放在链路中的正确位置，才知道该配什么、该测什么。
