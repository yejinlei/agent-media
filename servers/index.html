多媒体服务器：
不是加工厂，是转运中心

很多人把“流媒体服务器”想象成一台不停转码的机器。它更像快递转运中心：把一种运输方式送来的包裹收下，拆掉外箱、重新贴单，再用另一种方式送出去。延迟、并发和成本，取决于你让它“拆到哪一层”，而不是 CPU 有多强。

🚉 服务器到底在做什么：收、拆、贴、发

媒体服务器最常见的四种动作：接收（ingest，摄像头或主播推流进来）、转封装（remux，把 RTSP 的 RTP 包换成 FLV/HLS/WebRTC 需要的形式）、分发（把同一路流发给很多播放器）、按需拉流（有人看才去拉上游，没人看就断开）。它通常不转码——转码是另一台“加工厂”的活。

把这个边界认清，选型会简单很多：如果只是“RTSP 摄像头给浏览器看”，需要的是转封装 + WebRTC 网关；如果需要“把 4K 源压成 720p 再分发”，那就要在链路里加转码节点（FFmpeg、GPU 转码或服务器内置的转码能力），而不是指望一台轻量转发服务器帮你省带宽。

接入层（Ingest）

接收 RTSP/RTMP/SRT/WebRTC 推流，维持会话、鉴权、断线重连。并发压力主要在这里和网络带宽上。

源站（Origin）

保存并转发同一路流，生成 HLS/DASH 切片，提供 FLV/WebRTC 出口。通常是单点或小集群。

边缘（Edge）

从源站回源，承担大量观众。回源协议常见 RTMP/SRT，边缘只做转发，不再向上游重复拉流。

🔍先问一句：这路流需要“被处理”吗？只换协议，选轻量转发（MediaMTX）；要国标接入与多协议出口，选 ZLMediaKit；要做直播源站与集群，选 SRS；只做 WebRTC 会议网关，选 Janus；只是维护老系统，才考虑 nginx-rtmp。把“转发”和“转码”混为一谈，是最常见的选型错误。

🛣️ 协议与延迟地图：卡车、专线、对讲机、连载小说

RTMP 像专线卡车：稳定、生态成熟，但需要 Flash 时代留下的通道；RTSP 像遥控器：适合和摄像头一对一对话；SRT 像带纠错单号的快递：能在公网丢包环境下把货补齐；WebRTC 像双向对讲机：延迟最低，但要处理 ICE、DTLS、SRTP；HLS 像“切片连载小说”：兼容性最好，代价是切片与缓冲带来的延迟。

协议传输典型延迟浏览器原生支持典型用途
RTSPTCP / UDP（RTP）0.2–1 s（局域网）否摄像头、NVR、局域网监看
RTMPTCP 19351–3 s否（需 FLV.js）直播推流、源站回源
HTTP-FLVHTTP（长连接）1–3 s否（需 MSE）低延迟网页直播
HLSHTTP（切片）6–30 s；LL-HLS 约 2–5 s是点播、大规模直播、移动端
SRTUDP0.3–2 s（可配）否弱网推流、跨公网回源
WebRTCUDP（SRTP）+ ICE0.2–1 s是会议、云游戏、低延迟监看

延迟是“端到端典型值”，会随 GOP、缓冲策略、网络与播放器实现变化，不是协议标准的一部分。HLS 的延迟主要来自切片时长与播放器起播缓冲，而不是编码本身。

⚠️浏览器不是万能播放器。Chrome 不认 RTSP，不认裸 RTMP；能直接播的是 HLS（Safari 原生、Chrome 需 MSE 或 hls.js）和 WebRTC。所谓“网页看 RTSP”，中间一定有一台服务器帮你转成 HLS/FLV/WHEP。选型时先确定“最后一公里”给浏览器什么协议。

🧩 MediaMTX：一个二进制，把四种协议接在一起

MediaMTX（前身 rtsp-simple-server）像一座小型转运站：Go 写的单二进制，默认就开 RTSP、RTMP、HLS、WebRTC、SRT，配置文件按“路径（path）”组织。一条路径既可以是被推流的目标，也可以是按需从上游拉来的源。它不做国标 SIP，也不做复杂转码，定位就是“轻量、好部署、协议转换”。

# mediamtx.yml（节选；键名与默认值以官方文档为准）
rtspAddress: :8554
rtmpAddress: :1935
hlsAddress: :8888
webrtcAddress: :8889
srtAddress: :8890
apiAddress: :9997
hlsAllowOrigin: '*'

paths:
  cam1:
    # 有人观看时才去拉上游，最后一个人离开 10 秒后断开
    source: rtsp://user:pass@192.168.1.64:554/Streaming/Channels/101
    sourceOnDemand: yes
    sourceOnDemandCloseAfter: 10s

  live:
    # 没有 source：等待外部推流进来
    record: no
# 推到 live 路径
ffmpeg -re -i in.mp4 -c:v libx264 -preset veryfast -tune zerolatency \
  -f flv rtmp://server:1935/live

# 从 cam1 拉 RTSP（也可以让服务器按需回源）
ffplay -rtsp_transport tcp rtsp://server:8554/cam1

# 浏览器播放：HLS / WebRTC(WHEP)
# http://server:8888/cam1/index.m3u8
# http://server:8889/cam1/whep

MediaMTX 的默认端口是 8554（RTSP）、1935（RTMP）、8888（HLS）、8889（WebRTC HTTP）、8890（SRT）、9997（API）。部署在 NAT/云主机后，WebRTC 还需要把公网地址告诉 ICE（例如 webrtcAdditionalHosts），否则浏览器只能拿到内网候选地址。

🧰 ZLMediaKit：多协议 + 国标接入的“国产瑞士军刀”

ZLMediaKit 更像一座带报关窗口的转运中心：除了 RTSP/RTMP/HLS/HTTP-FLV/WebRTC/SRT，它原生支持 GB28181 的 RTP/PS 收流，还能通过 HTTP API 与 hook 被业务系统编排。国内常见的组合是“wvp-GB28181-pro 管 SIP 信令与业务，ZLM 管媒体收流与转协议”。

# config.ini（节选，键名与默认端口以官方文档为准）
[protocol]
enable_rtsp=1
enable_rtmp=1
enable_hls=1
enable_fmp4=1
enable_mp4=0
enable_rtc=1

[rtp_proxy]
# GB28181 收流端口段；示例值，必须与防火墙/端口映射一致
port_range=30000-30500

[http]
port=80

按需拉流在 ZLM 里通常由两件事配合完成：hook（例如“无人观看”时通知业务层）与 HTTP API（例如按需打开/关闭 RTP 收流端口）。国标点播时，wvp 先通过 SIP 让设备推流，再调用 ZLM 的 openRtpServer 分配收流端口；没人看时关闭端口并让设备停止推流，避免 7×24 空转。

# 最小启动（端口段需与 config.ini 和防火墙一致）
docker run -d --name zlm \
  -p 1935:1935 -p 8080:80 -p 554:554 \
  -p 10000:10000/udp \
  -p 30000-30500:30000-30500/udp \
  -p 5060:5060/udp -p 5060:5060/tcp \
  -v $PWD/zlm/config.ini:/opt/media/conf/config.ini \
  zlmediakit/zlmediakit:master

# HTTP API 示例（实际参数与返回结构见官方 API 文档）
# /index/api/openRtpServer?port=30000&tcp_mode=1&stream_id=test
# /index/api/closeRtpServer?stream_id=test
💡国标链路的关键不是 ZLM，而是“端口账”。SIP 5060（UDP/TCP）要通、RTP 收流端口段要整段放行、设备侧要能访问到平台的收流地址。三者缺一，表现就是“注册成功、点播 200 OK、但画面不来”。国标细节见 GB28181 专页。

📡 SRS：直播源站与边缘集群的老牌选手

SRS 像一家成熟的快递网络：RTMP 是它的主干线路，HLS/HTTP-FLV/WebRTC/SRT 是不同出口。它擅长“源站 + 边缘”的层级分发：边缘节点从源站回源，观众只连边缘，源站不会被每个观众直接压垮。

# srs.conf（节选；不同大版本的指令有差异，以官方文档为准）
listen              1935;
max_connections     1000;
http_server {
    enabled         on;
    listen          8080;
    dir             ./objs/nginx/html;
}
vhost __defaultVhost__ {
    hls {
        enabled     on;
    }
    http_remux {
        enabled     on;
        mount       [vhost]/[app]/[stream].flv;
    }
    rtc {
        enabled     on;
        rtmp_to_rtc on;
        rtc_to_rtmp on;
    }
}

集群的典型做法：源站开启 forward 把流推到边缘，边缘不再回源给观众；或者让边缘按需回源。配置项名称、WebRTC 端口与证书要求随版本变化，落地前先对照官方文档与示例配置。

源站（Origin）

接收主播推流，负责切片与回源服务。通常只部署少量实例，关注上行带宽与磁盘（HLS 切片）。

边缘（Edge）

从源站拉流并服务观众。可水平扩展，关注出口带宽与并发连接数；回源链路要稳定，否则边缘会放大故障。

🎛️ Janus：只做 WebRTC 的“会议室网关”

Janus 不是通用媒体服务器，而是一座 WebRTC 网关：它把浏览器的 PeerConnection 接到服务端，再通过“插件”决定这间屋子是会议室、直播分发、SIP 网关还是录制器。它像一栋写字楼：楼里有很多会议室（插件），但楼本身不生产内容。

插件（示例）用途典型场景
janus.plugin.videoroom多人音视频房间（SFU）视频会议、在线课堂
janus.plugin.streaming把 RTSP/RTMP 等流分发给多个 WebRTC 观众低延迟监看、直播
janus.plugin.sipWebRTC 与 SIP 互通呼叫中心、传统电话网
janus.plugin.echotest回声测试连通性排查、媒体质量验证

Janus 的部署难点不在“装起来”，而在 NAT 与 ICE：它必须让浏览器拿到可达的候选地址，必要时配合 STUN/TURN；信令层通常是你自己的业务服务器通过 REST/WebSocket 调 Janus，而不是让浏览器直连。媒体端口段、证书、鉴权 token 都要在配置里明确声明。

⚠️Janus 不做 HLS，也不做 RTMP 接入。如果业务同时需要“会议 + 大规模 HLS 回看”，通常要组合部署（Janus 负责实时房间，SRS/ZLM 负责直播与录制），而不是硬让一个组件干所有事。

🧱 nginx-rtmp：能用，但别拿它开新局

nginx-rtmp-module 像一辆还能启动的老卡车：RTMP 推拉、HLS 切片、简单的 stat 页面都有，部署也不复杂。但它长期缺少活跃维护，不支持 WebRTC/SRT，复杂的按需拉流与集群能力也有限。维护遗留系统可以继续用，新项目更适合 SRS/ZLM/MediaMTX。

# nginx.conf（节选）
rtmp {
    server {
        listen 1935;
        application live {
            live on;
            record off;
            hls on;
            hls_path /tmp/hls;
            hls_fragment 4s;
        }
    }
}
http {
    server {
        listen 8080;
        location /hls {
            types {
                application/vnd.apple.mpegurl m3u8;
                video/mp2t ts;
            }
            root /tmp;
            add_header Cache-Control no-cache;
        }
    }
}

注意：HLS 切片目录要由 HTTP 服务暴露，且 Cache-Control 不能缓存 m3u8；RTMP 本身不携带鉴权，推流密钥通常靠 URL 参数 + 业务校验。上述指令在不同分支/模块版本中可能略有差异，以所使用模块的文档为准。

🐳 最小 Docker：三条命令先跑起来

先用最小配置验证“推得进、拉得出”，再谈集群与鉴权。下面的端口映射是示例，实际要与配置文件、防火墙和安全组保持一致。

# MediaMTX：RTSP 8554 / RTMP 1935 / HLS 8888 / WebRTC 8889 / API 9997
docker run -d --name mediamtx \
  -p 8554:8554 -p 1935:1935 -p 8888:8888 -p 8889:8889 \
  -p 8890:8890/udp -p 9997:9997 \
  bluenviron/mediamtx:latest

# ZLMediaKit：注意 RTP 端口段要与容器内 config.ini 一致
docker run -d --name zlm \
  -p 1935:1935 -p 8080:80 -p 554:554 \
  -p 30000-30500:30000-30500/udp \
  -v $PWD/zlm/config.ini:/opt/media/conf/config.ini \

# SRS：RTMP 1935 / API 1985 / HTTP 8080 / WebRTC 8000(UDP，示例)
docker run -d --name srs \
  -p 1935:1935 -p 1985:1985 -p 8080:8080 -p 8000:8000/udp \

Janus 通常需要从源码或社区镜像构建，且必须配置 NAT/ICE 与媒体端口段；镜像 tag 与配置项以官方文档/镜像页为准。容器化后最容易忘的是“UDP 端口段”——只映射 TCP 端口，WebRTC/SRT 一定失败。

💡验证顺序：① docker logs 看监听是否成功；② 用 FFmpeg 推一路测试流；③ 用 ffplay 拉 RTSP/FLV；④ 浏览器打开 HLS/WHEP；⑤ 最后才接业务鉴权。把变量分开，比一上来就调业务代码快。

🧯 排错：端口、CORS、ICE、鉴权，四道门

媒体服务器“跑起来了”不等于“能看了”。下面四道门，任何一道没过，表现都可能是黑屏或一直转圈。按顺序验证，比在日志里翻找更快。

协议 / 组件示例端口传输常见坑
RTSP554 / 8554TCP（RTP 可 UDP）只开 TCP 没开 UDP；摄像头 URL 通道号写错
RTMP1935TCP推流 key 写错；防火墙只放行 80/443
SRT8890（示例）UDP只映射 TCP；streamid 与访问控制不匹配
WebRTC8889（HTTP）+ 动态 UDPTCP + UDPICE 只拿到内网地址；UDP 被禁；没配 TURN
HLS / HTTP-FLV8888 / 8080TCP跨域头缺失；m3u8 被缓存；切片目录未暴露
GB28181 SIP / RTP5060 / 30000–30500（示例）UDP/TCPRTP 端口段未整段放行；收流地址设备不可达

HLS、HTTP-FLV、WHEP 都是浏览器发起的 HTTP 请求，页面与流不在同一个源时，必须有正确的 Access-Control-Allow-Origin。常见配置入口：MediaMTX 的 hlsAllowOrigin，ZLM/SRS 的 HTTP 跨域开关（键名以各自文档为准）。不要用 * 搭配凭证请求，也不要把 CORS 当成鉴权。

WebRTC 失败先看候选地址：host 是内网、srflx 是 STUN 反射、relay 是 TURN 中继。云主机/容器部署要显式告诉服务器“我的公网地址是什么”，否则浏览器拿到 172.x/10.x 的候选，ICE 永远连不通。企业网禁 UDP 时，只能走 TURN/TCP 或换 HLS/FLV。

至少区分“推流鉴权”和“播放鉴权”：推流 key 泄露会导致别人冒名开播；播放 token 泄露会导致盗链。常见做法是业务服务器签发短时 token，媒体服务器通过 HTTP hook 或内置鉴权校验。不要在公开页面里硬编码长期密钥，也不要把 key 只放在 URL 里当唯一防线。

症状优先排查快速验证
推流成功，页面黑屏拉流协议是否被浏览器支持；CORS用 ffplay / VLC 拉同一路径；浏览器控制台看请求
HLS 一直转圈m3u8 是否可访问；切片是否生成；缓存头直接打开 m3u8 与首个 ts；看服务器日志
WebRTC 连不上ICE 候选、UDP、TURN、证书看 offer/answer 的候选类型；用 Trickle ICE 测试页
首个画面很慢GOP 过长；服务器等关键帧缩短 GOP；观察首个 IDR 到达时间
播放几分钟后卡死鉴权过期；按需拉流被断开；带宽不足对照 token 有效期与 sourceOnDemand 超时
⚠️四道门按顺序过：端口通 → 协议能握手 → 浏览器跨域允许 → 鉴权通过。任何一步跳过去，都会把问题带到下一层，最后变成“看起来像编码问题”的玄学。实在定位不了，就在服务器侧抓包，看请求有没有到、回包是什么。

🔗 与国标、播放器衔接：服务器只是中间那一跳

安防场景里，服务器前面是 SIP/PS 的国标世界，后面是 HTTP/WebRTC 的浏览器世界；直播场景里，服务器前面是推流端，后面是播放器与 CDN。把它放在链路中的正确位置，才知道该配什么、该测什么。

🗺️ 链路全景：一台服务器站在哪三个工位之间

把直播链路想成一条跨城快递线：主播是发货人，源站是城市总仓，边缘是小区驿站，观众是收件人。总仓负责拆包、换单、留底；驿站只负责把同一批货分给附近的人。绝大多数“服务器配置问题”，其实是把总仓的活交给了驿站，或者反过来。

每一跳的“协议账”

链路谁终止会话常见协议 / 默认端口这一跳该盯的指标典型故障
推流端 → 源站源站RTMP 1935 / SRT 10080 / RTSP 554 / WHIP 443上行丢包、推送码率、握手耗时推流 key 错、UDP 未放行、vhost 不匹配
源站内部源站自己RTP / FLV tag / TS 切片单流 CPU、切片耗时、GOP 缓存命中切片写盘慢导致 HLS 404、关键帧缺失
源站 → 边缘两端都维持RTMP 1935 / SRT 10080回源延迟、回源断开次数边缘把源站打挂、回源链路抖动被放大
边缘 → 播放端播放端HLS/FLV 8080 / WHEP 8889 + UDP 8189出口带宽、并发连接、首帧时间CORS 缺失、ICE 只有内网候选、m3u8 被缓存
💡判断“要不要边缘”只用一道算术题：单机出口带宽 × 利用率 ÷ 单观众码率 = 单机能扛的观众数。若这个数远大于实际观众，源站兼边缘最省事；若不够，再加边缘，而不是给源站换更强的 CPU——瓶颈通常在网卡，不在算力。

⚙️ SRS 生产级配置：把每一行都翻译成人话

SRS 的配置文件像一张“插座面板”：每个花括号是一个功能区，分号是插头的固定螺丝。少一个分号，整台服务器可能起不来；把 candidate 写成内网地址，WebRTC 就会“握手成功、画面不来”。下面这份骨架能直接落地，注释说明“这行是干什么的、不懂会怎样”。

# srs.conf —— 单机直播源站骨架（SRS 5.x / 6.x；键名以官方文档为准）
listen              1935;        # RTMP 接入：OBS / FFmpeg 默认推这里
max_connections     5000;        # 连接上限（观众也算），不是“5000 路流”
daemon              off;         # 交给 systemd / Docker 管进程，别自己 daemon 化
srs_log_tank        console;     # 容器里输出到 stdout，docker logs 才看得到
srs_log_level       info;        # 排障临时改 trace，稳定后回 info，否则日志涨得很快

http_api {                       # “遥控器”：查询状态、踢客户端，默认 1985
    enabled         on;
    listen          1985;
    crossdomain     on;          # API 的 CORS；这个端口只应暴露给内网
}

http_server {                    # “货架”：HLS 切片、静态页，默认 8080
    enabled         on;
    listen          8080;
    dir             ./objs/nginx/html;
    crossdomain     on;          # HLS/FLV 被跨域播放时必须开
}

vhost __defaultVhost__ {
    tcp_nodelay     on;          # 小包立即发，降低交互延迟
    min_latency     on;          # 关闭部分缓存，延迟优先；追剧式回看可关

    play {
        gop_cache   on;          # 缓存一个 GOP，新观众不必等下一个 I 帧
        queue_length 10;         # 播放队列上限（秒）；太大延迟高，太小易卡
    }

    hls {
        enabled         on;
        hls_fragment    2;       # 一片 2 秒；延迟≈片长×(缓冲片数+1)
        hls_window      10;      # 清单保留 10 秒；太小播放器会追不上
        hls_path        ./objs/nginx/html;
        hls_m3u8_file   [app]/[stream].m3u8;
        hls_ts_file     [app]/[stream]-[seq].ts;
        hls_cleanup     on;      # 自动删过期切片，防止磁盘被 ts 写满
        hls_dispose     30;      # 无人观看 30 秒后清理切片目录
        hls_wait_keyframe on;   # 每片从关键帧开始，避免花屏与时间戳错位
    }

    dvr {
        enabled         on;
        dvr_plan        session; # 一次推流一个文件；改成 segment 则按时长切
        dvr_path        ./objs/nginx/html/record/[app]/[stream]-[timestamp].flv;
        dvr_duration    30;      # 仅 segment 模式生效：单段秒数
        dvr_wait_keyframe on;
    }

    http_remux {
        enabled         on;
        mount           [vhost]/[app]/[stream].flv; # HTTP-FLV 出口
    }

    http_hooks {
        enabled         on;
        on_publish      http://127.0.0.1:8085/hooks/publish;
        on_unpublish    http://127.0.0.1:8085/hooks/unpublish;
        on_play         http://127.0.0.1:8085/hooks/play;
        on_stop         http://127.0.0.1:8085/hooks/stop;
        on_hls          http://127.0.0.1:8085/hooks/hls;
    }

    rtc {
        enabled         on;
        rtmp_to_rtc     on;      # RTMP 进，WebRTC 出
        rtc_to_rtmp     on;      # WebRTC 进，RTMP 出（需要反向接入时再开）
    }

    srt {
        enabled         on;
        srt_to_rtmp     on;      # SRT 推流可直接转成 RTMP 供下游使用
    }
}

rtc_server {
    enabled         on;
    listen          8000;        # UDP，不是 TCP；安全组必须放行
    candidate       203.0.113.10; # 必须是浏览器可达的公网/映射地址，不能写 172.x
}

srt_server {
    enabled         on;
    listen          10080;       # UDP；SRT 不是 TCP 协议
    maxbw           1000000000;  # 最大带宽（bps），按网卡能力留 20% 余量
    peerlatency     300;         # 对端延迟 ms；跨国/弱网可加到 500–1000
    recvlatency     300;
}

四组配置，各管一件事

① 接入与进程

listen 1935 是 RTMP 的门；max_connections 是整栋楼的人数上限（推流端 + 播放端都算）。daemon off 让 Docker/systemd 能接管进程，容器里尤其别开。

② 遥控器与货架

http_api（1985）是遥控器，能查状态、踢人，绝不能直接暴露公网；http_server（8080）是货架，HLS/FLV 从这里出货。两个端口职责不同，别用一个反代把 1985 也带出去。

③ HLS 的延迟与磁盘

hls_fragment 决定切片多长，hls_window 决定清单多长。hls_cleanup + hls_dispose 是磁盘保险丝：只切片不清理，几天就能写满一台机器。

④ WebRTC 与 SRT 的 UDP

rtc_server.listen 8000 与 srt_server.listen 10080 都是 UDP。candidate 写错是“能连上但没画面”的头号原因；SRT 的 peerlatency 是拿延迟换抗丢包。

HLS 延迟到底从哪来

HLS 像“连载小说”：观众要先拿到几章（切片）才肯开读。服务器切得快，观众也得先攒缓冲；所以延迟不是单一参数决定的。

端到端延迟 ≈ 切片时长 × (播放器缓冲片数 + 1) + 网络与解码 ≈ 2 s × 3 + 1 s ≈ 7 s

把 hls_fragment 从 6 秒降到 2 秒，延迟会明显下降，但请求数变成 3 倍、切片文件更多、磁盘 I/O 更高。想进 3 秒以内，应该换 LL-HLS 或直接用 HTTP-FLV/WebRTC，而不是把切片切成 0.5 秒硬扛。

⚠️上线前先做语法体检：./objs/srs -t -c conf/srs.conf。SRS 的配置错误经常只表现为“进程起来又退出”，docker logs 里才有那一行 parse config failed；先体检，比对着黑屏猜半小时快。

🎛️ SRS HTTP API 与 WebHook：让业务系统“管得住”媒体服务器

HTTP API 像电梯里的按钮面板：你按一下，服务器告诉你现在几楼、谁在电梯里、能不能把人请出去。WebHook 则像门口的保安：每次有人推门（推流/播放/断流），保安先给你的业务系统打电话，问“这个人能不能进”。一个是你主动查，一个是服务器主动报。

先分清两组接口

curl -s http://127.0.0.1:1985/api/v1/summaries | jq

# 查流列表，挑出“有客户端但码率为 0”的异常流
curl -s http://127.0.0.1:1985/api/v1/streams | jq '.streams[] | {name, clients, kbps}'

WebHook 配置：每个动作一个 URL

vhost __defaultVhost__ {
    http_hooks {
        enabled      on;
        on_publish   http://127.0.0.1:8085/hooks/publish;   # 推流鉴权：返回非 0 直接拒绝
        on_unpublish http://127.0.0.1:8085/hooks/unpublish; # 断流通知：清理会话、结算时长
        on_play      http://127.0.0.1:8085/hooks/play;      # 播放鉴权：防盗链
        on_stop      http://127.0.0.1:8085/hooks/stop;      # 停止播放：扣减在线数
        on_hls       http://127.0.0.1:8085/hooks/hls;       # 每个 ts 生成后通知：异步上传对象存储
    }
}

SRS 用同一个 JSON 结构把上下文送过来，业务端按 action 分流即可。下面是 on_publish 的典型请求体（字段随版本略有增删，以官方文档为准）：

{
  "action":    "on_publish",
  "client_id": "9304f0a1",
  "ip":        "1.2.3.4",
  "vhost":     "__defaultVhost__",
  "app":       "live",
  "stream":    "demo",
  "param":     "?token=abc&ts=1700000000",
  "tcUrl":     "rtmp://media.example.com/live"
}

# 业务后端允许：
{ "code": 0 }

# 业务后端拒绝（token 错、黑名单、并发超限）：
{ "code": 403, "msg": "invalid token" }

on_publish：推流鉴权

最适合做“谁能开播”。把 token、签名、过期时间放在推流 URL 的查询串里；业务后端验签后返回 code=0。密钥不要硬编码在网页里，也不要把长期 key 当唯一防线。

on_play / on_stop：播放鉴权与计费

最适合做防盗链与在线数统计。注意 on_play 在每次播放请求时触发，HLS 的每个切片请求不一定都走它；别把“切片请求数”当成“观众数”。

on_hls：切片落地通知

每个 ts 生成后回调，带上文件路径、时长、序列号。适合异步转存对象存储、生成回看清单；不要在回调里同步做重活，否则会拖慢切片。

on_unpublish：断流收尾

推流异常断开时也会触发，适合释放“正在直播”的频道锁、写结束时间。业务端要按 client_id 做幂等，避免重复结算。

🚨两个绝不能犯的错：① 把 1985 端口直接映射到公网——任何人都能查你的流、踢你的观众；② 在 on_publish 里做 10 秒级的外部请求——SRS 会等，推流端会超时，最后表现为“OBS 一直重连”。回调要在几百毫秒内返回，慢活全部异步化。

🧰 ZLMediaKit 深入：ini 配置、hook 与国标接口

ZLM 的 ini 像一张“报关单”：每一栏都写清楚这票货怎么进、怎么出、出了问题找谁。[protocol] 决定开哪些窗口，[hook] 决定每次进出要不要问业务系统，[rtp_proxy] 决定国标收流的港口范围。它比 SRS 多了一层“国标报关”的能力，代价是配置项更多、端口账更复杂。

# config.ini —— ZLM 生产骨架（键名与默认值以官方文档为准）

ZLM hook 与 SRS WebHook 的差异

两者都叫“回调”，但 ZLM 的 hook 像一整套门禁系统：不只管进出，还管“流发生变化”“没人看了”“RTSP 要认证”。SRS 的 WebHook 更像几个固定岗位，职责清晰但覆盖点少。

维度ZLMediaKit hookSRS WebHook
配置位置[hook] 段，统一开关 + 多个 URLvhost 内 http_hooks，逐事件配 URL
覆盖面更广：发布/播放/流变化/无人观看/RTSP 认证/HTTP 访问聚焦发布、播放、断流、HLS、DVR
返回约定{"code":0,"msg":"success"}；on_stream_none_reader 可返回 close:true{"code":0}；非 0 拒绝
典型用途按需拉流、无人观看自动停、国标频道鉴权推流/播放鉴权、切片通知
失败影响鉴权类失败会拒绝；通知类失败通常只记日志鉴权类失败通常直接拒绝
调试方式看 ZLM 日志里的 hook 请求与响应耗时看 SRS 日志与业务后端访问日志对时间戳

RESTful API：用 URL 指挥媒体服务器

ZLM 的 API 都挂在 /index/api/ 下，统一带 secret 参数（在配置里设定）。它像一台“带遥控的转运中心”，业务系统不用改媒体配置，就能开端口、拉流、录制、截图。

接口作用关键参数
/index/api/getMediaList列出所有流与应用vhost、app、stream 过滤
/index/api/getMediaInfo查单路流的轨道、编码、在线人数schema、vhost、app、stream
/index/api/getSnap抓一张 JPEG 截图url、timeout_sec、expire_sec
/index/api/startRecord开始录制（MP4/HLS）type、vhost、app、stream
/index/api/stopRecord停止录制type + 流定位参数
/index/api/openRtpServer分配 GB28181 收流端口port、tcp_mode、stream_id
/index/api/closeRtpServer关闭收流端口stream_id
/index/api/addStreamProxy让 ZLM 主动拉一路上游流url、vhost、app、stream
/index/api/startSendRtp把流回推给设备/上级平台（国标语音、级联）dst_url、dst_port、stream_id
/index/api/getThreadsLoad看各线程负载无
/index/api/getStatistic看全局统计（连接、流量）无
 
# 国标点播：先让 ZLM 开一个收流端口，再把端口写进 SIP INVITE 的 SDP
curl "http://127.0.0.1/index/api/openRtpServer?secret=xxx&port=30000&tcp_mode=1&stream_id=cam1"

# 浏览器要截图：让 ZLM 从 RTSP 拉一帧，返回 JPEG
curl -o snap.jpg "http://127.0.0.1/index/api/getSnap?secret=xxx&url=rtsp://127.0.0.1:554/live/cam1&timeout_sec=5&expire_sec=10"

# 查线程负载：某些线程打满时，先怀疑单路大码率或切片写盘
curl "http://127.0.0.1/index/api/getThreadsLoad?secret=xxx"
💡国标场景为什么常选 ZLM：它原生能收 RTP/PS，能把 PS 解成 H264/H265 再转 RTMP/HLS/WebRTC；openRtpServer/closeRtpServer 让“按需点播”变成两个 API 调用；startSendRtp 还能做语音对讲与向上级联。SRS 与 MediaMTX 不具备这套“国标报关”能力，通常要在前面加网关或换方案。
⚠️国标的三本账要对齐：① SIP 5060（UDP/TCP）能通；② port_range 与防火墙/安全组整段一致；③ 设备能路由到平台的收流地址。openRtpServer 返回的端口如果不在放行范围，表现就是“SIP 200 OK、PS 流不来”。排查顺序永远是：信令 → 端口 → SDP 里的地址 → PS 解封装。

🧩 MediaMTX 深入：一个二进制，四张网口

MediaMTX 像一把随身工具钳：不装依赖、不拉一堆插件，单个二进制就把 RTSP、RTMP、HLS、WebRTC、SRT 接在一起。它的世界观只有两个字——路径（path）：一条路径就是一个频道，可以等人推、可以去上游拉、也可以在没人看时自动断。

paths 的四种玩法

等人推

只写路径名，不写 source。外部用 RTMP/SRT/WHIP 推进来，路径就成了直播间。适合主播开播。

按需回源

source + sourceOnDemand：第一个观众到来才去拉摄像头，最后一人离开若干秒后断开。省带宽，也省摄像头连接数。

常连转发

去掉 sourceOnDemand，MediaMTX 启动即回源。适合“必须随时可播”的电视墙，但上游会一直有连接。

正则批量

路径名写成 ~^cam([0-9]+)$，用 $1 拼上游 URL。几十个摄像头不用手写几十段配置。

内建 WebRTC / WHEP：浏览器直接看

MediaMTX 把 WebRTC 做成“一条 URL”：推流用 WHIP，播放用 WHEP，不需要另起 Janus，也不需要业务后端转发 SDP。浏览器像点播一个普通网页一样发起协商。

# 播放（WHEP）：浏览器 POST SDP offer，服务器回 answer
# http://server:8889/live/whep

# 推流（WHIP）：OBS 30+ 或支持 WHIP 的编码器
# http://server:8889/live/whip

# HLS 兜底：兼容性最好，代价是延迟
# http://server:8888/live/index.m3u8

# 查路径状态：有没有发布者、有没有读者
curl -s http://127.0.0.1:9997/v3/paths/list | jq '.items[] | {name, ready, readers}'
API用途排障时看什么
/v3/paths/list所有路径与状态ready 为 false：没有源；readers 为 0：没人看
/v3/config/paths/list当前路径配置核对 sourceOnDemand 是否真的生效
/v3/rtspconns/listRTSP 会话摄像头是否连上、用的 TCP 还是 UDP
/v3/webrtcsessions/listWebRTC 会话协商成功但无媒体时，看 ICE 状态
/v3/recordings/list录制任务路径是否在录、分段是否正常
🚨只映射 8889 是 MediaMTX 最常见的坑：WebRTC 的 HTTP 协商在 8889（TCP），但 ICE 媒体默认走单一 UDP 端口 8189。容器只发布 8889:8889 时，SDP 能换成功，画面却永远不来。部署时同时发布 8189:8189/udp，并确认 webrtcAdditionalHosts 是公网地址。
⚠️它的边界也很清楚：不做 GB28181 SIP/PS，不做转码，不做复杂集群调度。需要“国标接入”找 ZLM；需要“源站+边缘+鉴权体系”找 SRS；只需要“把摄像头翻译成浏览器能看的协议”，MediaMTX 最省心。

🧱 nginx-rtmp 与历史方案：老卡车还能开，但别用来跑新线路

nginx-rtmp 像一辆保养得还不错的老卡车：能拉货（RTMP 推拉）、能装箱（HLS 切片）、油耗也不高。但它没有 ABS（WebRTC/SRT）、没有车载导航（API/集群），配件也早停了。维护旧系统可以继续开；新项目上路，最好换一辆现代车。

# nginx.conf —— 能跑的最小 RTMP + HLS 组合
rtmp {
    server {
        listen 1935;
        chunk_size 4096;

        application live {
            live on;
            record off;

            hls on;
            hls_path /var/www/hls;
            hls_fragment 2s;
            hls_playlist_length 10s;

            # 推流鉴权：nginx-rtmp 把参数拼到 URL 上回调
            on_publish http://127.0.0.1:8085/auth;
        }
    }
}

http {
    server {
        listen 8080;
        location /hls {
            types {
                application/vnd.apple.mpegurl m3u8;
                video/mp2t ts;
            }
            root /var/www;
            add_header Cache-Control no-cache;
            add_header Access-Control-Allow-Origin *;
        }
    }
}

注意 hls_path 与 location /hls 的目录关系：hls_path /var/www/hls 对应 root /var/www + location /hls，少一层目录就会 404。m3u8 必须 no-cache，ts 可以短缓存；这两条写反，表现是“画面卡住不更新”。

为什么不建议新项目首选它

维护与生态

模块更新长期停滞，和 nginx 新版本、新编译参数的兼容性要自己扛；出问题可查的资料越来越旧。媒体协议在演进（WebRTC、SRT、LL-HLS），它基本停在 RTMP/HLS 时代。

能力边界

没有原生 WebRTC/SRT/GB28181，没有完整的 HTTP API，没有成熟的源站-边缘集群与按需拉流。要做鉴权、录制管理、监控，得在外部再搭一套。

延迟与体验

HLS 延迟由切片与播放器缓冲决定，做低延迟直播很吃力；HTTP-FLV 需要额外模块/配置，首帧与 GOP 缓存策略也不如现代服务器细。

安全与运维

推流鉴权靠 URL 参数 + 回调，缺少细粒度的播放鉴权、Token 生命周期与踢人能力；监控指标少，容量评估基本靠猜。

顺手认识一下 FLV：HTTP-FLV 到底在传什么

HTTP-FLV 像“把一段段压缩帧装进贴了编号的纸箱”，再把纸箱排成一条长龙通过 HTTP 发出去。龙头是 9 字节的 FLV Header，后面跟着一个个 Tag。看懂它，排障时就知道“服务器到底有没有把媒体写出去”。

第一个 Tag 通常是 onMetaData（AMF0），携带宽高、帧率、码率等；随后是 video/audio tag。播放器“能连上但一直黑屏”，常见原因是 header 的标志位与实际轨道不符，或者服务器只写了 audio tag。

⚠️老方案的“能跑”不等于“能扛”：nginx-rtmp 在几百并发、单机小流量下依然可靠；但一旦要做鉴权体系、录制回传、边缘扩容、WebRTC 低延迟，补丁成本会超过迁移成本。选型时把“未来半年要加的功能”列出来，再决定要不要继续开老卡车。

🕸️ 集群与边缘：总仓只发几车货，驿站面对所有收件人

单机直播像一家小卖部：进货、上架、收银都一个人干。观众一多，收银台先垮，仓库还闲着。集群做的事只有一件——把“面对观众”的活分给很多台边缘，源站只负责把同一路流复制给这几台边缘。边缘越多，源站的出口越省；但边缘的回源链路一旦抖动，故障也会被放大。

SRS 源站与边缘的两段配置

# 源站：主动把流“推”给边缘（forward），适合热门流、边缘数量固定
vhost __defaultVhost__ {
    cluster {
        mode        local;              # 我是源站
    }
    forward {
        enabled     on;
        destination 10.0.0.21:1935;    # 边缘 A
        destination 10.0.0.22:1935;    # 边缘 B
    }
}

# 边缘：观众来了才向源站“拉”（remote），适合长尾流、按需点播
vhost __defaultVhost__ {
    cluster {
        mode           remote;          # 我是边缘
        origin         10.0.0.10:1935;  # 源站地址
        token_traverse off;             # token 是否透传，按鉴权方案决定
    }
}

forward 与 remote 的区别，像“总仓主动发车”与“驿站缺货再叫货”：forward 会把每一路流都复制到所有边缘，热门流很稳，但长尾流会浪费大量回源带宽；remote 只在有人观看时回源，省带宽，但首个观众要等一次回源，首帧更慢。生产上常见混合策略：热门流 forward，冷门流 remote。

负载均衡的三种做法

做法怎么分优点代价 / 坑
DNS 轮询一个域名解析到多个边缘 IP，靠 TTL 轮换改动最小，播放器无感TTL 缓存导致切换慢；没有健康检查；同一观众可能被分到远端
HTTP 302业务网关按地域/负载返回 302，播放器跟随到边缘可控、可带 token、可做灰度每个清单请求多一次跳转；播放器必须支持重定向；切片地址也要指向边缘
API 调度App 先请求调度接口，拿到“边缘地址 + 短时 token”再播放最灵活，可结合实时负载与计费客户端要配合；调度服务本身要高可用，不能成为新单点

带宽账：为什么必须上 CDN

总出口带宽 = 单观众码率 × 并发观众数 × (1 + 冗余 20%)
1 Mbps × 10,000 人 = 10,000 Mbps = 10 Gbps

10 Gbps 是什么概念：一张 10G 网卡理论 10 Gbps，实际可用约 9.5 Gbps，还要留给重传、突发和监控；也就是说，1 Mbps 的流想扛 1 万人，至少要两张 10G 网卡做绑定，且没有余量。若码率是 2 Mbps，就是 20 Gbps；4 Mbps 的 4K 直播，1 万人就是 40 Gbps。这就是为什么“自建源站 + 边缘”到一定规模后一定要接 CDN——不是服务器算不动，而是出口带宽和地域覆盖买不起。

源站侧的压力则小得多：源站出口 = 单路码率 × 边缘节点数。100 个边缘、每路 4 Mbps，源站也只需 400 Mbps。真正随观众数线性增长的，是边缘与 CDN 的出口。

⚠️边缘不是越多越好：每多一个边缘，就多一条回源连接、多一份源站出口、多一个可能抖动的环节。边缘数量应该由“地域覆盖 + 单机出口”决定，而不是拍脑袋。回源链路建议用 SRT 或专线对抗丢包；公网 RTMP 回源抖动时，观众侧会表现为“所有边缘一起卡”。

💾 录制与截图：把“流过”变成“留下”

录制像在传送带旁边放一台复印机：货照常走，复印机另存一份。它最怕两件事——写盘把直播拖慢，以及“录了但文件打不开”。前者靠目录规划与异步落盘，后者靠选对容器与收尾方式。

SRS 的 dvr：先决定“一段”还是“一场”

vhost __defaultVhost__ {
    dvr {
        enabled           on;
        dvr_plan          segment;   # 按时长切段；session 则一场直播一个文件
        dvr_duration      3600;      # 每段 1 小时，便于分片上传与失败重试
        dvr_path          ./objs/nginx/html/record/[app]/[stream]/[timestamp].flv;
        dvr_wait_keyframe on;        # 每段从关键帧开始，避免切出半帧
    }
}

[timestamp] 让每段文件名不重复；[app]/[stream] 让目录天然按频道分层，清理时不会误删别的业务。录制目录不要和 HLS 切片目录混在一起：一个需要长期保留，一个需要频繁删除，清理脚本很容易误伤。

HLS 录制 vs FLV / MP4 录制

形态落盘方式崩溃安全性回看体验适合
HLS / ts持续生成小切片 + m3u8高：最多丢最后一片直播结束即可按清单回看直播回放、边播边看
FLV单个持续增长的文件中：异常断电可能丢尾部与索引需转封装或播放器支持归档、后续转 MP4
MP4ZLM 直接写 MP4；或 FLV 转封装低：moov 未写完时可能打不开下载、剪辑、跨平台最好成片归档、交付客户
 
# FLV 转 MP4：不重新编码，只换容器；+faststart 让网页能边下边播
ffmpeg -i record/live/demo-1700000000.flv -c copy -movflags +faststart demo.mp4

# 如果录制被异常中断，先尝试修复索引再转封装
ffmpeg -err_detect ignore_err -i broken.flv -c copy fixed.mp4

ZLM 的 [record] enable_mp4=1 会直接落 MP4；方便，但进程崩溃时文件可能缺 moov。对“必须可交付”的录制，优先 FLV 或分段 MP4，再由后处理生成最终文件。MediaMTX 则可用 recordFormat: fmp4 做分段，网页回放更友好。

ffmpeg -y -rtsp_transport tcp -i rtsp://user:pass@192.168.1.64:554/Streaming/Channels/101 \

存储账与回传

单路录制容量 ≈ 码率 × 3600 ÷ 8 = 1 Mbps × 3600 ÷ 8 ≈ 450 MB/小时
24 小时约 10.8 GB；4 Mbps 则约 43 GB/天

录制是“按天线性增长”的成本，必须配保留策略：本地只留 3–7 天，长期归档转对象存储（S3/OSS/COS）。回传用 rclone、aws s3 cp 或 SRS 的 on_hls 回调触发异步上传；不要在媒体线程里同步上传，否则切片与录制都会变慢。

目录规划

按 app/stream/日期 分层；HLS 切片、DVR、截图各自独立根目录。清理脚本只碰“可再生成”的目录，归档目录只允许生命周期规则删除。

磁盘与 inode

HLS 会产生大量小文件，除了容量还要看 inode；df -h 与 df -i 都要看。SSD 写满会拖慢切片，进而让所有观众卡顿。

回传与校验

上传后校验文件大小与 MD5，成功再删本地；失败重试要幂等。对象存储的生命周期规则比“手写 rm”可靠得多。

🚨最常见的录制事故：录制目录和 HLS 目录共用，清理脚本按“修改时间”删文件，把刚录好的成片一起删了；或者磁盘写满后，SRS 仍在推流，但切片写不进去，观众看到的是“直播还在、HLS 404”。录制与切片必须分盘或至少分目录，并给磁盘留 20% 余量。

容器内常见在 ./objs/logs/srs.log；srs_log_tank console 时直接进 docker logs。健康检查：curl 127.0.0.1:1985/api/v1/versions。

ZLMediaKit

日志在镜像内的 log/ 目录（具体路径以镜像为准）；健康检查：curl 127.0.0.1/index/api/getStatistic?secret=xxx。

MediaMTX

默认输出到 stdout，docker logs -f mediamtx 或 journalctl -u mediamtx；健康检查：curl 127.0.0.1:9997/v3/paths/list。

一份能直接用的 docker compose

# docker-compose.yml —— SRS 单机源站 + 挂载配置与 HLS 目录
services:
  srs:
    image: ossrs/srs:5
    container_name: srs
    restart: unless-stopped
    command: ./objs/srs -c conf/srs.conf
    ports:
      - "1935:1935"          # RTMP 推流
      - "1985:1985"          # HTTP API，建议只绑内网
      - "8080:8080"          # HLS / HTTP-FLV
      - "8000:8000/udp"      # WebRTC 媒体
      - "10080:10080/udp"    # SRT
    volumes:
      - ./conf/srs.conf:/usr/local/srs/conf/srs.conf:ro
      - ./html:/usr/local/srs/objs/nginx/html
    ulimits:
      nofile:
        soft: 65535
        hard: 65535
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://127.0.0.1:1985/api/v1/versions || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s

# 常用运维命令
docker compose up -d
docker logs -f --tail=100 srs
docker stats --no-stream srs
docker compose exec srs ./objs/srs -t -c conf/srs.conf

若镜像内没有 curl，删掉 healthcheck 或换成镜像自带的探测工具即可。生产上把 1985 改绑内网地址（例如 127.0.0.1:1985:1985），只让反向代理访问；8000/udp 与 10080/udp 必须真的映射，否则 WebRTC/SRT 只会“握手成功、媒体不来”。

排障 FAQ：八个“看起来像玄学”的问题

▶① 推流提示 404 / 被拒绝：vhost、app、stream 到底怎么对应？

把 URL 拆成三段：rtmp://host:1935/live/demo 中 live 是 app，demo 是 stream，vhost 默认是 __defaultVhost__。SRS 的 vhost 段、ZLM 的 appName、MediaMTX 的 paths 键必须与实际 URL 对上。常见错误是配置写了 vhost live，推流却推到默认 vhost；或者 ZLM 的 appName 与播放地址里的 app 不一致。

快速验证：用 ffprobe rtmp://host/live/demo 反向确认流是否存在；再看服务器日志里打印的 vhost/app/stream 三元组，不要凭记忆。

▶② HLS 延迟十几秒，调哪个参数？

先算账：延迟 ≈ 切片时长 ×（播放器缓冲片数 + 1）。默认 6 秒切片 + 3 片缓冲，十几秒很正常。把 hls_fragment 降到 2 秒、hls_window 保持 10 秒左右，通常能到 6–8 秒；再低就要 LL-HLS 或 HTTP-FLV/WebRTC。

别只改服务器：播放器（hls.js）自己的 maxBufferLength、liveSyncDuration 也会加延迟。服务器切 1 秒、播放器缓冲 10 秒，结果还是 10 秒以上。

▶③ WebRTC 能协商、没画面：先查哪三件事？

① UDP 端口：SRS 默认 8000/udp，ZLM 默认 8000/udp，MediaMTX 默认 8189/udp；只映射 TCP 一定没媒体。② 候选地址：candidate/externIP/webrtcAdditionalHosts 必须是浏览器可达的公网地址，写 172.x 就只能内网看。③ 证书与混合内容：HTTPS 页面调 HTTP 的 WHEP 会被浏览器拦截；DTLS 证书指纹不匹配会直接握手失败。

再看编码：浏览器普遍支持 H.264，H.265 在多数浏览器里仍不可用；音频优先 Opus/G711。编码不支持时，表现也是“连上了、没画面”。

▶④ 网页播放报 CORS：到底该加哪个头？

HLS/FLV/WHEP 都是浏览器发起的 HTTP 请求，页面源与流源不同就需要 Access-Control-Allow-Origin。SRS 开 http_server.crossdomain 或 http_api.crossdomain；ZLM 在 [http] 配跨域；MediaMTX 用 webrtcAllowOrigin/hlsAllowOrigin。带 Cookie 的请求不能用 *，要回显具体 Origin。

CORS 只是浏览器策略，不是鉴权。加完头能播，不代表别人不能盗链；播放鉴权仍要 token + 回调。

▶⑤ 回调超时导致推流被拒：业务后端该怎么改？

鉴权回调是同步阻塞的：SRS/ZLM 等业务后端返回，超时通常按拒绝处理。把回调控制在几百毫秒内：token 验签用本地缓存、频道状态放 Redis、慢查询与外部 API 全部异步化；回调接口单独做限流与降级，别和业务主站共用一套容易抖动的依赖。

排障时对齐三个时间戳：推流端发起时间、媒体服务器日志里的 hook 请求时间、业务后端收到/返回时间。若业务端很快但服务器仍超时，查网络与 DNS，不要继续改代码。

▶⑥ 磁盘写满：为什么直播还在，HLS 却 404？

HLS 依赖“切片写盘 + HTTP 读盘”。磁盘满时，内存里的流还在转发，但新 ts 写不进去，m3u8 不更新，观众自然 404 或卡住。先看 df -h 与 df -i，再确认 hls_cleanup/hls_dispose 是否生效、录制目录是否被无限保留。

治本：切片与录制分盘；设置保留天数与生命周期；给磁盘留 20% 余量；监控 inode，HLS 的小文件很容易先耗尽 inode 而不是容量。

▶⑦ 首个画面很慢：是编码问题还是服务器问题？

先看 GOP。服务器要等一个关键帧（IDR）才能让新观众起播；GOP 2 秒和 GOP 10 秒，首帧体验差一个数量级。再看 gop_cache 是否开启，按需回源是否让第一个观众承担了整次回源延迟。最后才怀疑编码器。

快速验证：同一路流用 ffplay 拉，若 ffplay 也慢，问题在服务器/上游；若 ffplay 快、浏览器慢，查播放器缓冲与 HLS 清单。

▶⑧ SRT 连不上：为什么 UDP 通了还失败？

SRT 不只是“UDP 端口通”：还要看 streamid（部分服务器用它做路径/鉴权）、peerlatency/recvlatency 是否匹配、防火墙是否按“无连接 UDP”放行。SRS 默认 10080/udp，MediaMTX 默认 8890/udp，两者都不是 TCP。

先用 ffmpeg -f mpegts -i ... -f mpegts "srt://host:port?streamid=..." 做最小验证，再逐步加 latency 与加密参数；一次只改一个变量。

💡排障顺序固定成习惯：① 用 curl 确认 API 活着；② 用 ffprobe 确认流存在；③ 用 ffplay 绕开浏览器；④ 再打开浏览器看控制台与网络；⑤ 最后才看业务代码。媒体问题里，“服务器没这路流”和“浏览器不支持这个协议”占了大多数，别一上来就怀疑编码器。
