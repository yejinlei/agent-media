在浏览器里播流：

🧱 浏览器到底能播什么：先认清墙在哪

把浏览器想成一个只接收快递柜取件码的人：它只肯按 HTTP(S) 的规矩去取东西，而且取到的必须是它认识的包裹格式。RTSP 是一套“我直接打个电话过去，你来我这儿取”的旧式协议，浏览器没有这部电话，也没有开这种电话的权限。

更技术一点：网页里的 JavaScript 没有任意 TCP/UDP socket 能力。它只能发 HTTP 请求、开 WebSocket、或者用 WebRTC。RTSP 走的是自己的 TCP 控制通道 + RTP 媒体通道，RTMP 走的是自定义 TCP 协议——两者都无法由 JS 直接建立。这就是“不能直连”的根本原因，而不是某个浏览器偷懒。

⚠️别被“能播”骗了：HLS 能播，不代表延迟能满足你。标准 HLS 的分片通常 6 秒一片，端到端延迟 15–30 秒很常见。要做“按门铃就看到人”，必须用 WebRTC 或 HTTP-FLV。

① WHEP（WebRTC）——低延迟首选

用 HTTP 完成 WebRTC 的 SDP 交换，浏览器原生能力，不需要任何第三方库。延迟通常 200–800 ms，适合监控、门铃、远程操控。代价：需要网关、需要处理 ICE/NAT、对编码有要求（H.264/VP8 等）。

看协议细节 →

② HLS——兼容性之王

服务器把流切成小分片，浏览器按 playlist 顺序下载。穿透性极好、能过几乎所有 CDN 和防火墙。代价：延迟大；标准 HLS 不适合实时互动。LL-HLS 能压到 2–4 秒，但要求服务端支持。

看 HLS 细节 →

③ HTTP-FLV——折中方案

一个 HTTP 长连接，持续下发 FLV tag。延迟 1–3 秒，实现简单，国内 CDN 支持好。代价：不是所有浏览器/环境都稳定，且依赖 mpegts.js 这类 MSE 库；iOS Safari 的 MSE 支持要单独验证。

如果只是“播放一段录好的视频”，不需要网关。注意 MP4 的 moov 要前置（faststart），否则浏览器要下完整个文件才能开始播。

📡 WHEP：用 HTTP 完成 WebRTC 的“握手”

WebRTC 本身不规定“怎么交换 SDP”。传统做法是自己写一个信令服务器（WebSocket 传来传去），很麻烦。WHEP（WebRTC-HTTP Egress Protocol）把这件事标准化成一次 HTTP 请求：POST 一份 SDP offer，服务器回一份 SDP answer。就这么简单。

async function playWhep(url, video) {
  const pc = new RTCPeerConnection({
    iceServers: [{ urls: 'stun:stun.l.google.com:19302' }]
  });

  // 只收不发
  pc.addTransceiver('video', { direction: 'recvonly' });
  pc.addTransceiver('audio', { direction: 'recvonly' });

  const stream = new MediaStream();
  video.srcObject = stream;
  pc.ontrack = e => stream.addTrack(e.track);

  // 1) 生成 offer
  await pc.setLocalDescription(await pc.createOffer());

  // 2) 等 ICE 候选收集完成（WHEP 常用非 trickle 模式）
  await new Promise(res => {
    if (pc.iceGatheringState === 'complete') return res();
    pc.addEventListener('icegatheringstatechange', () => {
      if (pc.iceGatheringState === 'complete') res();
    });
  });

  // 3) 一次 POST 交换 SDP
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/sdp', Accept: 'application/sdp' },
    body: pc.localDescription.sdp
  });
  if (!res.ok) throw new Error('WHEP ' + res.status);

  // 4) 记住资源地址，用于结束会话
  const resource = res.headers.get('Location');
  await pc.setRemoteDescription({ type: 'answer', sdp: await res.text() });
  await video.play();

  return { pc, resource };
}

为什么是 201 + Location

201 表示“资源已创建”。Location 指向这次会话；停止播放时对它发 DELETE，服务端才会释放转码/转发资源。只关 pc 不 DELETE，会留下僵尸会话。

Trickle ICE 要不要等

标准 WHEP 支持两种模式。等收集完成（非 trickle）实现最简单，代价是多等几百毫秒；trickle 模式要在建立后再发 PATCH，复杂度更高。

延迟为什么这么低

没有分片、没有 playlist、没有缓冲队列。RTP 包到浏览器就进 jitter buffer，通常只缓 100–300 ms。真正的大头是编码器 GOP 与网关的缓冲策略。

编码兼容性

浏览器 WebRTC 普遍支持 H.264、VP8、VP9、AV1；H.265 支持面很窄。国标摄像头若只出 H.265，网关需要转码，成本会明显上升。

🍰 HLS：把直播切成一块块“小蛋糕”

HLS 的思路非常朴素：把流切成固定时长的小分片（通常是 .ts 或 .m4s），再写一个播放列表 .m3u8 告诉浏览器“先下这个，再下那个”。浏览器只要会 HTTP，就能播。

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:6
#EXT-X-MEDIA-SEQUENCE:120
#EXTINF:6.000,
seg00120.ts
#EXTINF:6.000,
seg00121.ts
#EXTINF:6.000,
seg00122.ts
#EXT-X-ENDLIST   ← 直播时没有这一行
概念含义影响
EXT-X-TARGETDURATION分片目标时长越大越省请求，延迟也越大
EXT-X-MEDIA-SEQUENCE当前窗口第一个分片序号播放器据此判断“有没有落后”
EXT-X-PROGRAM-DATE-TIME分片对应的绝对时间做回放定位、时间校准
EXT-X-DISCONTINUITY时间轴断裂码率切换/广告插入后常见，处理不好会卡顿
LL-HLS 的 PART把分片再切成部分传输延迟压到 2–4 秒，但服务端/客户端都要支持

为什么 HLS 天生慢

延迟由三段叠加：分片时长（必须等一片写完）+ playlist 刷新间隔（浏览器才知道有新片）+ 播放器安全缓冲（通常囤 2–3 片）。6 秒分片 × 3 片缓冲，30 秒延迟就出来了。想快，只能把每一段都缩短——这就是 LL-HLS 在做的事。

💡选型口诀：要“看得到”用 HLS，要“看得及时”用 WHEP。HLS 的优势是便宜、稳定、能上 CDN；劣势是它天然为“容忍延迟”的场景设计。

📺 HTTP-FLV：一条不结束的 HTTP 响应

HTTP-FLV 把 FLV 的 tag 直接写进一个 HTTP 响应体，连接不关闭，数据持续下发。浏览器通过 MSE（Media Source Extensions）把收到的 tag 喂给 <video>。它比 HLS 少了两层“切片 + 写 playlist”的等待，所以延迟更低。

// mpegts.js 的最小用法
const player = mpegts.createPlayer({
  type: 'flv',
  url: 'https://example.com/live/cam.flv',
  isLive: true,
  hasAudio: true
}, {
  enableWorker: true,
  lazyLoad: false,          // 直播别懒加载
  liveBufferLatencyChasing: true  // 追帧，防止延迟越积越大
});

player.attachMediaElement(video);
player.load();
video.play();

为什么比 HLS 快

没有分片边界，不需要等“一片写完”；数据一到就能进 MSE 缓冲。少了 playlist 轮询，也就少了那几秒的发现延迟。

为什么不如 WHEP 稳

它仍然是 TCP。网络抖动时，TCP 的重传与拥塞控制会让延迟累积；WebRTC 则用 UDP + 丢帧策略，宁可丢一帧也不让延迟涨上去。

⚠️iOS 的坑：iPhone 上 MSE 的支持受限制（尤其非 Safari 内核的浏览器）。如果目标用户大量使用 iOS，优先评估 WHEP 或原生 HLS，别把宝押在 FLV 上。

🚪 MediaMTX 网关配方：RTSP 进，WHEP/HLS/FLV 出

MediaMTX 是一个单文件媒体服务器：它能把 RTSP、RTMP、SRT 的流转成 WebRTC（WHEP）、HLS、HTTP-FLV 等。它不做 GB28181（不解析 SIP/PS），所以国标设备要先经国标平台/网关，再交给 MediaMTX 做“第二跳”。

🔐 HTTPS、CORS 与自动播放：三个“非技术”的真问题

混合内容

页面是 https:// 时，浏览器会拦截 http:// 的媒体与 WHEP 请求。网关也必须上 HTTPS（或放在同域反向代理后面），否则“本地能播、线上一片空白”。

CORS

WHEP 的 POST 带 Content-Type: application/sdp，属于“非简单请求”，会触发预检。服务端必须允许 OPTIONS、POST、DELETE 与该 Content-Type。最省事的办法是同域反代。

自动播放

没有用户手势时，只有静音视频能自动播放。产品上要么默认静音 + 显式“开启声音”按钮，要么让用户先点一下播放键。别和浏览器策略硬刚。

# 同域反向代理（Nginx 示例）：把网关藏到 /live/ 下，绕开 CORS
location /live/ {
  proxy_pass http://127.0.0.1:8889/;
  proxy_http_version 1.1;
  proxy_set_header Host $host;
  # WHEP 需要透传 DELETE / POST
  proxy_set_header X-Forwarded-For $remote_addr;
}
