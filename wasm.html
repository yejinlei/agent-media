🧬 为什么 FFmpeg 能在浏览器里跑

浏览器不认识 C 语言，但它认识 WebAssembly。Emscripten 把 FFmpeg 的 C 代码、libavformat/libavcodec/libavfilter 以及 x264、libvpx、Opus 等第三方库一起编译成一个 .wasm 模块；模块在 Web Worker 中运行，输入输出文件放在内存虚拟文件系统（MEMFS）里。

你的页面UI / 事件
→
Worker避免阻塞主线程
→
WASM 模块FFmpeg / libav*
↔
MEMFS虚拟文件系统
→
输出 Blob预览 / 下载

① Emscripten

把 C/C++ 编译为 wasm32，并提供 POSIX 风格的系统调用垫片（shim）：文件、线程、时钟、内存。FFmpeg 的 avformat_open_input 在 wasm 里读的不是磁盘，而是 MEMFS 里的字节。

② Worker

转码是 CPU 密集型任务。放进 Worker 后，主线程仍能响应点击、渲染进度；页面与 Worker 之间只传消息和文件字节，不共享 DOM。

③ MEMFS

一个建立在 WASM 线性内存中的内存文件系统。writeFile('/input.mp4', bytes) 把浏览器 File 变成 FFmpeg 眼中的普通文件；readFile 再把输出读回 JS。

💡它不是“云端转码”：数据不会离开浏览器。首次点击“加载引擎”时，只会从本站加载 ffmpeg.js、ffmpeg-core.js 与约 30 MB 的 ffmpeg-core.wasm（已随仓库放在 vendor/ffmpeg/，无需联网）；之后所有像素运算都在本机完成。

单线程 core 与多线程 core

官方提供两种核心：@ffmpeg/core（单线程）与 @ffmpeg/core-mt（多线程）。多线程版依赖 SharedArrayBuffer，而浏览器只在跨源隔离（响应头 Cross-Origin-Opener-Policy: same-origin 与 Cross-Origin-Embedder-Policy: require-corp）下才开放它。GitHub Pages 不能自定义这些响应头，所以本站使用单线程 core：兼容性最好，速度慢一些。

// 多线程版 LOAD 的差别（仅示意；本站未启用）
await ffmpeg.load({
  coreURL: await toBlobURL(base + '/ffmpeg-core.js', 'text/javascript'),
  wasmURL: await toBlobURL(base + '/ffmpeg-core.wasm', 'application/wasm'),
  workerURL: await toBlobURL(base + '/ffmpeg-core.worker.js', 'text/javascript')
});
// 需要页面响应头：COOP: same-origin + COEP: require-corp

🔬 wasm ffprobe：在浏览器里"读透"一个文件

  
原生 ffprobe 是一个独立二进制；这里我们让 ffmpeg.wasm 干同样的活：跑一条隐藏了 banner 的探测命令，从 stderr 里解析出容器、流、编码参数、时长、码率、时间基，再渲染成结构化卡片。整个解析都在浏览器内存里完成，文件不上传。

它和 ffprobe 的关系

      
真正的 ffprobe 能输出 -show_streams / -show_format / -print_format json 这种机器可读 JSON。浏览器里没有独立 ffprobe 二进制，所以用 ffmpeg -hide_banner -i 的文本输出做等价解析——字段一样，只是解析层在我们这。

    

    

      
能读什么

      
凡 @ffmpeg/core 编进了解码器的格式都能读：MP4/MKV/FLV/TS、H.264/H.265/AV1/VP9、AAC/MP3/Opus 等。读到的是封装层 + 流层元数据，不是逐帧内容。

    

    

      
为什么在浏览器里做

      
文件不出本机：适合私有素材、涉密录像、或者你只是想快速确认"这文件到底什么编码、多长、有没有音轨"再决定怎么转。省去装 FFmpeg 命令行。

    

  


  
💡等价命令行：原生环境里你会敲 ffprobe -v error -show_entries format=duration,bit_rate:stream=index,codec_type,codec_name,width,height,avg_frame_rate -of json input.mp4。浏览器版在解析逻辑里复刻了同一套字段提取，输出结构与它一致。






  
▶️ wasm ffplay：边转码边播的网页播放器

  
原生 ffplay 是一个 SDL 播放器；浏览器里没有 SDL，但有 <video> + MediaSource。做法：ffmpeg.wasm 把输入转码成浏览器认识的 fMP4，逐段塞进 MSE，于是你得到"选本地文件 → 网页内播放、可拖进度条、可暂停/继续"——这就是一个 wasm 版的 ffplay。

为什么需要转码

      
浏览器 <video> 只认 H.264/VP8/VP9/AV1 视频 + AAC/Opus 音频、且要在 MP4/WebM 容器里。你的监控文件可能是 H.265、H.264 带 B 帧乱序、或封装在 FLV/TS 里——浏览器直接播不了，必须经 wasm 解码重编。

    

    

      
为什么用 MSE 而不是整体转完

      
整体转完要等全程解码，几十秒起。用 MediaSource 分块追加：转完几秒就喂几秒，视频先响、进度条能拖，体验接近本地播放器。

    

    

      
和原生 ffplay 的等价

      
原生 ffplay input.mp4 就是"解码 + 显示 + 走钟"。这里换成"解码 + 喂 MSE + 走钟"，输入输出都是本地文件，不上传、不依赖网络。

    

  


  
⚠️能播 ≠ 实时：单线程 wasm 的解码速度可能赶不上视频码率（尤其 4K/H.265）。此时会"边转边播、越播越慢"，或干脆先缓冲够再播。这是 @ffmpeg/core 单线程版的固有边界，不是 bug；换多线程 core（需 COOP/COEP）或原生 FFmpeg 会快很多。






  
🔌 API 生命周期：五步完成一次处理

  
ffmpeg.wasm 的 API 很小：加载一次，然后把每次任务当成“写文件 → 执行 → 读文件”。理解这五步，你就能把任何 FFmpeg 命令搬进浏览器。

  

    
1. load()加载并实例化 core，创建 Worker 与 MEMFS
↓
    
2. writeFile(name, bytes)把 File/Blob 写进虚拟文件系统
↓
    
3. exec(args)等价于命令行 ffmpeg，日志与进度通过事件回调
↓
    
4. readFile(name)读出 Uint8Array，包成 Blob
↓
    
5. deleteFile / terminate清理虚拟文件；释放 Worker 与内存

  


  
import { FFmpeg } from '@ffmpeg/ffmpeg';
import { fetchFile, toBlobURL } from '@ffmpeg/util';

const ffmpeg = new FFmpeg();
ffmpeg.on('log', ({ message }) => console.log(message));
ffmpeg.on('progress', ({ progress }) => console.log(progress));

// 1) 加载：core 与 wasm 通过 blob URL 注入，规避跨源 Worker 限制
//    本站已把 core 放进 vendor/ffmpeg/，优先读本地；线上可选回退 CDN
const base = 'vendor/ffmpeg';
await ffmpeg.load({
  coreURL: await toBlobURL(base + '/ffmpeg-core.js', 'text/javascript'),
  wasmURL: await toBlobURL(base + '/ffmpeg-core.wasm', 'application/wasm')
});

// 2) 写入输入文件（浏览器 File 对象）
await ffmpeg.writeFile('input.mp4', await fetchFile(file));

// 3) 执行：参数数组，不需要写 "ffmpeg" 本身
await ffmpeg.exec([
  '-i', 'input.mp4',
  '-c:v', 'libx264', '-crf', '23', '-pix_fmt', 'yuv420p',
  '-c:a', 'aac', '-b:a', '128k',
  '-movflags', '+faststart',
  'output.mp4'
]);

// 4) 读回并生成可下载的 Blob
const data = await ffmpeg.readFile('output.mp4');
const url = URL.createObjectURL(new Blob([data.buffer], { type: 'video/mp4' }));

// 5) 清理
await ffmpeg.deleteFile('input.mp4');
await ffmpeg.deleteFile('output.mp4');
// ffmpeg.terminate(); // 页面卸载或需要彻底释放时


  

    

      
为什么用 toBlobURL？

      
Worker 内部要 importScripts(coreURL)。如果 URL 跨源，某些浏览器会因同源策略拒绝。先把 core.js/wasm 下载成 Blob，再生成同源 blob: URL，就能稳定实例化。

    

    

      
参数为什么是数组？

      
exec(['-i','a.mp4','b.webm']) 不做 shell 解析，空格、引号、通配符都不会被解释。滤镜字符串里的逗号、方括号要作为单个数组元素传入，避免被拆开。

    

  






  
📉 性能、内存与能力边界

  

    
维度原生 FFmpegffmpeg.wasm（单线程）工程含义

    
      
CPU多核 + SIMD + 汇编优化单核，部分 SIMD同一 preset 下慢 3–10 倍；长视频不现实

      
GPUNVENC/QSV/VAAPI…无（WASM 内无 GPU 后端）不能做硬件零拷贝；高分辨率很吃力

      
内存可达数十 GBwasm32 地址空间上限 4 GB，实际更小大文件/多轨/4K 易 OOM

      
I/O磁盘/网络流式整文件进 MEMFS需要一次性读入；超大文件会翻倍占用

      
线程slice/frame 多线程单线程 coreGitHub Pages 无 COOP/COEP，无法开 SAB

      
编码器全部（含闭源/硬件）编译进 core 的开源编码器以 -encoders 实际输出为准

      
稳定性生产级实验/教学级崩溃表现为 Worker 终止；需容错与超时

    
  

  
实测建议

  
    
    
  • 文件：1080p 30 秒以内、几十 MB 最稳；4K 或 10 分钟以上建议先裁剪。
    • 
    
  • 编码器：libx264 -preset ultrafast/veryfast 明显快于 medium；libvpx-vp9 很慢，学习时优先用短片段。
    • 
    
  • 滤镜：scale/fps/trim 便宜；loudnorm、降噪、复杂 overlay 昂贵。
    • 
    
  • 内存：处理前关闭其他大页面；输出后及时 deleteFile，否则 MEMFS 会持续占用。
    • 
    
  • 兼容性：需要 WebAssembly、Worker、Blob；现代 Chrome/Edge/Firefox/Safari 均支持。
    •

🍳 命令配方与原理对照

  
实验台里的每个预设都是一条真实命令。重点观察“输入 → 解码 → 滤镜 → 编码 → 封装”这条链在日志中的顺序。

  

  

    
任务关键参数背后发生了什么

    
      
查看信息-i input只打开输入并打印容器/流/编码参数，不产生输出（退出码非 0 是正常现象）

      
转 H.264 MP4-c:v libx264 -crf 23 -pix_fmt yuv420p -c:a aac -movflags +faststart解码 → 可选滤镜 → x264 编码 → AAC 编码 → MP4 mux；faststart 把 moov 提前

      
转 WebM-c:v libvpx-vp9 -crf 32 -b:v 0 -c:a libopusVP9 恒定质量（crf + b:v 0），Opus 音频，Matroska/WebM 封装

      
提取 MP3-vn -c:a libmp3lame -q:a 2丢弃视频流，音频解码后用 LAME 重编码为 MP3

      
裁剪 5 秒-ss 0 -t 5从指定时间开始取 5 秒；重新编码可保证从关键帧开始、时间戳连续

      
缩放到 720p-vf scale=-2:720swscale 做像素格式/尺寸变换；-2 表示按比例且保证偶数（4:2:0 要求）

      
生成 GIF-vf fps=10,scale=480:-1:flags=lanczos -loop 0抽帧 → 缩放 → GIF 编码；调色板优化可显著减小体积

      
抽取封面-ss 1 -frames:v 1 output.png定位到 1 秒，解码一帧，PNG 编码

      
生成测试源-f lavfi -i testsrc2=... -f lavfi -i sine=...用 lavfi 合成视频与正弦音频，不依赖外部文件，适合验证引擎

    
  

  


  

    ▶GIF 调色板优化（原生 / wasm 都适用）
    

      
ffmpeg -i input.mp4 -vf "fps=12,scale=480:-1:flags=lanczos,palettegen" palette.png
ffmpeg -i input.mp4 -i palette.png -filter_complex \
  "fps=12,scale=480:-1:flags=lanczos[x];[x][1:v]paletteuse" output.gif

      
第一遍生成 256 色调色板，第二遍复用调色板。GIF 只有 256 色，渐变与阴影容易出现色带；这是格式本身的限制，不是编码器问题。

    

  

  

    ▶为什么 wasm 里常用 -preset veryfast
    

      
x264 的 preset 控制搜索范围、参考帧、B 帧、lookahead 等。medium 在原生 CPU 上通常实时，但在单线程 wasm 中可能远慢于实时。veryfast/ultrafast 牺牲一些压缩率换取速度，适合“先跑通再优化”的学习场景。

    

  






  
🔒 隐私、安全与部署

  

    

      
数据边界

      
文件字节通过 File.arrayBuffer() 进入页面，经 Worker 消息传给 WASM 内存；没有 fetch 上传步骤。关闭标签页后，MEMFS 与 Blob 随进程释放。你可以在 DevTools 的 Network 面板验证：除了加载 vendor/ffmpeg/ 里的脚本与 wasm（首次约 30 MB），没有任何媒体数据请求。

    

    

      
供应链边界

      
本站采用“自托管优先、CDN 兜底”：默认从同源的 vendor/ffmpeg/ 读脚本与 wasm，版本已锁定（core 0.12.6 / ffmpeg 0.12.10 / util 0.12.1）；只有本地读取失败时才回退 unpkg。生产环境应完全移除回退分支，只信任自己的静态目录。

    

    

      
CSP 与 Worker

      
若站点启用严格 CSP，需要允许 worker-src blob:、script-src blob: 与 wasm-unsafe-eval。blob URL 是 ffmpeg.wasm 注入 core 的常用方式。

    

    

      
适合的落地场景

      
浏览器内预览转码、隐私敏感素材的本地处理、教学演示、离线小工具、上传前压缩。不适合长视频转码农场、4K 批量处理、需要 GPU 的实时直播。

    

  

  
✅学习路径建议：先用“查看信息”认识流与编码 → 用“裁剪 5 秒”理解时间戳 → 用“缩放 720p”理解像素格式 → 用“转 WebM”对比编码器差异 → 最后自定义参数，观察日志里的 Video: h264 … yuv420p 与 Audio: aac …。






  
🧭 浏览器兼容矩阵：哪款浏览器能跑什么

  
ffmpeg.wasm 依赖三大浏览器能力：WebAssembly、Web Worker、SharedArrayBuffer（仅多线程版）。主流浏览器最近两三年的版本都能跑单线程 core；多线程版需要 SharedArrayBuffer，而它在跨源隔离环境下才开放。GitHub Pages 与普通 HTTP 服务都不满足这个条件，所以本站固定使用单线程 core。


  

    

      
浏览器最低版本（单线程）多线程（需 COOP+COEP）备注

      
        
Chrome / Edge5789+多线程需要响应头 Cross-Origin-Opener-Policy: same-origin 与 Cross-Origin-Embedder-Policy: require-corp。

        
Firefox5279+Firefox 对 COOP 更严格；本地 file:// 通常也能跑单线程。

        
Safari1115.2+iOS Safari 对 Worker 数量限制更严；macOS 没问题。

        
Opera4475+Chromium 内核，同 Chrome 表现。

        
iOS 独立浏览器11❌iOS 所有浏览器都是 WebKit 内核，共享 Safari 的限制；WKWebView 也受此影响。

      
    

  


  
本站的处理策略

  
    
    
  • 固定用单线程 core（@ffmpeg/core@0.12.6），因为 GitHub Pages 没法加 COOP/COEP 响应头。任何浏览器只要支持 WASM 就能跑。
    • 
    
  • 本地优先、CDN 兜底：vendor/ffmpeg/ 下放好 ffmpeg.js、ffmpeg-core.js、ffmpeg-core.wasm；本地读不到时才回退 unpkg。这样离线也能跑，CDN 崩了也不影响。
    • 
    
  • Blob URL 注入 Worker：Worker 不能跨源 importScripts。先把 core.js/wasm 下载成 Blob，再生成同源 blob: URL 传给 coreURL，规避同源限制。
    •
