📦 为什么需要国标：把“方言”变成“普通话”

十多年前，安防行业是典型的“方言现场”：海康用一套私有 SDK，大华用另一套，宇视再一套；同一个省里，不同厂商的平台甚至无法互相看到对方的摄像头。GB/T 28181《公共安全视频监控联网系统信息传输、交换、控制技术要求》做的事情，就是给所有设备发一张统一样式的快递面单：地址怎么写、包裹怎么打包、签收怎么确认，全部写死。

它不规定“画面用 H.264 还是 H.265”，也不规定“码率多少”——这些留给设备自己协商。它只规定三件事：怎么找到对方（SIP）、怎么描述媒体（SDP）、怎么把画面送过去（PS over RTP）。记住这三件事，后面所有名词都能挂上去。

SIP信令：注册 / 点播 / 控制
+
SDP谈判：地址、端口、编码、SSRC
+
PS / RTP媒体：打包、分片、传输

标准版本怎么看

GB/T 28181-2011 打底，2016 版补齐了 TCP 传输、H.265、语音对讲等；2022 版进一步规范了安全、级联与扩展。设备铭牌或说明书上通常会写“支持 GB/T 28181-2016”。版本差异主要影响是否支持 H.265、TCP 被动、以及一些 XML 字段。

它属于“应用层规范”

底下完全复用成熟标准：SIP 来自 RFC 3261，SDP 来自 RFC 4566，RTP 来自 RFC 3550，PS 复用 MPEG-2 System（ISO/IEC 13818-1）。国标的价值在于把这些积木拼成一个固定组合，让不同厂商能互操作。

最常见的落地形态

摄像头 / NVR 作为“设备”注册到“国标平台”；平台再向上级平台级联。浏览器看不到 RTSP，也看不到 SIP——所以工程上几乎总要再加一个流媒体网关，把 PS 流转成 WebRTC / HLS / FLV。

⚠️先纠正一个常见误解：“GB28181”不是“一种视频编码”，也不是“一个可以直接用 VLC 打开的地址”。它是一套信令 + 私有封装组合。你拿到的往往只是 SIP 服务器地址、设备 ID、平台域名和密码，真正的播放地址要经过一次 INVITE 协商才诞生。

🏢 四个角色，一串 20 位身份证

国标网络里，所有实体都有一个 20 位 ID。它不是随机数，而是“行政区划 + 行业 + 类型 + 网络 + 序号”拼出来的身份证。理解了编号规则，你就能从 ID 一眼看出对方是平台还是摄像头、属于哪个地市。

角色典型实体职责在信令里的身份
SIP 服务器国标平台的信令模块接收注册、转发/处理 INVITE、维持在线状态REGISTER 的接收方，INVITE 的发起方
设备（Device）IPC、NVR、解码器、下级平台上报目录、送媒体流、响应控制20 位 DeviceID，通常以 13x / 11x 开头
通道（Channel）NVR 下挂的每一路摄像头真正可点播的“一路画面”NVR 的 ID + 通道号，Catalog 里逐条上报
客户端Web 播放器、电视墙、上级平台发起点播/控制，或接收级联目录有时也拥有独立 ID，作为 SIP 用户

20 位 ID 是怎么拼出来的

类型编码里，200 常见于平台/服务器，13x 常见于摄像机，215 / 216 用于业务分组与虚拟组织。不同厂商和地市会有自己的分配习惯，不要靠猜编号来判断设备类型，最终以 Catalog 上报为准。

💡为什么 ID 这么重要？SIP 的 From / To / Call-ID、XML 里的 DeviceID、SDP 里的 y=SSRC、目录里的 ParentID，全都围着这串数字转。现场对不上号，八成是 ID 抄错了一位，或者把“设备 ID”和“通道 ID”混用了。

📇 注册：门卫登记，还要盖一个动态章

设备上电后的第一件事不是推流，而是“报到”。注册就像进大楼登记：先报上姓名（DeviceID），门卫说“请出示盖章的介绍信”（401 + WWW-Authenticate），设备用账号密码算出一个摘要（Authorization），门卫核对无误后发通行证（200 OK），并注明“这张证 3600 秒后过期”。

关键点：第一次 REGISTER 一定是被拒绝的。这不是故障，而是 Digest 鉴权的标准流程——服务器先给随机数（nonce），客户端才能算出不可重放的 response。抓包里看到 401 不要慌，看第二次 REGISTER 有没有带 Authorization。

REGISTER sip:34020000002000000001@3402000000 SIP/2.0
Via: SIP/2.0/UDP 192.168.1.64:5060;rport;branch=z9hG4bK123456
From: <sip:34020000001320000001@3402000000>;tag=abc123
To: <sip:34020000001320000001@3402000000>
Call-ID: 0a1b2c3d4e5f@192.168.1.64
CSeq: 1 REGISTER
Contact: <sip:34020000001320000001@192.168.1.64:5060>
Max-Forwards: 70
Expires: 3600
User-Agent: IPC v1.0
Content-Length: 0

注意 To 里是设备自己的 ID，Contact 里带真实 IP 和端口——平台之后就用它来找设备。CSeq 每发一条新请求就加一，重复请求（重传）才保持同一个值。

SIP/2.0 401 Unauthorized
WWW-Authenticate: Digest realm="3402000000",
  nonce="a3f5c9e2b1d4", algorithm=MD5, qop="auth"

realm 通常是 SIP 域名，nonce 是一次性随机数。服务器用它防止“录播”攻击：同一个 response 不能用第二次。

REGISTER sip:34020000002000000001@3402000000 SIP/2.0
CSeq: 2 REGISTER
Authorization: Digest username="34020000001320000001",
  realm="3402000000", nonce="a3f5c9e2b1d4",
  uri="sip:34020000002000000001@3402000000",
  response="9c1f0b7a6d3e5f...", algorithm=MD5, qop=auth,
  nc=00000001, cnonce="8f2a1c"
Expires: 3600

摘要的计算对象是“用户名:realm:密码”再做一次 MD5，然后与 nonce、uri、method 等再算一次。下一节的代码示例会把它写出来。

SIP/2.0 200 OK
CSeq: 2 REGISTER
Expires: 3600
Date: 2026-11-02T10:00:00
Contact: <sip:34020000001320000001@192.168.1.64:5060>;expires=3600

200 里回带的 Expires 才是平台认可的租期。设备应在到期前（通常是 1/2 或 2/3 处）重新注册，而不是等到最后一秒。

🔍排错口诀：“注册成功”不等于“在线”。平台判在线靠的是心跳，不是注册。注册只证明“我知道你在哪”，心跳才证明“你还活着”。

💓 心跳、目录、状态：都装在 MESSAGE 里

SIP 只负责“送信”，真正的内容是贴在信里的 XML——这套 XML 在国标里叫 MANSCDP（监控报警联网系统控制描述协议）。可以把 SIP MESSAGE 想成一个信封，XML 是信纸；CmdType 决定这封信是“报平安”、“交名单”还是“查状态”。

心跳 Keepalive

<Notify>
  <CmdType>Keepalive</CmdType>
  <SN>101</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <Status>OK</Status>
</Notify>

默认 60 秒一次。平台通常“连续 3 个周期收不到”就判离线。SN 是请求序号，用于把应答和请求对上；心跳的应答是一条空的 200 OK，不带 XML。

设备信息 DeviceInfo

<Response>
  <CmdType>DeviceInfo</CmdType>
  <SN>102</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <DeviceName>大门口</DeviceName>
  <Manufacturer>Hikvision</Manufacturer>
  <Model>DS-2CD3T</Model>
  <Firmware>V5.6</Firmware>
  <Channel>1</Channel>
</Response>

常用来确认“这台设备到底是谁”。有的平台在 Catalog 之前会先查一次 DeviceInfo。

发送方式：MESSAGE sip:平台ID@平台域 SIP/2.0，并带上 Content-Type: Application/MANSCDP+xml。如果 Content-Type 写错，很多平台会直接丢弃——这是“心跳明明发了却显示离线”的高频原因。

⚠️时钟与 SN 的坑：部分设备重启后 SN 从 1 重新开始，平台侧如果按“SN 必须递增”做严格校验，会误判为异常。对账时请以 DeviceID + CmdType 为准，SN 只做请求-应答配对。

📋 目录查询：平台怎么知道你有几路画面

注册只告诉平台“有一台设备”。平台还需要知道“这台设备下有哪些可看的通道”。于是它发一封 Catalog 查询，设备回一份通道清单。NVR 尤其重要：一个 NVR 的 DeviceID 下可能挂着 8、16、32 个通道，每个通道都有自己的 20 位 ID。

// 平台 → 设备：查询目录
<Query>
  <CmdType>Catalog</CmdType>
  <SN>110</SN>
  <DeviceID>34020000001320000001</DeviceID>
</Query>

// 设备 → 平台：目录应答（节选）
<Response>
  <CmdType>Catalog</CmdType>
  <SN>110</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <SumNum>16</SumNum>
  <DeviceList Num="2">
    <Item>
      <DeviceID>34020000001320000001</DeviceID>
      <Name>大门口</Name>
      <Manufacturer>Hikvision</Manufacturer>
      <Model>DS-2CD3T</Model>
      <Owner>保卫科</Owner>
      <CivilCode>340200</CivilCode>
      <Address>一号门</Address>
      <Parental>0</Parental>
      <ParentID>34020000002000000001</ParentID>
      <RegisterWay>1</RegisterWay>
      <Secrecy>0</Secrecy>
      <Status>OK</Status>
    </Item>
    <Item>…</Item>
  </DeviceList>
</Response>

SumNum 与 Num 的区别

SumNum 是通道总数，DeviceList Num 是本条消息里带了几条。通道多时设备会分多条 Response 发送，平台要按 SumNum 判断收齐没有。

Parental 是什么

表示有没有下级。NVR 下的通道常为 0（无下级）；如果一台设备还挂着子设备，平台需要递归查询，否则目录树会断。

Status 只是快照

Catalog 里的 Status 是“查询那一刻”的状态。通道后来掉线，要靠 DeviceStatus 查询或平台主动订阅来更新。

💡工程建议：把“设备 ID → 通道 ID”的映射持久化下来。点播时用的是通道 ID，不是设备 ID。把两者混用，INVITE 会 404 或直接没有媒体。

🎬 点播：一次 INVITE，把画面“请”出来

点播就是打一通 SIP 电话，只不过接通后传的不是声音，而是视频。平台发 INVITE 并附上 SDP：“我想收你的视频，用 PS 封装，我的地址是 10.0.0.5:15060，SSRC 是 0123456789”。设备回 200 OK 确认，平台回 ACK，媒体流才开始。

INVITE sip:34020000001320000001@3402000000 SIP/2.0
From: <sip:34020000002000000001@3402000000>;tag=platform1
To: <sip:34020000001320000001@3402000000>
Call-ID: play-20261102-001@platform
CSeq: 1 INVITE
Subject: 34020000001320000001:0100000000,34020000002000000001:0
Contact: <sip:34020000002000000001@10.0.0.5:5060>
Content-Type: application/sdp
Content-Length: …

v=0
o=34020000002000000001 0 0 IN IP4 10.0.0.5
s=Play
c=IN IP4 10.0.0.5
t=0 0
m=video 15060 RTP/AVP 96
a=rtpmap:96 PS/90000
a=setup:passive
a=connection:new
y=0123456789
f=v/2/4/25/1/4000/1a/…
字段含义为什么重要
m=video 15060媒体类型、平台收流端口、payload 类型端口写错 → 设备把流发到空气里；防火墙没放行 → 看不到画面
a=rtpmap:96 PS/90000payload 96 对应 GB28181 的 PS 封装，时钟 90 kHz这是“国标媒体”的暗号。写成 H264 就不是国标 PS 了
y=0123456789SSRC，十位十进制平台用它区分多路流；设备必须把 RTP 头里的 SSRC 写成这个值，否则平台可能直接丢包
a=setup:passiveTCP 连接角色（RFC 4145 语义）决定谁主动发起 TCP；厂商实现有差异，以抓包握手方向为准
f=v/2/4/25/1/4000/1a/…媒体描述参数：视频/音频、编码、分辨率、帧率、码率等给平台做展示与校验用；不是所有设备都严格填写
Subject点播的通道与接收方标识部分平台/设备依赖它做路由；漏写可能 404

接流之后，还要“控”

点播建立后，播放、暂停、快进、停止都靠 SIP INFO 里的 MANSCDP 控制指令。它不是 RTSP 的 PLAY/PAUSE，而是另一套 XML：

<Control>
  <CmdType>Play</CmdType>
  <SN>120</SN>
  <DeviceID>34020000001320000001</DeviceID>
</Control>

<!-- 暂停 -->
<Control><CmdType>Pause</CmdType><SN>121</SN>…</Control>
<!-- 拖动（回放时） -->
<Control><CmdType>Play</CmdType><SN>122</SN><Scale>1</Scale><Range>…</Range></Control>

注意：控制走 SIP INFO，媒体走 RTP——两条完全独立的通道。抓包时如果只看了 RTP，永远看不到“暂停”这件事。

🎞️ PS over RTP：把“节目流”塞进快递箱

为什么不是 MP4？因为 MP4 需要索引（moov），而实时流不能等录完再发。为什么不是 TS？TS 为广播设计，包头开销大、结构复杂；PS（Program Stream）更轻，适合点对点。国标选 PS，本质是选了一种“足够简单、能实时切、开销可控”的封装。

几个实战中必须知道的事实

关键帧决定“第一眼”

平台开始接流时，只有收到一个完整 IDR 才能出画面。设备若正在 GOP 中间，可能先来几秒绿屏/黑屏。低延迟点播要在 INVITE 后让设备尽快强制一个 I 帧（部分设备通过 f= 参数或私有指令支持）。

SSRC 是“取件码”

同一台平台可能同时收几十路流，全靠 SSRC 区分。设备把 SSRC 写错 → 平台按 SDP 里的值过滤 → 包全被丢，表现为“有 RTP 但没画面”。

PS 包与 RTP 包的边界

常见实现让每个 RTP 载荷携带完整的 PS 包，避免接收端做跨包重组。大 I 帧会通过多个 PS 包/PES 承载，接收端按 PTS 与 marker 拼成一帧。

没有索引，就没有随机访问

PS 是流式的，不能像 MP4 那样“跳到第 30 秒”。回放要拖动，必须重新协商时间范围（见下一节），而不是在流里 seek。

🚚 UDP 还是 TCP：两种送法，各有代价

国标允许 UDP 和 TCP 两种媒体传输。UDP 快、开销小，但丢包；TCP 稳、能穿一些 NAT，但延迟更高、断线影响更大。真正的难点不是“选哪个”，而是搞清楚谁连谁。

方式谁发起连接SDP 常见写法适用场景典型问题
UDP设备直接往平台端口发包m=video 15060 RTP/AVP 96局域网、专网，链路稳定丢包花屏；NAT/防火墙挡 UDP
TCP 被动设备监听，平台去连常见 a=setup:passive平台能访问设备端口设备端口未放行；平台连不上
TCP 主动设备主动连平台常见 a=setup:active设备在 NAT 后、平台有公网平台监听端口未开；设备连错地址
⚠️厂商差异提醒：“主动/被动”是国标语境下从设备视角的命名，而 setup 是 RFC 4145 从 SDP 发送方视角的语义。两者并不总能一一对应，海康、大华、宇视的实现也出现过相反理解。结论：不要背字段，去抓 TCP 握手（SYN 方向）。

⏪ 录像回放：不能 seek 的流，怎么拖进度条

实时流是“现在”，回放流是“过去”。PS 流本身没有索引，所以国标换了个办法：每次拖动都重新发一次 INVITE，在 SDP 里写明起止时间，让设备从录像文件的那个位置重新开始推。

INVITE sip:34020000001320000001@3402000000 SIP/2.0
Content-Type: application/sdp

v=0
o=34020000001320000001 0 0 IN IP4 10.0.0.5
s=Playback
u=34020000001320000001:0
c=IN IP4 10.0.0.5
t=1762000000 1762003600          ← 起止时间（NTP 秒，UTC）
m=video 15060 RTP/AVP 96
a=rtpmap:96 PS/90000
a=setup:passive
y=0123456789

s=Playback 是回放，s=Download 是下载（通常也走 SIP + RTP/PS，但语义是“尽快传完”）。时间用 NTP 秒，也就是从 1900-01-01 起算的秒数——不是 Unix 时间戳，换算时别差 70 年。

拖动 = 新的 INVITE

先 BYE 掉旧会话，再用新的 t= 范围发起新会话。播放器看到的“秒开”其实是设备侧重新定位文件并等到下一个 I 帧。

倍速 = Scale

通过 SIP INFO 下发 <Scale>2</Scale> 实现 2 倍速，负值表示倒放。设备是否支持、支持到几倍，取决于型号。

时间对不上？先查时区

国标时间基准是 UTC。前端界面显示本地时间，换算链路里任何一环漏掉 +8 小时，都会出现“回放八小时前”的经典问题。

🔍为什么回放容易“卡在第一帧”？因为设备定位到的是关键帧之前的 P 帧，必须先等到一个 IDR 才能解码。工程上要么让设备对齐关键帧，要么在播放器侧容忍这段等待。

🌐 级联：平台之上还有平台

区县平台要把画面交给市局，市局再交给省厅——这就是级联。技术上它没有魔法：下级平台把自己当成一台“设备”，向上级平台注册，然后共享目录、接受点播，媒体流可以直连，也可以经下级转发。

摄像头 / NVRDevice
→
区县平台下级平台（同时是设备）
→
市局平台上级平台
→
省厅 / 客户端多级观看

目录怎么共享

下级平台向上级上报 Catalog，上级看到的 DeviceID 仍然是原始通道 ID（或按级联规则映射）。这就是为什么跨级点播时，上级用的通道 ID 可能在下级设备上并不存在——它属于“平台虚拟目录”。

媒体走哪条路

两种模式：上级直接向下级设备点播（需要网络可达），或下级平台转发（跨网闸、跨安全域更常见）。后者会多一跳，延迟与带宽都要重新算。

💡级联排错先看三样：下级平台是否用平台类型 ID注册成功、上级目录里有没有通道、以及上级点播时 SDP 里的收流地址是否可达。三者缺一，画面都不会出现。

🎥 PTZ 与预置位：转动摄像头

云台控制是"给摄像头发一组方向指令"——不是 SIP 报文，而是塞在 SIP MESSAGE 里的 XML。比喻成"给保安发微信：左转 30°，向上 15°，变焦 2 倍"。指令按 MANSCDP 格式编码，摄像头执行完会回一份 200 OK（成功）或 403 Forbidden（不支持）。

# PTZ 方向控制（Pant / Tilt / Zoom）
# MESSAGE 请求体，发往设备 DeviceID@域名
<Control>
  <CmdType>DeviceControl</CmdType>
  <SN>300</SN>                              
  <DeviceID>34020000001320000001</DeviceID>
  <PTZCmd>A5 0F 01 64 00 00 03 </PTZCmd>    
</Control>

# 摄像头回 200 OK（XML body）
<Control>
  <CmdType>DeviceControl</CmdType>
  <SN>300</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <Result>OK</Result>
</Control>

PTZCmd 字节的分段含义

A5 0F 01 64 00 00 03 共 7 个字节，是最常见的"方向 + 速度"组合：

0xA5首字节：命令头，固定值 0x0F字节 2：命令类型
0x01=方向控制
0x03=预置位设置
0x04=调用预置位
0x09=巡航起始
0x0B=巡航终止
0x0E=看守位设置 0x01字节 3：方向编码
0x01=上 / 0x02=下
0x04=左 / 0x08=右
0x10=变倍+/0x20=变倍-
可多方向按位或 0x64字节 4：水平速度 0-255
0x64=100=中速 0x00字节 5：垂直速度 0-255 0x00字节 6：变倍速度 0-15 0x03字节 7：校验/结束

预置位与巡航

预置位就是"先让摄像头转到一个好位置，记下来；下次一个命令让它回到这里"。设置用 CmdType=DeviceControl + PTZCmd=A5 0F 03 …（命令类型 0x03=预置位设置），调用用 PTZCmd=A5 0F 04 …（命令类型 0x04=预置位调用）。预置位编号从 1 开始。

巡航是"在几个预置位之间按顺序来回巡逻"：先设置好几个预置位，再发巡航起始/终止指令（命令类型 0x09 / 0x0B），摄像头自己在巡航时间内循环。

⚠️方向是"持续"的：发了"左转"指令后，摄像头会持续左转，直到你发"停止"（方向字节全 0x00）或发相反方向指令。做网页 UI 时一定要在 mouseup 里发停止指令，否则用户松手了摄像头还在转。

🎤 语音对讲与广播

对讲就是平台和摄像头互相"打电话"——媒体流方向是双向的：摄像头把现场声音往平台送，平台把麦的声音发回摄像头（让它的喇叭响）。广播是"平台单方面喊话"，摄像头只要接收不需要回应——像校园广播，校长讲话，全体喇叭都响。

对讲 vs 广播的本质差别

对讲（双向）

用 SIP INVITE + a=sendrecv（或 a=sendonly / a=recvonly 的组合），SDP 里双方都声明自己的音频能力（G.711A 最常见）。平台 AAC-LC 通常没问题，但设备侧大多只原生支持 G.711——平台必须在发送前转码。

广播（单向）

可以用 INVITE 也可以用 SIP NOTIFY（MANSBROADCAST）。SDP 里只出现 a=sendonly。关键是"多个设备同时收听"：平台把同一条音频流发给每台设备，每台设备的 SIP 会话独立。

对讲常见的三个坑

  1. G.711 vs AAC 的转码：设备侧几乎都只原生 G.711（μ-law 或 A-law），浏览器采到的是 AAC 或 PCM。平台必须用 ffmpeg 转。ffmpeg -f alsa -i hw:0 -acodec pcm_mulaw -ar 8000 -ac 1 …
  2. 端口与 NAT：对讲是双向 RTP，设备 NAT 后平台能不能直接打进设备端口，取决于 NAT 类型。Symmetric NAT 下通常要走 TURN 中继。
  3. 回声消除：摄像头喇叭在现场同时放平台音频又被自己的麦采回来，会让平台听到回音。WebRTC 的 AEC（Acoustic Echo Cancellation）可以缓解，但对讲场景下距离近必须平台侧也要做一次 AEC。

📜 录像查询 RecordInfo：我什么时候录过什么

点播和回放是"假设你知道有录像"。但平台其实必须先问"这台设备有哪些录像文件、时间戳是多少、存了多久"——这就靠 RecordInfo 查询。像查快递单之前先看"哪天发了什么包裹"。

MESSAGE 里的查询 XML

# 向设备查询录像，时间窗口 2026-11-01 00:00:00 ~ 2026-11-02 23:59:59
# SIP MESSAGE 请求体，发往设备 DeviceID@域名
<Query>
  <CmdType>RecordInfo</CmdType>
  <SN>150</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <StartTime>2026-11-01T00:00:00Z</StartTime>
  <EndTime>2026-11-02T23:59:59Z</EndTime>
  <Secrecy>0</Secrecy>                 
  <Type>all</Type>                      
</Query>

设备的响应

设备回 200 OK，body 是一份 RecordInfo 列表。当录像很多时，设备会分批返回，每次返回一个 SumNum（总条数）和当前批次。

# 200 OK，body 示例
<Response>
  <CmdType>RecordInfo</CmdType>
  <SN>150</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <SumNum>128</SumNum>                
  <RecordList Num="3">               
    <Item>
      <DeviceID>34020000001320000001</DeviceID>
      <StartTime>2026-11-01T08:00:00Z</StartTime>
      <EndTime>2026-11-01T12:00:00Z</EndTime>
      <Secrecy>0</Secrecy>
      <Type>alarm</Type>
      <File><URI>rtsp://192.168.1.64/live/001</URI></File>
    </Item>
    …
  </RecordList>
</Response>

拿到 RecordInfo 列表之后怎么播放：对每个 Item 再发一次 INVITE，SDP 的 y= 行换成回放的 SSRC，Subject 换成该 Item 的 StartTime（格式有差异）。设备回 200 OK 并开始推对应时间段的媒体流。如果要拖放，就再发一条带 a=range 或 Subject 带新时间戳的 INFO/INVITE。

🔬 抓包与排错：把“没画面”拆成可验证的假设

国标排错最有效的方法不是猜，而是按层次验证：注册成没成 → 心跳在不在 → 目录有没有 → INVITE 成没成 → RTP 到没到 → PS 能不能解 → 解码器有没有关键帧。每层都有明确的证据。

# 同时抓 SIP 与媒体端口（示例网段，按实际改）
tcpdump -i eth0 -s 0 -w gb.pcap \
  'port 5060 or (portrange 15000-15100)'

# 只看 SIP
tcpdump -i eth0 -A -s 0 'port 5060'

# 确认 TCP 媒体是谁主动连的（看 SYN 方向）
tcpdump -i eth0 -n 'tcp[tcpflags] & tcp-syn != 0'

建议：在平台侧和设备侧同时抓，对比时间戳。只抓一侧时，很容易把“包到了但被丢”误判成“设备没发”。

sip                      # 所有 SIP
sip.Method == "REGISTER"
sip.Method == "INVITE"
sip.CSeq.method == "MESSAGE"
rtp                      # RTP 流
rtp.ssrc == 0x499602D2   # 十进制 1234567890 的十六进制
ps                       # PS 封装（Wireshark 可识别部分字段）
http                     # 若是 WebRTC/HLS 网关

怀疑 SSRC 不匹配时，直接按 rtp.ssrc 过滤，再和 SDP 里的 y= 对比。十进制作十位、十六进制八位，换算时别丢前导零。

🧑‍💻 最小代码：算摘要、拼 XML、读 PS

下面三段代码不依赖任何国标 SDK，目的是让你看清“协议到底做了什么”。真实项目请用成熟库（pjsip、wvp、ZLM），但读懂这几段，排错时你会知道该看哪里。

① SIP Digest 摘要

import hashlib, os

def md5(s): return hashlib.md5(s.encode()).hexdigest()

def digest(username, password, realm, nonce, uri, method, qop='auth', nc='00000001'):
    ha1 = md5(f'{username}:{realm}:{password}')
    ha2 = md5(f'{method}:{uri}')
    if qop:
        cnonce = os.urandom(8).hex()
        resp = md5(f'{ha1}:{nonce}:{nc}:{cnonce}:{qop}:{ha2}')
        return (f'Digest username="{username}", realm="{realm}", nonce="{nonce}", '
                f'uri="{uri}", response="{resp}", algorithm=MD5, qop={qop}, '
                f'nc={nc}, cnonce="{cnonce}"')
    return f'Digest username="{username}", realm="{realm}", nonce="{nonce}", uri="{uri}", response="{md5(f"{ha1}:{nonce}:{ha2}")}"'

要点：HA1 包含密码，HA2 包含方法和 URI。所以同一个 nonce 下，REGISTER 和 INVITE 的 response 一定不同——这也是为什么“抄一条 Authorization 去发别的请求”永远失败。

② 扫描 PS 起始码

PS_START = {
    0xBA: 'pack_header', 0xBB: 'system_header', 0xBC: 'program_stream_map',
    0xE0: 'video_pes',   0xC0: 'audio_pes',
}

def scan_ps(data):
    """在 RTP 载荷里找 PS 起始码：00 00 01 xx"""
    i, out = 0, []
    while i < len(data) - 3:
        if data[i] == 0 and data[i+1] == 0 and data[i+2] == 1:
            code = data[i+3]
            if code in PS_START:
                out.append((i, PS_START[code]))
            i += 3
        else:
            i += 1
    return out

真实解析还要读 PES 头里的 PTS/DTS（33 位，拆成 3 段存放），以及处理 stream_id。但“先找起始码”这一步，足以让你判断一段 RTP 里到底有没有 PS 数据。

③ 用 FFmpeg 验证“码流本身能不能解”

# 如果你已经能把 PS 落成文件（例如网关导出的 .ps）
ffprobe -show_streams clip.ps
ffmpeg -i clip.ps -c copy clip.mp4

# 如果是标准 RTSP 摄像头（不是国标 PS），可直接：
ffplay -fflags nobuffer -flags low_delay \
  -rtsp_transport tcp rtsp://user:pass@192.168.1.64/Streaming/Channels/101

把“网络问题”和“码流问题”分开，是排错的分水岭：文件能解 → 问题在网络/信令；文件都解不了 → 问题在封装或编码参数。
