编码：把 746 Mbps 压到 4 Mbps，
靠的不是魔法

视频编码像抄一本 300 页的书：你不会逐字重抄，而是写“和上一页一样，只有第 3 段改了 5 个字”。I 帧是原稿，P/B 帧是批注；DCT 把画面拆成 64 个音叉，量化负责“听不见的就别记”，熵编码再把剩下的符号换成最短的暗号。这一页把整条流水线拆开，每一步都给出真实参数和可验证的命令。

📉 压缩到底在压什么：四种冗余

一段 1080p30、4:2:0、8 bit 的原始视频，每秒要传 1920 × 1080 × 12 × 30 = 746,496,000 bit，约 746 Mbps。H.264 用 4 Mbps 就能给出可看的画面，压缩比约 187 : 1。这不是“把像素变少”，而是把画面里可预测、可忽略、可重复的部分换成更短的描述。

时间冗余

相邻两帧大部分相同。只传“哪里动了、动了多少”，就是帧间预测与运动矢量。

空间冗余

一块草地、一面墙，像素彼此高度相关。用左边/上边的像素预测当前块，只传残差。

统计冗余

小数值、零、重复的符号出现得多。用变长码或算术编码，让常见符号占更少比特。

视觉冗余

人眼对高频纹理与色度细节不敏感。量化直接把这些系数抹成 0，且不打算恢复。

预测减去“已知”
→
变换能量集中
→
量化丢掉细节
→
熵编码换成短码

有损与无损的分界：H.264/HEVC/AV1/VP9 都是有损，量化后的系数不可能还原成原始像素；FLAC、ZIP 是无损，只去统计冗余。所以“把 H.264 转成 FLAC”没有意义，“把 MP4 转成 MKV”也不会变清晰。

🔍先记住一句话：码率低不等于压缩好，可能是把细节量化没了；码率高也不等于画质好，可能是编码器不会找预测。判断画质要看内容、 preset、CRF 与主观感受，不能只看数字。

🔁 编码流水线：一条带“回声”的流水线

编码器不是单向流水线，而是一个闭环：它一边把残差编码成码流，一边在本地把同一份残差解码回来，得到“重建帧”，再用它预测下一帧。这个内部解码器叫重建环（reconstruction loop）。没有它，编码端和解码端的参考帧会逐渐分叉，误差越滚越大，也就是漂移（drift）。

真正决定码率的顺序是：预测越准 → 残差越小 → 变换后非零系数越少 → 量化后更容易全零 → 熵编码越省。所以编码器的核心竞争力往往在预测（运动估计、块划分），而不是熵编码。

🧩 预测：帧内“补墙”，帧间“找相同段落”

帧内预测像补一面墙：你只有左边和上边的砖，就按纹理方向一块块猜过去；帧间预测像在两页书里找相同的段落：找到了，就只记“从上一页第 3 行搬过来，向右移了 4 个像素”。预测不是压缩本身，而是把要编码的数据变少。

帧内预测：用邻居猜当前块

标准亮度模式色度模式块尺寸
H.2644×4 有 9 种（V/H/DC + 6 种对角）；16×16 有 4 种（V/H/DC/Plane）4 种（DC/V/H/Plane）宏块 16×16，子块 4×4
HEVC35 种：Planar、DC + 33 个角度沿用亮度或独立选择CU 8–64，PU 可 2N×2N / N×N
AV113 种：DC/V/H/Paeth/Smooth + 8 个方向；另有 CfL、调色板可从亮度派生（CfL）块 4×4 到 128×128

H.264 的 4×4 模式用 13 个相邻像素生成预测；HEVC 的 33 个角度以 1/32 像素精度指向参考边。模式越多，编码器要试的组合越多，耗时也越长——这就是“压缩率换 CPU”的第一处体现。

帧间预测：运动矢量与亚像素

帧间预测在参考帧里搜索最相似的块，把位置差写成运动矢量（MV）。H.264 的亮度 MV 精度是 1/4 像素（6 抽头插值），色度是 1/8 像素；HEVC、AV1 也以 1/4 亮度精度为主。搜索范围越大、参考帧越多，越可能找到好匹配，但计算量也成倍上涨。

块划分决定“贴合度”

H.264 宏块 16×16，可切成 16×8、8×16、8×8，再细分为 8×4、4×8、4×4。HEVC 用 64×64 CTU 四叉树，CU 最小 8×8；AV1 最大 128×128 超级块。小块贴合运动边界，但头和 MV 的开销更大。

Skip / Merge 是免费午餐

当某块与邻居运动一致，HEVC 的 merge 模式只传一个索引，不传 MV；H.264 的 P_Skip 连残差都不传。静态背景里大量块走这条路，码率自然降下来。

# x264 的运动估计相关参数（越大越慢、通常越好）
ffmpeg -i in.y4m -c:v libx264 -preset slow \
  -me umh -subme 7 -ref 3 -bf 3 -g 48 out.mp4

# 看每个帧的类型与大小，感受 I/P/B 的差距
ffprobe -select_streams v -show_frames \
  -show_entries frame=pict_type,pkt_size -of csv in.mp4 | head -20
💡一个常见误解：“运动矢量就是物体的真实运动”。不是。它只是“哪块像素最省比特”的匹配结果，可能指向完全无关的区域。编码器优化的是率失真，不是物理真值。

🎹 变换：把 8×8 块拆成 64 个音叉

一块 8×8 的像素，可以看成 64 个不同频率“音叉”的叠加：左上角是平坦的直流分量，越往右下频率越高。DCT 做的事情，就是算出每个音叉响多大。自然画面的大部分能量集中在低频，高频系数通常很小——这给量化提供了“下手的地方”。

H.264 的 4×4 变换核心只有 1 和 2，全部用加法和移位完成，不需要浮点，避免不同平台产生细微差异：

H.264 4×4 整数变换核心矩阵 H：

 1   1   1   1
 2   1  -1  -2
 1  -1  -1   1
 1  -2   2  -1

Y = H · X · Hᵀ      （X 为 4×4 残差块）
反变换只需转置与移位，整数运算可逐比特复现
标准变换尺寸类型要点
H.2644×4；High profile 可自适应 8×8整数 DCT 近似4×4 只用 1/2 系数；8×8 改善平坦区域
HEVC4/8/16/32整数 DCT；4×4 帧内亮度用 DST-VII大块变换适合 4K 平坦区域，残差边界更少
VP94/8/16/32DCT / ADSTADST 更适合预测残差的分布
AV14/8/16/32/64DCT / ADST / Identity 组合变换类型可逐块切换，含翻转与转置

为什么变换有效：一个平坦的 8×8 块，DCT 后只有左上角 DC 系数非零，其余 63 个接近 0；量化后全变 0，熵编码几乎不花比特。反过来，强纹理块的高频系数很大，压缩就难——这也是“草地、毛发、雨滴”比“天空、墙面”更吃码率的原因。

🔍变换本身不丢信息：理想精度的 DCT + IDCT 可以完全重建。真正丢信息的是下一步量化。变换的作用是把“难压缩的像素”变成“容易量化的系数”。

🎚️ 量化：唯一不可逆的一步

量化像抄写时的“四舍五入”：把每个系数除以一个步长，取整，再乘回去。步长越大，省下的比特越多，细节也丢得越多。H.264 的 QP 范围是 0–51，步长近似 2^((QP−4)/6)：QP 每加 6，步长翻倍，码率大致减半。

QP近似步长效果典型用途
228细节丰富，码率高高质量点播 / 中间母版
2613平衡x264 CRF 23 附近的常见区间
3226平坦区域开始出现块效应低码率直播
4064细节明显丢失极低码率 / 监控缩略流
51224几乎只剩轮廓仅用于极端场景

量化不是简单“除以步长”：编码器通常保留一个死区（dead zone），把接近 0 的系数直接归零，因为小幅值系数的编码成本可能高于它带来的画质收益。随后率失真优化（RDO）会比较“多花这些比特能换来多少失真下降”，再决定取舍。

量化矩阵

H.264/HEVC 可以传缩放矩阵，对不同频率用不同步长：低频保护、高频重压。默认通常是平坦矩阵；JPEG 里那张“左上小、右下大”的表就是经典例子。

不同标准的 QP 尺度

H.264/HEVC 的 QP 是 0–51；AV1 的 base_q_idx 是 0–255；VP9 的 cq-level 是 0–63。跨编码器比较“QP 26”没有意义，要比 CRF 或实际码率 + 质量指标。

🔐 熵编码：把符号换成最短的暗号

量化之后，我们得到一堆“多少、在哪里、连续几个零”的符号。熵编码负责把它们写成比特。它不改变画质，只改变“表达同样的信息要花多少比特”。这就是为什么同样的 QP，换 CABAC 就能省码率。

CAVLC：查表换码

H.264 Baseline 使用。先编码 coeff_token（非零系数总数 + 尾随 ±1 的个数），再编码每个 level、total_zeros 与 run_before。实现简单、功耗低，但压缩效率略差。

CABAC：算术区间

H.264 Main/High 使用，HEVC 只保留 CABAC。它根据上下文为每个二进制决策估计概率，把整个 slice 映射到 [0,1) 区间中的一个数。常见测试下比 CAVLC 省 约 9–14% 码率，代价是串行依赖、难并行。

H.264 的语法元素大量使用指数哥伦布码 ue(v) / se(v)：数值越小，码字越短。例如 ue 编码 0 是 1（1 bit），1 是 010（3 bit），2 是 011。这和“常用词用短缩写”的直觉一致。AV1 则使用多符号算术编码，VP9 使用布尔编码器，思路相同：让高概率符号占更少区间。

⚠️熵编码不能救回量化丢掉的信息。它只是把“已经决定要传的符号”写得更省。QP 从 26 调到 40，熵编码再强也补不回细节；反过来，QP 很低但熵编码差，文件会不必要地大。

🔑 I/P/B 帧与 GOP：钥匙帧与补丁帧

GOP 像一串“钥匙 + 补丁”：I 帧是钥匙，能独立开门；P 帧是“在上一把钥匙基础上打补丁”；B 帧是“同时参考前后两把钥匙的补丁”。想跳到某一帧，必须先找到它之前最近的钥匙，再把中间的补丁全部贴上——这就是为什么长 GOP 的随机访问代价高。

帧型参考谁能否独立解码码率占比（经验）
I只用帧内预测是（IDR 还清空参考缓冲）通常是 P 帧的数倍
P前面的 I/P否中等
B前后双向否通常最低，但增加延迟
IDR不使用任何旧参考是，且重置 DPB比普通 I 更“干净”，也更贵

算 GOP 的秒数：GOP 秒 = keyint / fps。25 fps 下 -g 48 是 1.92 秒，-g 50 正好 2 秒，-g 250 是 10 秒。直播通常 1–2 秒一个关键帧，点播可以用 5–10 秒换更低码率。拖动时平均要从关键帧解 GOP/2 帧，GOP 越长，seek 越慢。

# 固定 2 秒 GOP（25 fps），并禁止场景切换插入额外关键帧
ffmpeg -i in.mp4 -c:v libx264 -g 50 -keyint_min 50 -sc_threshold 0 out.mp4

# 低延迟直播：关闭 B 帧与前瞻
ffmpeg -i in.mp4 -c:v libx264 -tune zerolatency -g 50 -bf 0 out.mp4
🔍B 帧的延迟账：连续 3 个 B 帧时，解码器要等后续参考帧到达才能输出，显示延迟约 (bframes + 1) 帧；25 fps 下约 160 ms。视频会议、云游戏通常把 B 帧设为 0，就是为了这 100 多毫秒。

🎓 profile 与 level：工具箱与限高杆

profile 决定“允许用哪些工具”，像驾照的准驾车型；level 决定“最大能开多快”，给出分辨率、帧率、码率的上限。两者组合写成 High@L4.1：工具集是 High，上限是 Level 4.1。解码器只要看到这个标签，就能判断自己能不能接。

标准profile关键能力常见场景
H.264Baseline（66）无 B 帧、CAVLC、8 bit 4:2:0老设备、视频会议
Main（77）B 帧、CABAC、8 bit 4:2:0早期广播、机顶盒
High（100）8×8 变换、缩放矩阵、8 bit 4:2:0当今最通用的点播/直播
HEVCMain（1）8 bit 4:2:04K 直播、硬件解码
Main 10（2）10 bit 4:2:0HDR、广色域
AV1Main（0）/ High（1）8/10 bit，4:2:0 为主网页视频、免专利分发

level 的数字是可验证的：H.264 Level 3.1 的 MaxFS（最大帧尺寸）是 3600 个宏块、MaxMBPS 是 108000 宏块/秒——1280×720 正好 3600 块，30 fps 正好 108000，所以 720p30 卡在 3.1 的边界。Level 4.0 是 8192 块 / 245760 块每秒，1920×1080 为 8160 块，30 fps 为 244800，刚好通过。Level 5.1 的 36864 块 / 983040 块每秒，覆盖 4K30。超过上限，部分硬件解码器会直接拒绝。

⚠️profile/level 写错会直接导致“能解但不给解”：例如把 10-bit HDR 标成 High（8 bit），或把 4K60 标成 Level 4.1。转码时显式指定 -profile:v high -level 4.1，比让编码器自动猜更稳。

🎛️ 码控：CBR / VBR / CRF，三个不同的旋钮

码控决定“每一帧分多少比特”。它不改变编码工具，只改变 QP 的分配策略。理解三种模式，你就能解释“为什么直播码率是平的、点播文件码率是波动的”。

模式目标码率曲线典型参数
CBR恒定码率，缓冲不溢出平直，简单画面浪费比特-b:v 4M -minrate 4M -maxrate 4M -bufsize 8M -x264-params nal-hrd=cbr
VBR / ABR平均码率接近目标随内容波动-b:v 4M -maxrate 6M -bufsize 12M
CRF恒定质量因子，不管码率复杂画面自动升高-crf 23（x264 默认）
CQP每帧固定 QP码率完全由内容决定-qp 24，一般只用于测试
目标码率 ≈ bpp × 宽 × 高 × 帧率　　（bpp = bits per pixel，含亮度与色度）

例如 bpp = 0.1、1080p30：0.1 × 1920 × 1080 × 30 = 6,220,800 bit/s ≈ 6.22 Mbps。0.05 bpp 约 3.11 Mbps，0.15 bpp 约 9.33 Mbps。这个估算比“拍脑袋定 4M”可靠，但最终仍要看内容复杂度与质量指标。

# 恒定质量（点播最常用）
ffmpeg -i in.mp4 -c:v libx264 -preset slow -crf 23 out.mp4

#  capped CRF：质量优先，但给码率设上限（直播常用）
ffmpeg -i in.mp4 -c:v libx264 -preset medium -crf 21 \
  -maxrate 6M -bufsize 12M out.mp4

# 两遍 ABR：先分析再编码，码率分布更合理
ffmpeg -i in.mp4 -c:v libx264 -b:v 4M -pass 1 -an -f null -
ffmpeg -i in.mp4 -c:v libx264 -b:v 4M -pass 2 -c:a aac -b:a 128k out.mp4

CRF 的数字怎么选：18 通常接近视觉无损，23 是 x264 默认的平衡点，28 开始明显省码率但细节下降。CRF 越低画质越好、文件越大；它不是“百分比”，也不能跨编码器直接比较（x265 的 CRF 28 与 x264 的 CRF 23 不能等同）。

🔍VBV 缓冲是什么：它模拟解码器的输入缓冲。bufsize 太小会让码率被强行压平、画质抖动；通常取 maxrate × 1–2 秒。CBR 直播里，bufsize 与 nal-hrd=cbr 要一起设，否则“标称 CBR”并不恒定。

🎨 色度采样 4:2:0：人眼对颜色更迟钝

视网膜上负责亮度的细胞多、负责颜色的少，所以“把颜色分辨率砍一半”肉眼几乎察觉不到。4:2:0 就是每 2×2 个像素共享一组 Cb/Cr：亮度全保留，色度在水平和垂直方向都减半。这也是报纸彩印“颜色套印可以糊一点”的现代版。

采样8 bit 每像素比特1080p30 原始码率典型用途
4:4:424 bpp≈ 1493 Mbps演播室、绿幕抠像、无损母版
4:2:216 bpp≈ 995 Mbps专业采集、10 bit 中间片
4:2:012 bpp≈ 746 MbpsH.264/HEVC/AV1 消费级默认
4:1:118 bpp≈ 1120 Mbps早期 DV、部分硬件采集
4:2:0 10 bit15 bpp≈ 933 MbpsHDR、HEVC Main 10

工程上的三条硬约束：① 4:2:0 的宽高必须是偶数，奇数尺寸会直接编码失败；② 浏览器最稳的像素格式是 yuv420p（8 bit），10 bit 需要 Main 10 与硬件/浏览器支持；③ 色彩空间与范围要写对，BT.709 的 limited range（16–235）被误标成 full range（0–255），画面会发灰或死黑。

# 统一转成浏览器最兼容的 8 bit 4:2:0
ffmpeg -i in.mov -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2,format=yuv420p" \
  -c:v libx264 -crf 23 -c:a aac -b:a 128k out.mp4

# 看像素格式与色彩标签
ffprobe -show_streams -show_entries stream=pix_fmt,color_space,color_range,color_transfer
⚠️“颜色不对”不一定是编码问题：先查 color_space、color_range、color_primaries。容器里的 colr box 与码流里的 VUI 必须一致；两处冲突时，不同播放器会做不同选择，于是“同一个文件在不同浏览器里颜色不一样”。

⚔️ H.264 / HEVC / VP9 / AV1：怎么选

四个编码器的目标相同：在同样的主观质量下用更少比特。差异在于工具集、专利、硬件支持与编码成本。下表里的压缩率是公开测试中的常见区间，真实收益取决于内容、preset 与调参，不能当成固定折扣。

# H.264（兼容性优先）
ffmpeg -i in.mp4 -c:v libx264 -preset slow -crf 23 -profile:v high -level 4.1 \
  -c:a aac -b:a 128k out_h264.mp4

# HEVC（4K / HDR，Apple 生态建议加 hvc1 tag）
ffmpeg -i in.mp4 -c:v libx265 -preset medium -crf 28 -tag:v hvc1 \
  -c:a aac -b:a 128k out_hevc.mp4

# VP9（WebM，免费）
ffmpeg -i in.mp4 -c:v libvpx-vp9 -crf 32 -b:v 0 -row-mt 1 -c:a libopus out_vp9.webm

# AV1（SVT-AV1，编码快于 libaom）
ffmpeg -i in.mp4 -c:v libsvtav1 -preset 6 -crf 35 -c:a libopus out_av1.mkv

要“谁都能播”

H.264 High + AAC 仍是网页与安防的通用解。兼容性带来的运维成本，往往低于省下的那点带宽。

要“4K HDR / 省带宽”

HEVC Main 10 的硬件解码覆盖好，适合电视、机顶盒、手机；注意专利授权与 hvc1 标签。

要“免专利 + 新浏览器”

VP9/AV1 适合网页分发。AV1 的编码成本高，点播可以先编一次；实时直播要算清 CPU 账。

💡不要只看“省多少”：HEVC 省 40% 带宽，但如果被迫转码、软解、或付出专利费，总成本可能更高。工程决策要算“带宽 + 算力 + 兼容 + 授权”四笔账。

🎧 音频编码：AAC / Opus / MP3 / FLAC

音频压缩利用的是人耳的掩蔽效应：一个强音旁边的小声音你听不见，干脆不编码。AAC、MP3、Opus 都基于 MDCT（改进离散余弦变换）与心理声学模型；FLAC 则完全不同，它只做无损的线性预测与熵编码。

编码类型 / 核心帧长典型码率专利与场景
AAC-LC有损，MDCT + 心理声学1024 采样/帧（48 kHz → 21.33 ms）96–128 kbps 立体声有专利；MP4/HLS/浏览器最通用
HE-AACAAC + SBR（v1）/ PS（v2）同上，SBR 扩展高频32–64 kbps 立体声低码率流媒体、老设备兼容
Opus有损，SILK + CELT 混合2.5–60 ms 可配，内部 48 kHz6–510 kbps（RFC 6716）免专利；WebRTC 默认，语音/音乐都能打
MP3有损，MDCT1152 采样/帧（44.1 kHz → 26.12 ms）32–320 kbps专利已过期；遗留兼容
FLAC无损，LPC + Rice 编码可变块，常见 4096 采样约为 WAV 的 50–70%免专利；母版归档、音乐分发

听感上的“透明码率”：常见测试里，AAC-LC 立体声约 128 kbps、Opus 约 64 kbps 就能接近透明；MP3 通常要到 192–256 kbps。Opus 在低码率与抗丢包上优势明显，所以 WebRTC 选它；AAC 胜在生态与硬件支持，所以 HLS/MP4 选它。

# AAC-LC 128k（MP4 / HLS 通用）
ffmpeg -i in.mp4 -c:a aac -b:a 128k -ar 48000 out_aac.mp4

# Opus 64k（WebRTC / WebM 常用）
ffmpeg -i in.wav -c:a libopus -b:a 64k -application audio out_opus.webm

# MP3 192k（老设备）
ffmpeg -i in.wav -c:a libmp3lame -b:a 192k out.mp3

# FLAC 无损（压缩级别 0–12，8 是常用折中）
ffmpeg -i in.wav -c:a flac -compression_level 8 out.flac
🔍AAC 的“帧”不是“一秒钟”：1024 个采样在 48 kHz 下只有 21.33 ms，一秒约 46.9 帧。音频时间戳通常以采样数为单位（timescale = 采样率），这也是容器里音频轨道 mdhd 常见 48000 的原因。

📏 质量指标与验证：别只凭眼睛

“看起来差不多”不能写进验收标准。工程上用三类指标：像素误差（PSNR）、结构相似度（SSIM）、感知质量（VMAF）。它们各有盲区，最稳的做法是指标 + 抽帧主观对比。

PSNR = 10 · log₁₀(255² / MSE)　（8 bit 视频）

PSNR 40 dB 左右通常算“不错”，45 dB 以上接近透明；但它对模糊与块效应不敏感，对轻微整体偏移又过度惩罚。SSIM 看亮度、对比度、结构三部分，取值 0–1，越接近 1 越好。VMAF 用机器学习模型预测主观评分，范围 0–100，业内常以 93 左右作为 1080p 的透明参考线（不是绝对标准）。

# 计算 PSNR / SSIM（要求同分辨率、同帧率）
ffmpeg -i enc.mp4 -i ref.y4m -lavfi "[0:v][1:v]ssim" -f null -
ffmpeg -i enc.mp4 -i ref.y4m -lavfi "[0:v][1:v]psnr" -f null -

# 计算 VMAF（需要 libvmaf 编译支持）
ffmpeg -i enc.mp4 -i ref.mp4 -lavfi libvmaf -f null -

# 逐帧看关键帧与帧类型，定位画质突变
ffprobe -select_streams v -show_frames \
  -show_entries frame=pict_type,pkt_size -of csv enc.mp4 | head -30

BD-rate（Bjøntegaard Delta rate）用来比较两个编码器：在相同质量下，平均码率相差多少百分比。BD-rate 为 −30% 表示“同等质量下省 30% 码率”。它依赖测试序列、质量指标与拟合方式，论文里的数字不能直接搬到你的业务内容上。

⚠️别用 PSNR 选 preset：高 PSNR 可能来自“模糊但误差小”，观感反而更差。先定业务场景（人脸、文字、运动、暗场），再用对应素材做 A/B，指标只作为辅助。
