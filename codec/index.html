📉 压缩到底在压什么：四种冗余

一段 1080p30、4:2:0、8 bit 的原始视频，每秒要传 1920 × 1080 × 12 × 30 = 746,496,000 bit，约 746 Mbps。H.264 用 4 Mbps 就能给出可看的画面，压缩比约 187 : 1。这不是“把像素变少”，而是把画面里可预测、可忽略、可重复的部分换成更短的描述。

时间冗余

相邻两帧大部分相同。只传“哪里动了、动了多少”，就是帧间预测与运动矢量。

空间冗余

一块草地、一面墙，像素彼此高度相关。用左边/上边的像素预测当前块，只传残差。

统计冗余

小数值、零、重复的符号出现得多。用变长码或算术编码，让常见符号占更少比特。

视觉冗余

人眼对高频纹理与色度细节不敏感。量化直接把这些系数抹成 0，且不打算恢复。

有损与无损的分界：H.264/HEVC/AV1/VP9 都是有损，量化后的系数不可能还原成原始像素；FLAC、ZIP 是无损，只去统计冗余。所以“把 H.264 转成 FLAC”没有意义，“把 MP4 转成 MKV”也不会变清晰。

🔍先记住一句话：码率低不等于压缩好，可能是把细节量化没了；码率高也不等于画质好，可能是编码器不会找预测。判断画质要看内容、 preset、CRF 与主观感受，不能只看数字。

🔁 编码流水线：一条带“回声”的流水线

编码器不是单向流水线，而是一个闭环：它一边把残差编码成码流，一边在本地把同一份残差解码回来，得到“重建帧”，再用它预测下一帧。这个内部解码器叫重建环（reconstruction loop）。没有它，编码端和解码端的参考帧会逐渐分叉，误差越滚越大，也就是漂移（drift）。

真正决定码率的顺序是：预测越准 → 残差越小 → 变换后非零系数越少 → 量化后更容易全零 → 熵编码越省。所以编码器的核心竞争力往往在预测（运动估计、块划分），而不是熵编码。

🧩 预测：帧内“补墙”，帧间“找相同段落”

帧内预测像补一面墙：你只有左边和上边的砖，就按纹理方向一块块猜过去；帧间预测像在两页书里找相同的段落：找到了，就只记“从上一页第 3 行搬过来，向右移了 4 个像素”。预测不是压缩本身，而是把要编码的数据变少。

HEVC35 种：Planar、DC + 33 个角度沿用亮度或独立选择CU 8–64，PU 可 2N×2N / N×N
AV113 种：DC/V/H/Paeth/Smooth + 8 个方向；另有 CfL、调色板可从亮度派生（CfL）块 4×4 到 128×128

H.264 的 4×4 模式用 13 个相邻像素生成预测；HEVC 的 33 个角度以 1/32 像素精度指向参考边。模式越多，编码器要试的组合越多，耗时也越长——这就是“压缩率换 CPU”的第一处体现。

帧间预测：运动矢量与亚像素

帧间预测在参考帧里搜索最相似的块，把位置差写成运动矢量（MV）。H.264 的亮度 MV 精度是 1/4 像素（6 抽头插值），色度是 1/8 像素；HEVC、AV1 也以 1/4 亮度精度为主。搜索范围越大、参考帧越多，越可能找到好匹配，但计算量也成倍上涨。

块划分决定“贴合度”

H.264 宏块 16×16，可切成 16×8、8×16、8×8，再细分为 8×4、4×8、4×4。HEVC 用 64×64 CTU 四叉树，CU 最小 8×8；AV1 最大 128×128 超级块。小块贴合运动边界，但头和 MV 的开销更大。

Skip / Merge 是免费午餐

当某块与邻居运动一致，HEVC 的 merge 模式只传一个索引，不传 MV；H.264 的 P_Skip 连残差都不传。静态背景里大量块走这条路，码率自然降下来。

# x264 的运动估计相关参数（越大越慢、通常越好）
ffmpeg -i in.y4m -c:v libx264 -preset slow \
  -me umh -subme 7 -ref 3 -bf 3 -g 48 out.mp4

# 看每个帧的类型与大小，感受 I/P/B 的差距
ffprobe -select_streams v -show_frames \
  -show_entries frame=pict_type,pkt_size -of csv in.mp4 | head -20
💡一个常见误解：“运动矢量就是物体的真实运动”。不是。它只是“哪块像素最省比特”的匹配结果，可能指向完全无关的区域。编码器优化的是率失真，不是物理真值。

🎹 变换：把 8×8 块拆成 64 个音叉

一块 8×8 的像素，可以看成 64 个不同频率“音叉”的叠加：左上角是平坦的直流分量，越往右下频率越高。DCT 做的事情，就是算出每个音叉响多大。自然画面的大部分能量集中在低频，高频系数通常很小——这给量化提供了“下手的地方”。

H.264 的 4×4 变换核心只有 1 和 2，全部用加法和移位完成，不需要浮点，避免不同平台产生细微差异：

 2   1  -1  -2

Y = H · X · Hᵀ      （X 为 4×4 残差块）
反变换只需转置与移位，整数运算可逐比特复现
标准变换尺寸类型要点
H.2644×4；High profile 可自适应 8×8整数 DCT 近似4×4 只用 1/2 系数；8×8 改善平坦区域
HEVC4/8/16/32整数 DCT；4×4 帧内亮度用 DST-VII大块变换适合 4K 平坦区域，残差边界更少

为什么变换有效：一个平坦的 8×8 块，DCT 后只有左上角 DC 系数非零，其余 63 个接近 0；量化后全变 0，熵编码几乎不花比特。反过来，强纹理块的高频系数很大，压缩就难——这也是“草地、毛发、雨滴”比“天空、墙面”更吃码率的原因。

🔍变换本身不丢信息：理想精度的 DCT + IDCT 可以完全重建。真正丢信息的是下一步量化。变换的作用是把“难压缩的像素”变成“容易量化的系数”。

🎚️ 量化：唯一不可逆的一步

量化像抄写时的“四舍五入”：把每个系数除以一个步长，取整，再乘回去。步长越大，省下的比特越多，细节也丢得越多。H.264 的 QP 范围是 0–51，步长近似 2^((QP−4)/6)：QP 每加 6，步长翻倍，码率大致减半。

QP近似步长效果典型用途
228细节丰富，码率高高质量点播 / 中间母版
2613平衡x264 CRF 23 附近的常见区间
3226平坦区域开始出现块效应低码率直播
4064细节明显丢失极低码率 / 监控缩略流
51224几乎只剩轮廓仅用于极端场景

量化不是简单“除以步长”：编码器通常保留一个死区（dead zone），把接近 0 的系数直接归零，因为小幅值系数的编码成本可能高于它带来的画质收益。随后率失真优化（RDO）会比较“多花这些比特能换来多少失真下降”，再决定取舍。

量化矩阵

H.264/HEVC 可以传缩放矩阵，对不同频率用不同步长：低频保护、高频重压。默认通常是平坦矩阵；JPEG 里那张“左上小、右下大”的表就是经典例子。

不同标准的 QP 尺度

H.264/HEVC 的 QP 是 0–51；AV1 的 base_q_idx 是 0–255；VP9 的 cq-level 是 0–63。跨编码器比较“QP 26”没有意义，要比 CRF 或实际码率 + 质量指标。

🔐 熵编码：把符号换成最短的暗号

量化之后，我们得到一堆“多少、在哪里、连续几个零”的符号。熵编码负责把它们写成比特。它不改变画质，只改变“表达同样的信息要花多少比特”。这就是为什么同样的 QP，换 CABAC 就能省码率。

CAVLC：查表换码

H.264 Baseline 使用。先编码 coeff_token（非零系数总数 + 尾随 ±1 的个数），再编码每个 level、total_zeros 与 run_before。实现简单、功耗低，但压缩效率略差。

CABAC：算术区间

H.264 Main/High 使用，HEVC 只保留 CABAC。它根据上下文为每个二进制决策估计概率，把整个 slice 映射到 [0,1) 区间中的一个数。常见测试下比 CAVLC 省 约 9–14% 码率，代价是串行依赖、难并行。

H.264 的语法元素大量使用指数哥伦布码 ue(v) / se(v)：数值越小，码字越短。例如 ue 编码 0 是 1（1 bit），1 是 010（3 bit），2 是 011。这和“常用词用短缩写”的直觉一致。AV1 则使用多符号算术编码，VP9 使用布尔编码器，思路相同：让高概率符号占更少区间。

⚠️熵编码不能救回量化丢掉的信息。它只是把“已经决定要传的符号”写得更省。QP 从 26 调到 40，熵编码再强也补不回细节；反过来，QP 很低但熵编码差，文件会不必要地大。

📦 H.264 NAL：码流的最小包裹

NAL 像快递面单：每个包裹外面贴一字节标签，写明“这是什么件、能不能丢、丢了后面的件会不会坏”。解码器先读标签，再决定把包交给参数集解析器、slice 解码器，还是当作填充物直接扔掉。

NAL（Network Abstraction Layer，网络抽象层）把编码数据切成独立的 NAL 单元。每个单元都以 1 字节 NAL header 开头；在 Annex B 里它前面还有起始码，在 MP4 里则改成长度前缀。理解这一个字节，等于拿到了读码流的钥匙。

NAL header · 1 byte · bit 7 → bit 0
forbidden_zero_bit1 bit · 必须 0
nal_ref_idc2 bit · 0–3
nal_unit_type5 bit · 0–31

以 0x67（SPS）为例：0 11 00111 → forbidden=0、nal_ref_idc=3、type=7；以 0x65（IDR）为例：0 11 00101 → type=5。看到 67 / 68 / 65 连续出现，基本就是“SPS、PPS、IDR”三件套。

nal_ref_idc 不是“优先级”，而是“能不能丢”：0 表示这个包不参与后续参考（B slice、SEI、AUD、filler 常见 0）；非 0 表示后面帧可能要用它，丢了会连带坏一片。SPS/PPS 与 IDR 的该字段必须非 0，x264 习惯写 3。

Annex B 与 AVCC：同一条 NAL，两种装箱法

Annex B：起始码分隔

每个 NAL 前面加 00 00 01（3 字节）或 00 00 00 01（4 字节）。TS、MPEG-2 PS、裸 .h264/.264 用它；参数集通常随流内联，解码器边读边建表。

代价：负载里若出现 00 00 00 / 00 00 01 这种组合，会被误认成起始码，所以编码器插入防竞争字节 03；解码器再删掉。原始 RBSP 里的 00 00 01 到码流里会变成 00 00 03 01。

AVCC：长度前缀

MP4 的 avcC 与 FLV 的 AVCDecoderConfigurationRecord 用“长度 + NAL”排列。长度通常是 4 字节（lengthSizeMinusOne = 3），SPS/PPS 集中放在 extradata 里，不占每个样本。

好处：按样本取 NAL 容易，适合随机访问与编辑；代价是参数集与样本分离，封装器必须把 extradata 写对，否则播放器拿到一条“没有 SPS”的流。

# MP4（AVCC）→ 裸流（Annex B）：只换装箱方式，不重编码
ffmpeg -i in.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 out.h264

# 转 TS：过滤器会把 SPS/PPS 插到 IDR 前，满足广播/监控设备的要求
ffmpeg -i in.mp4 -c:v copy -bsf:v h264_mp4toannexb -f mpegts out.ts

# 反向（裸流 → MP4）：muxer 自动生成 avcC，不需要手写 bsf
ffmpeg -i out.h264 -c:v copy out.mp4

一句话区分：文件打开是一堆 00 00 00 01，那是 Annex B；打开是一串“长度 + NAL”，且 SPS/PPS 只在 avcC 里出现一次，那是 AVCC。两者可以无损互转，画质不会变化。

拆一个真 SPS：1280×720 Baseline@L3.1

这段 9 字节的 SPS 由 1280×720、Baseline、Level 3.1 的参数生成。它不包含 VUI（没有色彩与帧率描述），所以非常短；真实流里常见几十字节，因为还要写 HRD、色彩原色、时序等信息。

🔍为什么参数集要单独成包：一帧的分辨率、量化、熵编码开关会在整段视频里反复使用。把 SPS/PPS 抽出来重复广播，比在每个 slice 里重复写几十字节便宜得多；代价是它们一旦丢失，后面的 slice 全成“无头数据”。

🔑 I/P/B 帧与 GOP：钥匙帧与补丁帧

GOP 像一串“钥匙 + 补丁”：I 帧是钥匙，能独立开门；P 帧是“在上一把钥匙基础上打补丁”；B 帧是“同时参考前后两把钥匙的补丁”。想跳到某一帧，必须先找到它之前最近的钥匙，再把中间的补丁全部贴上——这就是为什么长 GOP 的随机访问代价高。

帧型参考谁能否独立解码码率占比（经验）
I只用帧内预测是（IDR 还清空参考缓冲）通常是 P 帧的数倍
P前面的 I/P否中等
B前后双向否通常最低，但增加延迟
IDR不使用任何旧参考是，且重置 DPB比普通 I 更“干净”，也更贵

算 GOP 的秒数：GOP 秒 = keyint / fps。25 fps 下 -g 48 是 1.92 秒，-g 50 正好 2 秒，-g 250 是 10 秒。直播通常 1–2 秒一个关键帧，点播可以用 5–10 秒换更低码率。拖动时平均要从关键帧解 GOP/2 帧，GOP 越长，seek 越慢。

# 固定 2 秒 GOP（25 fps），并禁止场景切换插入额外关键帧
ffmpeg -i in.mp4 -c:v libx264 -g 50 -keyint_min 50 -sc_threshold 0 out.mp4

# 低延迟直播：关闭 B 帧与前瞻
ffmpeg -i in.mp4 -c:v libx264 -tune zerolatency -g 50 -bf 0 out.mp4
🔍B 帧的延迟账：连续 3 个 B 帧时，解码器要等后续参考帧到达才能输出，显示延迟约 (bframes + 1) 帧；25 fps 下约 160 ms。视频会议、云游戏通常把 B 帧设为 0，就是为了这 100 多毫秒。

⏱️ DTS / PTS：B 帧为什么让时间戳分家

PTS 像电影票上的“第几分钟上映”，DTS 像演员“几点到片场”。B 帧要同时参考前后两帧，所以它前面的 P 帧必须先到片场解码；结果就是送进解码器的顺序和屏幕上出现的顺序不是同一个顺序。

PTS（Presentation Time Stamp）决定什么时候显示；DTS（Decoding Time Stamp）决定什么时候送去解码。没有 B 帧时两者通常相同；有 B 帧时，解码器必须先拿到“未来”的参考帧，于是 P 帧的 DTS 提前，B 帧的 DTS 往后排。

PTS 与 DTS 的差，不一定为正

容器里通常还会记一个 composition offset（CTS，合成偏移），满足 PTS = DTS + CTS。对 B 帧来说，这个偏移可能是负的：它解码得晚，却要显示得早。MP4 常用 elst（edit list）把整条时间轴平移，避免出现负时间戳；播放器则只按 DTS 排队解码、按 PTS 排序显示。

没有 B 帧时，DTS 与 PTS 可以完全相同；一旦开了 -bf 3，编码器就需要一个重排缓冲（reorder buffer），直播端的延迟随之增加。这就是“画质换延迟”的第二笔账（第一笔是 lookahead）。

  -show_entries frame=pict_type,pts,dts,pts_time,dts_time,key_frame -of csv in.mp4 | head -12

# 固定 2 秒 GOP、3 个连续 B 帧、closed GOP

  -bf 3 -g 50 -keyint_min 50 -sc_threshold 0 -flags +cgop out.mp4

IDR 与普通 I 帧：都叫“关键帧”，权限不同

普通 I 帧（nal_unit_type = 1）

所有宏块都用帧内预测，不参考别的帧，但它不清空 DPB，也不重置 POC 与 frame_num。在 open GOP 里，它后面的 B 帧（leading pictures）仍可能参考前一个 GOP 的帧；从这一帧开始解码，未必能得到正确画面。

IDR 帧（nal_unit_type = 5）

IDR 把参考帧列表清空、重置 POC 与 frame_num，后续帧只能参考 IDR 之后的数据。它是绝对安全的随机访问点，也是直播丢包后请求“关键帧”时真正想要的东西。代价是它通常比普通 I 帧更大。

open GOP 的流里，编码器还可能写入 recovery point SEI，告诉解码器“从这里开始可以恢复，但前面几帧可能不显示”。如果业务要求“任意拖动都能出画”，用 -flags +cgop 或 -x264-params open-gop=0 把 GOP 关成 closed，比事后猜 SEI 可靠。

🎓 profile 与 level：工具箱与限高杆

profile 决定“允许用哪些工具”，像驾照的准驾车型；level 决定“最大能开多快”，给出分辨率、帧率、码率的上限。两者组合写成 High@L4.1：工具集是 High，上限是 Level 4.1。解码器只要看到这个标签，就能判断自己能不能接。

level 的数字是可验证的：H.264 Level 3.1 的 MaxFS（最大帧尺寸）是 3600 个宏块、MaxMBPS 是 108000 宏块/秒——1280×720 正好 3600 块，30 fps 正好 108000，所以 720p30 卡在 3.1 的边界。Level 4.0 是 8192 块 / 245760 块每秒，1920×1080 为 8160 块，30 fps 为 244800，刚好通过。Level 5.1 的 36864 块 / 983040 块每秒，覆盖 4K30。超过上限，部分硬件解码器会直接拒绝。

⚠️profile/level 写错会直接导致“能解但不给解”：例如把 10-bit HDR 标成 High（8 bit），或把 4K60 标成 Level 4.1。转码时显式指定 -profile:v high -level 4.1，比让编码器自动猜更稳。

🎚️ profile / level 细则：工具箱与限高杆

profile 是“准驾车型”：决定你能开大巴还是只能开小车；level 是“限高杆 + 载重上限”：决定这辆车最多能跑多快、装多少。两者都写在 SPS 里，解码器先看标签，再看自己有没有对应的工具和算力。

怎么读：先算宏块数：MB = ceil(宽/16) × ceil(高/16)，再算每秒宏块数：MBPS = MB × fps。720p30 是 3600 与 108000；1080p30 是 8160 与 244800；4K30 是 32400 与 972000。三个数字都落在哪一行，就至少需要那一级的 level。MaxBR 是解码器 CPB 的上限，不是“建议码率”：Level 4.1 允许 62.5 Mbps，但 1080p30 实际给 8 Mbps 也完全合法。

DPB 帧数 ≈ MaxDPB / MaxFS，并受编码器与 profile 约束。1080p 在 Level 4.1 下是 32768 / 8192 = 4 帧；Level 5.1 下是 184320 / 36864 = 5 帧。参考帧越多，压缩率通常越好，但解码器内存与延迟也越高。

老设备 / 软解

Baseline 或 Constrained Baseline，Level 3.0–3.1。没有 B 帧与 CABAC，码率略高，但几乎所有芯片都能解。

网页 / 点播

High@L4.1 是最稳的 1080p 组合；4K 若坚持 H.264，通常要 Level 5.1 以上，但同画质码率会明显高于 HEVC。

4K / HDR

HEVC Main10 + Level 5.1 是电视与手机的常见组合；H.264 的 High 10 在消费级硬件里支持面窄。

专业母版

High 4:2:2 / High 4:4:4 Predictive，保留色度与高位深。代价是文件大、播放器支持少。

MP4 里的 codec string 就是 avcC 前三字节：avc1.42E01F 是 Baseline@3.1（42=66，E0=约束标志，1F=31），avc1.4D401F 是 Main@3.1，avc1.64001F 是 High@3.1。浏览器与播放器很多判断只看这一串，不会去深度解析 SPS。

🎛️ 码控：CBR / VBR / CRF，三个不同的旋钮

码控决定“每一帧分多少比特”。它不改变编码工具，只改变 QP 的分配策略。理解三种模式，你就能解释“为什么直播码率是平的、点播文件码率是波动的”。

模式目标码率曲线典型参数
CBR恒定码率，缓冲不溢出平直，简单画面浪费比特-b:v 4M -minrate 4M -maxrate 4M -bufsize 8M -x264-params nal-hrd=cbr
VBR / ABR平均码率接近目标随内容波动-b:v 4M -maxrate 6M -bufsize 12M
CRF恒定质量因子，不管码率复杂画面自动升高-crf 23（x264 默认）
CQP每帧固定 QP码率完全由内容决定-qp 24，一般只用于测试
目标码率 ≈ bpp × 宽 × 高 × 帧率　　（bpp = bits per pixel，含亮度与色度）

例如 bpp = 0.1、1080p30：0.1 × 1920 × 1080 × 30 = 6,220,800 bit/s ≈ 6.22 Mbps。0.05 bpp 约 3.11 Mbps，0.15 bpp 约 9.33 Mbps。这个估算比“拍脑袋定 4M”可靠，但最终仍要看内容复杂度与质量指标。

# 恒定质量（点播最常用）
ffmpeg -i in.mp4 -c:v libx264 -preset slow -crf 23 out.mp4

#  capped CRF：质量优先，但给码率设上限（直播常用）
ffmpeg -i in.mp4 -c:v libx264 -preset medium -crf 21 \
  -maxrate 6M -bufsize 12M out.mp4

# 两遍 ABR：先分析再编码，码率分布更合理
ffmpeg -i in.mp4 -c:v libx264 -b:v 4M -pass 1 -an -f null -
ffmpeg -i in.mp4 -c:v libx264 -b:v 4M -pass 2 -c:a aac -b:a 128k out.mp4

CRF 的数字怎么选：18 通常接近视觉无损，23 是 x264 默认的平衡点，28 开始明显省码率但细节下降。CRF 越低画质越好、文件越大；它不是“百分比”，也不能跨编码器直接比较（x265 的 CRF 28 与 x264 的 CRF 23 不能等同）。

🔍VBV 缓冲是什么：它模拟解码器的输入缓冲。bufsize 太小会让码率被强行压平、画质抖动；通常取 maxrate × 1–2 秒。CBR 直播里，bufsize 与 nal-hrd=cbr 要一起设，否则“标称 CBR”并不恒定。

码控像开车时的油门策略：CBR 是定速巡航，不管上坡下坡都咬住同一个速度；VBR 是看路况给油；ABR 是“这个月油费平均不能超”；CRF 是恒温器，只认体感温度；CQP 是把手动油门焊死。五种模式没有绝对好坏，只有“你要稳定带宽，还是要稳定画质”。

VBV：码率不是平均数，是“瞬时不能超”

VBV（Video Buffering Verifier）是解码器端的虚拟缓冲区模型。编码器一边编，一边模拟“这些比特到达解码器时，缓冲区会不会溢出或饿死”。它不是提高画质，而是给码率加一条瞬时包络，让网络与解码器都能跟得上。

maxrate

任意短时间窗口内的码率上限。超过它就触发 QP 上升，宁可牺牲这一小段画质，也不让缓冲区溢出。

bufsize

缓冲区容量。太小 → QP 剧烈波动、画面忽好忽坏；太大 → 约束形同虚设，突发码率仍然会打爆网络。

minrate

CBR 时的码率下限，靠填充数据（filler）凑满。只对“必须恒定输出”的链路有意义，普通点播不要设。

缓冲时长 ≈ bufsize ÷ maxrate　→　例如 12M bufsize 配 6M maxrate，约等于 2 秒的“水库”

缓冲区越大，编码器越能容忍短时复杂画面（先多花、后少花）；缓冲区越小，码率越“贴地”，但画质波动越明显。直播常把 bufsize 设成 0.5–2 秒的 maxrate，点播可以放到 2–4 秒。

# 直播 CBR：码率、上下限、缓冲、HRD 一起设；nal-hrd=cbr 会让 x264 按 CBR 模型填充
ffmpeg -i in.mp4 -c:v libx264 -preset veryfast \
  -b:v 4M -minrate 4M -maxrate 4M -bufsize 4M \
  -x264-params nal-hrd=cbr -g 50 -keyint_min 50 -sc_threshold 0 \
  -f flv rtmp://live.example/app/stream

# 点播 capped CRF：质量优先，但复杂场景不许超过 6 Mbps

ffmpeg -i in.mp4 -c:v libx265 -preset medium -crf 26 \

CRF 与 CQP：都不是“码率目标”

CRF（Constant Rate Factor）追求的是“感知质量大致恒定”：简单画面多压一点，复杂画面少压一点，码率是结果而不是目标。数值越小越好看，x264 常用 18–28；-crf 0 才是无损，-crf 18 已经很高但绝不是无损。CQP 则是所有帧用同一个 QP，不做任何码率补偿，文件大小会随内容剧烈起伏，通常只用于实验对照。

CRF 也不是“全自动”：它仍然受 -maxrate/-bufsize 的 VBV 约束；一旦触顶，编码器会临时升 QP。想要“稳定质量 + 网络不炸”，capped CRF 是点播最常见的选择。

preset：用编码时间换压缩率

preset 控制的是“编码器愿意花多少时间做搜索”。越慢的 preset 会尝试更多块划分、运动矢量、参考帧与 RDO，同 CRF 下通常得到更低的码率；但它不会改变 profile/level，也不会让解码端变慢。

tune film

真人影视，保留胶片颗粒与细节。大多数实拍内容可用。

tune animation

动漫、平涂、线条多。会调整去块与 psychovisual 策略，避免线条糊掉。

tune grain

强胶片颗粒素材，宁可多花码率也不把颗粒磨平。

tune zerolatency

关闭 B 帧与 lookahead，牺牲压缩率换最低延迟。直播/云游戏常用。

tune fastdecode

减少解码端负担（如关闭部分滤波工具），适合低端播放器，不一定让编码更快。

tune stillimage

单帧或幻灯片，优化静态细节，别用于运动视频。

💡选型口诀：要“固定带宽”选 CBR，要“固定体积”选两遍 ABR，要“固定观感”选 CRF，要“瞬时别超”加 maxrate + bufsize。-crf 与 -b:v 同时出现会让意图变模糊：CRF 仍会按质量走，-b:v 只在部分模式生效；要么 CRF + maxrate，要么纯 ABR。

🎨 色度采样 4:2:0：人眼对颜色更迟钝

视网膜上负责亮度的细胞多、负责颜色的少，所以“把颜色分辨率砍一半”肉眼几乎察觉不到。4:2:0 就是每 2×2 个像素共享一组 Cb/Cr：亮度全保留，色度在水平和垂直方向都减半。这也是报纸彩印“颜色套印可以糊一点”的现代版。

要“谁都能播”

H.264 High + AAC 仍是网页与安防的通用解。兼容性带来的运维成本，往往低于省下的那点带宽。

要“4K HDR / 省带宽”

HEVC Main 10 的硬件解码覆盖好，适合电视、机顶盒、手机；注意专利授权与 hvc1 标签。

要“免专利 + 新浏览器”

VP9/AV1 适合网页分发。AV1 的编码成本高，点播可以先编一次；实时直播要算清 CPU 账。

💡不要只看“省多少”：HEVC 省 40% 带宽，但如果被迫转码、软解、或付出专利费，总成本可能更高。工程决策要算“带宽 + 算力 + 兼容 + 授权”四笔账。

🌳 HEVC：64×64 的四叉树与 35 个方向

H.264 的宏块像 16×16 的固定瓷砖：墙面再平、再碎，也只能按同一块大小铺。HEVC 的 CTU 像一套带隔层的收纳箱：先给你 64×64 的大格子，遇到平坦墙面就用大格子，遇到细节就一层层拆成 32、16、8，直到够用为止。

CTU（Coding Tree Unit，编码树单元）最大 64×64；它按四叉树递归拆成 CU（Coding Unit），最小可到 8×8。每个 CU 再分成 PU（预测单元，决定怎么预测）与 TU（变换单元，决定怎么做变换）。H.264 的 16×16 宏块也有子划分，但“块大小”这件事远没有 HEVC 灵活。

35 个帧内方向，比 H.264 的 9 个细得多

H.264 的 4×4/8×8 帧内预测有 9 种：DC 加 8 个方向；16×16 只有 4 种。HEVC 则给出 35 种：Planar（平面渐变）、DC（平均值），再加 33 个角度模式（模式 2–34）。角度以 1/32 像素精度采样，斜边、细线、渐变天空的预测都能更贴合。

方向多不等于一定更好：编码器要为每个 CU 试更多模式，时间成本上升；但对 4K、细纹理与合成内容，方向精度带来的残差减少很可观。

去块滤波 + SAO：先修边界，再修噪点

Deblocking（去块滤波）

在 8×8 网格边界上判断“这是真实边缘还是压缩块效应”，只对后者做平滑。HEVC 的滤波决策比 H.264 更细，能根据边界强度与 QP 自适应。

SAO（Sample Adaptive Offset）

去块之后，按 CTU 把像素分成“条带”或“边缘”类别，给每一类加一个小偏移。它专门修振铃与暗场 banding，开销只有每 CTU 几个比特。

顺序是：预测/变换/量化 → 反变换 → 去块滤波 → SAO。两者都在解码环路里，编码器也要模拟一遍，所以它们会同时影响客观指标与主观观感。

🧱 AV1 与 VVC：OBU、tile 与新工具箱

AV1 的码流像一套活页说明书：每一页叫一个 OBU，页头写清“我是序列头、帧头还是数据页”，还写这一页有多长。整帧又像一张拼图，切成多个 tile 分给不同 CPU 核心同时拼——这就是它能在浏览器里流畅解码的原因之一。

tile：把一帧拆给多个核心

AV1 可以把一帧切成最多 64 列 × 64 行的 tile 网格（实际数量受帧大小与规范约束），每个 tile 独立做熵编码与预测边界处理。好处是多核并行解码、某一块损坏不污染整帧；代价是 tile 边界不能共享上下文，压缩率会略降，tile 头也有一点开销。编码器的 tile-columns / tile-rows 就是在“并行度”与“压缩率”之间调平衡。

AV1 的 superblock 最大 128×128，变换最大 64×64；块划分同样递归，但工具更多。下面这些工具是它区别于 HEVC 的“新玩具”：

CfL（Chroma from Luma）

用同一块的亮度预测色度：先算亮度的 AC 分量，再乘一个缩放系数当色度预测。彩色边缘、文字边缘特别受益。

Palette（调色板）

块内颜色很少时（图标、截图、UI），直接传“几种颜色 + 索引”，比逐像素预测便宜得多。

IntraBC（帧内块复制）

在同一帧已解码区域里找相同块复制过来。屏幕共享、PPT、网页滚动是它的主场。

CDEF

Constrained Directional Enhancement Filter：沿边缘方向滤波，专治变换/量化带来的振铃，同时尽量不糊掉真实边缘。

Loop Restoration

在 CDEF 之后再修一遍：Wiener 滤波或自引导恢复（SGR），按 superblock 切换，进一步压低噪声与模糊。

Film Grain Synthesis

编码器把胶片颗粒“抹掉”，只传颗粒参数；解码器在播放端重建。码率省下来，观感仍是“有颗粒”的。

AV1 的生态与命令

AOMedia（Alliance for Open Media）主导 AV1，标准免版税；Chrome、Firefox、Edge 都已支持，硬件解码在手机/电视上越来越普遍。它的软解 dav1d 很快，编码侧 SVT-AV1 把速度拉到了可用的程度（preset 0 最慢最好，13 最快）。

# SVT-AV1：preset 6 是速度/质量的常用平衡点，CRF 30–40 常见
ffmpeg -i in.mp4 -c:v libsvtav1 -preset 6 -crf 35 -g 120 \
  -c:a libopus -b:a 96k out_av1.webm

# 大分辨率想提高并行度：显式切 tile（tile 越多，压缩率略降）
ffmpeg -i in.mp4 -c:v libsvtav1 -preset 6 -crf 35 -g 120 \
  -svtav1-params tile-columns=2:tile-rows=1 -c:a libopus -b:a 96k out_av1_tiles.webm

# 10 bit 源：让 SVT-AV1 保留 10 bit，而不是先降到 8 bit
ffmpeg -i in.mp4 -c:v libsvtav1 -preset 6 -crf 32 -pix_fmt yuv420p10le \
  -c:a libopus -b:a 128k out_av1_10bit.webm

AV1 的 CRF 与 x264 的 CRF 不是同一把尺子：数值范围 0–63，内容与分辨率不同，不能直接照搬。AV1 在低码率、屏幕内容、4K 上的优势最明显；极低延迟直播仍要评估编码器算力与硬件支持。

VVC / H.266：HEVC 的正式继任者

VVC（ITU-T H.266 | ISO/IEC 23090-3）在 2020 年定稿，公开测试里相对 HEVC 常见 30–50% 的 BD-rate 收益。它把 CTU 扩到 128×128，用 QTBT + MTT（四叉树加二叉/三叉树）做更灵活的划分，新增 ALF（自适应环路滤波）、仿射运动、解码端运动修正、调色板与子图像等工具。

代价是编码复杂度高、硬件支持铺开慢、专利池同样复杂。FFmpeg 新版可以通过 libvvdec 解码 VVC，编码侧多用 VVenC；生产环境要先确认播放链路，而不是只看压缩率。

🎧 音频编码：AAC / Opus / MP3 / FLAC

音频压缩利用的是人耳的掩蔽效应：一个强音旁边的小声音你听不见，干脆不编码。AAC、MP3、Opus 都基于 MDCT（改进离散余弦变换）与心理声学模型；FLAC 则完全不同，它只做无损的线性预测与熵编码。

ffmpeg -i in.wav -c:a libopus -b:a 64k -application audio out_opus.webm

# MP3 192k（老设备）

AAC-LD / ELD23 / 39低延迟滤波器组，牺牲少量压缩率换延迟64–128 kbps会议、专业低延迟链路
xHE-AAC42USAC，整合更多工具，面向极低码率16–32 kbps流媒体与广播的新链路（支持面较窄）

SBR（Spectral Band Replication）不是“凭空造高频”：它把低频的谐波结构搬到高频，再用少量参数修正包络。所以 HE-AAC 的核心采样率可以只有输出的一半，解码器再重建到 48 kHz；文件头仍然标 48 kHz。PS（Parametric Stereo）则只传一个声道加空间参数，解码端重建左右差异。

封装差别：MP4 用 mp4a + AudioSpecificConfig（通常 2 字节，写 AOT、采样率索引、声道配置）；TS/ADTS 每帧带 7 字节头（带 CRC 是 9 字节），同步字是 12 个 1（0xFFF）。同一段 AAC，换封装不会改变音频数据。

# 注意：ffmpeg 自带的 aac 编码器只支持 LC，写 aac_he 会报 Profile not supported
ffmpeg -i in.wav -c:a aac -b:a 128k out_lc.m4a

# HE-AAC / HEv2 需要 libfdk_aac（非自由构建）或外部编码器
ffmpeg -i in.wav -c:a libfdk_aac -profile:a aac_he -b:a 48k out_he.m4a
ffmpeg -i in.wav -c:a libfdk_aac -profile:a aac_he_v2 -b:a 32k out_hev2.m4a

# 看实际写入的 profile、采样率、声道与码率
ffprobe -v error -select_streams a:0 \
  -show_entries stream=codec_name,profile,sample_rate,channels,bit_rate -of default=nw=1 in.m4a

Opus：为什么实时通话偏爱它

Opus 是 IETF 的 RFC 6716（2012），内部固定以 48 kHz 处理，把 SILK（语音、低码率）与 CELT（音乐、低延迟）拼在一个编解码器里；编码器可以逐帧切换，也可以走 Hybrid 模式。码率范围 6–510 kbps，帧长可选 2.5 / 5 / 10 / 20 / 40 / 60 ms。

延迟账：Opus 的算法延迟可以低到约 5 ms（2.5 ms 短帧模式），最大约 62.5 ms（60 ms 长帧，另加前视与重采样开销）。相比之下，MP3 一帧 1152 个样本，48 kHz 下就是 24 ms，再叠加解码缓冲；AAC-LC 一帧 1024 个样本，约 21.3 ms。Opus 的短帧与低前视，是它在视频会议、云游戏、WebRTC 里胜出的关键。

Opus 还内置 FEC（前向纠错，低码率冗余）、DTX（静音不传）、CBR/VBR 切换与丢包隐藏。它的“低延迟”不是单个数字，而是“短帧 + 小前视 + 抗丢包”的组合。

# 语音实时：10 ms 帧、CBR、开 FEC，优先稳定与低延迟
ffmpeg -i in.wav -c:a libopus -b:a 48k -application voip \
  -frame_duration 10 -vbr off -fec 1 out_voip.webm

# 音乐点播：20 ms 帧、VBR，优先听感
ffmpeg -i in.wav -c:a libopus -b:a 96k -application audio \
  -frame_duration 20 -vbr on out_music.webm

# 极致低延迟：CELT-only 的 lowdelay 模式
ffmpeg -i in.wav -c:a libopus -b:a 64k -application lowdelay \
  -frame_duration 10 out_lowdelay.webm

采样率、位深、声道与码率：四个数不是乘法

无损 PCM 的码率才是“采样率 × 位深 × 声道”：48 kHz、16 bit、立体声 = 48000 × 16 × 2 = 1,536,000 bit/s，即 1.536 Mbps。换成 24 bit 就是 2.304 Mbps；5.1 声道则是 4.608 Mbps。有损编码的码率是“目标值”，不是这个乘积，压缩比通常 10–25 倍。

采样率

决定能保留的最高频率（Nyquist = 采样率 ÷ 2）。视频行业统一 48 kHz；44.1 kHz 是 CD 遗留。48 kHz 与 44.1 kHz 的听感差异，远小于码率与编码器差异。

位深

决定量化噪声底。16 bit 约 96 dB 动态范围，24 bit 约 144 dB；制作与中间片用 24 bit，最终分发 16 bit 足够。AAC/Opus 内部精度更高，但输出文件不标“位深”。

声道

立体声不是简单翻倍：可以用联合立体声/PS 共享信息。5.1 常见 AAC 256–384 kbps、Opus 192–320 kbps；声道越多，空间信息越贵。

经验透明码率：AAC-LC 立体声约 128–192 kbps；HE-AAC 48–64 kbps；HE-AACv2 32–48 kbps；Opus 立体声 64–96 kbps 已接近透明；MP3 需要 128–192 kbps 才勉强追平 AAC-LC。FLAC 无损通常是 PCM 的 50–60%，具体取决于内容。

MP3 的历史一句话：Fraunhofer 在 1987 年展示，1993 年成为 MPEG-1 Layer III；核心专利 2017 年到期，所以今天可以免费使用。它的 1152 样本帧与较长的滤波器组，注定了延迟高于 Opus，但在兼容性上仍有价值。

⚠️别把“采样率 48 kHz”当成“高频一定到 24 kHz”：有损编码会用心理声学模型砍掉听不见的高频，HE-AAC 甚至只传一半带宽再用 SBR 重建。采样率只是容器上限，真正保留了多少频带，要看码率与编码器策略。

📏 质量指标与验证：别只凭眼睛

“看起来差不多”不能写进验收标准。工程上用三类指标：像素误差（PSNR）、结构相似度（SSIM）、感知质量（VMAF）。它们各有盲区，最稳的做法是指标 + 抽帧主观对比。

PSNR = 10 · log₁₀(255² / MSE)　（8 bit 视频）

PSNR 40 dB 左右通常算“不错”，45 dB 以上接近透明；但它对模糊与块效应不敏感，对轻微整体偏移又过度惩罚。SSIM 看亮度、对比度、结构三部分，取值 0–1，越接近 1 越好。VMAF 用机器学习模型预测主观评分，范围 0–100，业内常以 93 左右作为 1080p 的透明参考线（不是绝对标准）。

# 计算 PSNR / SSIM（要求同分辨率、同帧率）
ffmpeg -i enc.mp4 -i ref.y4m -lavfi "[0:v][1:v]ssim" -f null -
ffmpeg -i enc.mp4 -i ref.y4m -lavfi "[0:v][1:v]psnr" -f null -

# 计算 VMAF（需要 libvmaf 编译支持）
ffmpeg -i enc.mp4 -i ref.mp4 -lavfi libvmaf -f null -

# 逐帧看关键帧与帧类型，定位画质突变
ffprobe -select_streams v -show_frames \
  -show_entries frame=pict_type,pkt_size -of csv enc.mp4 | head -30

BD-rate（Bjøntegaard Delta rate）用来比较两个编码器：在相同质量下，平均码率相差多少百分比。BD-rate 为 −30% 表示“同等质量下省 30% 码率”。它依赖测试序列、质量指标与拟合方式，论文里的数字不能直接搬到你的业务内容上。

⚠️别用 PSNR 选 preset：高 PSNR 可能来自“模糊但误差小”，观感反而更差。先定业务场景（人脸、文字、运动、暗场），再用对应素材做 A/B，指标只作为辅助。

📐 画质评价进阶：三把尺子与一条 RD 曲线

PSNR 像拿卷尺逐像素量“你和我差了几毫米”；SSIM 像看两张照片的“骨架、明暗、纹理”是不是同一副；VMAF 像请一群观众盲测打分，再把他们的偏好训练成一个裁判。三把尺子各有盲区，最稳的是“指标 + 抽帧 + 人眼”。

PSNR：最直白，也最容易被“平均”骗

先把两帧逐像素相减、平方、求平均，得到 MSE；再用 PSNR = 10 · log₁₀(MAX² / MSE) 换成对数刻度。8 bit 视频的 MAX = 255。对数的好处是：MSE 减半，PSNR 约 +3 dB；MSE 翻倍，约 −3 dB。所以 40 dB 不是“40% 好”，而是“误差已经很小”。

PSNR 的盲区：它对“整体亮度偏移 1”与“局部糊成一片”一视同仁，对人眼敏感的块效应、振铃反而不够敏感；不同分辨率、不同内容之间也不能直接比。它适合做同一片源、同一分辨率的快速回归，不适合当唯一验收标准。

SSIM：看结构，不只看像素差

SSIM 把局部窗口拆成三部分：亮度（均值）、对比度（方差）、结构（协方差），三项相乘得到 0–1 的分数，越接近 1 越像。它更接近人眼对“边缘与纹理是否还在”的判断，所以模糊、块效应通常会让 SSIM 明显下降。

SSIM 也有盲区：对噪声、色彩偏移不敏感；不同尺度的结构权重不同，于是有了 MS-SSIM（多尺度）。工程上常把 SSIM 与 PSNR 一起看：PSNR 高但 SSIM 低，往往意味着“平均误差小，但结构被抹平”。

VMAF：把“观众觉得好不好”变成分数

VMAF（Video Multimethod Assessment Fusion）提取一组特征（细节损失、运动、对比度等），再用训练好的模型融合成 0–100 的分数。它不是简单公式，而是“主观打分数据训练出的预测器”；因此模型文件与训练集决定了它的脾气。1080p 用 vmaf_v0.6.1.json，4K 用 vmaf_4k_v0.6.1.json，用错模型会系统性偏高或偏低。

这些是经验参考线，不是验收规范：动画、体育、暗场、文字密度都会改变阈值。真正可用的做法是“同一片源、同一分辨率、同一帧对齐”，再结合业务码率定自己的红线。

# PSNR：把统计写到日志，再取平均
ffmpeg -i enc.mp4 -i ref.mp4 -lavfi \
  "[0:v]setpts=PTS-STARTPTS[a];[1:v]setpts=PTS-STARTPTS[b];[a][b]psnr=stats_file=psnr.log" \
  -f null -

# SSIM：同样的对齐方式
ffmpeg -i enc.mp4 -i ref.mp4 -lavfi \
  "[0:v]setpts=PTS-STARTPTS[a];[1:v]setpts=PTS-STARTPTS[b];[a][b]ssim=stats_file=ssim.log" \
  -f null -

# VMAF：需要 ffmpeg 编译时带 libvmaf，并准备模型 JSON
ffmpeg -i enc.mp4 -i ref.mp4 -lavfi \
  "libvmaf=model=path=/usr/share/model/vmaf_v0.6.1.json:log_path=vmaf.json:log_format=json" \
  -f null -

模型文件不在 ffmpeg 二进制里，通常来自 Netflix/vmaf 仓库的 model 目录；Windows 下把路径换成本机实际位置。若你的 ffmpeg 版本较旧，可能要用 model_path=... 而不是 model=path=...。没有 libvmaf 时，PSNR/SSIM 仍然可用，但不要拿它们硬套 VMAF 阈值。

RD 曲线：把“省 40% 码率”读出来

RD 曲线（Rate–Distortion）横轴是码率、纵轴是质量。每个编码器在同一段内容上扫多个码率点，连成一条线。曲线越靠左上越好：同样的码率得到更高质量，或同样的质量只花更少码率。

怎么读，不误读：① 先固定质量点（例如 VMAF 90），再看两条曲线与该水平线的交点；② 交点之间的水平距离就是码率差，除以 H.264 的码率得到节省比例；③ 如果想比较整条曲线而不是单点，用 BD-rate：在质量区间上对码率的对数差做积分再平均，负值表示“省”，−40% 就是平均省 40%。

三个前提：同一片源、同一分辨率与帧率、同一质量指标与模型。拿 H.264 的 VMAF 90 去比 HEVC 的 PSNR 40，或拿 1080p 模型量 4K，都是无效比较。还有，“省 40% 码率”不等于“同 CRF 文件小 40%”：CRF 只是编码器内部的质量旋钮，不同编码器的 CRF 数值不可互换。

💡指标是地图，不是领土：VMAF 高也可能出现局部糊字、暗场色带、运动拖影，因为这些内容在训练集里权重不高。上线前至少抽 10–20 个代表镜头（人脸、文字、暗场、快速运动、渐变天空）做并排对比；指标负责“筛掉明显差的”，人眼负责“最后拍板”。

🧰 编码工具箱：ffprobe 与八条真命令

ffprobe 是听诊器，ffmpeg 是手术刀：先听清 codec、profile、level、帧类型、关键帧间隔，再决定“转什么、怎么转”。很多“转码后花屏/不能播”的问题，不是编码参数错，而是根本没诊断出源流的真实结构。

先诊断：三条 ffprobe

# 1) 流概览：codec / profile / level / 分辨率 / 帧率 / 码率 / tag
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,level,width,height,r_frame_rate,avg_frame_rate,bit_rate,nb_frames,codec_tag_string,pix_fmt \
  -of default=nw=1 in.mp4

# 2) 逐帧：帧类型、是否关键帧、PTS/DTS、包大小（看到 B 帧与重排）
ffprobe -v error -select_streams v:0 -show_frames \
  -show_entries frame=pts_time,dts_time,pict_type,key_frame,pkt_size -of csv=p=0 in.mp4 | head -20

# 3) 只看关键帧时间：直接算出 GOP 间隔与 seek 粒度
ffprobe -v error -select_streams v:0 -skip_frame nokey -show_frames \
  -show_entries frame=pts_time,pict_type -of csv=p=0 in.mp4 | head -20

读法：r_frame_rate 是容器标称帧率，avg_frame_rate 是实际平均；两者差很多说明是 VFR（可变帧率），转码前最好先 -vf fps=30 或 setpts 统一。关键帧时间相减就是 GOP 秒数；pict_type 的 I/P/B 与 key_frame 的 1/0 一起看，别把普通 I 帧当成 IDR。

再开药：五条转码配方

# 4) H.264 → H.265：音频能 copy 就 copy，视频重编码
ffmpeg -i in.mp4 -c:v libx265 -preset slow -crf 24 -profile:v main10 \
  -tag:v hvc1 -c:a copy out_hevc.mp4

ffmpeg -i in.mp4 -c:v libx264 -preset medium -crf 21 \

# 6) capped CRF：质量优先，但复杂场景不许超过 8 Mbps
ffmpeg -i in.mp4 -c:v libx264 -preset slow -crf 20 -maxrate 8M -bufsize 16M \
  -c:a copy out_capped.mp4

# 7) 两遍 ABR：目标平均码率 6 Mbps；两遍参数必须一致
ffmpeg -y -i in.mp4 -c:v libx264 -preset slow -b:v 6M -pass 1 -an -f null -
ffmpeg -y -i in.mp4 -c:v libx264 -preset slow -b:v 6M -pass 2 \
  -c:a aac -b:a 128k out_2pass.mp4

# 8) 抽 Annex B，再用 trace_headers 把 SPS/PPS 的语法元素打印出来
ffmpeg -i in.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 in.h264
ffmpeg -loglevel trace -i in.h264 -c:v copy -bsf:v trace_headers -f null - 2> trace.log

trace_headers 的两个前提：① 日志级别必须是 trace，否则过滤器不会打印；② MP4 的 SPS/PPS 常在 avcC 的 extradata 里，先转成 Annex B 才能稳定地在包内看到。打开 trace.log 搜 Sequence Parameter Set / Picture Parameter Set，就能逐项看到 profile_idc、level_idc、pic_width_in_mbs_minus1、frame_mbs_only_flag 等字段。

几条容易踩的坑：① ffprobe 的 level 可能显示 -99，表示码流没写或解析不出，不代表文件坏；② bit_rate 是容器估算，短文件/流式文件偏差大，精确值要把 packet 的 size 求和再除以时长；③ -c:a copy 只适合源音频与目标容器兼容的情况（AAC→MP4 一般可以，PCM→MP4 就不行）；④ 两遍编码不要在第一遍加 -c:a，音轨不会参与视频统计。

🔍诊断顺序建议：ffprobe 流概览 → 逐帧类型 → 关键帧间隔 → 再选编码器与参数。先确认“源流是什么”，再谈“目标流要多小”；反过来做，往往会在错误的 profile/level 上反复试错。

🔬 理论一角：DCT、量化表与 zigzag

DCT 像把一块 8×8 的布料拆成 64 根粗细不同的琴弦：低频是厚重的低音，代表整块的平均明暗；高频是细碎的高音，代表边缘与纹理。自然画面的大部分能量都集中在低音上，所以只要把高音削掉，画面看起来仍然完整。

8×8 DCT：从“像素”变成“频率”

DCT（离散余弦变换）把 8×8 的像素值投影到 64 个固定的“花纹”上：左上角是全白/全黑（DC，平均值），越往右下，花纹越细碎（高频）。每个系数就是“这块画面里含多少这种花纹”。变换本身是可逆的，真正丢信息的是下一步的量化。

为什么是 8×8？太小（4×4）时，一块里装不下复杂的纹理，能量压缩不够；太大（16×16、32×32）时，一块里混进不同物体，预测与变换都更费。H.264 用 4×4/8×8，HEVC 用 4×4–32×32，都是在“局部平稳”与“计算量”之间找平衡。

量化：把“小数”变成“0”，也是唯一不可逆的一步

量化就是把每个系数除以一个步长，再四舍五入：量化值 = round(系数 / 步长)。步长越大，越多的系数变成 0，文件越小，细节也越少。下面用 JPEG 的标准亮度量化表做直观演示（H.264/HEVC 默认矩阵是平坦的，但“高频更容易归零”的现象仍然存在）：

(1,0)−10912−9横向低频，仍有明显能量

JPEG 表里高频步长可达 99，低频只有 11–16；H.264/HEVC 默认不做这种“重罚高频”，但自然图像的高频系数本来就只有个位数，加上编码器的 dead-zone，量化后仍会大量归零。归零不是“坏”：它让后面的熵编码能用一个短码表示一大片零，换来的体积下降通常远大于那点看不见的细节。

zigzag：让零聚在队尾

量化后，非零系数大多集中在左上角，右下角一大片 0。如果按行扫描，零会被“打断”；zigzag 按 0→1→2…63 的斜线顺序走，先把低频扫完，再把高频的零排到后面，于是可以用“连续零的个数 + 下一个非零值”成对记录，最后用 EOB（End of Block）收尾。

最后一步：熵编码把“零”变成短码

CAVLC 像查表：把“连续零的个数、非零值、符号”映射到固定码表；CABAC 像自适应算术编码：根据上下文不断更新概率区间，常用符号越编越短。同样一组量化系数，CABAC 通常比 CAVLC 省 9–14% 码率，代价是解码更复杂、更难并行。H.264 两者都支持，HEVC 只用 CABAC。

所以一条完整链路是：像素 → 预测（减掉可预测部分）→ DCT（变频率）→ 量化（丢高频）→ zigzag（排零）→ 熵编码（写短码）。解码端反向走，但量化那一步的信息已经丢了，只能靠去块滤波、SAO 等后处理“补妆”。

💡直觉总结：DCT 不丢信息，只负责“重新排列”；量化才是压缩的来源；zigzag 让零变得好写；熵编码让常见符号变短。所有视频编码标准，本质上都在“怎样更便宜地预测、怎样更狠地量化、怎样更省地写零”这三件事上做文章。
